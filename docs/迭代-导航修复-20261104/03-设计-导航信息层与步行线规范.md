## 0. 结论摘要

### 题 A（需求 5）· 导航信息行

1. 该行是 `.rc-line` 里的**等车行**（`NavDetailBody.tsx:462-494`，引导图标 `busStop`），不是另起一块。上车后**同一个 DOM 位置**换成两行布局，纵条（站点流程列表）紧接其下 —— 与既定口径一致。
2. 两种状态装进同一个容器（`.nav-inforow`）：**巴士卡定高 52px**（两态零差）；**轻轨卡 `pre` 最小 52、可长高至 132**（左槽有 3 个纵向块，硬压会裁字或压纵条），`post` 两者都钉 52。**不做 height 动画**（动画 height 属反模式）。
3. 上车后两行的角色是：**主行 = 下一站（要盯的站）**，**次行 = 还有 n 站下车 · 约 x 分（要盯的数）**。次行的时间是**到下车**的时长，且文案里必须有「下车」二字承担区分 —— 这是需求 4 的语义落点，不能只靠数字位置区分。
4. 390×844 实测预算：站名可用 **254px**，最多容纳 **17 全角字符**（全库实测最长站名 `望信樓/慕拉士政府綜合服務中心-1` = 17 字，宽 228.5px），余量 25px，**不需要截断**。窄屏按四档让位阶梯处理（见 §2.5），全档禁用省略号。
5. 上车瞬间整块内容替换：**入场淡入 150ms、退场 0ms**，只动 `opacity`；`prefers-reduced-motion` 下直接瞬切。
6. **候车期可显示候选车牌**（`来车 MB1234`，信息行 `pre` 次行，巴士专用；不可靠一律不显示）：高度仍 52，不改判定、不提前上车 —— 见 §2.10。
7. **三个刻意例外（都已冻结，不要"修"）**：① 轻轨卡 `pre` 可长高（§2.6.1）；② **换乘候车期整块不渲染**（高度 0，`data-nav-info` 属性缺席；§2.6.5，v3.11 有意取舍）；③ 头部"门到门剩余"与信息行"本段到下车"是**两个口径**，差值属预期（§2.9）。

### 题 B（需求 2）· 赶车标签

1. **唯一判定真源 = 「是否已进入过乘车态」这个单向锁存（latch），不是当前 phase。** 因为 `body[data-nav-phase]` 在「步行去车站」是 `walk`、在「下车后步行去目的地」也是 `walk`；用 phase 直接判会同时复现两次历史缺陷。
2. 显示：未开始导航 / 步行前往车站 / 已到站候车。隐藏：**进入 riding 那一刻起，到本次导航结束前永不复活**。
3. 判定口径：**以进入 riding 那一刻为准**，不等关门/发车（不可观测）；**自动判定与手动「我已上车」一视同仁**（两者产物都是 `ride.phase === "riding"`）。
4. 隐藏方式：**DOM 移除（不渲染）**。禁止 `opacity: 0` —— 它对屏幕阅读器仍然可读，等于把错误结论从"看得见"变成"听得见"。
5. 上车后**不新增替代形态**。闭环信息已由底部状态行（`乘车中 · 车牌`）与纵条（`停靠中 / 下一站`）承担，再加「本班已赶上」是第三处重复。

### 题 C（需求 1）· 步行线

1. 「深浅两种绿」的根因是**同一段连续未走路径被切成两种透明度**：`aheadPath` 用 `--map-walk-op-ahead: 0.55`、`nowPath` 用 `--map-walk-op-now: 1`，而两者都是「未走」（`nav-map-walk.ts:65-76`）。线宽也从 6 变 7，进一步放大割裂感。
2. 定案：**未走 = `#0b6e4f`（保持不动）+ 线宽 6 + 透明度 0.75**，`now` 与 `ahead` 由**同一组变量**提供（不是两份相等的值），唯一差异是层级 `z` 与**方向箭头（showDir）**。
3. 透明度 0.55 → 0.75 是**无障碍修复**，不是口味调整：0.55 在浅色瓦片上的实际对比度只有 **2.26:1**（低于图形 3:1 底线），0.75 为 **3.70:1**。（team-lead 已裁决采 0.75，不采"now 也改 0.55"的最小改动方案。）
4. 与巴士彩段（宽 6 / 层 72 / 透明度 0.92）**同宽不同色相**；层级仍为 步行 68-73 < 巴士 72 < 站点 90/95 < pin 120 < 蓝点 128 < 车辆 130。
5. 外部道路与无路网回退段**不做地图线型区分**（虚线已被负责人明确否掉、更淡会退回"深浅不一"缺陷、新色违反既有色彩体系）；精度说明放在**步行步骤文案**里，不放在地图线上。

# 题 A（需求 5）· 导航信息行的两套布局

## 2.1 位置与归属

**结论**：在现有等车行（`NavDetailBody.tsx:462-494`）的位置上，用一个定高容器承载「上车前 / 上车后」两套布局；原来的 `.nav-note-neutral--eta` 块（`NavDetailBody.tsx:511-526`）**并入本行后删除**，否则同一信息会出现两处（"两个真相"缺陷的经典形态）。

DOM 顺序（改造后，自上而下）：

```
.rc-dhead            头部（总用时 / 到达时刻 / 线路标签）
.rc-line             步行 → 上车站
  .rc-row--walk      （不变）
  .nav-inforow       ← 本次改造；定高 52px；两套布局二选一
.rc-strips           进度纵条（站点流程列表；上车后自动逐站展开）
.rc-line             下车站 → 目的地
.nav-fold            其他线路
.rc-foot             数据来源
```

**为什么并入而不是另起一块**：
- 单独保留 `.nav-note-neutral--eta`，上车后就会出现「下一站」两处（信息行一处、纵条 `.navstrip__badge` 一处）；
- 该块位于纵条**上方**，与"信息行 → 站点流程列表"的阅读顺序天然一致；
- 并入后，上车瞬间"等车 ETA + 邻班档位徽章"随布局切换一起消失，**顺带解决了轻轨邻班徽章在乘车态泄漏的问题**（见 §3.7）。

引导图标（20px 圆角方框内，来自项目锁定图标库，全项目一套 SVG）：

| 状态 | 图标 | 语义 | 证据 |
|---|---|---|---|
| 上车前 | `busStop` | 在站台等这班车 | 现状已用，`RoutePieces.tsx:143` |
| 上车后 | `bus` | 我在这辆车上 | 图标已存在，`ui/Icon.tsx:140` |

> 图标只换形状、不换色（两者同为 `--muted`），避免"颜色承担状态"。

## 2.2 上车前布局（单行）

```
[busStop]  还有 3 站 · 约 6 分          [小跑能赶上]
 └ 20px ┘  └── 主信息（14px，数字 600）──┘  └ 12px 胶囊 ┘
```

| 槽位 | 内容 | 说明 |
|---|---|---|
| 左（主） | `还有 {n} 站 · 约 {x} 分` | **车辆到本站**的量化预期；`n` = 车辆距本站站数，`x` = 到站分钟 |
| 右（次） | `tierText`（档位短词，≤9 全角） | 步行速度分档结论；**本行不使用带时刻的 `catchHint`**（理由见 §2.5） |

**轻轨分支（必须保留的例外）**：轻轨是时刻制，没有"还有 n 站"的可靠数据。左槽继续用 `LrtEtaInline`（`NavDetailBody.tsx:466-480`），**不伪造站数**。右侧标签：轻轨仅用 `tierText`。

**禁止**：左槽与右槽同时承载"时刻"（`LrtEtaInline` 已给 `14:32 开`，右侧再挂 `走快一点可赶上 14:32 那班` 就是同一数字说两遍，且一定挤爆 320px）。

## 2.3 上车后布局（两行）

```
[bus]  下一站  M220  黑沙環馬路
       还有 4 站下车 · 约 9 分
       └ 次行：13px，--muted，数字 600 ┘
```

| 行 | 内容 | 层级 | 说明 |
|---|---|---|---|
| 第 1 行（主） | `下一站` + `{站号}` + `{站名}` | 站名 15px / 600 / `--fg`；前缀与站号 13px / 400 / `--muted`·`--meta` | **"下一站"是不可省的语义锚**（口径已冻结）；`站号` 用等宽数字 |
| 第 2 行（次） | `还有 {n} 站下车 · 约 {x} 分` | 13px / 400 / `--muted`，数字 600 + `--fg-2` | `x` **必须是到下车（终点目的地）的时长**（需求 4 的修复点） |
| 右侧 | **空** | — | 上车后无赶车标签（题 B）；空白让主行拿到全部宽度，正好容纳 17 字长站名 |

**站点编号的呈现形式（定案）**：

```
下一站  M220  黑沙環馬路
        └┬─┘  └─┬──┘
         │      └ 站名：15px / 600（--fw-emphasize）/ --fg
         └ 站号：11px / 500 / --meta / font-variant-numeric: tabular-nums
                  前后各留 4px；不用括号、不加分隔符
```

- **不用括号**（口径写"（站点编号）"是示意，不是要求渲染括号）：括号在 13px 下占 2 个全角宽 = 30px，而括号不携带任何信息。
- 站号用 `tabular-nums`：相邻两帧换站时数字宽度不抖动。
- 站号颜色 `--meta`（比站名弱两档），确保"站名是主语、站号是坐标"。

## 2.4 排版规范（两态共用一套角色）

| 角色 | 字号 | 字重 | 行高 | 颜色 | 字距 | 数字 |
|---|---|---|---|---|---|---|
| 主信息·站名 | `--text-md` 15px | `--fw-emphasize` 600 | 1.3（20px） | `--fg` | `--tracking-body` 0 | — |
| 主信息·站号 | `--text-2xs` 11px | 500 | 1.3 | `--meta` | `0.02em` | `tabular-nums` |
| 主信息·前缀「下一站」 | `--text-xs` 13px | `--fw-read` 400 | 1.3 | `--muted` | 0 | — |
| 主信息·ETA（上车前） | 14px（`--text-md` 降一档；< 360px 降到 13px） | 400，数字 600 | 1.4 | `--fg-2`，数字 `--fg` | 0 | `tabular-nums` |
| 次行·「还有 n 站下车 · 约 x 分」 | `--text-xs` 13px | 400，数字 600 | 1.55（20px） | `--muted`，数字 `--fg-2` | 0 | `tabular-nums` |
| 赶车标签 | 12px | 600 | 1.0 | 由档位 Token 决定（`--error-container` / `--primary-container` / `--ok-container` / `--tier-4` / `--tier-5`） | 0 | — |

> **次行字号由 11px 提到 13px（相对现状 `.nav-note__sub` 的 `--text-2xs`，`globals.css:6857`）**：这行现在是「到下车还有多久」的唯一载体（需求 4 的修复点），是全程最需要被扫读的数字之一；而本项目禁止整页缩放（`layout.tsx` viewport），11px 在真机上不可读。代价是行高 17→20px，已计入 52px 定高。

**层级判定（回答"谁主谁次"）**：

- 上车前：**结论在右、事实在左** —— 左槽是"还要多久"，右槽是"来不来得及"。左槽信息量更大，视觉上先把左槽读成主语（14px），右槽是判词（12px 胶囊）。胶囊靠**形状+底色**而不是字号获得权重。
- 上车后：**站是主语、时长是谓语**。第 1 行 15px/600，第 2 行 13px/400。用户扫视顺序是"到哪了 → 还要多久"，而不是反过来。
- **两态的主行都占第一行**（站名 15px/600；ETA 14px/400 + 数字 600），因此切换时"视觉重心位置"不变 —— 变的是句子，不是版位。

**是否需要两行**：上车前 1 行、上车后 2 行 —— **但容器高度恒定 52px**（§2.6）。这是"内容行数变、布局高度不变"的组合，代价是上车前有 16px 上下留白，收益是切换零跳动。

**换行后是否保持对齐**：第 2 行**与第 1 行的站名左缘对齐**，不是与图标对齐。

```
[bus]  下一站  M220  黑沙環馬路
       还有 4 站下车 · 约 9 分
       ↑ 与「下一站」左缘对齐（x = 20 + 9 = 29px）
```

理由：`.rc-row` 的既有惯例是「文字区从 29px 起」（`globals.css:1319-1356`，`.rc-row--sub` 的 padding-left: 29px 就是同一套对齐）。第 2 行若与图标对齐，会读成"两个并列节点"而不是"一行的补充"。

## 2.5 字符预算与让位阶梯（390×844 起算）

**宽度推导（390px）**：

```
屏宽 390
− 面板左右内距 16 × 2                       = 358   （--space-4，globals.css:6029）
− 引导位 20 + gap 9                          = 329   （.rc-row，globals.css:1319-1322）
```

| 元素 | 390px 实占 | 计算 |
|---|---|---|
| 「下一站」前缀（13px × 3） + gap | 39 + 6 = 45 | 中文按 1em 计 |
| 站号 `M220`（11px tabular） + gap | 26 + 4 = 30 | 4 位半角 |
| **站名可用宽度** | **329 − 45 − 30 = 254px** | |

**最长站名实测**（`.verify/_q4-stations.json`，457 站全量排序）：

| 站名 | 字数 | 15px 实测宽 | 254px 预算 |
|---|---|---|---|
| `望信樓/慕拉士政府綜合服務中心-1` | 17 | 228.5px | 通过（余 25px） |
| `九澳水庫郊野公園/懲教管理局-1` | 16 | 215px | 通过 |
| `馬場東大馬路/黑沙環衛生中心` | 14 | 210px | 通过 |

> 结论：**390px 下最长站名不需要任何截断、不需要折行**。上限锁定为 **17 全角字符**。

**让位阶梯（只让位、不截断、不折行）**：

| 视口 | 站名 | 「下一站」前缀 | 站号 | 站名预算 | 17 字实测 | 依据 |
|---|---|---|---|---|---|---|
| ≥ 375px | 15px | 显示 | 显示 | 239px（375）/ 254px（390） | 228.5 通过 | 主目标 390 |
| 360–374px | 14px | 显示 | 显示 | 224px（360） | 213.2 通过 | iPhone SE 竖屏边界 |
| 320–359px | 14px | **隐藏** | 显示 | 229px（320） | 213.2 通过 | 语义由纵条 `.navstrip__badge`「下一站」承担（`NavStrip.tsx:131`） |

> 上车前左槽（ETA 文本）的同款阶梯：**≥ 360px 用 14px，< 360px 用 13px（项目小字地板）**。13px 是 `--vcode-font` 后项目统一抬升过的小字下限，不再下调。

**「下一站」可以隐藏的正当性**：纵条的下一站行**本来就有一枚「下一站」胶囊**（`NavStrip.tsx:131`），信息行里的前缀是第二次陈述。窄屏优先保住"站名完整"，比保住"第三次说下一站"更值。

**为什么不用省略号**：项目已冻结纪律 —— 同一条信息不折行、不用 `text-overflow: ellipsis`（`docs/改版-导航界面-20260925/06-设计-详细设计.md` §4.5.1）。本规范延续该纪律：**让位优先于截断**。

**最后一道护栏（可证明不会触发）**：若数据侧出现 > 22 全角字符的站名（当前全库最大 17），允许该行**行级换行**（站名整体落到第 2 行，`data-nav-info="wrap"`），容器高度例外 +20px。这条只为防白屏，不作为设计手段。

**次行预算**：`还有 12 站下车 · 约 25 分` 在 13px 下约 158px ≪ 329px，**上限 18 全角**，正常数据永远够。

**标签预算（关键决策）**：

| 候选文案 | 字数 | 12px 实占（含 padding） | 与 320px 左槽余量 |
|---|---|---|---|
| `全力冲刺有机会赶上`（`tierText` 最长） | 9 | 124px | 左槽可用 127px；ETA @14px 需 124px（余 3px）、@13px 需 115px（余 12px） |
| `走快一点可赶上 14:32 那班`（`catchHint`，轻轨档 1/2） | 13 | 约 165px | 320px 下左槽余 86px，**溢出** |

> **定案：导航信息行的右槽只用 `tierText`（≤9 全角），不使用 `catchHint`。**
> 理由：① 320px 物理放不下；② 带时刻的文案在 390px 下也要吃掉 165px，把左槽压到 156px，"还有 12 站 · 约 25 分"几乎贴边；③ 本行左槽已经用"还有 n 站 · 约 x 分"表达了同一件事，时刻只在轻轨分支由 `LrtEtaInline` 提供。
> 影响面：**仅导航信息行**。方案卡（`RecommendCard`）继续用合并式 `catchHint`（v3.9.0 已拍板），不动。

## 2.6 状态切换过渡与防跳动

### 2.6.1 高度：巴士卡定高 52 / 轻轨卡最小 52 可长高

```css
.nav-inforow {
  display: flex;
  align-items: center;            /* pre：单行垂直居中 */
  gap: 9px;
  padding: 5px 0;                 /* 沿用 .rc-row 既有 5px（globals.css:1319-1324） */
  min-height: var(--nav-info-h);  /* 52px —— 两种卡型共同的下限 */
  box-sizing: border-box;
}
/* 上车后（post）：两行贴顶，块高 42 = 20 + 2 + 20 */
.nav-inforow[data-nav-info="post"] { align-items: flex-start; height: var(--nav-info-h); }
```

- 基线 = 主行 20px（15px × 1.3 向上取整）+ 间隙 2px + 次行 20px（13px × 1.55 向上取整）+ padding 5px × 2 = **52px**。52 是 4px 网格整数倍；5px 沿用既有 `.rc-row`，不新造非标值。
- **不设 `transition: height`**：动画 height/width 属明令禁止的表现手法（引发布局抖动与掉帧）。

#### 两变体：差异来源是「行数」，不是随意破例

| 卡型 | `pre`（上车前） | `post`（上车后） | 差异来源 |
|---|---|---|---|
| **巴士卡** | **固定 52** | **固定 52** | 左槽是一句 `EtaText`（单行）⇒ 内容 30px < 52，被 `min-height` 撑到 52 |
| **轻轨卡** | **最小 52 / 可长高至 132** | **固定 52** | 左槽是 `LrtEtaInline`：**主行 + 「方向 · 开出时刻」小字行 + 邻班折叠区**（`.rc-live` 为列布局，`globals.css:1776-1784`） |

**为什么不能统一压到 52**：轻轨 `pre` 的左槽物理上有 3 个纵向块。硬钉 52 只有两种结局 —— 要么 `overflow:hidden` **裁掉邻班区**（违反项目「禁截断」纪律），要么让它溢出**压到下方纵条**（重叠）。两者都比"这一行长高"更严重，故按「**让位优先于定高**」处理。

**轻轨卡 `pre` 的高度（按 CSS 值推算，未逐机型实测；QA 以 `data-nav-info-h` 实测为准）**

| 轻轨 `pre` 子态 | 纵向块 | 推算高度 | 算式（line-height 1.55） |
|---|---|---|---|
| 仅主行（无方向、无邻班） | 1 | **52**（撑满下限） | 21 + padding 10 = 31 |
| 主行 + 方向·时刻 + 折叠键 | 3 | **72** | 21 + gap1 + 19 + margin1 + 20 + 10 |
| 再展开「前后班次」（+2 行） | 5 | **114** | 72 + gap2 + 19 + gap2 + 19 |

#### 最大高度上限与超限处理

**上限 = 132px**（`--nav-info-h-lrt-max`，= 52 + 80，4px 网格）。
定这个数的依据：当前内容最大 114，留 18px 余量；132 在 half 档（390×844 可视约 286px）占 46%，仍留 154px 给纵条首屏 —— 不把纵条整块挤出视野。

超限时按阶梯让位，**禁止裁切、禁止缩字**：

| 序 | 手段 | 省下 | 副作用 |
|---|---|---|---|
| ① | 邻班区强制折叠（不允展开） | ≈ 42px | 少看两条邻班；主班信息仍在 |
| ② | 省略「推算」角标等非必需装饰 | ≈ 0（同行） | 无 |
| ③ | 仍超 ⇒ **允许继续长高**，超出 132 也照实渲染 | — | 纵条首屏变少；但"看不见"比"变高"更严重 |

**明令禁止的三种"压缩"手段**：`overflow: hidden`（裁字，违反禁截断）、字号 < 13px（破坏项目小字地板，且已禁整页缩放）、行内嵌套滚动（面板内出现第二个滚动容器，手势冲突）。

#### 验收口径（按卡型区分，否则会假红）

| 卡型 | `pre` | `post` |
|---|---|---|
| **巴士卡** | `data-nav-info-h === "52"` | `data-nav-info-h === "52"` |
| **轻轨卡** | `52 ≤ h ≤ 132` | `data-nav-info-h === "52"` |

> **「两态恒 52」这条断言只对巴士卡成立。** 拿轻轨卡去测 52 必然失败，且失败的是断言本身不是实现。QA 脚本必须先判卡型（`card.rides[0].kind === "lrt"` 或读信息行内的 `.rc-live` 是否存在），再选断言分支。

### 2.6.2 入场动效

| 项 | 规格 | Token |
|---|---|---|
| 退场 | **0ms**（直接替换） | — |
| 入场 | 只动 `opacity: 0 → 1`，150ms，`ease-out` | `--dur-fast` + `--ease-standard` |
| 位移动画 | **不做**（不做 translateY；本行是信息锚点，上浮会与纵条展开的方向感打架） | — |
| 降级 | `@media (prefers-reduced-motion: reduce)` ⇒ `animation: none`，瞬切 | — |
| 并发元素数 | 1（整块） | — |

**为什么不做交叉淡出**：交叉淡出需要旧内容与新内容**同时存在于 DOM**（或至少旧内容延后卸载）。旧内容是"小跑能赶上"，新内容是"下一站…"—— 让两者共存 150ms，屏幕阅读器会读到两句互相矛盾的结论，且很可能读到旧的那句。**正确性优先于平滑度**：直接替换 + 新内容淡入。

### 2.6.3 两态高度差与面板联动（实测口径）

**三态高度（`data-nav-info` 的实际取值只有 `pre` / `post`；空态无节点，见 §2.6.5）**

| 卡型 | `pre` | `post` | 差值（pre → post） |
|---|---|---|---|
| **巴士卡** | 52 | 52 | **0** |
| **轻轨卡** | 52 / 72 / 114 | 52 | **−20 ~ −62**（折叠时 −20；展开邻班时 −62） |
| 任意卡（换乘候车 / 已下车） | — | — | **−52**（整块移除，见 §2.6.5） |

**上车瞬间的净变化（关键）**：`pre → post` 与「纵条从折叠变逐站展开」**由同一次状态变更驱动**（`track.phase === "riding"` 同时决定 `infoMode` 与 `NavStrip` 的 `nav` 入参），React 在**同一次 commit** 里完成 ⇒ 不存在"先收缩、后展开"的中间帧。

**纵条高度公式（N = 本段站数，含首末站）**

```
上车前（未导航，条折叠）：44（上车站行）+ 44（途经展开键）+ 44（下车站行）           = 132
上车后（导航，强制展开）：22（「车上约 N 分」行）+ 44 + 35×(N−2)（中间站行）+ 44     = 110 + 35(N−2)
纵条 Δ = 35(N−2) − 22      （N=3 → +13；N=4 → +48；N=6 → +118；N=10 → +258）
```
> 35px = 中间站行 `min-height 32` 与 `padding 6+6 + 23 行高` 取大；22px = 13px × 1.55 + 2。**推算值**，真机可用 `data-nav-leg` 前后各读一次纵条高度复核。

| 场景 | 信息行 Δ | 纵条 Δ | 净值 |
|---|---|---|---|
| 巴士卡 N = 3 | 0 | +13 | +13（几乎不动） |
| 巴士卡 N = 4 | 0 | +48 | +48 |
| 巴士卡 N ≥ 6 | 0 | +118 ~ +258 | 明显增长（预期行为：逐站可见） |
| 轻轨卡 N ≥ 6（邻班折叠） | −20 | +118 | +98 |
| 轻轨卡 N = 3（邻班展开） | −62 | +13 | **−49（向上收缩）** |

**结论与过渡约定**

1. **面板档位不动**：`.route-sheet` 的高度由 detent 决定（`sheet-detents.ts`），内容高度变化**不会**改变面板位置 ⇒ 不存在"面板跳一下"。
2. **内容会 reflow**：短轻轨段 + 邻班展开时，净值可能是向上收缩约 49px。这是**一次性**的、发生在用户主动按「我已下车/已上车」之后的模式切换时刻，且主按钮在吸底条（不随内容移动）⇒ 手指锚点不动。
3. **不做高度动画**（禁止 `transition: height`）；**不加空白占位**去"抹平"它（理由见 §2.6.5）。
4. **禁止把两者拆成两次渲染**（例如先切 `infoMode`、再切 `nav`）：那会产生真实的中间帧跳动。若将来重构，必须在同一 state 变更内完成。

| 其他变化源 | 是否跳动 | 处理 |
|---|---|---|
| 图标 `busStop → bus` | 否（同 20px 盒） | — |
| 右侧标签消失（`showTag` 变 false） | 否（主行行高 20 > 胶囊 20，容器 `min-height` 兜住） | §3.4 |
| 站名长短变化（相邻两站） | 否（单行 `nowrap` + `flex:none`，不改变行高） | §2.5 |

### 2.6.4 滚动容器

不新增滚动容器。信息行随 `.route-sheet__scroll` 滚动（`globals.css:6017`），不吸顶 —— 吸顶会与吸底操作条形成"上下夹击"，在 half 档只剩不到 100px 可读。

### 2.6.5 空态：换乘候车期整块不渲染（v3.11 有意取舍，不是缺陷）

**形态**

```
[步行行]     步行 4 分 → 換乘站
[信息行]     ← 无此节点（高度 0，不是空白占位）
[纵条]       第二程站点列表（上车站高亮 + 「等待上车」由底栏承担）
```

**触发条件**（`infoMode === "none"`，两条合并）

| 条件 | 场景 | 说明 |
|---|---|---|
| `hasEnteredRiding && ride.phase === "boarding"` | **换乘候车期**（下第一程、在换乘站台等第二程） | 本次要补档的主场景 |
| `hasEnteredRiding && ride.phase === "done"` 或末段步行 | 已到目的地 / 走去终点 | 既无"等车"也无"下一站"可说 |

**为什么不能复用 `pre` 行**：`pre` 行左槽**硬绑 `card.rides[0]`**。换乘期拿它会显示**第一程**的等车 ETA —— 那是错数据。**宁可不显示，也不显示错的**（错数据比空更糟：用户会据此判断"还有 6 分"，然后在站台白等）。

**高度与跳动**

- 高度：52 → **0**，下方内容上移 52px（一次性）。
- 面板档位不动（同上 §2.6.3）。
- **判定：接受，不做空白占位。** 三条理由：
  1. **同一帧里纵条在反向大幅位移**：`nav` 只在 `riding` 时传入（`NavStrip.tsx:73` 的 `open = openManual || !!nav`），所以换乘期纵条由「第一程逐站展开」**收回折叠**（`110 + 35(N₀−2)` → `132`，第一程 6 站时收缩约 **118px**）⇒ 52px 不是这一帧的感知主导项；
  2. 空白 52px 占位在"刚下车、正要判断下一步"的时刻会读成"**这里坏了**"——无解释的空槽比没有更让人不安；
  3. 该时刻的信息已由**底栏「等待上车 · 站名」+ 纵条**完整承担，信息行留空**不丢信息**。

**防它退化成缺陷的三条约束**

1. 移除必须与纵条换段在**同一次 commit**（现状成立：两者都由 `track.legIndex` / `phase` 驱动）—— 不得拆成两次渲染。
2. 禁止对信息行/纵条做 `height` 过渡（不得用动画"掩盖"位移）。
3. 空态时 `data-nav-info` **属性不存在**（不写 `"none"`）⇒ QA 用「属性缺席」断言空态，不会与 `pre`/`post` 混淆。

**未来支持它需要什么（下一批，本批不做）**

| 需要 | 现状 | 下一批 |
|---|---|---|
| 班次数据 | `pre` 硬绑 `card.rides[0]` | 按 `legIdx` 取 `card.rides[legIdx]` |
| 上车站名 | 写死第一程 | 取 `strips[legIdx].stops[0]` 对应的那一站 |
| 赶车标签 | 已由锁存关闭 | **必须继续受 `showTag` 约束**（补数据时不得顺手把标签放回来） |

**设计上它应该显示什么（下一批口径，本批不实现）**

- 主行：`在 {换乘站} 换乘 {下一程线路}`
- 右槽：**无**（标签锁存，`showTag === false`）
- 次行：**不显示**"等车约 N 分"，直到该段有真实班次数据（宁缺不猜）
- 高度：**52**（届时空态位移归零，§2.6.3 的 −52 消失）

### 2.7.1 已过站（坐过站）：主行文案定稿

**触发**：`stopsAway === 0` **且** `alarm === "none"`（车已驶离下车站）。此时底栏**不会**说「即将到达」，信息行若照常写「还有 0 站下车 · 约 1 分」，用户会以为车还没到、继续在座位上等。

**定稿文案**

| 槽位 | 定稿 | 字号/字重/颜色 |
|---|---|---|
| 主行前缀 | `已过站` | 13px / 400 / **`--fg-2`**（比常态前缀 `--muted` 提一档，见下） |
| 主行站号 | `{站号}` | 11px / 500 / `--meta` / tabular（不变） |
| 主行站名 | `{站名}` | 15px / 600 / `--fg`（不变） |
| 次行 | `请在下一站下车` | 13px / 400 / `--muted` |
| 「约 x 分」子句 | **不渲染** | — |

**为什么是「已过站」而不是「坐过站」/「已过」**

1. **前缀槽位宽度恒定**：现有前缀全部是 3 个全角 —— `下一站` / `已到站` / `下车站`，`已过站` 正好也是 3 个。⇒ 站号与站名的**左缘一格不移**，切换瞬间零水平重排。
2. **切换只发生在前缀上**：坐过站前那一刻主行是 `下一站 T306 澳科大`，过站后变成 `已过站 T306 澳科大` —— 站号与站名**逐字不变**，用户一眼就能看出"我盯的那一站已经过去了"，不必重读站名。这是本状态最重要的认知效果。
3. **不用「坐过站」**：它是动词短语（"你坐过站了"），做前缀会读成 `坐过站 T306 澳科大` 的怪句；且"坐过站"隐含责备，导航界面在中性陈述与指责之间应选前者。
4. **不用「已过」**（2 字）：少一个全角 ⇒ 站号左移 15px，产生可见重排，而收益为零。

**为什么前缀从 `--muted` 提到 `--fg-2`**：这是需要用户**立即行动**的纠错信息，而非常态进度。提一档后仍属中性灰阶，**不引入警示色**（不制造焦虑，也不靠颜色单独传达 —— 语义由「已过站」三个字承担）。

**次行为什么是「请在下一站下车」，不加「后重新乘车」**

1. **空间**：次行 13px，句长每多 6 个全角 = +78px；320px 视口下主行 `已过站` + 17 字长站名已接近预算，次行再长会挤压。
2. **正确性**：过站后的最优恢复取决于「下一站离目的地的步行距离」与「是否有回程线路」，应用此刻**没有**这个判据。写「重新乘车」可能与实际最优（走回去）相反 —— **给出错误的具体建议，比只给确定的那一步更糟**。
3. **恢复路径已闭环**：用户下车后，导航自动进入末段步行（`done` → 步行到达段），届时界面给出的就是"怎么走回去"。次行只需把用户**推到下车这个动作**上。

**边界：下车站是本段末站（终点站）时**

若 `alarm === "none"` 而 `stopsAway === 0` 且下车站后面**没有站**（终点站已过），"下一站"不存在，次行改为 `请下车`（3 全角）。不写"终点站已过"这类会让用户以为坐回头车的表述。

**高度**：仍是两行（主行 20 + 间隙 2 + 次行 20 + padding 10）= **52px**，`post` 定高不变（§2.6.1）。本条**不引入第三个 `data-nav-info` 取值**（理由见 §2.8.2）。

**写作纪律**：
- 只用「分」，不用「分钟」—— 本行是密集信息行，多一个全角字 = 14px，直接吃掉 320px 的余量。
- 分隔符用 `·`（U+00B7），与全站既有文案一致（`还有 ${n} 站 · 约 ${x} 分`）。需求原文里的「•」是键盘输入习惯，落地统一为 `·`。
- 不出现「估算」「推算」「轮询」「缓存」等内部词（延续既有纪律）。

## 2.8 观测钩子（供 QA 自动断言）

> 本节以**实现为准**（`NavDetailBody.tsx` 的 `NavInfoRow`），已与首版提案对齐过差异：首版写的 `data-eta-min` / `data-stops-to-alight` **未落地**，实际用 `data-nav-remain-min` / `data-stops-away`。QA 脚本按本节写。

| 钩子 | 值域 | 挂在哪 | 用途 |
|---|---|---|---|
| `data-nav-info` | `"pre"` \| `"post"`；**空态时属性不存在** | 信息行根节点 | 断言"布局切换发生过"；空态用**属性缺席**判（不写 `"none"`） |
| `data-nav-info-h` | 整数 px（`offsetHeight` 实测） | 同上 | **高度断言唯一依据**（巴士 52 / 轻轨 52–132，见 §2.6.1） |
| `data-eta-scope` | `"board"`（pre）\| `"alight"`（post） | 同上 | **需求 4 的核心断言**：上车后必须是"到下车"；上车前刻意是"到本站"，两者不同源 |
| `data-eta-base` | 整数分钟 | 同上 | **语义已变更，见下表** |
| `data-eta-remain` | 整数分钟 | 同上 | 旧名兼容（既有 QA 脚本仍在读），与 `data-eta-base` **同源同值** |
| `data-nav-remain-min` | 整数分钟 | 同上 | 与 `data-eta-base` 同值；新增的语义化名字（新脚本优先用它） |
| `data-stops-away` | 整数 | 同上 | 与纵条 `data-nav-leg` 交叉校验；`null` 时**属性不输出**。**`0` 有三种语义（已到站 / 即将到站 / 已过站），不能单独判「到了」——必须联合 `data-nav-missed`，见 §2.8.2** |
| `data-nav-missed` | `"1"` \| 不存在 | 同上 | **已过站**标记（`stopsAway === 0 && alarm === "none"`）。只在过站时输出；不输出 = 未过站。见 §2.8.2 |
| `data-nav-next-station` | `"1"` \| `"0"` | 同上 | 主行是否指向"下一站"（`0` = 已到站/退化为下车站） |
| `data-tag` | `"on"` \| 不存在 | 标签外层 `<span>` | 赶车标签是否渲染（题 B 验收用；锁存为真时**节点不存在**） |
| `data-nav-leg` | 段下标 | 纵条 `.navstrip` | 与 `data-stops-away` 交叉校验 |

### 2.8.1 `data-eta-base` 的语义变更（旧脚本必须改断言方式）

| | 旧语义（U4 之前） | 新语义（U4 之后，本批） |
|---|---|---|
| 含义 | 本行的**本地校准锚点** | 本行**显示的到下车分钟**（`shownAlightMin`） |
| 来源 | `segProgress.segRemainSec / 60`（**到下一站**）+ 逐跳求和 | `legRemainMinOf(...)`（**到本段下车**，与服务端 `remaining.ts` 同式） |
| 随时间 | 由 15s 心跳**本地递减** | **不递减**；由车辆帧（12s）重新校准 |
| 地板 | 无明确地板 | `Math.max(1, round(...))`（写"约 0 分"会与到站提醒抢语义） |

**因此**：
- 不可再断言"`data-eta-base` 每 15 秒一定变小" —— 它现在只在**新车帧到达**时变化；
- 应断言"车辆帧更新后 `data-eta-base` 跟随变化，且 **`>= 1`**"；
- 旧口径的锚点已不再单独暴露；若要断言"到下一站"，用 `track.segProgress.segRemainSec`（不进 DOM，属单测范围）。

> 为什么必须在 DOM 上留痕：需求 4 这类"算错口径"的缺陷，肉眼看到的都是"一个数字"，只有把口径写进属性才能自动判假绿。

### 2.8.2 `data-stops-away === 0` 必读：同一个 0，三种相反语义

**`0` 单独看不足以判断「到了」。** 乘车态下 `alarm` 有三种取值，`stopsAway === 0` 都可能成立：

| `data-stops-away` | `alarm` | `data-nav-missed` | 语义 | 主行 | 次行 | 底栏 |
|---|---|---|---|---|---|---|
| `0` | `now` | 不存在 | **已到站**（车停在下车站） | `已到站 {站号} {站名}` | `本站下车` | `已到站 · {站名}` |
| `0` | `soon` | 不存在 | **即将到站**（正开往下车站的区间） | `下一站 {站号} {站名}` | `还有 0 站下车 · 约 1 分` | `即将到达 {站名}` |
| `0` | `none` | `"1"` | **已过站**（车已驶离，用户坐过站） | `已过站 {站号} {站名}` | `请在下一站下车` | 无到站提示 |

**为什么必须联合判断（而不是看 `data-eta-scope`）**

- `data-eta-scope` 在 `post` 下**恒为 `"alight"`** —— 它只区分 `pre` / `post`，**没有**区分"到了/过了"的能力。用它判过站会写出永远为真的假断言。
- `alarm` 本身**不在 DOM 上**（当前没有对应属性），QA 读不到 ⇒ 因此新增 `data-nav-missed`，让过站可被自动断言。

**`data-nav-missed` 的判定式（唯一口径，实现须与此一致）**

```
data-nav-missed = "1"  ⟺  stopsAway === 0  &&  alarm === "none"
```

**QA 断言写法（避免踩坑）**

```js
// 正确：0 站 + 过站标记一起看
const away = Number(el.dataset.stopsAway);
const missed = el.dataset.navMissed === "1";
expect(away === 0 && missed).toBe(true);          // 过站
expect(away === 0 && !missed).toBe(true);         // 到站/即将到站（两者靠底栏文案或主行前缀再分）

// 错误：只判 0 就当"到了"
// expect(Number(el.dataset.stopsAway)).toBe(0);  // 过站时同样为 0，会假绿
```

**为什么不做成第三个 `data-nav-info` 取值**

1. `data-nav-info` 只有 `pre` / `post` 两值，是"布局形态"的枚举（单行 / 两行）；已过站**形态完全不变**（仍两行、仍 52px），它不是第三种形态。
2. 若加 `"missed"`，所有既有"两态"断言（含本规范 §2.6.1 的高度验收、Spec AC-10）都要改，且会把"布局"与"语义"两种维度混进同一个属性 —— 后续再加"终点已过""冻结"就会不断膨胀。
3. 用**增量属性** `data-nav-missed` 表达语义，既有断言零改动，新断言可叠加。

## 2.9 两个时间口径：头部门到门 vs 信息行本段（刻意不同，不要统一）

| | 头部 `剩余 X 分` | 信息行 `约 X 分` |
|---|---|---|
| 钩子 | `data-remain-total` / `data-remain-base` / `data-arrive-at` | `data-eta-base` / `data-eta-remain` / `data-nav-remain-min` |
| 口径 | **门到门剩余**（服务端 `remainingMin`，或 `remainOf(arriveAt, now)` 兜底） | **本段到下车剩余**（`legRemainMinOf`） |
| 范围 | 现在 → 目的地：含**下游换乘步行 + 下游候车 + 下游乘车 + 末段步行**；不含已发生的出发步行 | 基准站 → **本段下车站** |
| 归零处理 | **clamp 0**，归零切文案「即将到达」 | **地板 1 分**；到站时去掉时间子句写「本站下车」 |
| 何时存在 | 全程都有（含上车前 / 下车后） | 仅 `post`（在车上） |

**两者相差 = 换乘步行 + 下游候车 + 下游乘车 + 末段步行 ⇒ 属预期差异，不是 bug。**

**为什么必须保留两个（不是"没统一干净"）**

1. **只有门到门那个数能与"预计到达时刻"同源反推**：`arriveAt = now + remainingMin`。若把头部改成"本段剩余"，用户会看到「剩余 9 分 · 预计 14:32 到达」，而 14:32 与 9 分对不上（还要换乘），两个数字互相打架。
2. **上车前 / 下车后没有"下车"这个概念**：那一刻本段剩余无定义，但门到门仍然成立 ⇒ 头部必须是门到门。
3. **反过来，信息行问的是"我还要在车上坐多久"**（决定何时起身），必须是本段 —— 用门到门会让人以为"还有 28 分才到站"，其实 9 分后就该下车。

**冻结纪律**：要动只能动**文案**（各自标明范围），**不能动口径/分母**。
候选文案（**本批未采纳，仅登记**）：头部「全程剩余 28 分」、信息行「本段还有 9 分」。不采纳原因：320px 下「全程」「本段」各多 2 全角 = 28px，会挤掉站名余量；且两处已有位置差异（头部是大字总览、信息行在流程中），语境足够区分。

> 出处：`src/lib/nav/remaining-view.ts` 头注「两条语义红线（**刻意不同，不要"统一"**）」，①全程 clamp 0 / ②到下车 max(1)。本节的裁决与该文件一致。

## 2.10 候车期候选车牌（来车是谁）

### 2.10.1 为什么现在能做：判定层早就拿到了车牌，只是没显示

| 事实 | 证据 |
|---|---|
| 车停在本上车站时，`r1Of()` 返回 `{ kind: "weak", plate }` —— **带车牌** | `src/lib/nav/boarding-detect.ts:143`、`:160` |
| 该 `plate` 目前只参与"降低判定门槛"，从未进入任何展示 | `src/lib/nav/boarding-detect.ts:471` `const assisted = aux.strong || aux.weak` |
| 候选池 `ranked` 已下发到界面（`candidates`，含 6 辆） | `src/components/nav/useRideTracking.ts:1069-1071`、`:1844-1849` |
| 切 riding 需车离站并走够 35m（约 20s），是物理限制 | 判定链 `R2_*`（同文件） |

**结论**：等车时最焦虑的不是"系统何时判定我上车"，而是"来的这辆是不是我要坐的"。这个问题的答案**已经在内存里**，只差一个显示位。

**本设计只做"显示一个候选车牌"**，不改判定、不提前切 riding、不写 `plate` 状态。见 §2.10.7 的红线。

### 2.10.2 位置：信息行 `pre` 的次行（与 `post` 次行同槽）

```
等车期（可靠时）
[busStop]  还有 3 站 · 约 6 分              [小跑能赶上]
           来车 MB1234                                  ← 本次新增（次行）
           ↑ 与主行文字左缘对齐（x = 29px）

等车期（不可靠 / 无候选）
[busStop]  还有 3 站 · 约 6 分              [小跑能赶上]   ← 与今天完全一致，单行居中
```

| 项 | 规格 |
|---|---|
| 槽位 | `pre` 的**次行**，与 `post` 次行同一位置（20px 高） |
| 左缘 | 与主行文字左缘对齐（29px = 引导位 20 + gap 9） |
| 字号/字重 | 标签 `来车` 13px / 400 / `--muted`；车牌 `MB1234` 13px / **600** / `--fg` / `tabular-nums` / `letter-spacing: 0.02em` |
| 间距 | 标签与车牌之间 4px |
| 形态 | **纯文本，不用法规车牌胶囊**（`.plate`） |
| 图标 | **保持 `busStop`，绝不换成 `bus`** |
| 右槽 | 赶车标签保持在**主行**右侧（与主行同基线），不参与次行 |

**为什么不用 `.plate`（黑底黄字法规车牌）**：那是"已确认上车"的视觉语言 —— 乘车态底栏正是 `乘车中 · [黑底黄字车牌]`（`NavTrackBar.tsx:162-171`）。候选车若用同一形态，会读成"已经上车了"，与需求"不能看起来像已上车"直接冲突。**用形态区分"候选 / 已确认"，比用颜色区分更可靠**（色盲、强光下都成立）。

**为什么不放底栏**（也是硬约束）：底栏状态行是 `white-space: nowrap` 单行，可用宽 288px（320 − 16×2）；左槽 `● 等待上车 · {站名}` 在最长站名（17 全角 ≈ 221px）时已算到约 300px —— 本身就贴边，再塞 72px 的车牌必然横向溢出；而给底栏加一行会顶破 `--actions-slot-h: 96px`（`globals.css:7508`），连带影响滚动容器 padding-bottom。**放信息行则零高度成本**。

### 2.10.3 文案定稿

| 元素 | 定稿 |
|---|---|
| 标签 | `来车` |
| 车牌 | `{plate}`（如 `MB1234`，6 字符） |
| 整行 | **`来车 MB1234`** |

**为什么不写"是这辆" / "已确认" / "已到站"**

- 候选 ≠ 已确认。写"是这辆"会在我们判断错时变成**明确的错误承诺**；用户据此上车，反而更糟。
- `来车` 陈述的是**我们观测到的事实**（有一辆车停在本站，车牌是它）。事实错了是数据问题，措辞错了是设计问题 —— 后者不可接受。
- 不写"已到站"：与「到站提醒」（`alarm`，指**你要下车的站**）语义冲突，也与"车到站/人上车"的判定术语冲突。

**为什么车牌用纯文本而不是"仅显示已找到这辆车"**：用户站在车门口抬头看的就是车牌号，`MB1234` 是**可当场核对**的信息；"已找到这辆车"不可核对，等于没给信息。车牌是这条设计唯一的价值来源。

### 2.10.4 可靠才显示：判定表（含全部降级分支）

**总原则：显示错的车牌比不显示更糟** —— 用户看到 `MB1234` 就会去找这个号，来的不是这辆，他会怀疑整个应用。因此**默认不显示，只有证据充分才显示**。

| # | 条件 | 结果 | 理由 |
|---|---|---|---|
| 1 | `legKind !== "bus"`（轻轨段） | **不显示** | 轻轨判定链只走 R2、`plate` 恒为 `null`（`boarding-detect.ts:447-459`），无逐车数据 |
| 2 | `ride.phase !== "boarding"` | **不显示** | 只在候车期有意义 |
| 3 | `hasEnteredRiding`（U2 单向锁存为真） | **不显示** | 已上过车就不再是"候选"；与赶车标签同一条锁存纪律 |
| 4 | `body[data-veh] !== "fresh"` | **不显示**（`stale`） | `atStation` 是 DSAT 上报值，帧陈旧时可能停在上一个站 |
| 5 | 停靠本上车站的车 **恰好 1 辆**（`weaks.length === 1`） | **显示**（`unique`） | 唯一候选，可核对 |
| 6 | 停靠本上车站的车 **≥ 2 辆** | **不显示**（`ambiguous`） | `weaks[0]` 只是排序第一，不是"正确的那辆"（同线串车 / 同站台多线同码） |
| 7 | 无停靠车，但"刚离站"的车 ≤ **60m**（`strong` 且距上车站 ≤60m） | **显示** | 用户正在上车、车刚起步的那一刻；60m 保证不会在车开远后还挂着车牌 |
| 8 | 无停靠车，`strong` 车已 > 60m | **不显示** | 车已走远，再显示会引导用户追车 |
| 9 | 上述都不成立 | **不显示**（`none`） | — |
| 10 | `strong` 与 `weak` 车牌冲突 | **不显示** | 判定层已返回 `kind: "none"`（`boarding-detect.ts:147-151`），照此执行 |
| 11 | 车牌为空串 / 不匹配牌号格式 | **不显示** | 防御；不渲染半个车牌 |

**为什么单帧就显示（不要求 N 连帧）**：轮询 12s，任何"连续 2 帧"的防抖都等于 12–24s 延迟；而公交车停站只有 20–40s，防抖会把这条信息**整个吃掉**。改用**源头收紧**代替时间防抖：只有"车正停在本站 + 帧新鲜 + 唯一"这一组**权威条件**才显示 —— `atStation` 是 DSAT 的直接上报，不是几何推测，单帧即可信。

**为什么不做 20s 记忆（latch）**：会把"车已走"的车牌继续挂在屏幕上（用户照着一个已经离开的号找车）。**宁可闪断，不可滞留**。若真机上出现"停站期间车牌闪断"，那是下一批用"帧内锚定"解决的问题，不是本批。

### 2.10.5 不可靠时的降级形态：什么都不显示

| 项 | 规格 |
|---|---|
| 次行 | **不渲染**（不是空占位、不是灰字） |
| 主行 | 与今天完全一致：单行、垂直居中 |
| 底栏 | 保持 `正在检测车辆`（本设计不改底栏） |
| 赶车标签 | 不受影响，仍在主行右侧 |

**为什么不写"有车在站台，车牌待确认"**：
1. 它把"我们看到了但说不清是哪辆"这件事暴露给用户，等于**邀请用户自己猜** —— 而猜错的代价正是这条设计要消灭的；
2. 它会在停站期反复出现/消失（歧义是逐帧的），成为一行闪烁的噪声；
3. "待确认"这个词在乘车态已有明确用途（`NavTrackBar` 的中置信车牌），复用会让两个不同状态看起来一样。

**与赶车标签同一条纪律**：不确定就不渲染，**不用 `opacity: 0` / 灰色占位**（那对屏幕阅读器仍可读，等于把"不确定"念给用户听）。

### 2.10.6 与 52px 定高的关系

| 卡型 | 无车牌 | 有车牌 |
|---|---|---|
| **巴士 `pre`** | 52（单行居中） | **52**（两行：5 + 20 + 2 + 20 + 5） |
| 轻轨 `pre` | 52–132（§2.6.1，不受影响） | 同左（轻轨永不显示车牌） |
| `post` | 52 | 52 |

**高度恒为 52，但主行会上移 11px。** 如实记录：

- 无车牌：单行在 42px 内容区垂直居中 ⇒ 主行顶边 ≈ 5 + 11 = **16px**。
- 有车牌：两行块贴顶 ⇒ 主行顶边 = **5px**。
- ⇒ 车牌出现/消失时，主行上/下移 **11px**。

**判定：接受，不做"永久预留次行"。** 三条理由：
1. 这 11px 位移**与"新增一行"因果同帧**，人眼读作"插进来一行"，不是"内容跳了"；
2. **同样的 11px 位移今天已经在发生**：`pre` 用 `align-items: center`、`post` 用 `flex-start`（`NavDetailBody.tsx:306`，实测同一处三元表达式），所以上车瞬间主行本来就上移 11px。本设计没有引入新的位移类型，只是让它提前发生在"车到站"这一刻；
3. 若改为"永久预留次行"（主行恒贴顶），常见状态（没车）会永久上重下空 22px —— 用一个**常驻**的视觉缺陷换一个**偶发 11px** 的位移，不划算。

### 2.10.7 红线（实现侧必读）

1. **只读显示**：不得写 `setPlate()`、不得改 `boardMatch` / `matchSource`、不得影响 35m 判定与 `switchToRiding` 时机。判定链一行不改。
2. **不得复用 `data-plate`**：候选车牌用**独立属性** `data-cand-plate`。`data-plate` / `matchPending` 在乘车态的含义是"已锁定"，混用会让 QA 把候选误读成已确认。
3. **`data-nav-info` 仍为 `"pre"`**：出现车牌**不是**状态跃迁，不改布局枚举（与 §2.8.2「已过站不做第三态」同一条纪律）。
4. **图标不得换成 `bus`**：`bus` 图标是"我在车上"的语义（§2.1 表）。候选期必须保持 `busStop`。
5. **不可靠时不渲染**：不用 `display:none` 的占位节点、不用灰字、不用"待确认"。

# 题 B（需求 2）· 赶车标签的显示 / 隐藏时机

## 3.1 判定真源：两个 `data-nav-phase` 不能混用

| 钩子 | 取值 | 谁在写 | 本标签能否用它判 |
|---|---|---|---|
| `body[data-nav-phase]` | `off` / `recommend` / `detail` / `walk` / `riding` | `NavShell.tsx:927` | **不能单独用**：`walk` 同时覆盖"走去上车站"和"下车后走去目的地" |
| `.nav-actions[data-nav-phase]` | `off` / `boarding` / `riding` / `done` | `NavTrackBar.tsx:191` | **不能单独用**：一按「开始导航」就变 `boarding`，此时人还在家 |

**关键代码事实（缺陷 #1 的确切成因）**：`开始导航` 走 `startSession("out")`（`NavShell.tsx:685-702`），函数体在 `ridePhaseNow === "off"` 时**立刻** `rideStart()` 进入 `boarding`，同时 `setWalkSeg("out")` 进入步行段。因此**"步行去车站"这一整段时间里，`ride.phase` 已经是 `boarding` 而 `navPhase` 是 `walk`**。任何"`boarding` ⇒ 已到站 ⇒ 隐藏标签"的写法，都会在用户刚出门时把标签抹掉。

两次历史缺陷的机制正是各用了一个：

- **缺陷 #1（标签全删）**：用 `ride.phase === "boarding"` 判"已到站"，于是按下「开始导航」的瞬间标签就消失了 —— 但用户还在路上，这正是最需要它的时刻（成因见上）。
- **缺陷 #2（上车后仍显示）**：只按"是否有导航"判，没有"已上车"这个单向事实，于是 riding 甚至下车后的步行段都还在显示。

## 3.2 状态机（唯一真源 = 单向锁存 `hasEnteredRiding`）

```
                   ┌──────────────── 结束导航 / 换方案 ⇒ 复位 ────────────────┐
                   ▼                                                          │
  ┌────────┐  打开详情  ┌──────────┐  开始导航  ┌────────┐  进入 riding  ┌─────────┐
  │ 未开始 │ ─────────▶ │ 详情静态 │ ─────────▶ │ 步行中 │ ────────────▶ │ 乘车中  │
  └────────┘            └──────────┘            └────────┘   （锁存置位） └─────────┘
      │                      │                      │                        │
   标签显示               标签显示               标签显示                标签隐藏
                                                                          │
                                                          下车 / 末段步行 / 结束
                                                                          ▼
                                                                    标签仍隐藏（锁存）
```

| # | 状态 | 判定（与代码字段一一对应） | 标签 | 备注 |
|---|---|---|---|---|
| S0 | 未开始导航（推荐列表） | `navPhase === "off"` \| `"recommend"` | 显示 | 方案卡语境，v3.9.0 已拍板恢复 |
| S1 | 详情静态（未点开始导航） | `navPhase === "detail"` 且 `ride.phase === "off"` | 显示 | 用户正在比较"来不来得及" |
| S2 | 步行前往上车站 | `navPhase === "walk"` 且 `ride.phase !== "riding"` | **显示** | 缺陷 #1 的修复点：`ride.phase` 此时已是 `boarding`，**不得据此隐藏** |
| S3 | 已到站候车 | `navPhase === "detail"` 且 `ride.phase === "boarding"` | 显示 | 见 §3.7 已知边界 |
| S4 | 已上车（自动判定或手动标记） | `ride.phase === "riding"` | **隐藏** | 锁存置位，此后不回退 |
| S5 | 已下车 | `ride.phase === "done"`，或 `navPhase === "walk"` 且锁存已置位（末段步行） | 隐藏 | 锁存保证不复活 |
| S6 | 行程结束 | session 关闭 / 面板收起 | 隐藏（整行卸载） | 锁存复位 |

**锁存语义**：

```ts
// 唯一的判据：本次导航是否"已经上过车"
const hasEnteredRiding = useRef(false);
if (ride.phase === "riding") hasEnteredRiding.current = true;   // 只置位，不因 phase 变化清位
const showTag = pane === "detail" && !hasEnteredRiding.current;
```

- **只置位、不清位**：一旦上过车，"能不能赶上"就是一个已结算的过去时问题，任何后续 phase 变化（下车、末段步行）都无权让它复活。
- **唯一允许清位的入口**：用户点「我没上车」（`onNotBoard`）。这是显式撤回，语义等价于"我刚才那次上车判定作废"。复位点写在 `NavTrackBar` 的 `onNotBoard` handler 里，不在渲染期靠 phase 推断。

## 3.3 「上车之时」的判定口径

**定案：以进入 `riding` 那一刻为准。自动判定与手动「我已上车」一视同仁。**

理由（按权重排序）：

1. **可观测性**：本项目只有两类数据源 —— GPS 与车辆位置。**"关门/发车"没有任何数据源**（DSAT 接口不提供车门状态，车辆帧也没有）。把 UI 绑在不可观测事件上，结果只能是要么永不触发、要么用伪信号猜。
2. **单一真源**：`ride.phase` 已经是全项目"我在车上"的唯一表示（`NavTrackBar` 状态行、`data-track-state`、`alarm` 全都由它派生）。标签再引一个本地布尔，就是第二份状态 —— 两份状态必然漂移，这正是缺陷 #2 的成因。
3. **两条入口必须同构**：自动 `switchToRiding` 与手动 `board()` 最终都把 `ride.phase` 置为 `riding`（`NavTrackBar.tsx:110-118` 注释明确 `boardMatch` 的 `auto` / `manual` 差异只用于纠错文案）。如果标签对两者区别对待，就会出现"手动上车后标签还在"——**缺陷 #2 的原样复发**。
4. **语义时机正确**：用户上车（踏上车门）与车开动之间有 5~30 秒。标签要消失的是"我还要不要跑"这个决策，而决策在**上车那一刻**就归零了，不需要等发车。等到发车再消失，用户会在这段窗口里继续看到"小跑能赶上"而误以为要赶下一班。

**反例（明确禁止）**：

- 禁止用 `alarm`/`prog.passedIdx > 0` 当"已发车"代理 —— 首站拥堵时 3 分钟不动，标签会一直挂着。
- 禁止用 `plate !== null` 判"已上车" —— 无牌车辆（v3.7.0 已确认存在）永远判不出。
- 禁止用 `data-nav-phase === "riding"`（页面级）判 —— 步行段与乘车段都会是 `riding` 之外的值，且语义与乘车 phase 不同（团队已冻结"不可混用"）。

## 3.4 隐藏方式：DOM 移除 vs 视觉隐藏

**定案：不渲染（DOM 移除）。**

```tsx
{showTag && <span className="rc-tier rc-tier--3">{tierText}</span>}
```

| 方案 | 屏幕阅读器 | 布局 | 判定 |
|---|---|---|---|
| DOM 移除 | 不读 | 不影响（容器定高 52px） | **采用** |
| `display: none` | 不读 | 不影响 | 等价可接受，但多一层 CSS 分支，不必要 |
| `visibility: hidden` | 不读 | 占位（宽度仍在） | 不必要（定高已解决布局） |
| `opacity: 0` | **仍然读** | 占位 | **禁止** |
| 移出屏幕（`position: absolute; left: -9999px`） | **仍然读** | 不影响 | **禁止** |

**为什么 `opacity: 0` 是最坏的选项**：它把"错误结论"从视觉搬到听觉 —— 明眼用户看不到，屏幕阅读器用户却在乘车途中听到"全力冲刺有机会赶上"，而且没有任何视觉线索提示这句话是过期的。这是比缺陷 #2 更严重的信息污染，且**无法被截图验收发现**。

**布局影响**：无。标签宽度变化不影响主行（主行 `flex: 1; min-width: 0`，且容器定高）。因此**不需要任何占位元素**。

## 3.5 上车后是否需要替代形态

**建议：本批不做。**

理由：

1. **信息已闭环**：底部操作条状态行在 riding 显示 `乘车中 · 车牌`（`NavTrackBar.tsx:150-176`），纵条显示 `停靠中 / 下一站`，头部显示 `剩余 X 分 / 预计 HH:MM 到达`。"本班已赶上"不提供任何新决策量。
2. **每多一句就多一处真相**：本项目已经因为"两处真相"付出过代价（头部总时长 vs peek 摘要、`data-eta-base` 与 `data-remain-base` 的语义混淆）。再引入一句常驻结论，只会增加漂移面。
3. **情绪价值不成立**："赶上了"是一过性事件，常驻展示会在 30 秒后变成噪音。

**若团队坚持要闭环，唯一允许的形态**（本批仍建议不做）：

- 一次性 toast，`role="status"`，2500ms 自动消失，不进入版面；
- 文案 `已上车 · 本班赶上了`，`--text-xs` / `--muted`，无强调色、无动效；
- 只在 S4 置位的那一次渲染，之后不再出现（含重进面板）。

## 3.6 实现要点（给前端的落地约束）

1. `showTag` 的输入只有 `pane` 与 `ride.phase`，**不得**读取 `navPhase` 的 `walk`/`riding`（除 S6 卸载外）。原因见 §3.1。
2. 锁存必须放在 `NavShell`（session 层），不能放在 `NavDetailBody`（会随面板重挂载丢失 → 收起再展开标签又回来了）。
3. 面板重开（peek → detail）必须仍然隐藏：锁存的生命周期 = 一次导航 session，与 `startSession` / `stopSession` 对齐。
4. 不得新增全局布尔 `body[data-tag]` 之外的第二套 DOM 钩子；标签自身用 `data-tag="on"` 即可。

## 3.7 已知边界（明确写出来，不在本批修）

| 边界 | 现象 | 处理 |
|---|---|---|
| S3 已到站候车 | 人已站在站台，标签仍说「小跑能赶上」—— 前提（还要走路）已失效 | 本批不修：没有独立的"已到站"信号（自动上车判定的 80m 门槛是内部量）。若将来数据层暴露 `atStop`，标签应改为「已到站 · 等车」。**登记为下批候选**。 |

# 题 C（需求 1）· 步行线的视觉规范

## 4.1 缺陷定位（根因，非现象）

`nav-map-walk.ts` 绘制三条独立折线，其中**两条语义都是"未走"**：

| 层 | 语义 | 颜色 | 宽度 | 透明度 | z |
|---|---|---|---|---|---|
| `nowPath` | 当前步**还没走的那截** | `#0b6e4f` | **7** | **1.00** | 73 |
| `aheadPath` | 后续步（尚未开始） | `#0b6e4f` | **6** | **0.55** | 70 |
| `donePath` | 已走过（累积轨迹） | `#8c93a0` | 5 | 0.85 | 69 |

证据：`nav-map-walk.ts:70-76`（now）、`:64-69`（ahead）、`globals.css:7726-7731`。

**为什么用户会读成"缺陷"而不是"层级"**：这两条线**在几何上是首尾相接的**（当前步的剩余部分 → 下一步 → 再下一步）。一条连续的路径在接缝处突然从饱绿变成淡绿、从 7px 变成 6px，人眼判定为渲染错误，而不是"这一段更重要"。层级感必须由**不连续**的线索承载（箭头、宽度、标签），不能由**连续同路径上的深浅**承载。

第二个绿：`ghost`（非当前段的完整走廊）用 `op 0.4`（`globals.css:7743`）。它与当前段不连续（通常在地图的另一侧），所以读起来像"远景"，本身可接受 —— 但它让"未走绿"出现了第三个深浅档，必须一起收口。

## 4.2 最终规范

| 语义 | 层 | 颜色 | 宽度 | 透明度 | 端点/连接 | z | 备注 |
|---|---|---|---|---|---|---|---|
| 已走（当前段） | `donePath` | `walked.color` = `--map-walk-done` `#8c93a0` | 5 | 0.85 | `lineCap: round` / `lineJoin: round` | 69 | **保持现状，不动** |
| 未走（当前段·当前步） | `nowPath` | `unwalked.color` `#0b6e4f` | **6** | **0.75** | round / round + **`showDir: true`** | 73 | 与下一行**同组三元组（同一对象引用）**，唯一差异是 `z` 与方向箭头 |
| 未走（当前段·后续步） | `aheadPath` | `unwalked.color` `#0b6e4f` | **6** | **0.75** | round / round | 70 | 同上 |
| 未走（非当前段走廊） | `ghost` tone=ahead | `unwalked.color`（同色） | **4** | **0.6** | round / round | 68 | 独立层：细一档 + 淡一档，**不得与未走段同值** |
| 已走（非当前段走廊） | `ghost` tone=done | `walked.color` | **4** | **0.85** | round / round | 68 | 与 done 同色同透明，只细一档 |

**三条硬规则**：

1. **同一段连续路径上的「未走」必须完全一致**（color / weight / opacity 三项全等，且来自**同一组变量**）。当前步与后续步的区分**只允许**用 `z` 与 `showDir` 箭头。
2. **同一语义只有一种透明度**：已走 = 0.85（含走廊已走），未走 = 0.75（当前段）/ 0.6（走廊）。透明度绑定**语义层级**（当前段 / 走廊），不绑定"第几步"。
3. **宽度只表达"是否当前段"**：当前段 6（与巴士彩段同宽）/ 走廊 4 / 已走 5。宽度不随进度变化。

**透明度微调的依据（0.55 → 0.75，无障碍修复）**：

| 透明度 | 与白色瓦片的混合色 | 对比度 | WCAG 1.4.11（图形 3:1） |
|---|---|---|---|
| 0.55（现状） | `rgb(121,175,158)` | **2.26:1** | 不达标 |
| **0.75（定案）** | `rgb(72,146,123)` | **3.70:1** | 通过 达标 |
| 0.92（巴士彩段参照） | — | 约 5.0:1 | 通过 |

> 现状 0.55 在强光下的实际效果是"看不清这条路" —— 这属于可用性缺陷，不只是美观问题。

**圆角端点**：`lineCap: "round"`、`lineJoin: "round"` 保留（`nav-map-walk.ts:96-107` 已设）。端点圆角半径 = 线宽 / 2 = 3px。**不要**改回 `strokeDasharray`（v3.8.1 已按负责人要求去掉圆点串）。

## 4.3 与巴士段 / 站点 / 蓝点的关系

```
z 130  车辆图标
z 128  用户蓝点
z 120  pin / 目的地
z  95  轻轨站点
z  90  巴士站点
z  73  未走·当前步（含方向箭头）
```

| 关系 | 规范 | 理由 |
|---|---|---|
| 与巴士彩段**粗细** | **同宽 6** | 一条动线两种含义（走 / 坐），粗细一致读起来是"同一条行程"；靠色相（绿 vs 线路色）+ 透明度（0.75 vs 0.92）区分 |
| 与巴士彩段**层级** | ahead 70 < 彩段 72 < now 73 | 共线时线路色压住后续步；当前步（带箭头）必须浮上来说明"先走这段" |
| 与站点图标 | 所有步行线 < 90/95 | 站点是可点元素，绝不能被线盖住（既有纪律） |
| 与蓝点 | 128 恒在最上 | "我在哪"永远优先 |
| 与车辆 | 130 最高 | 重叠时车压人 = "我在车上"的既有语义 |

**为什么 now 在 73 而不是 70**：`nowPath` 是当前步的剩余部分，带 `showDir` 箭头。若落在彩段之下，箭头会被线路色吃掉，"先走这段"的指引消失。步行与乘车在几何上几乎不共线，73 不会造成遮挡问题。

## 4.4 外部道路 vs 内部小路 / 无路网回退段

**定案：地图上不区分。**

三条理由，按权重：

1. **手段都被堵死**：
   - 虚线 → v3.8.1 负责人明确要求"步行路径与巴士段一样用实线"，回退代价是推翻已拍板口径；
   - 更淡 → 直接退回"深浅两种绿"缺陷（本文档要修的就是它），且 0.55 已跌破 3:1；
   - 新颜色 → 违反既有色彩体系（绿 = 走，灰 = 已过，线路色 = 乘车）；引入第五种色相会让"绿=走"的语义松动。
2. **用户不需要这个信息**：用户看地图要回答的是"往哪走"。道路等级（大马路 / 内巷）不改变动作；而"这段是直线估算"改变的是**可信度**，可信度属于**文字层**（步骤卡片），不属于地图层。
3. **回退段本身已被文字层兜住**：步行路径失败时，步骤卡片给的是「步行路径暂时取不到 · 直线 210 米 · 约 3 分钟」（`NavDetailBody.tsx:357-361`），已经明确说了"这是估算"。地图再叠一层视觉差异属重复，且没有图例就无人能读懂。

**若架构师坚持要区分**，唯一可接受的方案（不新增色、不改线型）：

- 在回退段的**终点**放一个 12px 空心圆环（描边 `--map-walk-ahead` 2px，填充 `--surface`），z 74；
- 步骤卡片对应行加一句 `此段为直线估算`；
- **必须**同时给图例（否则等于没做）。

> 本批建议：**不做**。理由是本项目当前没有"回退段"的可靠判据暴露给渲染层（`WalkStep` 里没有 `fallback` 标记），实现它需要动数据契约 —— 性价比低。

## 4.5 Token 对接

**只读事实**：`nav-map-walk.ts` 全部样式经 `readWalkStyle()` 从 CSS 变量读取（`:55-84`），组件里**零硬编码色**。这是好底子，本次只需改 Token 值与「谁引用谁」。

### 4.5.1 复用（不改）

| Token | 值 | 用途 |
|---|---|---|
| `--map-walk-done` | `#8c93a0` | 已走（浅/深色同值，底图恒浅） |
| `--map-walk-ahead` | `#0b6e4f` | **未走唯一色**（含当前步） |
| `--map-walk-w-done` | 5 | 已走线宽 |
| `--map-walk-op-done` | 0.85 | 已走透明度 |
| `--map-z-walk-*` | 68 / 69 / 70 / 73 | 层级不变 |

### 4.5.2 新增（A2，语义单一真源）

> **命名的第一原则：按「语义层级」命名，不按「第几步」命名。**
> 本缺陷的结构性成因不是色值错，而是**存在两套可独立调参的变量**（`-op-ahead` 与 `-op-now`）—— 只要两套变量并存，下一次就一定有人只改一半。因此本次**不给 now 与 ahead 各留一套**，而是只留一套「未走」变量，由两条线共同引用。

```css
:root {
  /* ── 未走：一条语义 = 一组三元组。now 与 ahead 共用，禁止派生第二套 ── */
  --map-walk-unwalked-color: var(--map-walk-ahead); /* #0b6e4f，复用既有色，不新增色相 */
  --map-walk-w-unwalked: 6;                          /* = 巴士彩段宽度，动线同宽 */
  --map-walk-op-unwalked: 0.75;                      /* 混白 3.70:1（0.55 时仅 2.26:1，低于图形 3:1） */

  /* ── 走廊（非当前段的完整步行走廊）：独立一层，同色，只细一档 + 淡一档 ── */
  --map-walk-w-corridor: 4;
  --map-walk-op-corridor: 0.6;

  /* ── 已走：一组三元组（含走廊已走，不另设值）── */
  --map-walk-w-done: 5;      /* 既有，不变 */
  --map-walk-op-done: 0.85;  /* 既有，不变 */
}
```

**命名取舍说明**：用 `unwalked` 而不是 `undone`。
`done` 在本项目已有明确含义（已走），`undone` 会被读成「取消/未完成」；`unwalked` 与 `done` 不是反义对，语义上不与既有 `-done` 冲突，且直接对应「未走」。颜色仍复用 `--map-walk-ahead`（既有变量，语义就是"你前方的路"），**不新增色相** —— 这条是团队已冻结的色彩体系约束。

### 4.5.3 重定义 / 弃用（显式变更）

| Token | 旧值 | 处理 | 原因 |
|---|---|---|---|
| `--map-walk-w-ahead` | `6` | **弃用**（保留定义，值改 `var(--map-walk-w-unwalked)`） | 与 now 分叉的入口之一 |
| `--map-walk-w-now` | `7` | **弃用**（保留定义，值改 `var(--map-walk-w-unwalked)`） | 消除粗细差；**JS 不得再读取** |
| `--map-walk-op-ahead` | `0.55` | **弃用**（保留定义，值改 `var(--map-walk-op-unwalked)`） | 对比度不达标 |
| `--map-walk-op-now` | `1` | **弃用**（保留定义，值改 `var(--map-walk-op-unwalked)`） | 消除深浅差；**JS 不得再读取** |
| `--map-walk-w-ghost` | `4` | **弃用**（值改 `var(--map-walk-w-corridor)`） | 语义命名 |
| `--map-walk-op-ghost` | `0.4` | **弃用**（值改 `var(--map-walk-op-corridor)`） | 第三个绿收口 |
| `--map-walk-op-ghost-done` | `0.5` | **弃用**（值改 `var(--map-walk-op-done)`） | 已走只有一种透明度 |

**「弃用」的确切含义（三段式，缺一不可）**：

1. **定义保留**：CSS 里仍存在这些变量名（符合本项目"只增不改名"回滚纪律），否则旧分支回滚时会拿到空值；
2. **值改为别名**：指向 4.5.2 的单一真源；
3. **引用归零**：`src/` 内**任何位置不得再读取**这 7 个变量（含 `readWalkStyle()`）。这一条是结构性的 —— 只要 JS 还在读 `-w-now`，就仍然存在"只改一半"的可能。

对应 CI 守卫（C-2）：

```
grep -rnE '\-\-map-walk-(w|op)-(now|ahead)\b' src/     ⇒ 必须 0 命中
grep -rn 'map-walk-op-ghost' src/                      ⇒ 必须 0 命中
```

> globals.css 里的**定义行**不在此检查范围（它必须有），只查 `src/` 下的**引用**。

### 4.5.4 JS 侧改动约束（结构性防复发）

`readWalkStyle()` 的返回结构**从「三套并列」收为「三个语义组」**，让"给 now 和 ahead 传不同值"在类型层面就不成立：

```ts
export interface WalkPolylineStyle {
  /** 未走：nowPath 与 aheadPath **共用同一个对象引用**（不是两份相等对象） */
  unwalked: { color: string; weight: number; opacity: number };
  /** 已走：donePath 与 ghost(done) 共用 */
  walked: { color: string; weight: number; opacity: number };
  /** 走廊：ghost(ahead/done) 的宽度来源 */
  corridor: { weight: number; opacity: number; opacityDone: number };
  /** 层级（不变） */
  z: { ghost: number; done: number; ahead: number; now: number };
}
```

- 调用处一律 `common(style.unwalked.color, style.unwalked.weight, style.unwalked.opacity, style.z.now, true)` / `…style.z.ahead)` —— **差异只剩 `z` 与 `showDir`**；
- 若有人将来想给 now 单独调透明度，必须**改接口**（会触发 code review 可见的结构变更），而不是悄悄改一个 CSS 变量；
- **回退值必须与 Token 一致**：`("--map-walk-unwalked-color", "#0b6e4f")`、`("--map-walk-w-unwalked", "6")`、`("--map-walk-op-unwalked", "0.75")`、`("--map-walk-w-corridor", "4")`、`("--map-walk-op-corridor", "0.6")`。回退值与 Token 不一致会导致"主题失效时静默变样"，本项目已踩过这个坑。
- 保留 `readWalkStyle()` 的**纯函数性质**（只读 `getComputedStyle`，无副作用）⇒ 可直接被单测驱动，不需要真地图。

**关于 `lineCap`（回应架构师建议）**：保留 `round`，**不改为 `butt`**。

理由：`butt` 会在每个 step 交界处留下一条 90° 平口，在弯道上呈现为明显的"断口"。`round` 产生的交界圆点（半径 = 3px，即线宽 6 的一半）在 now 与 ahead **同色同透明**之后已经**不可见** —— 圆点之所以现在看得见，正是因为它叠在 0.55 的淡绿上显出 1.0 的深绿。三元组统一后，圆点与两侧同色，交界处变成一条连续圆角曲线，符合"动线连续"的表达。

### 4.5.5 走廊层（ghost 0.6）的独立性约束

| 约束 | 内容 | 理由 |
|---|---|---|
| 命名 | `--map-walk-w-corridor` / `--map-walk-op-corridor` | 与「未走」区分语义，避免被当成同一个值 |
| **不得与未走段同值** | `--map-walk-op-corridor` (0.6) **严格小于** `--map-walk-op-unwalked` (0.75)，且 `--map-walk-w-corridor` (4) **严格小于** `--map-walk-w-unwalked` (6) | 走廊是"另一段路的预告"，不承载当前唯一可执行指引；一旦同值，地图上会出现两段同等权重的绿线，用户会误判"两条都要走" |
| 验收 | C-10 断言：`corridor.opacity < unwalked.opacity` 且 `corridor.weight < unwalked.weight`（**严格小于，非 ≤**） | 防止后续有人用"全都 0.75"把它抹平 |

> 明确写进 ADR-111：**0.75 属于「未走段（当前段）」，0.6 属于「走廊（非当前段）」，二者不是同一个数，不得合并。**

### 4.6.1 C-6 的机器可读形式（QA 可直接断言）

**先说清楚一件容易做错的事**：AMap 的 `Polyline` **不是 DOM 元素**，它由 canvas 绘制。因此

- `document.querySelector('.amap-polyline')` → 找不到；
- `getComputedStyle(el).strokeColor` → 读不到；
- CSS 变量值 → 只能证明"配置意图"，不能证明"地图上画了什么"。

C-6 必须在**「值真正传给地图」的那一层**断言。三级读法，优先级从高到低：

#### 一级（CI 门禁，推荐 · 无需浏览器）

用**假构造器捕获** `AMap.Polyline` 的构造入参与 `setOptions` 调用 —— 这正是 `nav-map-walk.ts` 已经预留的可测形态（`PolylineCtor` 是个只含 `new (o: Record<string, unknown>)` 的接口，`:36-38`，本身就为注入假实现而设计）。

```ts
// 断言伪代码（tsx 直接跑，不需要真地图、不需要 DOM）
type Rec = { path: [number, number][]; strokeColor: string; strokeOpacity: number; strokeWeight: number; zIndex: number };
const made: Rec[] = [];
class FakePolyline { constructor(o: Rec) { made.push(o); } setPath() {} setOptions() {} }
const style = readWalkStyle(fakeRootWithTokens);       // 或直接构造 style 对象
const layers = ensureWalkLayers(fakeMap, FakePolyline as never, style, empty, seed);

// ① 在同一次绘制里，找出「首尾相接」的两条（endA[last] ≈ startB[0]，容差 1e-6）
const seam = findSharedVertex(made[?], made[?]);        // 即 nowPath 与 aheadPath

// ② 三元组逐字段全等（不要用 toEqual 之外的自定义比较；NaN 不存在于这三项）
assert.equal(seam.a.strokeColor,   seam.b.strokeColor);
assert.equal(seam.a.strokeOpacity, seam.b.strokeOpacity);
assert.equal(seam.a.strokeWeight,  seam.b.strokeWeight);

// ③ 差异只允许在这两项（明确白名单，防止有人"顺手"再加一项差异）
assert.notEqual(seam.a.zIndex, seam.b.zIndex);          // 73 vs 70，层级本来就不同
assert.notEqual(seam.a.showDir, seam.b.showDir ?? false); // now 带箭头、ahead 不带
```

**关键点：三元组用 `assert.equal`（全等）而不是"差值 < ε"** —— 透明度不是连续量，0.75 与 0.7499 就是两个值，容差会掩盖"只改一半"的复发。

#### 二级（视觉回归，可选 · 需要 Playwright）

1. 进入步行态，**滚动/取景到接缝可见**（`map.setFitView` 或直接缩放）；
2. `await page.screenshot({ clip })` 截取接缝区域（建议 200×120，含两侧各 60px 路径）；
3. 用 PNG 解码器读像素，沿路径**法向取中轴**（不要取边缘：抗锯齿会有 1px 过渡带）：

```
对路径上每个采样点 p，沿法向 ±1.5px 内取 3 个像素的中位数作为该点颜色（避开边缘混色）；
在接缝前 10px 与接缝后 10px 各取 5 个点；
比较两组的 RGB 通道均值：每通道差 ≤ 3（8bit），判定为同一颜色。
```

4. 反推 α（可选，用于证明透明度也一致）：在线宽中心取像素，用 `混合色 = α·线色 + (1-α)·瓦片色` 解 α；两次解出的 α 差 ≤ 0.02。

#### 三级（人工，仅兜底）

在 390×844 真机、强光下沿未走路径走一遍，确认接缝处**看不出深浅突变**。此级不作判据，只作复核。

> **为什么必须做一级**：二级依赖瓦片底图颜色（底图有建筑/绿地/水域，局部底色不同会污染 α 反推），在 CI 上是不稳定判据；一级是纯函数，秒级、零 flaky、失败信息精确到字段。**C-6 的 CI 门禁用一级，二级只在发版前跑一次。**
