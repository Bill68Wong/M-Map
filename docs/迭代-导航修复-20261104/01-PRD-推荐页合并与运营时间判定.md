### 0.3 一句话产品判断

用户要的不是"少显示几条线"，而是**「我看到的每一条线，现在都能坐」**。把运营时间当过滤器、把「有车」当最终裁判，两者缺一不可——单独用任何一个都会出错（只用时间：误杀末班晚点车；只用实车：夜班线在白天也能出现在标签里）。

## 2. 竞品调研：四个直接竞品 + 一份规范

调研问题固定为三个：**同起点多线路怎么合并**、**同线多站点组合怎么处理**、**不在运营时间的线路怎么处置**。

### 2.1 高德地图（公交路径规划）

| 问题 | 做法 | 依据 |
|---|---|---|
| 同起点多线 | **在"换乘段"内部并列**：`segments[].bus.buslines[]` 是一个**数组**，同一段可返回多条线路；方案本身（`transits[]`）仍是一条方案一个上下车点 | `[官方文档]` 高德 Web 服务 API · 路径规划：<https://lbs.amap.com/api/webservice/guide/api/direction>（公交方案信息列表一节，`buslines` 字段；返回示例 `transits[] → segments[] → bus.buslines[]`） |
| 同线多站点 | 接口同时给**线路级**与**站点级**首末班：`start_time`/`end_time`（线路）、`station_start_time`/`station_end_time`（**上车站点**） | 同上（公交方案信息列表：`start_time 首班车时间`、`station_start_time 上车站点首班时间`） |
| 不在运营时间 | 两套机制：① **按时刻筛方案**——`date` / `time` 参数「根据出发时间和日期，筛选可乘坐的公交路线」；② **夜班车开关**——`nightflag` 默认 **0 = 不计算夜班车**；③ 事件标签里含「停运」 | 同上（请求参数 `nightflag` / `date` / `time`；返回字段 `emergency.eventTagDesc` 取值含「提示/甩站/突发/停运」） |

**可直接借鉴的两条**：`nightflag` 默认关闭，等于承认「夜班线不该混进白天方案」是行业默认；`station_start_time` 说明「首末班」的正确粒度是**上车站**，不只是线路两端。

### 2.2 Google Maps（公共交通 / Directions）

| 问题 | 做法 | 依据 |
|---|---|---|
| 同起点多线 | **不在一个步内合并多线**：一个 transit step 的 `transit_details.line` 是**单值对象**（非数组）。多线 = 多条独立 itinerary，由"按出发时刻求解"产生 | `[官方文档]` Directions API 参数页明确 `mode=transit` 可指定 `departure_time` 或 `arrival_time`（时间相关求解）：<https://developers.google.com/maps/documentation/directions/get-directions>；字段级结构见同站 `responses#DirectionsTransitDetails` `[官方文档/结构，页面未逐字核对]` |

### 2.5 规范侧：GTFS 对"运营时间"的建模（用于校验我们的判定口径）

| 事实 | 对本项目的含义 | 依据 |
|---|---|---|
| 班次频率用 `frequencies.txt`：`trip_id, start_time, end_time, headway_secs`，即「时间窗 + 间隔」——**与本项目 `route_frequency` 同构** | 我们的表结构不是自创，是 GTFS 频率模型的简化版，口径可信 | `[官方文档]` GTFS 频率示例：<http://vocab.gtfs.org/documentation/schedule/examples/frequencies> |
| 服务日由 `calendar.txt`（星期模式 + 起止日期）与 `calendar_dates.txt`（例外日）共同决定，**必须先合并两张表才能得出"某天是否服务"** | 本项目用 `day_type` 近似了这一步，并用 `lrt_holidays` 做例外日；缺的是「**服务日 vs 自然日**」的显式区分 | `[官方文档]` GTFS Reference · calendar.txt / calendar_dates.txt：<http://gtfs.org/documentation/schedule/reference> |
| **超过 23:59 的时刻合法**：「a trip departing at 25:30:00 leaves at 01:30 AM the following calendar day, but belongs to the prior day's service_id」；把跨午夜写成 `00:30:00` 会破坏服务日连续性 | 直接支持本项目「跨午夜时段 `to_min > 1440`」的处理（`headway.ts:170-171` 的 `nowMin + 1440` 探针），也说明**夜间线必须挂在"前一个服务日"**，不能用自然日 00:00 切一刀 | `[二手/工程解读]`：<https://www.transit-data.com/gtfs-feed-architecture-fundamentals>（原文引用 GTFS 时间语义；规范本身见上条 reference） |

### 2.6 调研小结（三步判断）

1. **没有任何一家把"不在运营时间的线路"与可乘线路并列展示。** 高德默认 `nightflag=0` 不计算夜班车，Citymapper 直接无结果，Google 按时刻求解。
2. **"多线合并"发生在「段内」，不发生在「方案级」。** 高德的 `buslines[]` 在 segment 内并列；Google 的 transit step 只有单值 `line`，多线走多条 itinerary。这与本项目现状（段内 `parallelRoutes` + 方案级一卡一条）结构一致，**不需要推翻重来，只需要给段内并列加条件**。
3. **"班次"与"下车站"是两件不同的事。** 班次差异（后续车）留在卡内小字（Google「Also at …」、本项目 `altBuses`）；下车站差异属"方案差异"，各家都按方案拆开。把两者塞进一张卡，是本项目U9 两个病症的总根源。

## 3. U8 · 判定规则草案（可执行）

### 3.1 术语与五态定义（v1.2：以负责人原话为最高依据）

> **需求原文（负责人 2026-11-04 原话，最高依据）**：
> 「**是 AND 的关系，不在运营时间且无车才不考虑，否则就要考虑**」

这句话是本节所有判定的**唯一准绳**，其余推导（五态、宽限、`no_data` 归属）都只是它的实现化。把它展开成逻辑式：

```
不考虑（隐藏） ⟺ (不在运营时间) ∧ (无车)
反过来：只要「在运营时间」∨「有车」∨「无法判断有无车」⇒ 必须显示
```

**注意「否则就要考虑」这一半更容易被漏掉**。它意味着**举证责任在「隐藏」一方**：想隐藏一条线，必须同时拿出①不在窗口 ②无车 两份证据；缺任何一份，就只能显示。§3.3 的规则表就是按这个不对称性写的。

**逐格复核「否则就要考虑」是否满足（这是本节的自检清单）：**

| 格 | 判定 | 有车状态 | 结论 | 是否满足「否则就要考虑」 | 依据 |
|---|---|---|---|---|---|
| 1 | `open` | `has` | **显示** | ✓ | 规则 1 |

| 11 | `before_first` | `none` / `unknown` | **隐藏** | ✓ / ⚠️ 同第 9 格 | 规则 2 |

**关于第 6 格（`closing` + `unknown`）—— 明确是「保守显示」，不是「漏判」**

按需求原文，「不在运营时间」这一条在 `closing` 带内**只是"刚过窗口"，尚未确证收车**（`G_tail` 的存在本身就是为了承认「表定收班 ≠ 实际收班」）。此时：
- 拿不出「无车」的证据 ⇒ 不能隐藏；
- 因此**显示**是忠实执行「否则就要考虑」的结果，不是实现缺陷。

⇒ 结论：**第 6 格是保守显示。** 且它的实际影响面很小——只有并行线（未被 `fetchLive` 覆盖）才会是 `unknown`，主干线一定有实时数据（§4.7 B1）。

**关于第 9 格（`closed` + `unknown`）—— 已裁定为隐藏，且必须如实标注「这是对原话的工程化收窄」**

> **team-lead 裁定（2026-11-04）**：`closed` + `presence === unknown` **判隐藏**。

**⚠️ 定性（不得含糊）**：本格**有意偏离负责人原话的字面要求**。原话是「不在运营时间且无车才不考虑，否则就要考虑」；`unknown` 拿不出「无车」的证据，严格按字面应当显示。我们判隐藏，是**工程化收窄**，不是「符合原话」。
任何文档、Spec、验收记录**不得写成"完全符合 AND 关系"**——必须保留"已知偏离"这四个字，否则下一轮会被当成口径正确而继续沿用，偏离就固化了。

引入一个**纯函数级**的新原语（落在 `src/lib/recommend/headway.ts`，与 `headwayAt` 同源，禁止另起一套口径；签名与常量采纳架构师建议）：

```ts
export type ServiceState = "open" | "closing" | "closed" | "before_first" | "no_data";
export function serviceStateAt(
  idx: HeadwayIndex, route: string, nowMs?: number,
  opts?: { gTailMin?: number; gHeadMin?: number },
): ServiceState;
export const SERVICE_G_TAIL_MIN = 20;
export const SERVICE_G_HEAD_MIN = 0;
```

**先定义两个「时间域」，这是跨午夜正确性的根**（沿用 `headway.ts:170-171` 的双探针口径）：

- `t0 = nowMin`（今天这个服务日）
- `t1 = nowMin + 1440`（**昨天**那个服务日仍在延续，用于 `toMin > 1440` 的跨午夜段）
- 今日匹配行集合 `R = { row | matchesDayType(row.dayType, weekday, isHoliday) }`（`headway.ts:48-66`）
- `minFrom = min(R.fromMin)`、`maxTo = max(R.toMin)`（`maxTo` 允许 > 1440）

判定顺序（**必须按此顺序**，先特例后通例；每步都只用 `R` 与 `t0/t1`）：

| 步骤 | 条件 | 结果 | 说明 |
|---|---|---|---|
| 1 | `idx.byRoute` 中**没有该线**（或该线行数组为空） | `no_data` | **唯一的真 `no_data`**：我们完全没有这条线的班距资料，无从判断。`special` 行载入时已排除（`headway.ts:79`），只剩 `special` 的线落到这里 |
| 2 | `∃ row ∈ R`，`t0 ∈ [fromMin, toMin]` **或** `t1 ∈ [fromMin, toMin]` | `open` | 跨午夜续班天然落在 `t1` 支。`headwayAt` 的 PRIORITY 单命中逻辑**不用于此处**（见下方要点 b） |
| 3 | 未命中，且 `min over d∈{t0,t1}, d > maxTo` 的 `(d − maxTo)` **∈ (0, G_tail]** | `closing` | 末班宽限带。取 `t0/t1` 两支的**最小正 gap** |
| 4 | 未命中，且 `t0 < minFrom − G_head` | `before_first` | 今天首班还没发。`25@03:00` 落这里（`t0=180 < 360`），比 `closed` 更能说明"今天首班 06:00" |
| 5 | 其余（**含"落在两个窗口之间的洞"**、**含"表内有该线但 `R` 为空"**） | `closed` | 今日不服务。见下方要点 a / c |

**要点 a（v1.1 推翻原判定）：时段有洞 ⇒ `closed`，不是 `no_data`。**
原判定把"洞"归入 `no_data`（永不隐藏）。查库证明这会让 **10 组尖峰专线**（§1.3 表）在平峰整天挂在标签里——`59｜mon_fri` 在 12:00 会显示，而它 10:00–15:00 根本停驶。这是 N3 bug 的镜像复制。
理由：`route_frequency` 的语义是**"运营窗口表"**；一个窗口与下一个窗口之间没有行，就是**该时段无服务**，不是"我们不知道"。

**要点 b：`closing` / `maxTo` 不能用 `headwayAt` 的 PRIORITY 单命中算。**
`headwayAt` 的 PRIORITY（`headway.ts:173`）只返回"最具体 dayType 的那一行"，拿不到"今日最晚的 `toMin`"。`serviceStateAt` 必须**自己扫 `R` 取 `max(min)`**。但 `matchesDayType` 与 `macauNowParts` **必须复用**（`headway.ts:48-66`、`:167-169`）——只允许一处日期语义，这是架构师与本文一致的要求。

**要点 c：`no_data` 收窄为"该线完全不在表里"；「表内有该线、今日 `R` 为空」改判 `closed`。**
原判定也把后者归 `no_data`。查库证明这会让 **12 条无周日覆盖的线**（§1.3）在周日显示、**`15T` 在平日显示**——而 `live.ts:268` 的注释早已把「15T 平日不运营」当成既定事实。
理由同上：有该线的行、只是今天这个 `day_type` 没有行，语义是"今天不按这个服务类型运营"。

**要点 d：为什么整体应偏 `closed` 侧（这是本次最重要的设计判断）。**
隐藏判据里 `presence === "has"` 永远**优先显示**（§3.3）。因此：
- 误判成 `closed` 的**最坏后果** = "本来能跑的线，在无车时也不显示"——而"无车"本来就该少显示；
- 误判成 `no_data` 的**最坏后果** = "根本不跑的线，全天都显示"——**正是用户报的这条 bug**。
非对称的后果 ⇒ 判定必须偏向"隐藏"侧，`no_data` 只留给零信息的情形。原 v1.0 的写法（"`no_data` 永不因时间隐藏"）在方向上过保守，已推翻。

**要点 e：`G_tail` 只许往下调，不许往上放宽**（上界推导见 §3.4）。常量注释格式照 `headway.ts:227` 的 `TRANSFER_WAIT_HI_WEIGHT`（列全备选取值与理由）。

### 3.2 「有车」的三态

```
presenceOf(live: RouteLive | undefined): "has" | "none" | "unknown"
```

| 载具 | `has` | `none` | `unknown` |
|---|---|---|---|
| 巴士 | `nearest`/`second`/`more` 任一非空（`types.ts:446-465`）；或 `waitEstimate` 存在（`types.ts:477`）；**或 `passedCount > 0`（§3.2.1 新增）** | `empty === true` 且无 `waitEstimate` **且 `passedCount === 0`** | **本轮没有为这条线取实时数据**（`ctx.live.get(route) === undefined`） |
| 轻轨 | `state === "running"` | `state ∈ {before_first, after_last}` | `state === "no_data"` |

#### 3.2.1 `passedCount` 必须透出（= I-1，独立验收）

**现状缺陷**：`empty` 是在过滤掉 `!e.passed` 之后算的（`live.ts:340-341`），而 `passed` 恰恰是"这辆车刚过我这一站"的**强运营证据**。于是「末班车刚过站」→ `empty = true` → `presence = none` → 按 §3.3 被隐藏；更严重的是 `model.ts:468-478` 会**把整条方案剔除**。这是一条**现在就已经存在**的静默错误（不是本次引入）。

**要求**：`live.ts` 在算 `empty` 的同一处把 `passed` 数量透出（该函数**已为 `estimateWait` 统计过** `passed`，见 `live.ts:279`，零额外计算）。`presenceOf` 把 `passedCount > 0` 记为 `has`。

**为什么单列一条**：它同时修掉两个位置的错（标签层与方案层），独立价值不低于U8 主修；若只当"实现细节"，验收必漏。验收见 §6.4。

### 3.3 隐藏规则（U8 的最终判据）

```
hide(route) ⟺ serviceState ∈ {before_first, closed} ∧ presence ∉ {has}
            ∨ serviceState === closing            ∧ presence === none
```

用自然语言写死三条，避免实现时漂移：

1. **窗口内（含跨午夜续班）**：一律显示。此刻无车由"未发车估算"承接（`live.ts:258-321`），不是隐藏的理由。
2. **窗口外（含首班前）**：**有车就显示**（此即用户说的"末班车实际比官方晚"），无车/未知就隐藏。
3. **宽限带（`closing`）**：**明确无车才隐藏**；`unknown` 保守保留。这就是 `G_tail` 存在的**唯一作用**——它不是"允许显示"的许可，而是"数据不全时不清除"的容错带。
4. **`no_data`（仅"该线完全不在班距表里"）不因运营时间隐藏**——零信息时不得判定收车。注意这与 v1.0 写法不同：v1.0 把所有"没命中"都算 `no_data`，等于放行 10 组尖峰专线与 13 条缺日覆盖线路（§1.3、§3.1 要点 a/c）。

### 3.4 宽限窗口取值与理由

## 4. U9 · 合并条件与"一条线路怎么显示方案"

### 4.1 先把"合并"拆成三级（这三件事常被混为一谈）

| 级别 | 含义 | 现状 | 本次结论 |
|---|---|---|---|
| **L1 段内多线并列** | 同一段（同方向、同 `board→alight`）上多条线路并列成一个标签 | 有（`parallelRoutes`） | **保留**，但加可乘性条件 |
| **L2 卡内多班次** | 同一张卡里列该线的后续班次 | 有（`altBuses`） | **不动** |
| **L3 卡级合并（跨线路/跨下车站）** | 多线或多下车站塞进同一张卡 | 无 | **不做**（见 4.5） |

#### 4.5.2 R2「按偏好选代表下车站」的产品口径（v1.4 确认，无需文案）

**方案（架构师提出，team-lead 已采纳）**：`balanced` / `fewer_transfers` 取**最快**（`cost` 最小），`less_walk` 取**步行最少**。

**产品侧结论：不需要任何文案说明。** 三条理由：

1. **偏好切换是用户主动动作，推荐跟着变符合心智**。用户点「少走路」，期望就是"给我走路少的方案"——下车站变了正是该期望的**兑现**，不是意外。
2. **href 同源自动同步**（架构师已确认）⇒ **不会出现"卡面 T363、详情 T367"**。这消除了唯一需要文案解释的风险（"点进去和看到的不是一回事"）。
3. **加提示反而有害**：任何提示（如「下车站已变更」toast）都会把一个**正常行为**渲染成**异常告警**，增加困惑。

**但有一条前置要求（是行为，不是文案）**：切偏好时必须**整体替换列表**，不得走 `mergeCardsStable` 的部分合并。
依据：`merge-cards.ts:28-34` 已写明「换 OD / 切偏好 / 切轻轨优先 ⇒ **必须整体替换**」，否则旧顺序会覆盖服务端重排 ⇒ **排序永久失效**。代码已有守卫（`mergedForRef`），**必须保持**。

### 4.5.1 收敛规则的执行顺序（避免规则互相打架）

```
枚举候选（enumerate.ts，现状）
  → R5 站台码归一（去重前）          ← 先让"同站群多站台"变成同一个键
  → R1 站内互斥（配置表）           ← 再削同线内的明显劣选
  → R4 保护：不同线不归并           ← 只设边界，不动作
  → R2 同线同站收敛（择代表）        ← 再削同线的重复卡
  → R3 降级为备选（信息不丢）        ← 只搬运，不删除
  → sortCards → slice(limit)
```

**关键点三条**：
1. **R5 必须在最前**——它是"归一"，若不先归一，R2 的判定键在同一站群多站台下会因为字符串不同而**认不出是同一站**（这正是 R5 会导致 R2 失效的机制）。
2. **R2 必须在 `slice(limit)` 之前**（否则被收敛掉的卡已经占了名额，收敛等于白做）。
3. **R3 必须在 R2 之后**（先定谁是代表，才知道其余的是"备选"）。

### 4.6 裁决结论与理由（**已定**：规则三 + R1–R5）

**负责人 2026-11-04 拍板：一卡一个下车点。** 本方案即最终执行依据；规则一/规则二已划线转为追溯（§4.2、§4.3）。

理由（按权重）：

1. **它精确对上两个病症**：N3 早上消失靠 §3.3；「同一条线出多张卡」靠 R2；「上车站同下车站不同 ⇒ 详情矛盾」靠"卡级不合并"从根上避免。
2. **它与竞品结构一致**：高德把多线放在 segment 内（`buslines[]`），方案仍一方案一下车点；Google 的 transit step 单值 `line`。**卡级合并没有行业先例可参考**，做了要自担全部设计风险（`05-调研` §2.1/§2.2）。
3. **它保住详情页契约**：`planId + route + board + alight` 四元组（`card-link.ts:6-8`）不变，`/api/card` 的命中判据（`card.ts:89-92`）不变，`route_changed` 的语义不变。
4. **它不新增 UI 元素**：标签形态、`+N` 折叠、hover 全名都是现成的（`RouteStack.tsx:87-104`）；符合本项目"不新增元素/不新增行"的既有约束（`RecommendCard.tsx:252-254` 的历史裁定）。
5. **失败模式可见**（这是与规则二最关键的区别）：本方案若收敛错代表下车站，用户看卡面就能发现「这站下车更远」，可以反馈；规则二若 href 契约破了，表现为「点了没反应」——**正是本批要修的 P0 同类问题**。在修 bug 的批次里引入同类隐性失败，风险不对称。

**明确不建议的两件事**：
- 不做卡级合并（L3）。若将来一定要做，前置条件是先重构"卡级单值"字段（下车行、上车到下车时长、`altBuses` 阈值分母），这是一次独立的、有规格的重构，不应塞进本次修复。
- 不把"运营时间"做成**卡片级**过滤（"整张卡不在运营时间"没有意义——卡是按方案组织的，方案里任何一段不在运营时间都已经被 `model.ts` 剔除）。

#### 5.5.1 产品判断：**3 条以上被置顶，产品上不可接受**

负责人要求我给出「若出现 3 条以上线路被置顶，产品上是否可接受」的判断。**结论：不可接受，建议硬上限 = 2 条。** 五条理由：

| # | 理由 | 依据 |
|---|---|---|
| 1 | **「轻轨优先」是一个可选开关，不是默认体验。** 把它做成能占满前 3 位的强干预，等于让一个默认关闭的偏好劫持整个列表。 | `nav-service.ts:97`（`lrtFirst` 可选，默认关闭） |
| 2 | **置顶的入口只有一个条件：`totalMin ≤ baseline + 15`。** 15 分钟是很宽的容忍带；5→6 后 `baseline` 本身抬高，两项叠加会让「慢 15 分钟的轻轨」挤掉「快 3 分钟的公交」。用户看到的第 1 位不再是「最快」，与页面语义（`/nav` 是导航选线）冲突。 | `lrt-priority.ts:25`（`LRT_PRIORITY_SLACK_MIN = 15`）、`:39-40` |
| 3 | **3 条以上等于「轻轨独占首屏」。** 在 375×667 下首屏大约能完整露出 1.5–2 张卡（§5.3 AC-10.5 的口径），3 条置顶意味着**用户滚一屏都看不到一条公交方案**。 | §5.3、`AC-10.5` |
| 4 | **用户无法感知「为什么这几条被置顶」。** 卡面只有 `lrtPromoted` 角标（`lrt-priority.ts:53`、`merge-cards.ts:93`），没有解释「因为你开了轻轨优先」。置顶 1 条时用户能理解为「推荐我坐轻轨」；置顶 3 条时会理解为「这个 App 是不是只认轻轨」。 | `lrt-priority.ts:53` |
| 5 | **失败模式不对称。** 上限取 2 时，最坏情况是「第 3 条该置顶的轻轨没置顶」——但它仍按正常顺序排在列表里，**用户能找到**；上限不设时，最坏情况是「前 3 位全轻轨，最快的公交被推到第 4 位以下」——**用户找不到**。前者是降级，后者是信息缺失。 | 与 §3.1 要点 d 同一逻辑：宁可少干预，不可藏信息 |

**补充：为什么是 2 而不是 1**
- 取 1 太保守：澳门轻轨仅 3 条线，若同一 OD 的氹仔线与石排湾线都顺路（换乘一次），置顶 1 条会让另一条完全沉底，反而损害「轻轨优先」这个开关本身的价值。
- 取 2 的依据：首屏可视卡数约 2（`AC-10.5`），置顶占满首屏 = 用户不需要滚动就能看到「轻轨优先」的全部意图，且第 3 张起回到正常排序，公交方案仍在第一屏边界内。

**实施口径（供架构师定阈值）**：`applyLrtPriority` 增加 `maxPromoted = 2`，超出的命中者**按 `totalMin` 升序保留前 2**，其余**不置顶、不删卡**（保持「只重排、不增删」原则，`lrt-priority.ts:9-11` 的既有约束）。角标只打在真正置顶的那几条上（现有逻辑已是「回写 true」，`lrt-priority.ts:53`）。

**若架构师量测后发现 6 张下置顶条数仍 ≤2**：则上限是**防御性护栏**（防将来改动），仍建议保留，成本仅 3 行代码。

### 5.6 「候选变多不挤掉更优方案」是否仍成立

**对「取前 N 张」成立；对「轻轨优先」不成立（v1.2 修正）。**

- **排序（`/recommend` 与 `/nav` 都是）**：`sortCards(...).slice(0, limit)`（`service.ts:151`）是**取有序数组前缀**。`slice(0,6)` 的前 5 项与 `slice(0,5)` **逐项恒等**，所以任何"原本在前 5"的方案不会被第 6 名挤掉。数学上无风险——**这条与 `limit` 取值无关，两条链路都适用**。
- **例外（`/nav`）**：`applyLrtPriority` 会**重排**（`lrt-priority.ts:48-56`），且其 `baseline` 直接吃 `limit`（`:39-40`）。5→6 ⇒ `baseline` 抬升 ⇒ 命中集合变大 ⇒ **置顶集合确实会变**。这不是"挤掉"，而是"顺序被前置干预"，已由 §5.5.1 的上限护栏约束。
- 另一处非"挤掉"但相关的行为变化：`altBuses` 阈值变化让**卡片内容**变化（§5.4），用户可能觉得"同一张卡刷新后多了一行"。这是**内容变多**，不是顺序变化。

| 编号 | Given | When | Then |

| AC-11.1 | 某线末班车**刚驶过用户上车站**（`passed = true`），本方向已无"还没到站"的车 | 查询 | `presenceOf` = `has`（`passedCount > 0`）；该线**不被判为 `none`** |

### 6.7 U11 · 全项目点击体验升级（负责人本轮追加，纳入逐条核验清单）

> **需求原文（负责人 2026-11-04）**：「做全项目用户操作点击体验升级，学习谷歌系列的实现方式，让用户在点击任何按钮时都有舒适的按键反馈，主要参照 YouTube 的触摸操作反馈」
> **分工**：产品调研（本文档 + `06-调研-触摸点击反馈-YouTube与Material对照.md`）由我出；设计规格由 designer 出；技术实现由 architect 出，**各自回传 team-lead，不互相直连**。
> **本 PRD 只定「验收什么」，不定「怎么实现」。**

**产品侧必须先说清的一件事**：本项目**不是从零做**。现状已有 20+ 个 `:active` 选择器与一套按压 Token（`--dur-press: 90ms`、`--dur-release: 240ms`、`scale(0.96)`、`--spring-press` 已等于 Material `easing-standard`）。所以 U11 的真实范围是**四件事**：

| # | 要修的 | 现状 | 证据 |
|---|---|---|---|
| 1 | **参数无出处** | 90ms / 240ms / `scale(0.96)` 均无来源注释；而 Material 有明确 token | `globals.css:278-284` |
| 2 | **覆盖不一致** | 列表行（`.rpanel__row`、`.rv-card`、`.line-result`）只有 `background` 切换、**无 transition ⇒ 瞬间跳变**；底部导航、开关、地图 pin **无 `:active`** | `globals.css:4521`、`:4677`、`:8406` 等 |
| 3 | **缺「最短按压保留」** | 快速点按（<90ms）时 `:active` 一闪而过 ⇒ 用户感「没反应」 | Material `MINIMUM_PRESS_MS = 225` |
| 4 | **缺触觉（且应有条件地放弃）** | 无 | MDN：`navigator.vibrate` **非 Baseline**（`https://developer.mozilla.org/en-US/docs/Web/API/Navigator/vibrate`） |

**验收标准**：见 `06-调研-触摸点击反馈-YouTube与Material对照.md` §6 的 **AC-U11.1 ~ AC-U11.11**（11 条，可逐帧/DevTools 断言）。本 PRD 不重复，只登记三条**产品红线**：

| 编号 | 红线 |
|---|---|
| AC-U11-R1 | **触觉只能作为可选增强，不得作为唯一反馈**；不支持的设备（含 iOS 上的 PWA）必须静默降级，**界面不得出现「已开启震动」类承诺** |
| AC-U11-R2 | **滚动列表时不得出现沿途按压反馈**（触摸需先判滑动再给反馈）；本项目已有 `usePressGuard`（8px/700ms）管"不误跳转"，但它**不管视觉反馈**，两件事都要做 |
| AC-U11-R3 | **地图 pin 不得 scale / translate**（会与地图缩放语义混淆、并造成 pin 位置误判）；**车辆图标不给按压态**（它是实时数据层，不是操作层） |

**⚠️ 一处需要 designer/architect 裁定的冲突（我只报事实）**：`globals.css:197` 写「禁弹跳曲线 —— 不使用 `--spring-release`」，但 `--spring-release: cubic-bezier(0.22, 1.9, 0.36, 1)` 在 `:282` 被定义、并在 `:473` 被 `button` 的 `transform` 过渡**实际使用**（`1.9` 是 back-out 过冲点）。两句话在同一个文件里互相矛盾，**必须由 designer 判定 `:197` 是局部规则（仅抽屉）还是全局规则**。产品倾向：按压抬起用无过冲（Material 全程 `standard`），理由见调研文档 §4。

**⚠️ 第二处需裁定的取值分歧（pressed 不透明度）**：设计规格（`07-设计-触摸点击反馈规范.md`）取 **0.10**，而我的调研取 **0.12**。两者都能找到出处，但**不能同时存在**——这属可审计常量，必须择一并注明来源：

| 来源 | pressed | focus | hover | dragged |
|---|---|---|---|---|
| Google 生成 token 文件（`tokens/versions/v0_192/_md-sys-state.scss`，逐行可核） | **0.12** | 0.12 | 0.08 | 0.16 |
| M3 规范站点的常用表述（本次正文未能抓取，`[未验证]`） | 0.10 | 0.10 | 0.08 | 0.16 |

**产品侧只坚持一件事**：落到 Token 时必须写明「取自哪个来源」，且**全站同一值**。视觉上 0.10 与 0.12 差异很小（实测由 designer 比对截图色值），但「两个数字同时存在于代码与文档」正是本次 U11 要消灭的那类问题。

### 6.8 U6 · 车牌绑定的验收基调（跨团队引用，v1.3 新增）

> 本节**不定义 U6 的技术方案**（归架构师），只定**验收基调**。因为 I-3 是 U6 的验收前提（§0.5）。

#### 6.8.1 验收基调：**「正常上车必然锁到车牌」，不是「锁不到时有兜底」**

> **负责人原话（2026-11-04）**：「就不能实时根据定位判定吗？上车判定及锁车牌修的足够好，就不用考虑修车牌锁不上的情况了」

这句话的产品含义必须落到验收上：

| 错误基调（本批不得采用） | 正确基调（本批执行） |
|---|---|
| 「锁不到车牌时显示兜底文案，用户也能继续用」 | 「正常上车**必然**锁到车牌；锁不到即判**缺陷**」 |
| 「允许 `plate` 为空并显示某文案」 | 「`plate` 为空属**缺陷**，必须**可观测**并**计入缺陷率**」 |
| 把兜底文案当作"需求已满足"的证据 | 兜底文案**只是**缺陷态的降级显示，**不能**当作验收通过的依据 |

**为什么必须这样定**：若允许"空车牌 + 文案"通过验收，那么 I-3 修不修都不影响交付，U6 会以「显示了一个空位」的方式"通过"——这是**需求被绕开**，不是被满足。而负责人已明确否决这类补偿思路（“记忆窗口”同属此类）。

#### 6.8.2 验收项

| 编号 | Given | When | Then |
|---|---|---|---|
| **AC-6.1（P0）** | 正常上车（非赶车冲刺误判、非「我没上车」后重试） | 进入乘车态 | 车牌在 N 秒内出现（N 由架构师按实测给值）；**每次都要出现**，不接受"偶发不出现" |
| **AC-6.2（P0）** | 同上，连续 10 次独立正常上车 | 统计 | 锁牌成功率 = **10/10**。任何 1 次失败都须记录为缺陷，并带上下文（定位精度、在途车数、判定耗时） |
| **AC-6.3（P0）** | 出现 `plate` 为空 | 查看诊断/埋点 | 该次会话**必须**被计入缺陷计数（不是只在控制台打一条日志）；指标可被外部读出 |
| **AC-6.4** | 出现 `plate` 为空 | 界面 | 不得伪造车牌、不得显示一个看起来像车牌的占位符（会误导用户在站台找错车）；须有明确的不可用表达 |
| **AC-6.5** | 「点我没上车」后重新上车 | 再次进入乘车态 | 能重新锁到车牌（不得因一次手动纠错而**永久**放弃自动判定）—— 这条与 Spec AC-13 同源，此处仅作**跨文档一致性**登记 |

#### 6.8.3 与 I-3 的关系（一句话）

I-3（正常上车拿不到车牌）**不修** ⇒ AC-6.1 / AC-6.2 **必然不通过**。因此 **U6 的验收会被 I-3 阻塞**，这不是验收标准过严，而是需求本身的前提未成立。架构师的 I-3 深查结论出来后，N 值（AC-6.1）与判定阈值才能定稿。

## 7. 边界条件

| 类别 | 情形 | 期望行为 |
|---|---|---|
| 空状态 | 该时段全部线路收班 | 沿用现有空态（`RecommendCards.tsx:58-70`）；文案不得声称"没有线路"，只能说"这个时段查不到可乘班次" |

| 数据缺失 | 某线**在表里但今日 `day_type` 无行**（如 `15T` 平日） | `closed` ⇒ 隐藏（不是 `no_data`，见 §3.1 要点 c） |
| 数据缺失 | 某线**今日有行但此刻落在两窗口之间（洞）**（如 `59` 平峰） | `closed` ⇒ 隐藏（不是 `no_data`，见 §3.1 要点 a） |
| 数据缺失 | 某线**只有 `special` 行**（载入即排除，`headway.ts:79`） | `no_data` ⇒ 不因时间隐藏（零信息） |
| 数据缺失 | 某线本轮**未取实时**（并行线常态） | `presence = unknown` ⇒ 仅 `closing` 带内保留，其余按 §3.3 |
| 数据缺失 | `lrt_holidays` 不可用 | 退化为按星期判定（`headway.ts:121-123`）；诊断标 `holiday_fallback`，不因此隐藏线路 |
| 时刻边界 | 06:00:00 整 / 23:59:59 / 00:00:00 | 单测逐点覆盖（§3.5）；跨午夜行用 `to_min > 1440` 表达（`headway.ts:32-35`） |
| 时钟 | 客户端与服务器时钟不一致 | 一律以服务端 `nowMs` 为准；不使用 `Date.now()` 直接判定（现有 `recommend` 已支持注入 `nowMs`） |
| 并发/缓存 | 10 秒内两次请求命中同一缓存（`service.ts:114-116`） | 允许跨窗口边界 10 秒内陈旧：06:00 收班的线最多再显示 10 秒，可接受；**不得为此缩短 TTL** |
| 权限 | 无（本功能无权限维度） | — |
| 离线 | PWA 离线 | 沿用既有：无实时数据时不伪造班次；运营时间判定属静态数据，可离线算，但不得据此给出"有车"结论 |
| 极端时刻注入 | 探针用假时间跑收班时段 | 巴士实时数据无法伪造（`service.ts:88-92` 已注明），验收时须区分"因假时间隐藏"与"因真实无车隐藏" |
