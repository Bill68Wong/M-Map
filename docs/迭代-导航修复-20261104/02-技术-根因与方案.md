## 1. 题 A：刷新后「站间行驶 ↔ 进站」预计时间突变

### 1.1 数据流（先建立事实，再谈根因）

`车辆帧(12s) → 服务端 attachProgress → 客户端 segProgress → POST /api/nav/remaining → 顶部总时长/到达时刻/纵条`

| # | 环节 | 文件:行 | 做了什么 |
|---|---|---|---|
| 1 | 车辆帧只对 `moving` 车算进度 | `src/lib/nav/progress.ts:200-206` | `if (v.status !== "moving" \|\| !v.interval) continue;` ⇒ **停靠中的车根本没有 `progress` 字段** |
| 2 | 进度是**hop 级**的 | `src/lib/nav/progress.ts:230-243` | `md` 取自 `route_hop_stats` 的 `from_main|to_main`（**相邻站对**）；`remainSecD = md × h[1−p]` ⇒ **到下一站**的剩余，不是到下车点 |
| 3 | 同仓另一处用法佐证「hop 级」 | `src/lib/recommend/live.ts:183-186` | `restSec = (sum − first)×60`；`etaSec = locSeg.remainSecD + restSec` ⇒ 官方口径是「首跳位置剩余 **+ 后续静态跳**」 |
| 4 | 客户端融合 | `src/components/nav/useRideTracking.ts:987-1000` | `pr = v.progress ?? null`；有值 ⇒ `fusedSec = w·remainSecD + (1−w)·max(md−u,0)`；**无值 ⇒ `setSegProgress(null)`** |
| 5 | 上行给前端 | `src/components/nav/NavShell.tsx:427-428` | `segRemainSec: ride.segProgress?.segRemainSec ?? null`，`nextIdx: ride.prog?.nextIdx ?? null` |
| 6 | 服务端第一段 | `src/lib/nav/remaining.ts:228-242` | 有 `segRemainSec` ⇒ `curRemainMin = segRemainSec/60`（**没有加后续跳**）；无值 ⇒ `hopMinutesFrom(nextIdx)`（**逐跳到末站**）→ 再退 `curRide.minutes` |
| 7 | 时间轴 | `src/lib/nav/remaining.ts:245-269` | `remainingMin = round1(max(0, cursor − nowMs)/60000)`；`arriveAtMs = nowMs + round(remainingMin×60000)` |
| 8 | 前端消费 | `src/lib/nav/remaining-view.ts:110-126`、`NavDetailBody.tsx:215-226` | 总时长走 `remainingMin`；`etaBaseMin`（「还有几分钟」）走同一套双口径 |

结论：**同一个字段 `segRemainSec`，在环节 6 被当成"整段剩余"，但它的产生逻辑（环节 1-3）是"首跳剩余"。**

### 1.2 可复现数值推演（手算，全部输入与公式来自上表）

合成输入（仅用于确定输出，不依赖数据库）：

```
线路 leg：board=A, alight=E，站条 codes = [A,B,C,D,E]
逐跳 lookupHop（min）：A→B=2.0, B→C=2.0, C→D=3.0, D→E=2.0   ⇒ ride.minutes = 9.0
当前位于 B→C 区间，p = 0.90，md = 120s（2 分钟），segLen < 1000 ⇒ 段型 "short"，w = 0.6
h[short] 桶 = floor((1−0.90)×20) = 1 ⇒ h = 0.25
```

行驶末帧：

```
remainSecD = round(120 × 0.25) = 30s
首见时 u0 = md − remainSecD = 90s；已流逝 24s ⇒ uSec = 114
fusedSec = 0.6×30 + 0.4×max(120−114, 0) = 18 + 2.4 = 20.4s
```

**⚠️ 本节数值已按实际代码路径修正过一版（2026-11-04 二次核对）。**
第一版误以为停靠时 `nextIdx` 指向「所停靠的站」，据此算出 5.0 分。实际 `progressOf` 在停靠时给的是
`passedIdx = atIdx − 1`、`nextIdx = atIdx + 1`（`src/lib/nav/track.ts:76-85`）——即 `nextIdx` 指向**所停站的下一站**。
按真实路径重算如下，并由此多暴露一处**独立缺陷**（见本节末）。

| 时刻 | 车辆状态 | `prog` | segRemainSec | remainingMin（现状） | 说明 |
|---|---|---|---|---|---|
| t0 | 行驶 B→C，p=0.90 | `between`, passedIdx=1, nextIdx=2 | 20.4 | **0.3 分** | `hasSegSec` 分支只用 segRemainSec，`nextIdx` 被完全忽略（`remaining.ts:233-234`） |
| t1 (+12s) | 停靠 C | `at`, passedIdx=1, atIdx=2, **nextIdx=3** | `null` | **2.0 分** | 回退 `hopMinutesFrom(3)` = D→E = 2.0（**漏掉 C→D 的 3 分**） |
| t2 (+24s) | 起步 C→D，p=0.02 | `between`, passedIdx=2, nextIdx=3 | round(180×0.889)=160 | **2.67 分** | 新区间首帧 `u0=20, u=20` ⇒ `fused = 160` |

- **行驶 → 停靠：+1.7 分钟**（0.3 → 2.0）
- **停靠 → 行驶：+0.67 分钟**（2.0 → 2.67）

两跳都向上，且方向相反于「时间应递减」的直觉。24 秒内剩余时间先涨 1.7 分、再涨 0.67 分。

**由此暴露的第二处缺陷（独立于跳变本身）**：停靠态漏算了「所停站 → 下一站」这一跳。
用户在 C 站车上，实际还需 C→D(3) + D→E(2) = 5 分，系统显示 2.0 分 —— **少算 3 分钟**。
根因：停靠时 `nextIdx = atIdx + 1`，而 `hopMinutesFrom` 从 `nextIdx` **起算**，把 `atIdx → atIdx+1` 这一跳整个跳过。
该缺陷与跳变**同源**（都是「`segRemainSec` 与 `nextIdx` 的基准点没对齐」），修法也同一处，因此合并进 §1.5 的改造点。

### 1.3 三个候选解释的判定

| 候选 | 判定 | 依据 |
|---|---|---|
| 里程口径变了 | **成立（主因）** | 环节 6 把 hop 剩余当 leg 剩余；环节 3 证明正确口径必须加后续跳 |
| 速度假设变了 | 不成立 | `w` 与 `h` 只在段型变化时换（`progress.ts:232-239`）；同段型内 `w` 恒定，`h` 单调（`progress-params.ts:36` 已 PAVA 单调化） |
| 「本段剩余」与「后续段」两套算法在拼接处不连续 | **成立（同一根因的另一面）** | 拼接点就是 `segRemainSec == null` 这一分支：一侧含后续跳、一侧不含 |

补充：**停靠态本身不提供任何时间信息**是第二层缺陷。`progress.ts:201` 把 `stopped` 车整体排除，导致停靠期间只能落到静态逐跳。停靠时长（澳门常见 10~40s）被完全丢掉，`arriveAt` 会系统性偏早。

#### 1.4.1 基准站规则（这一条是修法的核心，写错就还是跳）

设 `codes = [A,B,C,D,E]`（5 码 4 跳）。定义**基准站 `pivotIdx`** = 「`segRemainSec` 从哪一站起算之后的路程」：

| 车辆状态 | `prog` | `pivotIdx` | `segRemainSec` 语义 | 公式 |
|---|---|---|---|---|
| 行驶（between） | passedIdx=i, nextIdx=j | **`j`（= nextIdx）** | 当前位置 → 站 j 的剩余 | `segRemainSec/60 + Σ_{k=j}^{3} hop(codes[k],codes[k+1])` |
| 停靠（at） | atIdx=i, nextIdx=i+1 | **`i`（= atIdx，不是 nextIdx）** | 恒为 0（已在站 i） | `0 + Σ_{k=i}^{3} hop(codes[k],codes[k+1])` |

**为什么停靠时必须用 `atIdx` 而不是 `nextIdx`**：`hopMinutesFrom` 是「从 `fromIdx` 起累加」，
停靠时 `nextIdx = atIdx + 1`（`track.ts:83`）⇒ 从下一站起累加 ⇒ **把 `atIdx → atIdx+1` 这一跳整个跳过**。
这正是 §1.2 暴露的第二处缺陷（停靠少算 3 分钟）的成因。

统一写法：`pivotIdx = prog.kind === "at" ? prog.atIdx : prog.nextIdx`。

单调性推演（同一组合成输入，按上表）：

```
行驶末 (B→C, p=0.90)：20.4s/60 + Σ_{k=2..3} hop = 0.34 + (C→D 3 + D→E 2) = 5.34 min
停靠 C              ：0        + Σ_{k=2..3} hop = 0    + 5.0            = 5.00 min
起步 C→D (p=0.02)    ：160s/60  + Σ_{k=3..3} hop = 2.67 + 2.0            = 4.67 min
```

5.34 → 5.00 → 4.67，**单调递减，无跳变**（相邻 delta 分别 −0.34 / −0.33，均 < 0）。
对照现状 0.3 → 2.0 → 2.67（两次都上涨），修改后两个方向的突变同时消失。

同时发现一个额外收益：轻轨段（`lrt`）目前 `progressSource` 走 GPS，`segProgress` 恒为 `null` ⇒ 全程落在「逐跳累加」分支，剩余时间在段内**不随位置变化**（只在过站时整跳跳变）。方案 1 对轻轨的改善点为 0（因为无 `segRemainSec`），但方案 2 可以顺带解决 —— 这是把方案 2 排进下一批的第二个理由。

|---|---|---|
| `rides[0].minutes` | 2 | **6**（2 + `hopMinutesFrom(1)`=4） |
| `remainingMin` | 22.7 | **26.7**（6 + 2 + 8.7 + 8 + 2） |

**契约收紧（必须写进 route 注释）**：修法后 `segRemainSec` 与 `nextIdx` 应成对出现。
若只传 `segRemainSec` 不传 `nextIdx`，新公式取不到尾项 ⇒ 回落第 3 档 `curRide.minutes`（**不是** `segRemainSec/60`，
后者会少算下游跳）。该回落是保守的（偏长），且不会双计。③ 组（`segRemainSec=null` + `nextIdx`）**期望值不变**（4 / 24.7 / 8）。

### 1.6 验收判据（机器可验证，不许写「看起来正常」）

1. **段间单调性**（新增 `scripts/test-remaining.ts` 用例组）
   构造 20 帧序列（间隔 12s）模拟一次「B→C 行驶 → 停靠 C → 起步 C→D」：
   `segRemainSec = [160,140,…,20, 0, 0, 0, 160,140,…]`，`nextIdx/atIdx` 按 §1.4.1 规则同步变化。
   断言：对全部相邻帧 `remaining[i+1] − remaining[i] ≤ +0.1`（0.1 分 = `round1` 单向量化上界，推导见下）。
   **当前实现在该断言下必须失败**（0.3 → 2.0 差 +1.7），修好后必须通过 —— 该断言同时是根因证据与回归锁。

2. **口径恒等式**
   `|remainingMin(segRemainSec=x, nextIdx=k) − (x/60 + hopMinutesFrom(k))| < 1e-6`。

3. **停靠不漏跳（锁 §1.2 的第二处缺陷）**
   停靠 C（`atIdx=2`）时，`remainingMin` 必须等于 `hopMinutesFrom(2)` = C→D + D→E。
   断言 `remainingMin(停靠 C) === remainingMin(行驶至 C 前一刻中 segRemainSec=0 的那一帧)`，
   且 `remainingMin(停靠 C) − remainingMin(nextIdx=3 的错误口径) === hop(C→D)`。
   当前实现该断言必须失败（2.0 vs 5.0，差 3.0 分）—— 它是第二处缺陷的独立回归锁。

4. **停靠态不倒退**
   连续 3 帧 `segRemainSec = 0`（停靠）时，`remainingMin` 恒定、`arriveAt = now + remainingMin×60000` 随 `now` 顺延（即 `arriveAt` 递增、`remainingMin` 不变）。这条锁住「停靠时长被计入到达时刻」。

5. **成对一致性**（既有断言，`scripts/test-remaining.ts` ⑫ 段）
   `arriveAt − recomputedAt === remainingMin × 60_000`，残差 0ms。

6. **变异加固**：故意把 `hopMinutesFrom` 的返回值置 0，断言 ①③ 必须变红（防「补了后续跳但补成 0」的沉默逻辑错误）。

#### 1.6.1 两个数值上界的推导（team-lead 要求给具体值与依据）

**上界 ①：同一 OD 连续刷新，相邻两次 `arriveAt` 差值**

服务端输出（`remaining.ts:268-269`）：
```
remainingMin = round1(max(0, (cursor − nowMs)/60_000))     ← round1 量化，步长 0.1 min = 6 000 ms
arriveAtMs   = nowMs + Math.round(remainingMin × 60_000)
```
设两次刷新在 `t1 < t2`，真实剩余 `r1`、`r2`，且**模型时间一致**（`r2 = r1 − Δt/60_000`，Δ 为分钟）。
记量化函数 `q`（步长 0.1 min，`|q(x) − x| ≤ 0.05 min`）：

```
arriveAt(t) = t + 60_000·q(r_t)
ΔarriveAt   = (t2 − t1) + 60_000·[q(r2) − q(r1)]
            = (t2 − t1) − (t2 − t1) + 60_000·ε        （因 q(r2) − q(r1) = −Δt/60_000 + ε）
            = 60_000·ε,        |ε| ≤ 0.05 + 0.05 = 0.1 min
⇒ |ΔarriveAt| ≤ 6 000 ms
```

**结论：6 000 ms 完全来自 `round1` 的双向量化，与刷新间隔 Δt 无关。**

在 6 000 ms 之上还有一项**设计性**不连续，必须显式登记：

- `progress-params.ts` 的 `h` 曲线是 **20 桶阶梯**（`progress.ts:234` 的 `b = floor((1−p)×20)`）。
  车辆 `p` 跨桶时 `remainSecD` 阶跃 `md × Δh`，经融合权重后对剩余的影响 = `w × md × Δh`。
  实测各段型相邻桶最大 `Δh`：short 0.089 · mid 0.047 · long_fast 0.092 · long_slow 0.051（取自 `progress-params.ts:36-39`）。
  取上界 `w·md·Δh`：short（md=120s, w=0.6）→ 6.4 s；long_fast（md 取 600s, w=0.15）→ 8.3 s。**≤ 8.3 s**。
- 下游换乘候车「重估」（`reestimateWait` → `headwayAt`）按时段桶取整（`headway.ts:177-198`），
  跨时段边界时 `waitMin` 可在 `lo` 与 `hi` 之间整段跳（`conservativeWaitMin` 值域 `[lo, hi]`）。
  **这是时段表固有分段，本批不修**，属已知不连续点。

⇒ 验收分两级，写进 Spec：

| 级别 | 适用范围 | 断言 |
|---|---|---|
| **L1** | 单段卡（`rides.length === 1`，无下游候车） | `\|ΔarriveAt\| ≤ 15 000 ms`（6 000 量化 + 8 300 `h` 跨桶，向上取整留余量） |
| **L2** | 多段卡（含下游候车重估） | 先剔除「`headwayAt` 命中桶发生变化」的样本对（按下发 `strips[].transferAfter.waitMin` 是否变化判定），再套 L1 的 15 000 ms；未剔除的样本只记录不判定，另出一个「跨桶跳变分布」报告 |

**上界 ②：站间 ↔ 进站切换瞬间的 delta**

按 §1.4.1 公式，切换瞬间只有 `segRemainSec` 一项变化（静态尾 `Σ hop` 由 `pivotIdx` 决定，切换前后 `pivotIdx` 都指向同一站 i，尾项完全相同）：

- **行驶 → 停靠**：`segRemainSec: fused → 0` ⇒ `Δ = −fused/60`，**单调向下**。
- **停靠 → 行驶**：`segRemainSec: 0 → fused` ⇒ `Δ = +fused/60`，**单调向上**。

`fused` 的上界（`useRideTracking.ts:996`）：
```
fused = w·remainSecD + (1−w)·max(md − u, 0)
     ≤ w·md·h[19] + (1−w)·md            （h 最大 = h[19]，u ≥ 0）
```
- short（md=120, w=0.6, h[19]=0.889）：0.6×120×0.889 + 0.4×120 = 64.0 + 48.0 = **112.0 s**
- 但实际到站前一刻 `u` 已接近 `md`，时间项趋于 0，故实测远小于上界。

因此**不用 `fused` 的理论上界做验收**（太松、且依赖 `u` 估计），改用一条**可从记录序列直接检验的恒等式**：

| 断言 | 形式 | 说明 |
|---|---|---|
| **B-1（方向）** | `remaining[i+1] − remaining[i] ≤ +0.1 min` | 切换瞬间**不得整段上涨**；0.1 min = `round1` 量化容差。当前实现在「行驶→停靠」处为 +1.7 min，必红 |
| **B-2（幅度·精确形式）** | `\|Δremaining\| ≤ \|segRemainSec[i]/60\| + 0.1` | 切换前后静态尾相同 ⇒ delta 必须恰好等于切换前最后上报的 `segRemainSec`（含量化）。这条把「幅度」也钉住，且只依赖已记录的序列，不需要估计 `u` |
| **B-3（幅度·宽松兜底）** | `\|Δremaining\| ≤ md/60 + 0.1` | 完成一跳所耗时间不可能超过该跳的中位时长 `md`（`route_hop_stats.p50_sec`）。作为 B-2 取不到 `segRemainSec` 时的兜底 |

B-2 是对 B-3 的收紧形式，两者同时存在：B-2 精确但要求那条帧有 `segRemainSec`，B-3 宽松但永远可判。
示例（§1.2 输入）：切换前 `segRemainSec=20.4s` ⇒ `|Δ|` 必须 ≤ 20.4/60 + 0.1 = 0.44 min；修好后实际 Δ = −0.34 min ✓，
而现状 Δ = +1.7 min，同时违反 B-1 与 B-2。

### 2.2 因果链（需求 7：提前判定 → 真正上车后绑不上牌 → 手工也找不到正确车牌）

1. **为什么会提前判定**：冲刺赶车速度 ≳ 8 km/h 即命中 `r2Of` 速度下限。项目自己已量过：档 1 全力冲刺 = 12.96 km/h，**与实测段速 p50 = 14.8 km/h 几乎重叠**，速度单判据无法区分「冲刺赶车」与「乘车」（`match-vehicle.ts:18-22`）。这是判据的物理上限，不是参数没调好。
2. **为什么提前判定时基本拿不到车牌**：锁牌条件是 `aux.strong`（有车 `interval.from == 上车站`，即车刚离站）。冲刺赶车时用户多半还在站前、车尚未离站或已走远 ⇒ `lockedPlate = null`（`boarding-detect.ts:372`）⇒ `progressSource="gps"`，`plate=null`。
3. **为什么上车后补不上车牌**：唯一的补牌通道是 `fetchFrame` 的 `riding && !plate` 分支（`useRideTracking.ts:897-951`），它被 `MATCH_VEHICLE_ENABLED=false`（`match-params.ts:15`）在 `:898` 直接挡掉。`tryAuto` 也不会重跑（`:1070` 只认 `boarding`）。⇒ **无牌 riding 一旦发生，本段内没有任何自动补牌通路。**
4. **为什么点「我没上车」会更糟**：`:1898` 把 `autoUsedRef.current = true`，而 `autoBoardOf` 的硬门 `:322` 会因此永远 `noHit()`。boarding 期间没有复位点 ⇒ **用户点一次纠正，就把本段的自动判定彻底关死**（注释写「冷却后再允许自动」，但不存在这条路径）。
5. **为什么点「我已经上车」锁到的是后车**：`board()` 用 `filterPassed: true`（`:1681`），而 `passedBoardOf` 对 `between && passedIdx >= 0` 判为已过站（`track.ts:194-195`）。用户此刻真正坐的那辆车**已经驶离上车站**，恰好被判为「已过站」而被剔除 ⇒ `ranked[0]` 是**下一班车**。
6. **为什么「不是这辆」也翻不到**：`candidates` 只在两处写：候车轮询（`useRideTracking.ts:969`，同样 `filterPassed: true`）与 riding 的 match 分支（`:911-919`，开关关闭时不执行）。⇒ 用户看到的候选列表是**候车时那份**，全是还没到站的后车，自己坐的车不在里面。这解释了「找不到正确车牌」。

一句话：**问题不在"判早了"，在于判早之后系统没有任何一条可逆路径** —— 自动通道被单次锁死、手动通道被候选池口径挡住、候选池本身还是错的。

### 2.4 「车到站 + 人在站」的安全实现

#### 距离阈值取值依据

| 量 | 取值 | 依据 |
|---|---|---|
| 车侧「到站」判据 | **站码相等**，阈值 = 0 m | `atStation.code` 与 `boardMain` 同 `mainOf` 归一后比较（`track.ts:227`、`boarding-detect.ts:126-127`）。用站码而非距离，不存在距离误差 |
| 人侧「在站」地板 | **40 m** | 复用既有「已到站/刚上车」口径 `BOARD_NEAR_M = 40`（`useRideTracking.ts:83`、`:434`），不新造第二套口径 |
| 人侧精度放大 | **×1.5** | 与 `R2_ACC_TOL_FACTOR = 1.5` 一致（`boarding-detect.ts:46`） |
| 人侧上限 | **80 m** | 与 `R2_TOL_M = 80`（巴士投影容差基准，`boarding-detect.ts:42`）同级；超过 80m 说明精度或位置已不足以支撑「在站」结论 |
| 精度门 | `accuracy ≤ 150 m` | `R2_FIX_MAX_ACC_M`（`boarding-detect.ts:48`） |

即：`tolStation = clamp(max(40, accuracy × 1.5), 40, 80)`。

> 待验证（不写死结论）：澳门巴士站台物理尺度（约 10~25m 量级）与站间距中位数，需用 `route_station_mileage` 或地图量算确认；若站距 p10 < 80m，则 80m 上限需下调，否则会出现「人在 B 站、判成在 A 站」。

#### 推荐实现：两段式（到站记录 → 离站确认）

单纯「车在站 ∧ 人在站」仍会误判 —— 用户站在站台等的是另一条线的车，同站台来车即被判定上车。因此把判据拆成两段，**自动切换只允许发生在第二段**：

```
① 到站记录（不切换）：车 status==="stopping" ∧ atStation==boardMain ∧ 用户 tolStation 内
   ⇒ 只记 {plate, arriveTs, userDistM}，用于「车已到站」提示与手动一键上车
② 离站确认（才切换）：同一 plate 出现 interval.from==boardMain（车刚离站），且
   · 距 ① 的时刻 ≤ 2×POLL_MS（24s）
   · 且用户到**该车当前位置**距离 ≤ tolStation
   ⇒ 判定上车并锁牌（plate 唯一时才锁）
```

关键点：判据从「车在站时人在站」（人与车静止，无法区分"上车"与"同站台等别的车"）改成「**车动起来时人还跟着它**」—— 后者在物理上只有「上了车」能成立，同时完全满足需求 6「同时利用车辆 + 用户定位在该站」的要求，也不破坏 ADR-108「车辆不得单独触发」（②必须同时有人员定位项）。

附加强制条件（缺一不可）：

1. 复用 `SWITCH_COOLDOWN_MS = 20s` 冷却与「本腿单次自动」限制（`boarding-detect.ts:323`）；
2. 同帧多车满足 ② ⇒ **不锁牌、不切换**（沿用 A2 不锁牌原则 `boarding-detect.ts:370` 的保守取向）；
3. 用户精度 > 150m 的帧不参与（`trustedFixes`，`boarding-detect.ts:288-290`）；
4. 若 `r2Of` 已命中（用户自己在沿线高速移动），走原路径，新判据不介入 —— 避免双判据同时触发难以归因；
5. 新判据**整体挂 Feature Flag**（`RIDE_STATION_BOARD_ENABLED`，默认 false），关闭时行为与改前逐字节一致。

### 2.5 「提前判定不可逆」的修复方向对比

| 方向 | 做法 | 代价 | 只做它够不够 |

## 3. 题 C：步行线「未走」出现两种绿

### 3.1 事实：未走几何在代码里有**三档**绿，不是两档

| 层 | 语义 | 色 | 宽 | 透明 | z | 证据 |
|---|---|---|---|---|---|---|
| `nowPath` | 当前步**剩余**部分 | `--map-walk-ahead` = `#0b6e4f` | **7** | **1** | 73 | `nav-map-walk.ts:71-76`、`globals.css:7728-7731` |
| `aheadPath` | 当前步**之后**所有步 | `--map-walk-ahead` = `#0b6e4f` | **6** | **0.55** | 70 | `nav-map-walk.ts:65-70`、`globals.css:7727`、`:7730` |
| `ghost`（tone=ahead） | **另一段**步行走廊 | `--map-walk-ahead` = `#0b6e4f` | **4** | **0.4** | 68 | `nav-map-walk.ts:77-82`、`:212-216`、`globals.css:7742-7745` |

三者**同色不同参数**。同一屏可以同时出现其中 2~3 档：
- 步行跟随中：`now`（深粗）+ `ahead`（中）+ 另一段 `ghost`（淡细）—— `NavShell.tsx:829-839` 与 `NavMap.tsx:1453-1456` 各自负责一半，互斥条件只排除**同一段**；
- 未开始导航（`ride.phase==="off"`）：出发段 ghost 判 `ahead`（`NavShell.tsx:833`），末段 ghost 恒 `ahead`（`:836`）⇒ 两段都是绿，若两段在空间上共线（起点终点同一街区），会**叠加**成第三档绿。

### 3.2 四个假设逐一判定

| 假设 | 判定 | 证据 |
|---|---|---|
| ① `now` 与 `ahead` 在同一段折线上重叠绘制导致叠加 | **排除（结构互斥）** | `NavMap.tsx:1454-1456`：`now = splitStepByRatio(steps[idx]).remaining`（当前步后半），`ahead = steps.slice(idx+1)`（**严格从下一步起**）。两者只在「当前步末顶点 == 下一步首顶点」处共享 1 个点 |
| ② 按 step 分段绘制、相邻 step 端点重叠叠加 | **部分成立（局部）** | 共享顶点 + `lineCap:"round"`（`nav-map-walk.ts:102`）⇒ 每个 step 交界处会多出一个直径 ≈7px 的深绿圆点。面积小但数量随步数线性增加，是「深浅交替」的来源之一。另：`/api/nav/walk` 存在**被丢弃的步**（`walk/route.ts:122-125` 注释「`totalDistM` 含被丢弃的步」）⇒ 相邻 step 几何可能**不连续**，`flatMap` 后形成跨缺口的长直线段 |
| ③ 外部道路与内部道路/无路网回退走不同分支、透明度或线宽不同 | **部分成立（这是主因的另一面）** | 几何来源唯一（`walk/route.ts:101` 只有 `fetchWalkingSteps`；`src/lib/walk/` 内无任何几何回退分支），所以不是「不同来源」；但**同一来源被三档样式分别绘制**（§3.1），这是"两种绿"的结构性来源 |
| ④ 多次绘制未清理旧图层 | **排除** | `ensureWalkLayers` 幂等复用（`nav-map-walk.ts:118-142`）；`apply` 走增量 `setPath`，空则 `map.remove`（`NavMap.tsx:1479-1490`）；只在卸载时 `clearWalkLayers`（`:1533-1538`）；ghost 走 key-diff 增量（`nav-map-walk.ts:230-252`）。全仓无「每次渲染先 remove 再重建」路径 |

结论：**「未走两种绿」= 设计里的 `now`(w7/op1) 与 `ahead`(w6/op0.55) 被用户读成两种颜色**。设计文档把它定义为「三通道区分（色/宽/透明）」（`nav-map-walk.ts:6-11`），产品口径是「未走只有一种绿」。这是**口径冲突，不是实现 bug**；② 与「两段 ghost 共线叠加」是两个真实但局部的放大器。

### 3.3 可验证判定方法（三条，全部可机器执行）

1. **现有钩子直接读出三档参数**（无需改代码）
   `NavMap.tsx:1508-1527` 已把每层的 `点名:点数@色/w宽/z` 写到 `canvas[data-walk-layers]`，例如
   `done:2@#8c93a0/w5/z69 | now:6@#0b6e4f/w7/z73 | ahead:9@#0b6e4f/w5/z70`。
   ⇒ 只要 `now` 与 `ahead` 的 `w`/`z` 不同，双绿的**结构性成因即已确证**（同一份几何数据被两套样式绘制）。

2. **叠加层数检测（几何自检，不依赖 AMap 私有 API）**
   从 `paths.ahead` 等距取 20 个采样点；对每个点统计 `paths.now` 与 `paths.done` 中距该点 ≤ 2m 的折线段条数。
   断言 `max ≤ 1`。当前实现预期为 1（除交界顶点外），界顶点处为 2 —— 该断言能把「②」量化出来。

3. **几何断裂检测（针对被丢弃的步）**
   取一次真实步行 OD 的 `/api/nav/walk` 响应，逐对计算 `steps[i].polyline` 末点与 `steps[i+1].polyline` 首点的距离：
   `> 5m` ⇒ 存在被丢弃的步（几何断裂，会产生跨界直线）；`=== 0` 且重复出现 ⇒ 端点重叠（`lineCap` 圆点来源）。
   这一步只需接口响应，不需要真机。

| 0.40 | 1.89:1 | 1.84:1 | 否 |

| 0.60 | 2.73:1 | 2.60:1 | 否 |
| **0.75** | **3.69:1** | 3.44:1 | **是** |
| 1.00 | 6.25:1 | 5.59:1 | 是 |

`0.75` 与 designer 记录值（3.70:1）一致到小数点后两位；`0.55` 我算 2.48:1、designer 记 2.26:1（差异可能因其按底图瓦片色而非纯白混色），**但两档的达标/不达标结论完全一致**，故采 designer 定值。

2. `done`（`#8c93a0` @ 0.85 → 2.53:1）同样低于 3:1。已走段是**去强调**语义（用户不再需要它），同上豁免。

#### 3.4.2 结构性约束（本次缺陷的成因，定案为「合并 + 类型层阻断」）

本次「未走同一路径出现两种绿」的**成因不是有人画错，而是 `now` 与 `ahead` 各自保留了一套可独立调参的 CSS 变量** —— 于是任何一次「只改一半」都会重现缺陷。

我原先给了两条并列选项（合并变量 / 注释强制同改），**designer 选了合并，且做到类型层**：

- `readWalkStyle()` 返回结构由「三套并列」改为「三组语义」`{ unwalked, walked, corridor, z }`；
- `nowPath` 与 `aheadPath` 拿到的是**同一个对象引用**，不是两份相等的值
  ⇒「给 `now` 单独调透明度」**在类型层面写不出来**，不再靠人记得。

这比注释约束强一个量级，采纳。**C-6 因此退化为更强的断言**：`assert.strictEqual(now.unwalked, ahead.unwalked)`。

#### 3.4.3 `lineCap` 保持 `round` —— 但交界圆点**不会**消失（架构对 designer 前提的修正）

designer 建议保持 `round`、不改 `butt`，**结论我同意，但她的理由在数学上不成立**，必须纠正，否则真机验收会把它当新缺陷重提。

她的判断：「三元组统一成 0.75 后，圆点与两侧完全同色，交界自然成为连续圆角曲线」。
**实际不会**：`now` 与 `ahead` 是两个独立 `AMap.Polyline`，在共享顶点处是**两次 source-over 合成**，不是「同色画一次」：

```
单层 α=0.75            → rgb(72,146,123)
两层叠绘 α=1−(1−0.75)² = 0.9375 → rgb(26,119,90)      每通道差 Δrgb = [46, 27, 33]
对照改前（1.0 叠 0.55）  → rgb(121,175,158) vs rgb(11,110,79)   Δrgb = [110, 65, 79]
```

⇒ 圆点对比度**降低约 58%，但没有消失**，真机仍可见一个约 6px（= `strokeWeight`）的略深绿点。
**必须登记为「已知残留、已量化、已接受」**，不能写成「自然消失」—— 否则 C-5/C-6 的真机取色会判失败。

**为什么不改 `butt`**（这条她是对的）：相邻两段用 `butt` 时各自端面垂直于自己的走向，
在弯道上两端面不共线 ⇒ 弯道外侧留 V 形缺口、内侧重叠。用更明显的缺陷换一个已量化的小缺陷，不划算。

若真机确认圆点仍碍眼，**唯一能真正消掉**的做法是把 `now ∪ ahead` 合并成**一条** `Polyline`（方向引导只靠 `showDir`）——
但那会失去 `zIndex 73/70` 的层级差、且 `showDir` 会覆盖整条路，**需 designer 重新定案，不得由实现者自行选择**。

**C-6 的断言形式**（designer 提醒，成立）：`AMap.Polyline` 是 canvas 绘制、不是 DOM ⇒
`querySelector`/`getComputedStyle` 读不到任何折线样式，按 DOM 思路写必然空转。
正确做法是**注入假构造器**捕获 `new AMap.Polyline(opts)` 入参 ——
`nav-map-walk.ts:36-38` 定义 `PolylineCtor` 时已为注入留好口子，**无需改生产代码签名**。
断言：找首尾相接的两条（容差 1e-6），`strokeColor`/`strokeOpacity`/`strokeWeight` 三项 `assert.equal`（不设容差），
白名单只放 `zIndex` 与 `showDir`。

> ⚠️ C-6 只覆盖「两侧三元组相等」，**测不出交界圆点**（圆点是相等样式叠绘的后果）——
> 这正是必须把圆点登记为已知残留的原因。

#### 3.5.2 赶车标签的显隐必须是「单向锁存」，不能由 phase 推导

designer 指出两个必然复现的错法，我核对了代码，**成立**：

- **错法一（用 boarding 判「已到站就隐藏」）**：`NavShell.tsx:685-700` 的 `startSession("out")` 在按下「开始导航」时就 `rideStart()` 进 `boarding` **并** `setWalkSeg("out")`（`:694-696`）⇒ 整个「步行去车站」期间 `ride.phase === "boarding"`、`navPhase === "walk"`。任何用 `boarding` 推「已到站」的实现都会在步行段就误隐藏。
- **错法二（用 navPhase 判「不在 riding 就显示」）**：下车后进入末段步行，`navPhase` 回到 `walk` ⇒ 标签会重新出现。

**唯一正确实现**：session 层一个 `useRef` 锁存 `hasEnteredRiding`，`ride.phase === "riding"` 时置位，**只在「我没上车」（`onNotBoard`）时复位**。
锁存必须放 `NavShell`（session 层），**不能放 `NavDetailBody`** —— 面板重挂载会丢，收起再展开标签又回来。

**隐藏方式必须是「不渲染」**，禁止 `opacity: 0` / off-screen：对屏幕阅读器仍可读，且截图验收发现不了。

#### 3.5.3 数据口径确认（designer 要我确认的前提）

信息行左槽的数据源仍是「**车辆到本站**」的 ETA（巴士给「n 站 + x 分」），不自行编造站数；轻轨分支继续用 `LrtEtaInline`，不伪造站数。

**确认：本批不改这个数据口径。** 理由：编造站数需要「车辆当前站 + 本段站序」的可靠映射，而该映射在 GPS 驱动段（`progressSource === "gps"`，多数实际场景）本就不存在（`progressOf:102-103` 会如实返回 `unknown`），编造即等于静默造假。⇒ designer 的字符预算表**无需重算**。

唯一相关的口径变化来自题 A：`segRemainSec` 从「首跳剩余」修正为「本段剩余」后，信息行里「x 分」的**含义**由「到下一站」变为「到下车点」—— 这与 designer 的「到本站」表述**一致**（「本站」= 本段下车点），修完反而更贴合她的预算前提。

## 9.6 通用表述纪律（**适用于全文与 Spec，不限于本节的某个数值**）

> 本批已栽过两次同类问题：把**推算**的「最多 5 张卡」当实测（实际 2 张）、
> 把**预期**的 σ≈10m 当实然。两次都不是算错，而是**把推导值写成了观测值**。
> 一条通用纪律比两条具体修正更值。

### 纪律 1：推导值必须标为「定案预期值 · 待实测」

> **凡「理论推导得出、尚未真机实测」的数值，一律标为「定案预期值 · 待实测」，
> 不得写成「实然值 / 已实测 / 实测」。**

已适用对象（不限于此，新出现的一律照此标注）：

| 数值 | 来源 | 正确标注 | 错误标注（本批曾出现） |
|---|---|---|---|
| σ≈10m（GPS 精度） | `enableHighAccuracy: true` 的器件预期 | **定案预期值 · 真机待采** | ~~实然值~~ |
| 5 帧 / 6 秒判定窗口 | σ≈10m 前提下的 SNR 推导 | **设计基线（依赖上行的 σ 前提）** | ~~已验证~~ |
| 「最多 N 张卡」类的规模估计 | 跨 plan/跨字段候选集推算 | **待枚举层实测** | ~~最多 5 张卡~~（实际 2 张） |
| `others ≤ 4`、`altBuses ≤ 3` | 同量级类比（`MAX_PARALLEL=3`） | **产品建议值，非用户口径** | ~~产品要求~~ |

### 纪律 2：偏离预期时先判「环境差异」还是「实现缺陷」

> 真机实测偏离预期时，**先判断是环境差异还是实现缺陷**：
> 环境差异 ⇒ **重新标定判据**（并把新值按纪律 1 标注）；
> 实现缺陷 ⇒ 才叫 bug。

具体到本批：若真机 σ 实测 20~30m（而非预期的 ~10m），
则按 §14.3.1 的表回推所需帧数（σ 翻倍 ⇒ 帧数约翻倍），**这属环境差异，不算实现过失**。

**为什么这条重要**：若不立此纪律，真机 σ 偏大时「6 秒判据达不到」会被当成实现错误去修代码，
而正确动作是**调整判据参数**。两者方向相反，改错方向会白费一轮。

### 纪律 3（配套）：被推翻的结论要留痕，不静默删除

本批的两处实测纠正（5 张→2 张、board 侧零影响）都**保留了「原推算已被推翻」的痕迹**，
而不是把错数字悄悄删掉。

理由：静默删除会让后人**重算一遍同样的错**（因为没有记录说明这条路走不通）。
留痕 + 写明「不得再写 board 侧会出 5 张卡」，等于把被推翻的结论变成**不可重犯的约束**。

## 10. limit 5→6 的量测方案与护栏（O-4）

> 背景：负责人拍板两入口都改 6（§8.2）。架构原担忧「`/api/nav` 的 limit 会抬升 `applyLrtPriority` 的 baseline」**没有消失**，
> 本节把它变成可执行的量测 + 有阈值的护栏，而不是口头评估。

### 10.1 被量测的对象（先钉死机制，再谈测法）

`applyLrtPriority`（`src/lib/recommend/lrt-priority.ts:33-57`）的三行关键逻辑：

```
head     = items.slice(0, limit)                    // :39
baseline = Math.max(...head.map(i => i.card.totalMin))  // :40  ← 前 limit 张里最慢的
isLrtHit = 含 running 轻轨段 && totalMin <= baseline + LRT_PRIORITY_SLACK_MIN(15)   // :44-46
```

limit 5→6 时，`head` 多含第 6 张 ⇒ `baseline` 单调不减（`max` 只增）⇒
**命中共集只会变大，不会变小** ⇒ 置顶条数 `≥` 原来。
这是**结构性结论**，不需要量测就能确定方向；需要量测的是**幅度**（有多少 OD 会从 1 条变 2 条、2 条变 3 条）。

### 10.2 量测脚本方案（可执行，不入 `src/`）

脚本放 `scripts/measure-lrt-priority-limit.mjs`（新增，属独立工作量），只读、不写库：

```
输入：OD 清单（≥30 组），两类必须都覆盖
  · 轻轨可达类（≥12 组）：起点/终点在同一走廊且含 LRT 段（氹仔线 LRT-TSI…/石排湾 LRT-SBV…/横琴 LRT-HQ…）
  · 轻轨不可达类（≥12 组）：如澳门半岛内短途、离岛非轻轨走廊
  · 边界类（≥6 组）：totalMin 恰在 baseline+15 附近（±3 分），这是阈值敏感区
流程（每组 OD）：
  1. 调 planNav({ limit: 12, lrtFirst: true }) —— 一次拿足够深的候选（12 > 6，避免两次请求的实时抖动不一致）
  2. 对同一份 ranked 数组，分别 applyLrtPriority(ranked, 5, true) 与 (ranked, 6, true)
     ★ 必须复用**同一个数组快照**：分两次请求会因 DSAT 实时变化导致 baseline 不同的假差异
  3. 记录：置顶条数(5) / 置顶条数(6) / 置顶车牌或 planId 集合 / baseline(5) / baseline(6) / 第 6 张的 totalMin
输出：CSV + 汇总
  · 置顶条数分布（limit=5 vs 6）
  · 集合变化：仅 5 有 / 两者都有 / 仅 6 有
  · 「涨到 ≥3 条」的 OD 占比
```

> ⚠️ **实现约束（这条不写清会量错）**：`applyLrtPriority` 会**就地改写** `card.lrtPromoted`
> （`:37` 先全清、`:53` 给命中者置 true）。同一个 `ranked` 数组上连跑两次，第二次的入参已被第一次改过。
> ⇒ 量测脚本必须**先深拷贝出两份 ranked**（或两次都从同一份 JSON 重新 parse），否则第二次测量的 `lrtPromoted` 是脏的。
> 这是「量测工具本身要防沉默逻辑错误」的一条实例。

### 10.3 护栏判定阈值（加与不加「置顶 ≤2 条」）

| 量测结果 | 判定 | 动作 |
|---|---|---|
| 所有 OD 置顶条数仍 ≤ 2 | 不加 | **不加**上限。加一个用不到的护栏 = 多一处永不触发的分支 |
| 出现置顶 = 3 条的 OD，且占比 **< 5%** | 观察项 | **仍不加**，但必须记录在发版说明；下批复核 |
| 出现置顶 = 3 条的 OD，占比 **≥ 5%** | **必加** | 落地 `LRT_PRIORITY_MAX_PROMOTED = 2`：命中集合按 `totalMin` 升序取前 2 置顶，其余回到原相对序 |
| 出现置顶 ≥ 4 条（任一 OD） | **必加** | 同上，且额外检查 `baseline` 是否被第 6 张异常拉高（可能是长尾绕路卡） |

阈值取 5% 的依据：`LRT_PRIORITY_SLACK_MIN = 15` 分钟本身是宽口径（`lrt-priority.ts:25`），
置顶 3 条意味着用户首屏顶部 3 张全是轻轨方案 —— 这会**压掉「最快方案」的可见性**（置顶是稳定前插，不是排序）。
5% 是「偶发」与「常态」的分界经验值，**标注为待量测校准**，量到真实分布后可下调。

护栏的实现位置（若需要）：`lrt-priority.ts:52-53` 之间插入截断，纯函数、可单测、回滚 = 删 3 行。

### 10.4 这条为什么不能只写「评估一下」

因为我们已在本批见过同款教训：题 A 的跳变、题 B 的车牌、题 C 的两档绿，都是「口头认为没问题」的地方藏着静默错误。
`applyLrtPriority` 的输出是**数组顺序**，它错了不会报错、不会崩溃，只会让用户首屏第一屏是三条轻轨。
⇒ 必须有数值分布才敢上线。

| **① 详情页定位契约** | **不改**。四元组天然唯一（`card.ts:89-92`） | **必须扩**。同 `planId + route + board` 下会有多个 `alight` ⇒ 四元组仍唯一（`alight` 参与比较），**但**：<br>· 若并列下车点共用同一 `ride.minutes`，用户点哪个都进同一详情 ⇒ 并列无意义；<br>· 若各自有独立 `minutes`，则 `rides[]` 必须拆成多条 `RideLegView` 或新增 `alightAlternatives[]` 子结构 ⇒ `cardDetail` 的 `find` 逻辑要改成「四元组命中后，再在子结构里选 `alight`」<br>· **改动点**：`card.ts:89-92`（find）、`types.ts:327` 附近（新字段）、`card-link.ts:6-8`（参数语义注释） |
| **② 卡面单值字段** | `RecommendCard.tsx:275` 一个 `alightLabel`、`:269` 一个 `minutes`，无需处理 | **必须定一条显示规则**，三选一（都不是技术能决定的）：<br>(a) 显示**最早到**的那个下车点 + 「等 N 个可选」；<br>(b) 显示**步行最少**的那个；<br>(c) 显示区间「下车点 A 或 B，差 2 分」。<br>⇒ 无论选哪个，都要新增一个**派生函数**把这组 alternatives 压成一个可显示值，且这个函数会成为新的口径真源（后续所有渲染器读它）<br>**改动点**：`RecommendCard.tsx:269/275`、`NavDetailBody`、`Strips`、`StationReachFold` 全部 4 处渲染器（新增一列），外加 1 个纯函数 |
| **③ 收藏快照是否存下非法组合** | **安全**。快照存 `[route, ...parallelRoutes]` + 单一 board/alight（`snapshot.ts:81`），形状闭合 | **有风险，且是静默的**。若快照存「一组 alight」，读取时必须校验这组 alight 在当前时刻是否仍是合法并列（线路可能改道、站点可能停用）⇒ 需在读取侧加校验，失败则降级为「取第一个」<br>· 若不校验：用户收藏的「A 或 B」在改道后可能指向一个**不再可达**的 B，点进去得到 `route_changed`（`card.ts:93`），表现为「收藏点不开」<br>**改动点**：`snapshot.ts:33/81`（字段）、读取侧校验（新增） |

| **⑤ 回滚方式** | — | **无法一行回滚**。契约新增字段会扩散到 4 个渲染器 ⇒ 回滚需同步还原 5~6 处。<br>可缓解：字段设为 optional、渲染器读到 `undefined` 时走现状单值分支 ⇒ 回滚 = 不产出该字段（1 处），这是唯一能做到「一处回滚」的写法，**必须在设计阶段就定下来** |
| **⑥ 与需求 8（可乘性过滤）的交互** | 无交互 | **有交互**：并列下车点 × 可乘线路过滤 ⇒ 每个下车点都要单独判「从该 board 到该 alight 有没有可乘线」。谓词维度从 1 维（线路）变 2 维（线路×下车点）⇒ 需求 8 的 15 格真值表要扩成「× 下车点」 |

### 11.3 一个容易漏的工程事实（供负责人决策时参考）

方案 B 的价值前提是「同一上车站、多个下车点，且各有独立时间」。但本项目当前**没有这个数据**：
`lookupHop` 是逐跳查表（`segment-lookup.ts`），一条 `RideLegView` 的 `minutes` 是「board→alight 逐跳求和」的结果。
⇒ 要给出「同一 board、不同 alight 的时间」，不需要新数据（现有逐跳表够），
**但需要 `modelOption` 对同一 board 做 N 次求和**（N = 并列下车点数），成本线性增长。

这一条不影响方案选择，但影响**工作量估算**：方案 B 不是「加个数组」，是「在建模期做 N 次累加 + 在展示期压成 1 个值 + 在详情期按 alight 二次定位 + 在收藏期校验」。

### 11.4 对照结论（只给代价，不做选择）

| | 契约改动 | 渲染改动 | 快照风险 | 工作量 | 可回滚性 |
|---|---|---|---|---|---|
| A（现状 · 一卡一下车点） | 无 | 无 | 无 | 0 | — |
| B（卡内并列下车点） | 四元组保持 + 新增 alternatives 子结构 | 4 个渲染器 + 1 派生函数 | **有（静默）**，需读取侧校验 | 3~5× | 仅在「字段 optional + 单值兜底」写法下可一处回滚 |

### 11.5 定案：采用 A（一卡一个下车点）—— 落地细节

**负责人已拍板选 A。**但「A 是现状」不等于「A 无需改动」—— 当前实现**并没有真正收敛**，
存在两类重复出卡，必须修掉才算落地。

#### 11.5.1 先修一个真实缺陷：站码去重只做了字符串级，没做 mainCode 归一

`alightsOf`（`enumerate.ts:203-212`）与 `boardsOf`（`:196-202`）的末尾都是：

```ts
return applyStopPriority([...new Set(out.filter(Boolean))]);
```

`new Set()` 是**字符串全等**去重。而站码带站台号后缀（`C690/3`、`C690/1` 与 `C690` 是**同一物理站**），
`mainCodeOf` 才会把它们归一。⇒ 同一站的多站台会被当成多个下车点。

**⚠️ 数字以实测为准（架构推算已被推翻，此处为最终版）**

架构初版曾据一组跨 plan/跨字段的候选集合推算「最多 5 张卡」，**该数字无效**。
PM 用**枚举层实测**（`optionsFor` 纯函数、确定性，非运行时抽样）给出真实规模：

| OD | plan | 线路 | 修复前 alight 候选 | 修复后 | 卡片数 |
|---|---|---|---|---|---|
| `home→gate` | 28 | `25AX` | `M9/3`、`M9/4` | `M9/3` | **2 → 1** |
| `gate→home` | 33 | `25AX` | `C690/2`、`C690/3` | `C690/2` | **2 → 1** |
| `gate→home` | 33 | `51B` | `C690/2`、`C690/3` | `C690/2` | **2 → 1** |

⇒ **单组实测最多 2 个同主码写法，减卡效果为 2 张 → 1 张**（不是我推算的 5 张）。

**机制纠正（比数字更重要）：board 侧对卡片数零影响。**

`enumerate.ts:263` 是 `boardsOf(first, R)[0]` —— **只取首项**。
而静态命中里重复项从不是首项（首项恒为 `C690/1` 或 `C690/2`），去重后首项不变 ⇒ **卡片数不变**。

⇒ **本项（PRD R5 / 批次 IMP6）的价值应表述为**：

> **alight 侧 3 处真实减卡**（枚举层实测 2→1）+ **防御未来数据**（万一重复项哪天排到首位）+
> **候选全集语义正确**（board 侧重复对卡片数无影响，但会让「候选全集」含同一站的多种写法，
> 供后续 `alightAlternatives` 或调试输出时产生噪声）。

静态命中的 10 处实例清单**仍然有效**（它证明机制真实存在、且 alight/board 两侧都有），
只是结论从「最多 5 张卡」降级为「**单组实测最多 2 张；board 侧零影响**」。

**这是「同线同站出现多张卡」的主因，且与 STOP_PRIORITY 无关**（STOP_PRIORITY 处理的是
「地理近邻但不同站」如 T367/T363，属另一类）。修复：去重键改为 `mainCodeOf`。

> **展示值不得被抹平**：归一只用于**去重键**与**收敛键**，`board`/`alight` 的**展示值必须保留原始站台码**
> （如 `C690/3`）。否则用户看到的站名会与实际站台不符 —— 这条是 PRD AC-9.17 的硬要求。

#### 11.5.2 判定键与**收敛落点**（回答 team-lead 第 2 问 + 纠正架构此前一处错误）

**判定键结论：三层键 `route | mainCodeOf(board) | mainCodeOf(alight)`，用 mainCode 而非站码全等。**

1. **必须用 `mainCodeOf`**：其语义就是「剥掉站台号后缀，同站多台是同一物理位置」
   （`segment-lookup.ts:21-23`）。用站码全等会把 `C690/3` 与 `C690` 当成两个方案。
2. **必须带 `route`**：不同线路即使 `board→alight` 的 mainCode 相同，也是不同方案。
3. **刻意与 `card.ts:89-92` 四元组不同**：四元组用于「精确定位到那一张卡」，必须用**原始站码**；
   收敛键用于「判断是否同一方案」，必须**归一**。两者用途不同，**不要统一**。

**⚠️ 架构纠正（此前方案有错，以本节为准）**：架构上一版写「收敛在 `enumerate.ts` 生成处」——
**这是错的**，因为：

```
enumerate.ts 只产出 OptionSeed（未建模，没有 totalMin）
modelOption 在 service.ts:146-149 的循环里才跑
⇒ 在 enumerate 阶段无法回答「哪个下车站更快」⇒ 选不出代表站
```

**正确落点：`service.ts` 的建模循环之后、`sortCards` 之前**（`service.ts:150-151` 之间）。
与 PM §4.5.1 定的顺序**完全一致**：

```
枚举(enumerate) → R1 站内互斥(applyStopPriority) → R4 设边界 → 建模(modelOption 循环)
→ R2 同线收敛(service.ts，需 totalMin) → R3 降级备选 → sortCards → slice(limit)
```

**两条关键顺序的含义**（PM 已定，架构确认一致）：

| 顺序要求 | 为什么必须 | 违反后果 |
|---|---|---|
| **R2 收敛必须在 `slice(limit)` 之前** | 收敛会把 N 张卡合成 1 张 | 若在 slice 之后，被收敛掉的卡**已经占了名额** ⇒ 首屏实际只剩 5 张（6 张名额里有 2 张被合并成 1）⇒ **收敛等于白做**，且比以前更少 |
| **R3 降级备选必须在 R2 之后** | 必须先知道「谁是代表」才知道「其余是备选」 | 反过来会把代表自己也塞进 `others` |

**分工（两件事不要混）**：

| 事项 | 落点 | 是否需要 totalMin | 说明 |
|---|---|---|---|
| 站台归一（`C690/3` vs `C690`） | **`enumerate.ts`**（去重键改 `mainCodeOf`） | 不需要 | 同一物理站，纯字符串问题，§11.5.1 已述 |
| 同线不同下车点合并（`T367` vs `T363`） | **`service.ts`**（建模后） | **需要**（选 min totalMin 为代表） | 本节新增 |

**代表站的选取规则（与偏好档的关系见 §11.7）**：
`representative = argmin(totalMin)` over 该 `(route, boardMain)` 下的全部候选 alight。
**不用 `alights[0]`** —— 首项只是候选列表顺序，不代表更快（这正是 PM `AC-9.14` 要覆盖的场景）。

#### 11.5.4 其余下车站候选进详情页备选（回答第 3 问）

**现状问题**：`card.ts:157` 与 `:207` 都取 `r.alights[0]!` —— **首选项**，
而不是「本方案实际使用的那个」。收敛后二者会不一致（例：卡用了 T363，但 `alights[0]` 是 T367）。

**修法：新增字段，不改四元组。**

```ts
/** 详情页「其他下车点」备选（可选；缺省 = 无备选，渲染现状） */
export interface AlightAlternatives {
  /** 本卡实际使用的下车站（= 四元组里的 alight，原始站码） */
  chosen: string;
  /** 其余可选站（原始站码 + 展示名 + 该站到目的地的步行距离/时长） */
  others: { code: string; label: string; walkMin?: number; walkM?: number }[];
}
```

**渲染入口**（回答「具体数据结构与渲染入口」）：

| 位置 | 现状 | 改动 |
|---|---|---|
| `card.ts:157`（`buildReports` 的 `r.alights[0]`） | 取首选项 | 改为 `input.alight ?? r.alights[0]`（优先用本卡实际值） |
| `card.ts:207`（同函数内 `const alight = r.alights[0]!`） | 同上 | 同上 |
| 详情页 DOM | 下车行是单值（`RecommendCard.tsx:275`；详情页在 `NavDetailBody`） | 在**下车行右侧**加「另有 N 个下车点」的可展开入口，展开后列出 `others` |
| 交互 | — | 点选某个备选 ⇒ 走 `buildCardHref` 重进详情（四元组的 `alight` 变化）⇒ **不需要新状态机** |

**关键：`others` 只在详情页渲染，不进卡片列表**（卡片列表仍是一卡一下车点，符合 A 方案）。
这既满足「不重复出卡」，又保留「用户可以换下车点」的能力，且**回滚 = 不产出该字段**（渲染器读到 undefined 走现状）。

#### 11.5.5 跨线不收敛的边界（回答第 4 问）

**结论：收敛**只在「同一条线路（同一 `route`）」内**发生。跨线永不收敛。**

明确列出**允许两条不同线路各占一张卡**的情形（避免收敛过头把真实更优方案并掉）：

| 情形 | 是否合并 | 理由 |
|---|---|---|
| 同 `route` + 同 `boardMain` + 不同 `alightMain` | **合并为一张** | 同一线同一站上车，只是下车站不同 ⇒ A 方案下这是「备选下车点」 |
| 不同 `route` + 同 `boardMain` + 同 `alightMain` | **不合并** | 不同线路 = 不同班距/换乘/步行，是**真正不同的方案**（这正是 `parallelRoutes` 标签要表达的） |
| 不同 `route` + 不同 `alightMain`（但两站相距 <400m） | **不合并** | 用户对「坐哪条线」有偏好（班次密度、熟悉度），不能因步行距离近就替用户决定 |
| 同 `route` + **不同** `boardMain` | **不合并** | 上车站不同 = 走的路不同，是真实差异 |
| 换乘方案（≥2 段） | 只看**首段** | `enumerateOptions` 只展开首段的 alights（`enumerate.ts:208` 注释「首段才展开」），后续段用默认线，不参与收敛 |

**一条保护性上限**（防收敛后仍有海量备选）：`others` 最多 4 条，按「步行到目的地距离」升序取前 4。
理由：与 `RouteStack.tsx:28` 的 `MAX_PARALLEL = 3`、`altBuses ≤3` 同一量级，避免卡面/详情溢出。

#### 11.5.7 与 §8（可乘性过滤）的交互（必须注意）

需求 8 的 `isBoardable` 过滤（`model.ts:609-611`）作用于 `parallelRoutes`，
而本次收敛作用于「首段的 alight」。两者**作用维度不同**（一个改"并列线"，一个改"下车点"），
但都在 `modelOption` 附近 ⇒ **建议同批交付**，理由与 §9 A-4 相同（同区域反复冲突）。

**交互点**：收敛后 `others` 里的每个下车站，也需要单独判「该 board → 该 alight 有无可乘线」（若不过滤，

#### 11.6.6 半成品防线：静态检查 + 运行时检查**必须成对**（PM 实测教训）

PM 的基线脚本做了三态验证，抓到一个**单靠静态检查抓不到**的失败模式：

| 态 | 代码状态 | 口径 | 结果 |
|---|---|---|---|
| **A** | `limits.ts` 常量已建，但 `grep RECOMMEND_LIMIT_DEFAULT src/` **只命中定义本身 1 处**（9 处调用点一个没接） | 6 | **FAIL 38/38** |
| **B** | 同一份代码（调用点仍未接） | 5 | PASS（因为默认值恰好等于旧硬编码） |
| **C** | 调用点全部接入后 | 6 | **PASS 0/42** |

**这证明**：「建了常量但漏接调用点」是一种**静态字面量检查（AC-10.8）看不到、只有运行时跨模块检查才抓得到**的半成品状态 ——
因为此时 `src/` 里确实**没有残留字面量 5**，静态检查会通过，但行为完全没变。

⇒ **IMP1 的验收必须是两条，缺一即视为半成品**：

| 类型 | 检查内容 | 能抓什么 | 抓不到什么 |
|---|---|---|---|
| **静态**（AC-10.8） | ① `grep -rn "limit.*\b5\b" src/` 除常量定义外 0 命中<br>② `grep -c "RECOMMEND_LIMIT_DEFAULT" src/` = 9（1 定义 + 8 调用点） | 残留字面量、漏接调用点（靠计数） | ① 接入了但值仍错；② 接入位置对但没生效 |
| **运行时**（AC-10.1/10.7） | ① `/recommend` SSR 与刷新均 `cards.length === 6`<br>② `/nav` 亦 6<br>③ 第 6 张 `cardDetail` 不返 `route_changed`<br>④ **卡面张数 === href 的 `limit` 参数** | 行为是否真的变了；跨模块是否一致 | 是否还有别处硬编码（需静态补） |

#### ④ 的可交接表述（QA 不需要读代码、不需要理解四元组）

> **判据原文（照此执行即可）**：
> 取任一张卡，**读出卡面显示的张数 N**，再**读出该卡 `href` 里的 `limit` 参数 M**，断言 **`N === M`**。
>
> **反例（本批修复前实测）**：卡面 6 张、`href` 写 `limit=5` ⇒ 第 6 张点进去必然 `route_changed`。

**为什么必须是这个形式**：它不是「架构师知道要断言什么」，而是**任何人拿一台设备打开页面就能验** ——
看卡面数几个、看地址栏（或链接）里 `limit=` 是几，两个数不相等就是缺陷。
**QA 无需理解四元组、无需读 `card.ts`/`card-link.ts`/`RecommendCard.tsx` 的调用链。**

**为什么这一条静态检查抓不到**（这是它必须单列的全部理由）：
```
card-link.ts:39        q.set("limit", String(p.limit ?? 5))     ← 默认值 5 仍在
RecommendCard.tsx:158-169   buildCardHref({...})  ← 调用时**没有传 limit**
```
即使 9 处常量全部接好、`grep` 里一个残留字面量都没有，**只要这一处不传**，
`buildCardHref` 仍会落到 `p.limit ?? 5` ⇒ 行为完全没变而静态检查全绿。
**这是「静态检查通过但功能未生效」的典型形态**（PM 三态验证的 A 态即此类）。

**这条纪律可推广**（不只 IMP1）：凡「把散落字面量收敛为单一常量」的改动，都必须
**静态计数（接了几个）+ 运行时行为（真的变了吗）双检**。单靠任一侧都有半成品窗口。

### 11.7 PM advisory 1：切偏好档会不会改变卡的下车站（技术结论）

**结论：不会改变「同一张卡的 alight」，因此不存在「卡面写 A 站、点进去是 B 站」的风险。**
但存在一个**不同性质**的问题，需要产品决定。

**代码依据（两条，都是硬的）**：

1. **偏好只影响排序，不改卡片内部字段**：`cmpByPref`（`score.ts:159-188`）是**纯比较器**，
   函数体内无任何赋值；`sortCards` 在 `service.ts:151` 于建模**之后**调用，只重排数组。
   ⇒ 偏好不会改写 `card.rides[0].alight`。
2. **`buildCardHref` 的 `alight` 直接取自卡片自身**：
   `RecommendCard.tsx:167` 用 `first.alight`；`card.ts:251` 用 `m.card.rides[0]!.alight`。
   两处都是**卡片自己的 alight**，与卡面渲染的是同一个字段 ⇒ 天然同步，**不可能不一致**。

**但有一个真实的相关问题（收敛引入，非偏好引入）**：
§11.5.2 把代表站定为 `argmin(totalMin)`，这是**偏好无关**的。
于是 `less_walk` 档用户会看到「代表站 = 最快那个」，而不是「步行最少那个」——
虽然点进去完全一致（无 bug），但**卡面推荐不符合他的偏好**。

**✅ 已定案（2026-11-04，team-lead 采纳选项 A）**

| 项 | 定案内容 |
|---|---|
| **代表站的选取判据** | `balanced` / `fewer_transfers` ⇒ `argmin(totalMin)`；**`less_walk` ⇒ `argmin(walkMinutes)`** |
| **`prefs` 来源** | `service.ts:111` 已在上下文中，直接传入收敛点，**零额外成本**（不新增入参、不新增查询） |
| **副作用** | 切偏好档后同一 OD 的代表站会变 ⇒ 卡面文字变。**这是预期行为**，且因为 href 与卡面同源（见下），**不会产生"卡面写 A、点进去 B"** |
| **卡面是否需要极轻提示** | **不需要**。代表站已随偏好变化，用户看不到任何不一致 |

**⚠️ 结构性保证在选项 A 之下仍然成立（必须逐字守住）**：

> 代表下车站**必须就是 `card.rides[0].alight` 本身**，不得新增独立的「卡面代表站」字段。

选 A 改变的只是「**挑哪一张 card 作为代表卡**」的判据（从固定 `argmin(totalMin)` 变成偏好相关），
**没有改变「代表站从哪里来」** —— 它仍然直接取自胜出那张 card 的 `rides[0].alight`。

⇒ 因此：
- `buildCardHref` 的两个调用点（`RecommendCard.tsx:167` 读 `first.alight`、`card.ts:251` 读 `m.card.rides[0]!.alight`）

- AC-9.15（`route_changed` 不上升）**自动满足**，与选 A 还是选 B 无关。

**这条是本批最重要的结构性保证之一**（team-lead 判定），与以下两条同源：

### 11.8 PM advisory 2：`AC-9.14`（代表站 ≠ `alights[0]`）的可复跑构造

#### 11.8.1 为什么它一定存在

`alights[0]` = 候选列表**第一个**（由 `alightsOf` 的来源顺序决定：`meta.alight` → `alight_candidates`
→ `meta.to` → `to_station`，见 `enumerate.ts:203-212`）；
代表站 = **建模后 `argmin(totalMin)`**（§11.5.2）。
两者**没有任何机制保证一致** ⇒ 只要第二个候选更快，就会不等。

#### 11.8.2 合成用例（**首选，确定性 100%，不依赖 DB**）

这是 QA 应当**主要使用**的形式 —— 因为它不依赖任何实时数据，可在 CI 跑：

```

  cards[0].rides[0].alight === "T363"          ← 代表站 = argmin(totalMin)，≠ alights[0]
  cards[0].alightAlternatives.chosen === "T363"
  cards[0].alightAlternatives.others[0].code === "T367"
  buildCardHref({..., alight: cards[0].rides[0].alight}) 的 alight 参数 === "T363"   ← AC-9.15 的同步断言
```

再补一条**偏好相关**断言（对应 §11.7 选项 A）：

### 11.9 确认：`buildCardHref` 的同步已含在方案内（回答 team-lead 第 4 问）

**已包含，且是本方案的结构性保证，不是额外补丁。**

关键设计决定（写进 Spec 硬约束）：

> **代表下车站必须就是 `card.rides[0].alight` 本身，不得新增一个独立的「卡面代表站」字段。**

理由：`buildCardHref` 的 `alight` 参数在两个调用点都取自 `card.rides[0].alight`
（`RecommendCard.tsx:167` / `card.ts:251`）。只要代表站写进**这个字段**，href 就自动同步。
反之，若为卡面另设 `representativeAlight` 而 href 仍读 `rides[0].alight`，就会出现 PM 描述的
「卡面写 A 站、点进去 B 站」⇒ 详情页 `find` 不到 ⇒ `route_changed`。

⇒ **收敛的实现方式：直接采用「胜出的那张 modeled card」作为代表卡**（它的 `rides[0].alight`
本来就是对的），把落选卡的 alight 放进 `alightAlternatives.others`。**全程不改写任何卡片字段** ——
这样从结构上不可能分叉，也就不需要"记得同步"这种纪律。

这条设计同时满足 AC-9.15：**route_changed 不会因收敛上升**（因为四元组与卡面是同一份数据）。

### 12.1 业界怎么做「你已上车」（带来源）

| 产品 | 是否自动检测「已上车」 | 靠什么信号 | 触发方式 | 关键事实 |
|---|---|---|---|---|
| **高德地图**（公交换乘提醒 v6.60） | **否**。它检测的是「你**接近上车站**」，不是「你上了车」 | GPS 定位 + 站点地理围栏 | 用户先点上「换乘提醒」进入导航态 | 上车提醒在**距上车站 50 米**时触发；乘车中显示「已过站点 + 实时位置」；到站提醒在「距下车站 1 站**且** <500m」时触发（含后台震动持续 1 分钟直到用户确认）。全程**不识别具体车辆**（无人车绑定）<br>来源：[it168 报道](https://m.it168.com/articleq_1478134.html)、[新民网](https://wap.xinmin.cn/content/25767671.html)、[cioage 实测](https://www.cioage.com/article/457426.html) |
| **Google Maps** | **否**。用户按 Start 后它接管，不做上车判定 | GPS + 用户已声明的行程 | 用户按 **Start** 按钮 | 2017 上线「下车提醒 + 实时进度条 + 锁屏通知」，官方描述是「hit the Start button and let Maps do the rest」<br>来源：[TechCrunch](https://techcrunch.com/2017/12/09/google-maps-will-soon-tell-you-when-its-time-to-get-off-your-train-or-bus/)、[Engadget](https://www.engadget.com/2017-12-15-google-maps-will-tell-when-to-get-off-bus-train.html) |
| **Citymapper** | **否**（GO 模式同样是用户启动） | GPS + 实时车辆跟踪 | 用户按 **GO** | 功能清单是「跟着这辆车在地图上靠近你」「告诉你该上哪节车厢」「到站提醒你下车」，全部以用户已进入 GO 为前提<br>来源：[Citymapper 官方商店页](https://citymapper.com/android)、[App Store](https://apps.apple.com/gb/app/citymapper-your-transport-app/id469463298) |
| **Transit（GO）** | **是 —— 唯一的例外**，但判定对象是「**你是否在车上**」，不是「**你在哪一辆车上**」 | GPS + 步行速度 + **运动检测（地铁无 GPS 时用加速度计）** | 用户按 **GO**，之后自动 | 官方描述：「自动跟踪你的 transit vehicle、walking speed 和 location」；「进入地下轨道时用 motion detection 在无 GPS 下跟踪位置」；众包隐私条款明确「仅在 GO 激活**且你确实在车上**时共享；一旦下车 GO 立即停止」—— 说明它确实在推断 on-board 状态<br>来源：[MacRumors 转述官方公告](https://forums.macrumors.com/threads/transit-app-expands-real-time-crowdsourced-data-to-175-cities.2132916/post-26360795)、[SLO 市政府官方页](http://www.slocity.org/services/transportation/slo-transit/transit-app) |
| **Apple Maps** | **无公开资料** | — | — | 标注为**待验证**：未见官方文档描述自动上车检测。**不作为证据使用。** |

**从这张表能得出的三条结论（都可追溯）**：

1. **没有一家做「锁定具体车牌」的上车检测。** 全部止步于「用户已在某辆车上」或「用户接近站点」。
   Transit 是能力上限：它有运动检测，但推断的是「on-board」布尔量，不是车辆身份。
   ⇒ 本项目要做「锁到具体车牌」，在业界是**没有先例的更强诉求**，风险相应更高。
2. **所有产品都要求用户**显式启动（Start / GO / 换乘提醒）。**没有一家在用户没进入导航时就去猜**。
   ⇒ 这支持「手动为主、自动为辅」的方向，也说明「自动进入 riding」本身是个超出业界常规的设计目标。
3. **高德的「上车提醒」用 50 米站点围栏。** 这直接印证了 ADR-110 的 `tolStation` 地板取 40m
   （`BOARD_NEAR_M`）是**同一量级**的合理值 —— 我们用 40，行业用 50，差 10 米。
   **但注意语义差别**：高德 50m 只用于「提示你该上车了」，**不用于判定身份**；
   我们要用它判定「人在这辆车上」，是更重的用途 ⇒ 阈值相同不代表风险相同。

> 关于「车内与站台物理不可分」的公开讨论：本次检索**未找到**业界公开的技术讨论文档（这是负结果，如实记录）。
> 但业界行为本身就是间接证据：**全部要求用户手动启动、且无一家做车辆身份绑定** ——
> 这个一致的行为模式，比任何单篇博客都更能说明这两个问题（上车与否、上的是哪辆）在工程上有多难。

### 12.2 两段式（ADR-110 现方案）在澳门场景的具体风险

两段式 = ①车停靠本站 + 人 `tolStation` 内 ⇒ 只记录；②同一 plate 车刚离站 + 人仍在车旁 ≤24s ⇒ 才切换。

| 风险 | 具体表现 | 严重度 | 现有兜底 |
|---|---|---|---|
| **站台紧邻（站距 p10）** | 若相邻站站距 < 80m（`tolStation` 上限），人在 B 站而车停在 A 站、两站站台几何接近 ⇒ ①的记录可能挂到错误的站 | 中 | **待验证**：需量 `route_station_mileage` 的站距 p10。若 p10 < 80m 必须下调上限（已列 blocking） |
| **同站台多线** | 同一站台停靠多条线，用户等 A 线，B 线先来先走。①会为 B 线也记一条记录 | 中 | ②要求「人跟着同一辆车的位移」⇒ B 线车走了但人没动 ⇒ `dist(user, B车)` 迅速 > `tolStation` ⇒ 不切换。**这条两段式天然能挡** |
| **车辆 GPS 漂移** | 车辆坐标跳变几十米 ⇒ ②里「人距该车位置」的判据被拉偏 | 中 | ②用「≤ `tolStation`」是**双向**容错（车漂近/漂远都还在范围内）；且 `SWITCH_COOLDOWN_MS = 20s` 防抖 |
| **用户站台内走动** | 人在站台从候车区走到上车门，位移 10~30m | 低 | `tolStation` 40~80m 覆盖该范围，不会因此漏判 |
| **上车后车辆迟迟不动（塞车）** | ②需要「车刚离站（`interval.from == 上车站`）」，车不动就永远不触发 ⇒ **判定不出来**，用户得手动 | **高** | 这是两段式的**主要代价**：澳门半岛高峰期巴士在站内排队上客 1~3 分钟很常见。v3.6.0 原来的 R2（纯位移）在这段时间也可能判不出（车速 < 8km/h）。⇒ **两段式在塞车场景并不比现状更差，但也救不了它** |
| **末班/单班车** | ①记录后车走了，但用户上了后车 | 低 | ①记录失效（24s 超时），不会误锁；只是漏判，走手动 |

**结论**：两段式把「同站台等别的线」这个最大误判面**结构性挡住**（靠"人跟着车动"），
代价是「车不动时判不出来」——而这一点**现状同样做不到**，所以两段式是**净改善**，不是零和。

### 12.3 直切版（车在站 + 人在站 ⇒ 立即判定）的风险，与「靠可逆纠正兜」的量化

| 问题 | 量化回答 |
|---|---|
| 误判面有多大 | 直切版的触发条件在**任何**同站台来车时都成立（车停靠 + 人在站台）。澳门常见站台同时停/靠 2~4 条线 ⇒ 只要用户等的不是第一辆来的车，就会被判错 |
| 误判后用户需要几步纠正 | **最少 2 步**：① 点「我没上车」（`NavTrackBar.tsx:248-256`，`correctAuto` 为真时显示此文案）→ ② 确认回到候车态。<br>若要重新上车：③ 等判定再来一次或点「手动标记上车」⇒ **3 步** |
| 纠正后会不会劣化 | **会，且是硬伤**：`onNotBoard` 在 `useRideTracking.ts:1898` 置 `autoUsedRef.current = true`，而 `autoBoardOf` 的硬门 `boarding-detect.ts:321-323` 直接读它 ⇒ **本段内自动判定被永久关闭**（`autoUsed` 只在 `start()` `:1628` 与换腿 `:1783` 复位）。<br>所以「靠可逆纠正兜」这句在**当前代码上不成立** —— 纠正本身是**不可逆**的 |
| 因此直切版的成立前提 | 必须**同时**修 B2（`onNotBoard` 可逆化）与 B3（候选池含刚离站车），否则「误判 → 纠正 → 再也自动不了 → 手动也找不到车牌」= 现状缺陷 7 的复现 |
| 兜底程度总结 | 直切版 = **高频误判 + 纠正需 2~3 步 + 纠正后永久失去自动判定**。<br>只有把 B2/B3 修好，才谈得上「可兜底」；即便如此，误判频率仍显著高于两段式 |

### 12.4 第三条路：「手动为主 + 车辆到站时把该站所有在站车辆列成一排供一键选择」

| 维度 | 评估 |
|---|---|
| 机制 | 不猜。车停靠本站时（`v.atStation == boardMain`），把**该站当前所有在站/刚离站车辆**渲染成一排车牌按钮（复用现有 `candidates` 状态与 `NavTrackBar` 的候选区），用户点一下即锁牌 |
| 判定速度 | **最快**（人一点即定，无 12s×N 帧延迟） |
| 误判面 | **0**（系统不判定，只呈现；用户自己知道上了哪辆） |
| 可纠正性 | **天然可纠正**（再点另一辆即可，无需「我没上车」） |
| 实现复杂度 | **最低**：不加新判据、不加阈值、不改 `autoBoardOf`；只需在 `boarding` 相位的候选区按「在站优先」排序并把候选从 6 条缩到 3~4 条（屏幕宽度约束）。`rankBoardingVehicles` 已按「停靠本站 > 刚离站 > 距离」排序（`track.ts:228-237`）⇒ **排序逻辑已有** |
| 可验收性 | **最强**：`data-board-match="manual"` + 锁到的 plate 可断言；误判率按定义恒为 0 |
| 代价 | 依赖用户主动点（不满足需求 6 的「不要坐一段才判到」中的"自动"字面期待）；且**在站车辆为 0 时无按钮可点**（车还没来） |
| 与需求 6 的关系 | 需求 6 原话是「同时利用车辆 + 用户定位在该站即判定上车」。第三条路**用了车辆**（在站判定）、**用了位置**（哪一站），但把「判定」交给用户。⇒ 严格说它满足需求 6 的**手段**，不完全满足「即判定」的**自动语义**。这一点必须由负责人裁定，不能由技术决定 |

### 12.5 三方案对照表（供负责人出选择题）

| 维度 | ① 两段式（ADR-110 现方案） | ② 直切版 | ③ 手动为主 + 在站车辆一键选 |
|---|---|---|---|
| **判定速度** | 中（车离站后 1 帧，≈12s 内；塞车时判不出） | 快（车一停靠即判，≈0~12s） | 由用户（点得越快越准） |
| **误判面（结构性）** | **低** —— 「人跟着车动」只有上了车才成立；同站台多线被挡 | **高** —— 任何同站台来车都触发；用户等的不是第一辆时必错 | **0** —— 系统不判定 |
| **误判后纠正步数** | 2 步（且纠正后**永久失去**本段自动判定，除非修 B2） | 2~3 步（同左） | 0 步（再点另一辆即可） |
| **漏判场景** | 塞车不动、GPS 拒权、车辆帧丢失 | 少（几乎不漏） | 用户忘记点、在站无车可点 |
| **实现复杂度** | 中：新纯函数 + `tryAuto` 新分支 + Flag + 7 条单测 | 低（判据最简单） | **最低**：复用 `candidates` + 已有排序 |
| **可验收性** | 中（真机采样才能验阈值合理性） | 中 | **最强**（误判率恒 0，纯 UI 断言） |
| **是否需修 B2/B3** | 需要（否则纠正后死锁） | **必须** | 不需要 |
| **与业界惯例** | 超出业界（业界不做自动判定） | 远超业界 | **最接近业界**（Google/高德/Citymapper 都是用户启动 + 系统跟随） |
| **与需求 6 字面** | 满足（自动 + 用车辆 + 用位置） | 满足 | **部分满足**（用车辆/位置，但不自动判） |

**架构不替负责人选择。**若需要技术侧的一句话倾向，见 §12.6（明确标注为「倾向」而非结论）。

### 12.6 架构倾向（供参考，非结论）

若**必须**在「自动」与「不误判」之间取舍，架构倾向 **① 两段式 + 修好 B2/B3**，理由：
它是唯一在「保留自动语义」前提下把最大误判面结构性挡住的方案，且塞车场景的漏判**现状同样存在**（不是新增代价）。

但若负责人更看重「零误判 + 最强可验收」，**③ 可以单独做，且成本最低** —— 它甚至可以与 ① **并存**
（③ 作为常态入口，① 作为兜底自动），两者不冲突。这是本次研判最值得注意的发现：
**③ 不是 ① 的替代品，而是 ① 的补充面。** 是否并存属产品决策。

逐个判定标签后（`resolve-click-tags.mjs`），**真缺口只有 4 处**：

| 元素 | 位置 | 为什么没反馈 | 影响 |
|---|---|---|---|
| `<Link className="nav-brand">` / `<div className="nav-brand">` | `NavBrandBar.tsx:144`、`:58` | `<a>`/`<div>` 不走 `button` 兜底；`.nav-brand` 零 `:active` | 品牌栏入口按下无任何反馈 |
| `<div className="route-sheet__peek">` | `BottomSheet.tsx:141` | 同上（拖拽把手区域） | 拖动起点按下无反馈 |
| `<Link className="link-hit">` | `about` 页 3 处 | 同上 | 文字链按下无反馈 |
| `<Link className="rc-report__link">` | `RecommendCard.tsx:307` | 同上 | 报错入口按下无反馈 |
| `<summary className="help-faq__q">` | `help/page.tsx:304` | `<details>` 的 summary 不走 button 兜底；`.help-faq__q` 零 `:active` | FAQ 展开无反馈 |
| `<div className="fav-sheet__scrim">` | `FavoritesClient.tsx:242` | 遮罩层 | **不需要**（点遮罩关闭是惯例，加按压反而怪） |

> 都已覆盖。⇒ **不存在「5 张路线大卡按下去没反应」那类问题**（v1.1.7 已修，`:1247-1254` 有记录）。

### 13.2 三个真实缺陷（U11 要修的就是这三条，不是重做一套）

**缺陷 1｜非 button 可点击元素完全没有按压反馈（4 类，见上表）**

`.nav-brand` / `.link-hit` / `.rc-report__link` / `.route-sheet__peek` / `.help-faq__q` 都是「看起来可点」（有 `cursor:pointer`）但按下零反馈。
这正是 v1.1.7 已经踩过一次的坑（`:456-467` 注释：「站内大量按钮其实是 `<a class="btn">` … ⇒ 这些元素点了毫无反馈」）—— **当时只把 `.btn` 类补上了，没补非 `.btn` 的链接**。

**缺陷 2｜`prefers-reduced-motion` 的覆盖是「发现一处补一处」，不是系统性覆盖**

现状有**三个**独立的 `@media (prefers-reduced-motion: reduce)` 块：

- `:541-553` —— 全局 `*` 关动画/过渡 + `button:active { transform: none }`
- `:1755-1759` —— `.rc:active { transform: none }`（因为 `.rc` 是 div，不吃 `button` 规则）
- `:2707-2711` —— `.nav-locate-fab { transition: none }`

**问题**：`.rc` 需要单独补块，说明「非 button 的缩放类元素」不在全局覆盖内。
本批 U11 若给 `.nav-brand` 等元素加 `transform: scale()`，**必须同时加第四个 reduced-motion 块** ——
否则就是在扩大这个洞。这与题 C 的「两套可独立调参的变量」是同一类结构缺陷：**靠人记得补**。
⇒ U11 必须把 reduced-motion 的形变抑制**收口成一条规则**，而不是逐个补块。

**缺陷 3｜`filter` 反馈在 reduced-motion 下保留，但「是否算最小可见反馈」没有断言**

`--state-active` 是 `filter: brightness()`（`:260`、`:334`），属**颜色变化**不是**运动**。
⇒ 在 reduced-motion 下 `transition-duration: 0.01ms`（`:547`）会让它**瞬时生效**，仍然可见。
**这是当前唯一在 reduced-motion 下真实生效的反馈通道** —— 但它没有任何验收断言守着，
将来若有人把 `filter` 换成 `transform`（比如为了"更跟手"），reduced-motion 用户就**完全失去反馈**。

### 13.3 技术选型对照（三套，逐项给代价）

| 维度 | ① 纯 CSS（`:active` + transition） | ② Material ink ripple（JS 注入 `<span>` + 动画） | ③ 混合（CSS 为基座 + 仅少数元素 ripple） |
|---|---|---|---|
| **做法** | 沿用现有 `:active` 体系，给缺口元素补规则 | 每个可点元素内动态插入 ripple span，按点击坐标扩散 | 现有 CSS 体系不动；只对「大卡 / 底部导航」等大目标加 ripple |
| **首帧性能** | **零成本**（CSS 引擎合成层，无 JS） | 每次点击需 `document.createElement` + 计算坐标 + 强制 reflow（读取 `getBoundingClientRect`）⇒ **首帧风险最高**。要在 16ms 内完成，须预创建 span 池 + 只改 `transform/opacity` | 介于两者（只有大卡走 JS） |
| **布局抖动** | **无**（`transform`/`filter` 均走合成层，不触 layout） | **有风险**：插入 `<span>` 会改变父元素子节点数；若父元素是 flex/grid 且未设 `position: relative` + 子元素 `position: absolute`，会重排 | 同 ②，但影响面小 |
| **是否需要 `will-change`** | 不必（`scale` 在 90ms 内，浏览器已优化） | **建议**（`will-change: transform, opacity`），但滥用会导致层数爆炸、显存上涨 | 仅 ripple 元素需要 |
| **长列表开销** | **无**（样式匹配是 O(1)，无逐元素 JS） | 每次点击一次 DOM 操作；若列表项多且未预池化，GC 压力上升 | 仅限大卡（数量有界） |
| **与 `overflow:hidden` 冲突** | 无 | **有**：ripple 必须被父元素裁剪才不溢出圆角，而本项目多处容器有 `overflow:hidden`（如 `.rc`、各 sheet）⇒ 需逐个确认 `position: relative` + 圆角裁剪；漏一个就是「水波溢出卡片」 | 同 ②，但范围可控 |
| **300ms 点击延迟** | **已解决**：现有 `touch-action: manipulation`（`:471`）显式关掉双击缩放等待 | 若 ripple 用 `touchstart` 起手且未 `preventDefault`，可能与 `touch-action` 语义冲突 | 同 ② |
| **与 z-index 表的关系** | 只改自身 `transform/filter`，**不动 z-index** ⇒ 零风险 | 插入的 span 需 `z-index`，若设正值可能盖住既有层级（本项目 z 表很密：68~130，见 §13.5） | 需为 ripple 分配一个**低于所有内容层**的 z（如 `z-index: 0` + 父级 `isolation`） |
| **无障碍（reduced-motion）** | 只需收口 `transform` 抑制，`filter` 天然保留 | ripple 是纯运动 ⇒ reduced-motion 下**必须完全禁用**，否则违反用户偏好 | ripple 部分禁用，CSS 部分保留 |
| **与硬约束「不加依赖」** | 满足（0 依赖） | 满足（手写，但代码量较大：约 80~150 行 + 池化） | 满足 |
| **工作量** | **最小**：补 4~5 处 `:active` + 收口 reduced-motion | 大：ripple 组件 + 池化 + 裁剪排查 + 逐元素接入 | 中：ripple 只接 2~3 处 |
| **回滚** | 一处 CSS 规则 = 一行 | 需摘除所有接线点（多处） | 摘除少数接线点 |

### 13.4 架构建议（含理由，非口味）

**选 ① 纯 CSS，并把 U11 定义为「补齐 + 收口」，不引入 ripple。**理由四条：

1. **系统已经建成了**，而且是设计过的（双曲线 + `--state-active` + 已修过的 fill-mode 坑）。推倒换 ripple 是负收益 —— 现在缺的只是 4 处覆盖和 1 条收口纪律。
2. **`touch-action: manipulation` 已经把「跟手」这件事做到位了**（`:471`）。团队要的「YouTube 那种跟手」在本项目里**主要就是按压态即时出现** —— 90ms 曲线 + `scale(0.96)` + `filter` 加深，占击后 ≤16ms 就会看到。ripple 提供的是**装饰**，不是**跟手**。
3. **ripple 与 `overflow:hidden` / 密集 z-index 表的冲突面大于它的收益**。本项目 z 表已排到 68~130（§13.5），插一层 span 要挤进去，风险不对称。
4. **reduced-motion 下 ripple 必须全禁**，等于维护两套反馈；CSS 方案在 reduced-motion 下天然只剩 `filter`（最小可见反馈），正好符合硬约束。

> 若负责人坚持要 ripple 的视觉，**选 ③ 且只接 2~3 处大目标**（路线大卡 `.rc`、底部导航），
> 绝不全量接 —— 全量接就是给每个列表行加一次 DOM 操作 + 一次裁剪排查。

| # | 判据 | 形式（机器可读） |

| **P-1** | 覆盖率：所有「看起来可点」的元素**都有**按压缩放或颜色变化 | `node docs/迭代-导航修复-20261104/scan-click-feedback.mjs src/app/globals.css` 的输出中，**真缺口数 = 0**（允许白名单：`.fav-sheet__scrim`）。<br>⇒ 把当前 4 类真缺口修完后，`resolve-click-tags.mjs` 的「真缺口」段落必须为空 |

| **P-8** | 纪律收口（防回归） | `globals.css` 中 `prefers-reduced-motion` 块**数量不得增加**；形变抑制必须由**单一**规则承载（例如一条 `:where(...):active { transform: none }` 的收口规则），不允许继续「补一处加一块」 |

### 13.7 U11 的一条隐藏风险（必须写进方案）

`prefers-reduced-motion` 的形变抑制目前是**按选择器逐个补**（3 个块，`:541`/`:1755`/`:2707`）。
U11 若给 `.nav-brand` 等加 `transform`，会**扩大**这个洞。⇒ U11 必须**先收口**（P-8），**再补反馈**。
顺序反了会留下 4 个需要各自补 reduced-motion 块的新元素 —— 与题 C 的教训完全同型。

> 这正是本批的第四条「同一概念多处实现」：**反馈通道**（transform / filter / ripple）如果按元素各自实现，
> 就一定会有人只补一半。收口原则与题 C 一致：**一个语义一组参数，差异只允许用"程度"表达**。

### 14.1 原诊断（保留，但补一处关键修正）

**team-lead 已排除的方向**：`MATCH_VEHICLE_ENABLED` 在 v3.8.0/v3.9.0/本次三版都是 `false`（已复核一致）⇒ **不是这三笔引入的回归**。
但「不是这三笔」不等于「不是回归」—— 见 §14.2。

#### 第一层（主因）：速度门用「窗口平均」，且窗口被迫长达 45s

`r2Of` 的速度算法（`boarding-detect.ts:183-189`、`:207`）：

```ts
const disp = Math.abs(cum[i1] - cum[i0]);                   // 沿线位移
const dtSec = (win[win.length - 1].ts - win[0].ts) / 1000;  // 窗口总时长（含静止段）
const kmh = (disp / dtSec) * 3.6;                           // 被静止段稀释
return kmh > vMin && kmh <= vMax;                           // vMin = 8，严格 >
```

**修正：45 秒窗口不是设计者的偏好，而是精度决定的物理下限。**（这是本次重做新增的定量证据）

`useUserFix.ts:187-189` 在 `coarse = true` 时给 `watchPosition` 传
`enableHighAccuracy: false` + `maximumAge: 30_000`；而 `NavShell.tsx:352` 的
`coarse: navActive && ridePhase !== "riding"` ⇒ **整个候车期都是粗定位**。

斜率的信噪比（`SE = σ/√Σ(x−x̄)²`，σ 为定位标准差，3s 一帧，车速 3.33 m/s）：

| 定位方式 | σ | N=5(12s) | N=8(21s) | N=16(45s) |
|---|---|---|---|---|
| 高精度 `enableHighAccuracy: true` | ~10m | **SNR 3.16 ✔** | 6.47 ✔ | 18.4 ✔ |
| 网络定位（当前 coarse 路径） | ~50m | 0.63 ✘ | 1.29 ✘ | **3.68 ✔** |
| 低精度/室内 | ~150m | 0.21 ✘ | 0.43 ✘ | 1.23 ✘ |

⇒ **σ=50m 时必须 45s 才有 SNR≥3**。所以 45s 是「用低精度数据硬凑出来的」，不是算法冗余。
**要提高响应速度，正解是提高精度，而不是缩短窗口。**

推演（$V$ 行驶速度，$D$ 站内静止秒，$M$ 行驶秒）：

```
V=12 km/h D=20s：M 需 > 40s（行程 > 133m）才勉强越线；M=40 时测得 8.00 ⇒ 严格 > 判 fail
V=12 km/h D=40s：M=80s 测得 8.00 ⇒ 仍 fail（行程 267m 才刚触线）
```

#### 第二层（致命）：锁牌只看「当前帧」的 `strong`，窗口仅 1 个 hop

锁牌条件（`boarding-detect.ts:368-380`）：`const lockedPlate = aux.strong ? aux.plate : null;`
`aux.strong` = 存在车 `interval.from` 主码 == 上车站（`:122-124`）。
`interval` 由服务端在 `status === "0"`（已离挂载站、驶向下一站）时给出
（`src/app/api/route-vehicles/route.ts:206-213`）⇒ **下一站一到，`interval.from` 就变**。

**两层拼起来**：`r2Of` 终于通过时（上车后 45~60s），`strong` 往往已过期 ⇒ `plate = null`。
一旦进入 `riding`，`tryAuto` 立刻返回（`useRideTracking.ts:1070`）⇒ 本段内不再有锁牌机会。

#### 第三层：没有第二条补牌通路

- `MATCH_VEHICLE_ENABLED = false`（`match-params.ts:15`）⇒ riding 补牌分支在 `useRideTracking.ts:898` 直接 `return`。
- `pendingPlate` 唯一非 null 赋值在 `useRideTracking.ts:945`，**也在那个被挡住的分支内**
  ⇒ 当前构建下恒为 null，是**死代码**（UI 分支 `NavTrackBar.tsx:164-166` 永不渲染）。

#### 第四层（数据侧放大）

- `aux` 只从 `rankBoardingVehicles` 结果取，而它过滤掉 `status="unknown"`（`track.ts:239`）；
  `unknown` 正是**报站失败**（`route-vehicles/route.ts:204` 初值）⇒ 报站一失败，该车对 `aux` 完全不可见。
- `interval` 需 `next?.staCode` 存在（`route-vehicles/route.ts:211-213`）⇒ 本方向**末站**出发后 `interval=null`，`strong` 恒 false。

### 14.3 重做后的方案：实时判定 + 同帧锁牌

#### 14.3.1 判据：用「相对距离斜率」，不用「用户平均速度」

**核心改变：不再测量「用户自己动得多快」，而是测量「用户与目标车的相对位置是否稳定」。**

设 `u(t)` = 用户投影到 `leg.colored` 的沿线里程，`v(t)` = 目标车投影里程，
定义相对距离 `d(t) = |u(t) − v(t)|`。

| 场景 | `d(t)` 行为 | 斜率 |
|---|---|---|
| **人在站台，车开走** | 单调增大（每帧 +V·Δt） | **≈ 车速** |
| **人已上车，随车走** | 保持稳定（仅 GPS 噪声 + 上下车位置差） | **≈ 0** |
| 车停靠中，人在站台 | ≈0（两者都在站台） | ≈0 —— **与"人在车上"不可分**（见 §14.3.4） |

**为什么用户站内静止时不会被稀释**：因为 `d(t)` 的分母不是「窗口时长」，
而是**车自己的位移**——车在动这个事实由 `v(t)` 的变化提供，与用户是否静止无关。
用户静止 ⇒ `u(t)` 平坦 ⇒ `d(t)` 随 `v(t)` 线性增长 ⇒ 斜率 = 车速 ⇒ 判「未上车」。
用户随车 ⇒ `u(t)` 与 `v(t)` 同步增长 ⇒ `d(t)` 平坦 ⇒ 斜率 ≈ 0 ⇒ 判「已上车」。

**这就是原设计与本方案的本质区别**：原设计问「你动得快吗」（会被静止稀释），
本方案问「你相对这辆车有没有跑掉」（不受静止影响）。

**最小可用窗口（推导）**：
`d(t)` 的斜率用最小二乘估，`SE = σ/√Σ(x−x̄)²`。要求 SNR = V/SE ≥ 3：

| 帧数 N | 窗口（1.5s 帧） | 车位移 | SNR（σ=10m，**定案预期值 · 真机待采**） | 判定 |
|---|---|---|---|---|
| 3 | 3.0s | 10m | 1.41 | ✘ |
| 4 | 4.5s | 15m | 2.23 | ✘ 临界 |
| **5** | **6.0s** | **20m** | **3.16** | **✔ 最小可用（设计基线）** |
| 6 | 7.5s | 25m | 4.18 | ✔ 更稳 |
| 8 | 10.5s | 35m | 6.47 | ✔ |

⇒ **最小可用窗口 = 5 帧 = 6 秒**。**不能更短**：3~4 帧时 SNR < 3，会把「车开走」误判成「人跟上了」（假阳性）。

**为什么 6 秒够而 45 秒不必**：6 秒衡量的是「最近 5 帧的相对距离一致性」，
45 秒衡量的是「45 秒的位移平均速度」。前者不需要大位移来压噪声，
因为**相对距离的变化幅度由车速决定（6 秒 20m），而平均速度的对比量需要用户自己也动**。

**前提（已由负责人定案，不再是待定项）**：候车期改**全程高精度**（I0 定案，见 §14.0）。
⇒ σ≈10m 是**定案预期值（真机待采）**，上表 SNR 在该前提下成立，**5 帧 / 6 秒即验收基线**。
若真机实测 σ 明显大于 10m（如 20~30m），则按上表回推所需帧数（σ 翻倍 ⇒ 帧数约翻倍），
**这不是实现缺陷，而是环境差异**，判据应随实测 σ 标定后再定基线。
反证：若仍走 coarse（σ≈50m），5 帧 SNR 只有 0.63，判据失效（§14.3.1 的三档对比表已量化）。

#### 14.3.2 锁牌与判定同帧完成：可行，已证明

**结论：可行。**证明只需两个不等式：

```
判定窗口 T_detect = 6s（5 帧 × 1.5s）
锁牌条件窗口 T_lock  = 「车已驶离上车站」的持续时间 = 从离站到下车 ≈ 整段乘车（通常 3~40 分钟）
⇒ T_detect (6s) ≪ T_lock（整段）  ⇒ 判定成功那一帧，锁牌条件必然已成立
```

**关键改动：锁牌条件的定义要放宽。** 现状用 `aux.strong`（`interval.from == board`），
其窗口被「下一站到达」截断（1 个 hop）。改为**三条件并集**，任一成立即算「车已驶离上车站」：

| # | 条件 | 来源 | 窗口 |
|---|---|---|---|
| L-a | `v.interval.from` 主码 == `boardMain` | `boarding-detect.ts:122-124` | 1 个 hop |
| L-b | `v.progress.passedIdx >= 0` | 服务端进度模型（`progress.ts`） | **整段** |
| L-c | `v.atStation` 存在且主码 ≠ `boardMain` | `route-vehicles/route.ts:206-209` | 到下一站后 |

取并集后，锁牌条件在**整段乘车期**都成立 ⇒ 与判定的 6s 窗口形成包含关系 ⇒ **同帧锁牌**。

**误锁风险是否增加？** 不增加，因为判定本身（相对距离斜率 ≈ 0）已经保证了「用户确实在跟着某一辆车」。
放宽的只是「用哪一条证据确认车已离站」，不是「是否需要用户跟随」。

**多车消歧**（必须做，否则可能锁到同线的另一辆）：
若同一条线有多辆车同时满足 L-a/b/c，用 `d(t)` 最小者；若两车的 `d` 差 < `2σ`（无法区分）⇒ **不锁牌**（保守）。
这条与 ADR-110 的「单一候选」原则一致。

**最坏延迟（按帧换算）**：

| 组成 | 时长 | 说明 |
|---|---|---|
| 判定确认 | **6s**（5 帧 @1.5s） | §14.3.1 的 SNR 推导 |
| 等一个显示「车已离站」的车辆帧 | **0~12s** | 候车期一直在轮询（`POLL_MS=12s`）；典型 0（上一帧就已离站） |
| **合计最坏** | **18s** | 典型 6s |

对照现状：45~60s 且**大概率锁不到牌**。

#### 14.3.3 90 秒记忆窗口：移除

**移除。**理由按 team-lead 给的两个条件逐条回答：

1. 「证明同帧锁牌在物理上不可能」—— **不成立**，§14.3.2 已证明可行（`T_detect ≪ T_lock`）。
2. 「说明它保护的是哪种即使实时化也无法当场锁牌的情形」—— 无。实时化后，
   判定成功的**那一帧**锁牌条件必然成立，不存在"需要事后补"的窗口。

⇒ 记忆窗口保护的是一个**实时化之后不再存在的问题**。保留它就是无判据的冗余，
且会引入 §14.3.2 提到的「跨班次误锁」风险（同线路后一班车）。

#### 14.3.4 必须承认的物理限制：车停靠站台时不可分

team-lead 要求「若存在不可逾越的物理限制必须明确写出，不要为了迎合而编造可行方案」。有一条：

**当车停靠在用户所在站台时，「人在站台等车」与「人已在车上」在信号上不可分。**

理由：两种情形下 `d(t) ≈ 0` 且都稳定（车停着、人不动或都在车内）。
任何只依赖「位置 + 时间」的判据都无法区分 —— 用户就在车的位置上。
要区分需要额外信号（NFC 刷卡 / 蓝牙 / 加速度计的「上车动作」/ 车内气压变化），**本项目都没有**。

⇒ **「车已驶离上车站」是不可省的必要条件。** 它不是一个保守的额外门，而是唯一能把
「已上车」从「在站台」里分离出来的**事件**。这也是原设计坚持要 `strong` 的物理原因 ——
方向对，只是**窗口取得太窄**（1 个 hop 而非整段）。

**这意味着**：
- 车没动之前（停靠中），系统**必然**无法判定 —— 这是物理限制，不是缺陷。
- 但车一离站，6 秒内就能判定并锁牌（§14.3.1 + §14.3.2）。
- 因此「正常上车必然锁到牌」在物理上是可达成的：正常上车 = 车会离站 = 6 秒后必然判定并锁牌。

**唯一走不到锁牌的分支**（回答 team-lead 第 4 问）：
报站失败（`status="unknown"`）或本方向末站出发（`interval=null`）时，
`aux` 完全看不到该车 ⇒ 无法锁牌。这是**数据缺失**，不是判据缺陷；
承接方式是 B3 的手动候选池（含刚离站车）+ 可观测钩子，不应用猜测补。

### 14.4 验收判据（全部可机器量测，可合成用例断言）

**① 时限（按帧换算成秒，附推导）**

| 指标 | 定义 | 目标 | 推导 |
|---|---|---|---|
| 锁牌延迟 | `t(plate 首次非 null) − t(phase 首次 riding)` | **≤ 6s** | = 5 帧 × 1.5s（§14.3.1 的 SNR=3.16 最小可用窗口），且同帧锁牌 ⇒ 无额外等待 |
| 端到端（从车离站起算） | `t(plate 首次非 null) − t(车离站)` | **≤ 18s** | 6s 判定 + 最多 12s 等一帧显示"已离站"的车辆帧（`POLL_MS`） |
| 正常路径锁牌率 | 自动进 riding 且非冲刺的会话中 `plate != null` 占比 | **≥ 95%** | 剩余 <5% 对应 §14.3.6 的 4 类不可达分支 |

**② 观测钩子（现有不够，必须新增）**

现有 `data-board-match`（`NavTrackBar.tsx:201`）与 `data-match-source`（`:56`）
**无法区分**三种诊断上完全不同的情况：「没机会」/「有机会但没锁上」/「锁上了但 UI 没显示」。
新增（挂在 `.nav-actions`，与既有同级）：

| 钩子 | 取值 | 诊断价值 |
|---|---|---|
| `data-plate-state` | `none \| locked` | 直接回答「有没有牌」 |
| `data-board-evidence` | `slope \| r2 \| station \| none` | 本次判定走的哪条判据（P3 后主力是 `slope`） |
| `data-follow-slope` | 数值（2 位小数，m/s） | **本次根因的直接观测量**：斜率≈0 ⇒ 已上车；≈3.33 ⇒ 在站台 |
| `data-plate-ts` | epoch ms 或空 | 配合 `data-board-auto-ts` 算端到端时延 |

**③ 合成用例（`scripts/test-boarding-detect.ts` 新增，不依赖真机）**

1. **[核心·上车]** 5 帧 `d(t)` = [12, 10, 14, 9, 13]m（斜率≈0）+ 车已离站 ⇒ `hit=true` 且 `plate` 非空（**同帧**）
2. **[核心·站台]** 5 帧 `d(t)` = [10, 20, 30, 40, 50]m（斜率≈车速）+ 车已离站 ⇒ `hit=false`
3. **[不可分]** 车 `atStation==board` + 5 帧 `d(t)` 全 0 ⇒ `hit=false`（§14.3.4 的物理限制，必须如实不判）
4. **[窗口下限]** 只给 4 帧 ⇒ `hit=false`（证明 5 帧是下限，防有人缩到 3 帧引入假阳性）
5. **[锁牌窗口放宽]** 车已过下一站（`interval.from != board`）但 `progress.passedIdx>=0` ⇒ 仍能锁牌
6. **[多车消歧]** 两车 `d` 差 < 2σ ⇒ 不锁牌；差 > 2σ ⇒ 锁 `d` 小的那辆
7. **[P5 可逆]** `onNotBoard` 后剩余自动次数 2→1；用尽后不再解锁；`start()` 重置为 2
8. **[P1 前提]** `accuracy=50m` 的帧不参与斜率估计（σ 过大时判据失效，必须如实拒绝而非硬判）

**④ 误判后可纠正（安全网，不是主路径）**

保留原判据：点「我没上车」→ 点「我已经上车」→ 能从候选池锁到正确车。
断言：`boardMatch` 依次为 `auto → none → manual`，最终 `plate` 等于候选池中被点选的那辆。

M-3/M-4 下批，因为它们降低的是**长尾误判**，而当前主诉是**主路径漏锁**。

**一条必须写进 Spec 的连带影响**：M-1/M-2 会**改变 `r2Of` 的通过时机**（提前），
⇒ §10 的 limit 量测与 ADR-110 的误判率基线**必须在 M-1/M-2 之后重新采**，
否则基线是两个不同判据下的数，不可比。

## 15. 一句话交底

题 A 与题 B 是同一个病：**同一个概念有两条实现，在切换点没有对齐** —— A 是「剩余时间」有两个口径（首跳 vs 整段），且停靠时基准站错位一档（漏掉一跳）；B 是「我坐的是哪辆车」有两条通路（自动 vs 手动）且互相把对方关掉。题 C 不是病，是产品口径与设计口径没对齐（已由 designer 定案：未走收敛为一组参数，差异只留方向箭头）。三者的修法都不需要新架构，只需要把「单一真相」这条纪律在三个点上各落一次 —— 而推荐页那个「点第 6 张没反应」的 P0，是同一纪律在第四处的欠账（limit 9 处独立实现）；U11 的点击反馈是第五处（按元素各自补 `:active` / 按选择器各自补 reduced-motion）。

**I-3（新 P0）是同一病灶的第六处，也是最隐蔽的一处**：`r2Of` 与 `aux` 都在 `autoBoardOf` 里，
看似「同一帧、同一份数据、同一次判定」，实际一个用**回看 45s 的窗口平均速度**、一个用**当前瞬间的车站挂载状态** ——
**同一个函数里藏着两个时间基**。于是「判定发生了」与「锁得上牌」被拆成了两件时机不同的事，
而唯一补救通道（match）常年关闭、`pendingPlate` 是死代码 ⇒ 错过一次就是本段永久无牌。
修它不需要新算法，只需要让「锁牌证据」和「判定证据」共享同一个时间基（P0-1 锁存 + P0-2 恢复 weak 锁牌权）。
