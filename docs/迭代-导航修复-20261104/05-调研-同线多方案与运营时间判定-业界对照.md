## 0. 结论摘要

| # | 结论 | 强度 |
|---|---|---|
| 1 | **没有任何一家把「不在运营时间的线路」与可乘线路并列展示。** 高德用 `nightflag=0` 默认不计算夜班车 + `date`/`time` 按时刻筛；Google 按 `departure_time`/`arrival_time` 求解；Citymapper FAQ 直接把「你查的时段公交不在运行」列为查不到结果的第一位成因。 | 三家官方文档 |
| 2 | **「多线并列」发生在「段内」，不发生在「方案级」。** 高德的 `segments[].bus.buslines[]` 是**数组**（同段多线），但方案本身 `transits[]` 仍是「一方案一上下车点」；Google 的 `transit_details.line` 是**单值对象**，多线走多条 itinerary。 | 两家官方文档 |
| 3 | **「同线多班次」放在同一方案内展示**，不新开卡：Google 在站名下方写「Also at 1:30 PM & 2:15 PM」，可展开 `More departures`。这与本项目 `altBuses` 的设计方向一致。 | Google 帮助中心 |
| 4 | **「首末班」的正确粒度是「上车站」，不只是线路两端。** 高德同时给 `start_time`/`end_time`（线路级）与 `station_start_time`/`station_end_time`（**上车站点级**）。 | 高德官方文档字段表 |
| 5 | **Apple 无法在 API 层对照**：MapKit JS 的 `TransportType` 只有 `Walking / Automobile / Cycling`，**没有 Transit**。Apple 的公交能力只对消费者 App 开放，不对外提供公交路径规划接口。因此 Apple 只能做「界面层观察」，且公开文档未说明「同站多线是否并卡」。 | Apple 官方文档（字段枚举）+ 判断 |
| 6 | **「卡级跨下车站合并」在 5 家里找不到先例。** 5 家全都在「方案级」保留唯一上下车点。本项目若做卡级合并，是全自担设计风险。 | 综合 |

**一个必须先说明的方法论限制**：5 家的「卡片怎么排版」大多属于**界面实现细节**，厂商只在开发者文档里公开**数据结构**，不公开「是否把 A 线和 B 线放进同一张卡」。因此本文把三问拆成两层回答：

- **数据层**（有官方文档，可逐字引用）：接口返回的结构决定了「能不能并卡」的上限；
- **界面层**（多数只能观察/二手，标 `[未验证]`）：实际渲染成什么样。

对负责人决策真正有用的是**数据层**——因为我们自己的实现也必须先有数据结构，才谈得上界面。

## 2. 逐家对照

### 2.1 高德地图（公交路径规划 Web 服务 API）

**① 同一上车点有多条可乘线路：段内并列（数组），方案级不合并。**

来源：`[官方文档]` 高德开放平台 · 路径规划 <https://lbs.amap.com/api/webservice/guide/api/direction>

返回结构（原文层级）：

```
route.transits[]            ← 公交换乘方案列表（每项 = 一个方案）
  └ segments[]              ← 换乘路段列表（每项 = 一段）
      └ bus.buslines[]      ← 公交方案信息列表（数组 ⇒ 同段可多条线）
```

关键原文（「公交方案信息列表」一节字段）：

| 字段 | 原文含义 |
|---|---|
| `buslines` | 「步行路段列表」（原文如此，实为公交线路列表） |
| `departure_stop` / `arrival_stop` | 「此段起乘站信息」/「此段下车站」 |
| `name` | 「公交路线名称，格式如：445路(南十里居--地铁望京西站)」 |
| `start_time` / `end_time` | 「首班车时间」/「末班车时间」 |
| `station_start_time` / `station_end_time` | 「上车站点首班时间」/「上车站点末班时间」 |

⇒ **结论**：`buslines` 是数组 ⇒ 同一段（同起乘站）可以并列多条线路；但 `transits[]` 每个方案只有一个 `departure_stop` / `arrival_stop` ⇒ **方案级不合并**。

**② 同一条线多个站点都能下车：由请求策略决定，不是并行穷举。**

请求参数 `strategy` 原文枚举：`0` 最快捷 / `1` 最经济 / `2` **最少换乘** / `3` **最少步行** / `5` 不乘地铁。
⇒ 高德是「**按策略求一个解**」，而不是「把所有下车点各展开一个方案」。这一点与本项目 `enumerate.ts:265-266`（每个下车候选各展开一条独立方案）**方向相反**——本项目是穷举，高德是择优。

**③ 不在运营时间：三重机制，全部偏向「不显示」。**

| 机制 | 原文 |
|---|---|
| `nightflag` | 「是否计算夜班车，可选值：0：不计算夜班车；1：计算夜班车」，**缺省 0** |
| `date` | 「根据出发时间和日期，筛选可乘坐的公交路线，格式示例：date=2014-3-19」 |
| `time` | 「根据出发时间和日期，筛选可乘坐的公交路线，格式示例：time=22:34」 |
| 事件标签 | `emergency.eventTagDesc` 取值含「提示」「甩站」「突发」**「停运」** |

⇒ **结论**：高德 `nightflag` **默认关闭**，等于承认「夜班线不该混进白天方案」是行业默认；且它给「停运」留了**独立事件通道**（既不静默消失，也不混在正常线路里）。

### 2.2 Google Maps（公共交通 / Directions）

**① 同一上车点多条线路：不并进一个 step，走多条 itinerary。**

来源：`[官方文档]` Directions API（Legacy）参数页 <https://developers.google.com/maps/documentation/directions/get-directions>；结构字段见同站 `responses#DirectionsTransitDetails`。

- 原文（参数页）：「`transit` requests directions or distance using public transit routes (where available). If you set the mode to transit, you can optionally specify either a `departure_time` or an `arrival_time`.」
- 结构：`routes[] → legs[] → steps[]`，`transit_details` 内的 `line` 是**单值对象**（非数组）。⇒ 一个 transit step 只能表达一条线路。
- `[未验证]` 界面层：Google 地图结果页是否会把同站多线合并为一张卡，官方文档未说明。按数据结构推断，**多线必然表现为多条 itinerary**。

**② 同一条线多个站点都能下车：靠时刻求解 + 单一下车点。**

原文：`departure_time` = 「Specifies the preferred time of departure for transit directions, in seconds since midnight, January 1, 1970 UTC.」；不能与 `arrival_time` 同时指定。
⇒ 与高德同构：**按时刻求一个解**，方案里只有一个 `arrival_stop`。

**③ 不在运营时间：时刻不成立就不进结果。**

- 机制：按 `departure_time` 求解 ⇒ 该时刻没有班次的线路天然不进候选。
- 无固定时刻表时给 `headway`（秒）而非具体时刻（结构字段，`[官方文档]` 字段存在，本页未逐字描述）。
- **班次不新开卡**：`[官方文档]` Google 地图帮助 <https://support.google.com/maps/answer/6142130> 原文：「Under your departure station name, you'll find up to two later departure times, if available. For example, you might find 'Also at 1:30 PM & 2:15 PM'.」并可「tap `More departures`」。
  ⇒ **后续班次放在同一方案内**，这正是本项目 `altBuses` 的设计方向。

### 2.3 Citymapper

**① / ② 同站多线 / 多下车站：`[未获取到公开资料]`（实现层）。**

Citymapper 自研路由引擎，不对外提供 API，帮助中心只说明「We use our own routing algorithms for transit, walking and multimodal」，未公开方案组织方式。

可用的间接证据：`[二手]` 评测（<https://localsinsider.com/apps/get-around-with-citymapper-the-public-transit-app-reviewed/>）描述结果为「every plausible route, ranked by total journey time」，并提供偏好：`Walk less`（少走路）/ `Simple route`（最少换乘）/ `Turbo`（最快）/ `Rain-safe route`（雨天覆盖）。
⇒ 与高德 `strategy` 同构：**同一批候选，按偏好择优排序**，而非把下车点穷举成多张卡。

**③ 不在运营时间：直接无结果，并明确写在 FAQ 第一位。**

`[官方文档]` Citymapper FAQ <https://citymapper.com/i/141/frequently-asked-questions> 原文（"I don't get any results!" 一节）：

> 「You're searching at a time of day when transit is not running (e.g. late at night). If you change the arrival time, you should see results.」

⇒ 这是**最强的一条旁证**：行业头部产品把「非运营时段不显示」当成理所当然，以致它被写进「为什么查不到」的排查清单第一条。

**补充（可借鉴点）**：`[官方文档]` 产品公告 <https://citymapper.com/news/2838/citymapper-now-uses-ai-powers-to-help-you-choose-the-best-route> 说明其推荐理由**显式包含**「tight transfers（换乘太紧）」与「route frequency（班次频密程度）」——把「班次密度」当作可解释的推荐维度，而不只是内部排序因子。

### 2.4 Moovit

**① / ② 同站多线 / 多下车站：`[未获取到公开资料]`（实现层）。**

`[二手]` 使用指南（<https://fatofoco.com/en/moovit-veja-como-usar-o-app-para-planejar-trajetos>）：「The app may present alternatives with different combinations of lines and walking distances」，并提醒用户核对「the line name or number, the vehicle's direction, and the boarding location」——说明**方向与上车站是方案身份的一部分**（与本项目 `route + board + alight` 四元组同思路）。

**③ 不在运营时间：不隐藏，而是打标签说明。**

`[官方文档]` Moovit 帮助中心 <https://support.moovitapp.com/hc/en-us/articles/35543186031634-Moovit-Assistant-Smarter-Trip-Planning-Than-Ever-Before> 原文，Trip Insights 标签包括：

> 「Additional insights: "Last trip of the day," "Earliest arrival," "Minimal walking," and more.」

⇒ **这是 5 家里唯一把「末班」做成显式信息的**。它不是「显示一条已收班的线」，而是「在可乘范畴内，告诉你这是今天的最后一班」。

**这条对本项目有直接价值**：我们现在对末班**零表达**——要么有车照常显示，要么无车静默剔除。用户的痛点是「不知道还有没有末班」，而 Moovit 证明了这是个值得单独说的信息。

### 2.5 Apple Maps

**API 层事实（关键，可逐字引用）**

`[官方文档·字段枚举]` MapKit JS `TransportType` <https://developer.apple.com/documentation/mapkitjs/transporttype>

官方枚举的 Topics 只有三项：

> 「**Walking** — A constant identifying the mode of transportation as walking.
> **Automobile** — A constant identifying the mode of transportation as driving.
> **Cycling** — A constant identifying the mode of transportation as cycling.」

⇒ **MapKit JS 没有 Transit 模式**。Apple 不对外提供公交路径规划接口（iOS 原生 `MKDirections` 有 `.transit`，但那是 App 内 SDK，不是 Web/PWA 可用的服务）。

**因此对三问的回答**

| 问题 | 回答 | 说明 |
|---|---|---|
| ① 同站多线是否并卡 | `[未验证]` | 只能界面观察。`[二手]` iMore（<https://www.imore.com/how-find-best-transit-route-apple-maps-iphone>）原文：「whenever multiple options are available, you'll see all of the possible route suggestions」——**"multiple options" 指多个方案卡片**，不是卡内多线并列。这是间接旁证：Apple 走的是「多方案」路线 |
| ② 同线多下车站是否出多方案 | `[未验证]` | 公开文档未说明 |
| ③ 不在运营时间 | `[未验证]`（界面层） | `[二手]` 观察：仅有时刻表的站点「shows times in light gray」，有实时数据的站点「in bold with a small lightning-bolt indicator」（<https://iphonefilez.com/maps-mass-transit-info-iphone.html>）。即 Apple 用**视觉强弱**区分「静态时刻 vs 实时」，但未见「停运」标注的公开说明 |

**诚实结论**：Apple 只能作为**界面风格参考**（用视觉强弱表达数据可信度），**不能作为数据结构参考**，因为它不开放接口。

## 3. 对照表（5 家 + 本项目现状）

| | ① 同上车点多条可乘线路 | ② 同线多个下车站 | ③ 不在运营时间的线路 |
|---|---|---|---|
| **高德** | **段内并列**：`segments[].bus.buslines[]` 是数组；方案 `transits[]` 仍一方案一上下车点 | **按策略择优**（`strategy=0/1/2/3/5`），不穷举；每方案单一下车点 | **三重机制**：`nightflag` 缺省 0 不算夜班；`date`/`time` 按时刻筛；`eventTagDesc` 含「停运」独立通道 |
| **Google Maps** | **不并卡**：`transit_details.line` 单值；多线走多条 itinerary | **按时刻求解**（`departure_time`/`arrival_time`），方案内单一下车点 | 时刻不成立不进结果；无表时用 `headway` 表达班距 |
| **Citymapper** | `[未获取到公开资料]`；自研引擎不开放 | `[未获取到公开资料]`；有 `Walk less`/`Simple route` 等偏好择优 | **直接无结果**，FAQ 明写「非运营时段查不到结果」 |
| **Moovit** | `[未获取到公开资料]`；方案含「线路 + 方向 + 上车站」三要素 | `[未获取到公开资料]` | **不隐藏，打标签**：`"Last trip of the day"`、`"High frequency"` |
| **Apple Maps** | `[未验证]`；旁证支持「多方案卡片」而非卡内并列 | `[未验证]` | `[未验证]`；用「浅灰 vs 加粗+闪电」区分静态/实时 |
| **本项目现状** | **段内并列**（`parallelRoutes`，`RecommendCard.tsx:133`，≤3 条 + `+N`，`RouteStack.tsx:28`）——**但不过滤运营时间**（bug） | **穷举多方案**（`enumerate.ts:265-266` 每个下车点各展开一条），仅靠 `STOP_PRIORITY` 两组硬编码互斥（`enumerate.ts:175-188`） | **两层分裂**：方案层已隐式剔除（`model.ts:468-488`、`:506-511`）；**标签层完全不过滤**（这是用户报的 bug） |

**读表可得的三个差异点**

1. **② 这一列，本项目与所有 5 家都相反**：我们是**穷举**，他们是**择优**。这不是「我们更全」，而是我们的候选池没有排序压力下的收敛机制，于是同一条线会用多个名额说同一件事。
2. **③ 这一列，本项目的问题是「两层分裂」**：方案层守住了，标签层漏了。5 家没有任何一家出现这种分裂，因为它们的「线路」只有一处数据源。
3. **① 这一列，我们的结构是对的**（段内并列），缺的只是过滤条件——**不需要推翻重做**。

## 4. 可借鉴与不可借鉴

### 4.1 可借鉴（在我们的产品形态下可行）

| 做法 | 为什么可行 | 落地提示 |
|---|---|---|
| **段内多线并列**（高德 `buslines[]` 同构） | 我们已有 `RouteStack` 的斜切块 + 负空间缝 + `+N` 折叠（`RouteStack.tsx:87-104`），无需新增 UI 元素 | 只需加「可乘性」过滤（PRD §3.3） |
| **后续班次留在同一方案内**（Google「Also at …」） | 我们已有 `altBuses`（`types.ts:715-731`） | 不新增卡片；建议加每卡条数上限（PRD §5.3） |
| **`nightflag` 式「夜班线不混进白天」**（高德缺省 0） | 我们的 `route_frequency.day_type` + 时间窗已是同构数据 | 用 `serviceStateAt` 判定，不需要新表 |
| **「首末班」做到上车站粒度**（高德 `station_start_time`） | 我们的 `route_frequency` 只有线路级时间窗，但**用户实际关心的是「我这站还有没有车」** | 短期用「线路窗口 + 末班宽限 20 分钟」近似；长期可考虑按站推首末班（另开需求） |
| **「末班」做成显式信息**（Moovit `Last trip of the day`） | 用户痛点真实：现在对末班零表达 | 属**独立增强**，不阻塞本批；但值得进 Backlog |
| **「停运」留独立通道**（高德 `eventTagDesc`） | 比「静默消失」更诚实：用户知道为什么没有 | 对应我们的 `skipped_by_schedule` 诊断位 |
| **用视觉强弱表达数据可信度**（Apple 浅灰 vs 加粗） | 我们已有「估」字标记（`.rc-val--est`）与 `estimated` 字段 | 方向一致，不必改 |

### 4.2 不可借鉴（产品形态不匹配）

| 做法 | 为什么不可行 |
|---|---|
| **按偏好「择优求一个解」**（高德 `strategy` / Citymapper `Turbo`） | 我们是**本地枚举 + 全量排序**（`enumerate.ts` → `sortCards`），把「下车点」交给求解器择优意味着放弃「把选择权摆给用户看」。好处是卡少；代价是**用户看不到被舍弃的那个下车站**，与我们「卡片式三档面板 + 详情页备选下车点」的形态冲突。可作为**收敛规则**（R2）借用其思想，但不整体照搬 |
| **按时刻重新求解**（Google `departure_time`） | 我们是实时流（DSAT 报站），不是时刻表求解；重算成本高且与「10 秒缓存」架构冲突 |
| **Apple 的接口层能力** | MapKit JS 无 Transit 模式，无法对照实现 |
| **行程历史驱动的个性化推荐** | 本项目**无用户账户、无行程历史**（PWA + 匿名），Citymapper/Moovit 的「Personalized Route」类能力不可做 |
| **「AI 解释推荐理由」**（Citymapper/Moovit 的 insight 标签） | 需要额外算力与文案体系；本批目标是修 bug，不应打开新战线 |

## 5. 给负责人的建议（两方案并排，含工程代价）

> **✅ 本节已结案（2026-11-04）**：负责人拍板 **「一卡一个下车点」= 方案 A**。
> 本章保留 A/B 并排代价，**目的已从「供选择」变为「供追溯」**——防止同一诉求（"把同一站的车合起来"）日后被重新提出而无据可查。执行细节见 PRD `01-PRD-推荐页合并与运营时间判定.md` §4.4–§4.5（R1–R4 已成正式编号规则）。


### 5.1 方案 A · 段内并列 + 卡级不合并 + 下车站收敛（我推荐）

| 维度 | 内容 |
|---|---|
| 卡片粒度 | 一张卡 = `(首段线路, 上车站, 下车站)`；**同一趟车只出 1 张卡** |
| 同站多线 | 段内并列（`mainCodeOf(board)` 与 `mainCodeOf(alight)` 都相等 + 该线可乘 + ≤3 条） |
| 同线多下车站 | **收敛**：同线同站最多 1 张卡，代表下车站取当前偏好档 `cost` 最小者；其余进详情页「备选下车点」 |
| 不在运营时间 | 五态判定（`open/closing/closed/before_first/no_data`）× 有车三态；隐藏当且仅当「不在窗口 ∧ 无车」 |
| **与业界一致性** | ①③ 对齐高德/Google/Citymapper；② 是「借用高德的择优思想做收敛」，但**保留用户可见的选择权**（详情页仍有备选） |
| **工程代价（小）** | 详情页四元组契约 `planId+route+board+alight` **不变**（`card-link.ts:6-8`）；`/api/card` 命中判据不变（`card.ts:89-93`）；不新增 UI 元素 |
| **代价与风险** | ① 收敛规则要与偏好档耦合（`score.ts:158-186`），必须写清「代表下车站按当前档选」；② 被收敛的下车站必须仍可见（走 `alightCandidates`，`types.ts:882`）；③ 折叠栏现在取下车站首选项（`card.ts:157`），收敛后可能不一致，需同批修 |
| **卡数变化** | 会**减少**（同线不再占多张），与「5 改 6」的诉求不冲突——6 个名额装的是 6 条不同路线，而不是 6 个下车点 |

### 5.2 方案 B · 按上车站合并（用户概念约定的字面实现）

| 维度 | 内容 |
|---|---|
| 卡片粒度 | 一张卡 = **一个上车站**，卡内并列该站所有可乘线路 |
| 卡标题 | 「{站名} · {N} 条线路」，副标题给最快一条的到达时刻 |
| 下车站不同 | 卡内**逐线**各带下车站与到达时刻；必须把「下车 · X」与「上车到下车 X 分」这两个**卡级单值字段下沉到每条线** |
| **工程代价（大，架构师已确认）** | **详情页四元组定位契约失效**：`RecommendCard` 的 `buildCardHref` 依赖 `planId + route + board + alight` 作为**唯一身份**（`card-link.ts:6-8`）；卡内多下车站 ⇒ 一张卡没有唯一 href ⇒ `/api/card` 的 `find` 判据（`card.ts:89-93`）必须重写，`route_changed` 语义随之改变 |
| 附加代价 | ① 「上车到下车 X 分」由 `RecommendCard.tsx:140-144` 汇总卡级 rides，卡内多线时该数字失去意义；② `altBuses` 的阈值是「不差于第 N 张卡」（`service.ts:153-164`），卡内多线后「第 N 张」的分母模糊；③ 折叠栏每条线下车点取首选项（`card.ts:157`），会与卡内其他线冲突 |
| **好处** | 卡数最少；与用户口头的「合并」概念最贴合；同站候车场景（「我到站了，看这个站还有什么车」）体验最直观 |
| **风险** | 修 bug 的批次里做一次「方案抽象层重构」，回归面覆盖 `/recommend` + `/card` + `/nav` 三条链路的定位逻辑 |

### 5.3 并排对比（给负责人选）

| 判断维度 | 方案 A | 方案 B |
|---|---|---|
| 解决「早上显示 N3」 | 解决（靠可乘性过滤） | 解决（同靠过滤） |
| 解决「同线上车站同但下车站不同 ⇒ 详情矛盾」 | **从根上避免**（卡级不合并） | **必须重写详情定位契约** |
| 解决「同一条线出现在多个方案里」 | 解决（收敛 R2） | 部分解决（卡内仍多下车站，只是不占卡位） |
| 业界先例 | 有（高德/Google 段内并列 + 方案单一上下车点） | **无**（5 家全在方案级保留唯一上下车点） |
| 详情页唯一 href | **不需要改** | 需重写 |
| 工作量 | 小（1 处过滤 + 1 处收敛 + 1 个纯函数） | 大（卡结构 + href 契约 + 折叠栏 + `altBuses` 分母） |
| 用户可见变化 | 卡片变少、标签更准 | 卡片大幅变少、单卡变长 |
| 失败模式 | 收敛规则选错代表下车站（可见、可改） | 详情页点不进去 / 点进去内容对不上（**不可见、难发现**） |

### 5.4 我的建议（**已采纳为最终方案**）

**选方案 A。** ✅ 负责人 2026-11-04 已拍板采纳。三条理由按权重：

1. **「在哪站下车」不改变「上哪辆车」**——这是产品事实，不是实现细节。既然不改变上哪辆车，就不该消耗卡片名额（A 的收敛），但也不该被塞进同一张卡强行解释（B 的合并）。
2. **A 的失败模式是可见的，B 的是隐形的。** A 若收敛错代表站，用户看卡面就能发现「这站下车更远」；B 若 href 契约破了，表现为「点了没反应」——这正是本批要修的 P0 同类问题（点第 6 张卡没反应）。**在修 bug 的批次里引入同类隐性失败，风险不对称。**
3. **A 不新增 UI 元素。** 段标签形态、`+N` 折叠、hover 全名都是现成的（`RouteStack.tsx:87-104`）；B 需要新的「卡内多线下车站」表达，属新设计。

**但我把 B 的合理内核吸收了**：B 想解决的「到站候车」场景（我到站了，看这站还有什么车）确实真实存在——这个需求**不该靠推荐卡解决，应该靠站点详情页**（`station-routes.ts` 的 `reachableFrom` 已在做这件事，`card.ts:154-158` 的折叠栏就是它的落地）。⇒ 建议：**保持 A 的推荐卡，把「同站多线」的表达压力交给站点/详情页**。这样两件事各归其位。

**关于 B 方案（已否决，前置条件保留备查）**：若日后有人重提 B，前置条件必须写清（否则会在验收时炸）：
1. 先重构「卡级单值字段」（下车行、上车到下车时长、`altBuses` 阈值分母）；
2. 先定义「一张卡的唯一身份」是什么（不能再是四元组）；
3. 这三件事是一次**独立的、有规格的重构**，不应与本批 U8/U9 修复混在一起。
