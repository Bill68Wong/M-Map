# Spec · M Map 导航与推荐页十项修复

> 生成日期：2026-11-04
> 基于：01-PRD-推荐页合并与运营时间判定 + 02-技术-根因与方案 + 03-设计-导航信息层与步行线规范 + ADR-109/110/111
> 状态：**待负责人确认**

---

## 1. 产品定义

- **一句话描述**：M Map 是澳门通勤与全澳导航 PWA，覆盖 92 条巴士线 + 3 条轻轨线，用 DSAT 官方公开资料 + 高德路网，为通勤者推荐最省时的路线并在乘车途中实时跟踪进度。
- **目标用户**：澳门本地通勤者（含跨区上学、跨岛通勤），以手机竖屏单手使用为主。
- **核心问题**：本次修的是「看起来在跑、实际算错或显示错」这一类缺陷——时间数据在状态切换时突变、进度文案指向错误的量、自动判定无法纠正、推荐页把不在运营时间的线路当作可乘、同一段步行路出现两种绿色。

## 2. 范围（锁定 · 本次只做这十条）

| # | 需求（负责人原话要点） | 已锁定的口径 | 优先级 |
|---|---|---|---|
| 1 | 步行路线一段深绿一段浅绿，要求不管外部道路还是内部小路都正常显示 | 已走=灰色保持不变；**未走=统一一种绿**，两种绿属缺陷 | P0 |
| 2 | 「怎样能赶上」标签：应在上车时隐藏。第一次做成全删、第二次做成全恢复，两次都不对 | 按状态机 + **单向锁存**，进过乘车态即永久隐藏，唯一复位=「我没上车」 | P0 |
| 3 | 刷新后的时间数据有错：站间行驶↔进站切换时预计时间突变 | 剩余 = 首跳剩余 + 后续静态跳；停靠显式给 0；**相邻两次刷新差不超 0.25 分** | P0 |
| 4 | 「车上约几分」现在算的是到下一站，应该是到下车时长 | 全界面时间数字统一=**到下车（终点）时长** | P0 |
| 5 | 上车前/上车后两套信息行布局（详见 §9 AC-05） | **巴士卡**定高 52px 两态共用零跳动；**轻轨卡** `pre` 最小 52、可长高（≤132），`post` 钉 52 | P0 |
| 6 | 上车判定只看人不看车，希望「车到站 + 人在站」也参与 | **两段式**：到站记录（不切换）→ 离站确认（才切换），守坐标系 | P1 |
| 7 | 赶车冲刺被提前判上车，真上车后绑不上车牌，点「我没上车」再点「我已上车」也找不到车 | 三条同做：候选池 + 可逆 + 上限 2 次 | P0 |
| 8 | 早上显示 25/N3，N3 不在运营时间不该出现 | **不在运营时间 且 无车**才隐藏；末班宽限 20 分钟 | P0 |
| 9 | 决定线路合并条件与单线显示方案，避免同线多处出现、上下车站矛盾 | 只保留「段内并列」一级，**不做卡级跨下车站合并** | P0 |
| 10 | 路线推荐数量由 5 增到 6 | **卡片张数**（limit 默认值）5→6，**两个入口都改**（负责人 2026-11-04 拍板）；卡内并列条数不变 | P1 |
| **U11** | 全项目用户操作点击体验升级，参照 YouTube 触摸反馈，点击任何按钮都要有舒适反馈 | 设计系统 Token 化 + 分档反馈 + `prefers-reduced-motion` 降级；**不引入新依赖** | P1 |

> **编号约定（全文档统一）**：U1–U10 = 负责人原列十条；U11 = 本轮追加的点击体验升级；I-1 / I-2 = 团队在调研中发现的内部需求（末班车刚驶过用户站被误判无车、AC-95 回归护栏），不占用 U 编号。
> 负责人所说的「需求 11（对照核验）」= §9 的 AC 全量逐条核验，本身不是功能需求。

## 3. 明确不做（Out-of-Scope · 锁定）

| 不做 | 原因 | 何时考虑 |
|---|---|---|
| 统一里程轴（`route_station_mileage` + `buildLrtLadder` 同构） | 是本批时间方案的**严格超集**，不返工；且会动到投影口径，风险与收益不匹配 | 下一批（ADR-109 后续项） |
| 开启 `MATCH_VEHICLE_ENABLED` | 误锁代价与本批目标相反，需几何版本一致性保证 | 待专项评估 |
| 卡级跨下车站合并（一张卡里放两个下车站） | 卡面下车行与「上车到下车 X 分」是卡级单值，一旦并列必打架；详情页定位是 `planId+route+board+alight` 四元组，多下车站没有唯一 href；**行业无先例** | 不计划 |
| 上车后「本班已赶上」常驻替代形态 | 底部状态行 + 纵条已闭环，常驻会与本次要修的「上车后还看得见标签」混淆 | 有用户反馈再议 |
| 步行线用虚线/新色区分内部小路 | 虚线已被否；更淡会退回本次缺陷；新色违反色彩体系 | 不计划 |
| 改 `progress.ts` 的 `status !== "moving"` 排除逻辑 | 该排除本身正确，错在下游把它当「整段剩余」 | 不计划 |
| 轻轨剩余时间精度提升 | 轻轨无 `segRemainSec`，需统一里程轴 | 下一批 |
| 改既有常量（速度门 8km/h、位移门 60m、45s 窗口） | 已被双向实测，不动 | 不计划 |
| U11 引入 ripple 类 npm 依赖 | 本批不加依赖；且第三方 ripple 与既有 `overflow:hidden` 容器、地图手势易冲突 | 不计划 |
| U11 扩展到全站视觉重设计 | U11 只做「按下反馈」这一件事，不改配色/排版/图标体系 | 不计划 |

## 9. 验收标准（EARS · 逐条核验依据）

> 本节就是负责人所说「需求 11」的实际内容：AC-01~AC-10 与需求 1~10 一一对应，改完逐条打勾，未覆盖的必须写明。

| 编号 | 对应需求 | EARS 验收标准 | 优先级 |
|---|---|---|---|
| **AC-01** | 1 | **While** 导航步行段渲染中，**所有**「未走」折线的 `(color, opacity, weight)` 三元组**必须完全一致**；接缝两侧不得出现差异 | P0 |
| **AC-02** | 1 | **If** 任意两条未走折线在端点相接，**则** 接缝处不得因线帽圆角/叠绘产生可见的深色圆点（`lineCap:"round"` 的 7px 叠加为已知放大器） | P0 |

## 16. U6/I-3 车牌锁定的最终方案（定案 · 供实现直接依据）

### 16.1 真正的根因（三轮排查后定论）

**不是算法保守，是候车期定位被降级。** `NavShell.tsx:352` 的 `coarse: navActive && ridePhase !== "riding"` ⇒ 整个候车期 `enableHighAccuracy: false` + `maximumAge: 30s`（`useUserFix.ts:187-189`）。粗定位 σ≈50m，要在该噪声下算出「是否在移动」需 SNR≥3 ⇒ **45 秒是物理下限**（高精度 σ≈10m 时只需 5 帧 6 秒）。

叠加第二处断裂：判定用 45s 窗口的**平均位移速度**（用户站内静止时被稀释），锁牌用**当前瞬时**的 `aux.strong`（仅「车刚离站」的一个 hop 有效，约 45s）⇒ **判定通过时锁牌窗口已关闭**，且进 riding 后 `tryAuto` 立即返回，本段再无机会。

推论（解释所有现场现象）：
- **正常上车**必然经历站内静止 ⇒ 必然被稀释 ⇒ 必然错过锁牌窗口；
- **赶车冲刺**全程在动、无稀释、车又刚离站 ⇒ 反而更容易锁上（这是「异常路径比正常路径更灵」的原因）；
- `MATCH_VEHICLE_ENABLED = false` 使补牌分支（`:898`）直接 return ⇒ `pendingPlate` 的唯一赋值点（`:945`）在该分支内 ⇒ **当前构建下是死代码**。

### 16.2 定案方案（四件，按序实施）

| 编号 | 内容 | 回滚 |
|---|---|---|
| **I0** | `coarse` 去掉候车期条件 ⇒ **全程高精度**；`gpsIntervalMs` 不变（riding 1.5s / navActive 3s） | 1 行 |
| **I1** | 判据改为**相对距离斜率**：`d(t)=\|u(t)−v(t)\|`（用户与服务车各自沿线里程之差的绝对值），拟合最近 5 帧斜率 `k`；`k≈0` ⇒ 已上车随车走；`k≈车速` ⇒ 人在站台。**分母是车自己的位移，不是窗口时长**，故不受用户静止稀释 | 纯函数切换 |
| **I2** | 锁牌条件由单点放宽为**并集**：`interval.from==board` ∨ `progress.passedIdx>=0` ∨ `atStation!=board` ⇒ 覆盖整段乘车 ⇒ 与 6s 判定窗口形成包含关系 ⇒ **同帧锁牌** | 1~2 行 |
| **I3** | `boarding-detect.ts:184` 的 `Math.abs` 改带符号 + 单调前移校验（消「反向也算移动」漏洞） | 1 行 |
| **I4** | `onNotBoard` 由「永久关闭自动判定」改为「本腿剩余 2 次 + 20s 冷却」 | 1 行 |

**记忆窗口（原 90s `STRONG_SEEN_TTL`）已删除**：其保护的场景在同帧锁牌下不再存在，保留反而引入「跨班次误锁」风险。

### 16.3 不可逾越的物理限制（如实登记，不得算作缺陷）

车停靠在用户所在站台时，「人在站台等车」与「人已在车上」信号上不可分（`d(t)≈0` 且都稳定）。要区分需 NFC/蓝牙/加速度计动作识别/车内气压，**本项目均不具备**。
⇒ 「车已驶离上车站」是唯一能把二者分离的事件，**不可省**。但这不妨碍「正常上车必然锁到牌」——正常上车意味着车会离站。

不再覆盖的 4 类（均非判据缺陷，且打开 `MATCH_VEHICLE_ENABLED` 也修不了）：
1. 车停站台不动（塞车）—— 物理不可分，但不误判，车一动即可判；
2. 报站失败 `status="unknown"` —— 数据缺失；
3. 本方向末站出发 `interval=null` —— 数据缺失；
4. 同线多车且距离差 <2σ —— 主动保守，不猜。

### 16.4 验收判据（可合成用例断言）

| 指标 | 目标 |
|---|---|
| 锁牌延迟（riding → 车牌出现） | **≤6s** |
| 端到端（车离站 → 车牌出现） | **≤18s** |
| 正常路径锁牌率 | **≥95%** |

新增观测钩子：`data-plate-state ∈ {none,locked}` · `data-board-evidence ∈ {slope,r2,station,none}` · `data-follow-slope`（数值，m/s —— 本根因的直接观测量，≈0 表示已上车）· `data-plate-ts`。

必测合成用例（8 条，摘要）：5 帧 `d` 平稳 + 车已离站 ⇒ 同帧 `hit && plate`；5 帧 `d` 线性增长 ⇒ `hit=false`；车停靠本站且 `d≡0` ⇒ 不判；**只给 4 帧 ⇒ 不判**（锁死 5 帧下限）；车已过下一站仍能锁牌；两车 `d` 差 <2σ 不锁；`onNotBoard` 可逆；`accuracy>50m` 的帧不参与斜率估计。

### 16.5 已知代价（负责人已知并接受）

候车期全程高精度 ⇒ **等车时耗电与发热增加**（可能十几分钟）。若后续收到耗电反馈，再评估「有车接近才切高精度」的折中，**不属本批**。
