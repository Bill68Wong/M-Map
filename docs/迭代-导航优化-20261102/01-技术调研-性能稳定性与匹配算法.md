## 0. 结论摘要

| 问题 | 结论 | 最关键的数字 |
|---|---|---|
| 搜索加载慢 | **主因不是代码慢，是「执行区在美东」。** 函数固定跑在 `iad1`，而数据库在新加坡、高德在中国、DSAT 在澳门 | 函数外固定开销 **294–316ms**（两套独立脚本一致）；`/api/nav` 关闸→澳科大 **热 3345ms / 冷 15328ms（P90 17271）** |
| 能否不花钱修 | **能。** 官方文档：区域选择在 Hobby 也开放（限 1 个区域）。当前 `vercel.json` 没有 `regions` 键 ⇒ 才落回 iad1 | 加一行 `"regions": ["hkg1"]` |
| 最贵的单环节 | 高德 transit（无缓存 2.9–4.7s）+ DSAT 报站（热态仍在关键路径 0.7–2.6s）+ **未埋点的多策略补查**（触发时 0.8–4.0s，完全看不见） | `transitMs` 冷 **2.9–4.7s**；含 s=7/s=8 的 OD「未埋点」**2347–4022ms** |
| 缓存现状（易误判） | `stations` / `route-stops` **已经命中 CDN**（`HIT` + `Age` 1100+）；真正漏写的只有 `route-shapes` / `route-lines` | 判命中**只能看 `X-Vercel-Cache` + `Age`**，看 `Cache-Control` 会得出相反结论 |
| 稳定性 | 三处结构性缺失：**无回前台补刷**、**定位无看门狗**、**无网络连通监听**；且「新鲜度」被 GPS 帧污染 | 全项目 `online/offline` 监听 **0 处**、Service Worker **0 个** |
| 「上车后才开始导航」 | 根因不是阈值，是**候选池口径错了**：候选来自「上车站」，车开走后池子为空 | `filterPassed: true` 后候选 **0 辆**；而该线路该方向实际在途 **0–10 辆**（其中行驶中 1–3 辆） |

**三个必须记住的数字**
1. **~305ms** —— 每个请求固定付给「用户网络 + 香港边缘 + hkg1→iad1」的地板成本（两套独立脚本各测 4 组 OD 冷热，全部落在 294–316ms）。
2. **49.5%** —— 111 个线路方向里 **55 个是环线（首尾同站）**。这是车辆匹配最大误判风险面的量化值。
3. **46%** —— `transit_cache` 里 319 个坐标对中 148 个被重复请求过；而 TTL 只有 60s、OD 桶是 15min，两者不匹配 ⇒ 这些重复请求几乎全部白付高德往返。

### 1.2 口径（必须先读，否则数字会被误读）

- **「冷」有三个不同含义**，本文件分开标注，不混用：
  1. **实例热** —— 同一 Vercel 函数实例连续处理，进程内 60s 缓存有效；
  2. **服务端缓存过期** —— 进程内缓存 TTL 到期（会有 `staticMs` 1.7–3.2s 的尖峰）；
  3. **上游无缓存** —— `/api/nav?nocache=1`，真实打高德。
- **单点测量噪声很大**：两套脚本同时跑同一台 iad1 实例时，同一 OD 热态读到 `8864ms`（我的）与 `1451ms`（测试同学的）。**所有结论均取 3 次采样的中位数**，且不跨脚本混用。
- **`X-Vercel-Id: hkg1::iad1::...`** 的读法：`hkg1` = 边缘 POP（香港），`iad1` = 实际执行函数（美东）。
- 本机网络位置在澳门，到 `hkg1` 的单程延迟很小；因此**下面所有「函数外开销」几乎全是 hkg1→iad1 的跨洋段**，不是用户侧网络。
- **本机测量地板 157–180ms**：用「必然 CDN HIT 的小文件」（`/icons-*.png`、`/manifest.webmanifest`、`/robots.txt`）实测 TTFB 得出，含本地 HTTP 代理与 TLS。⇒ 我的绝对毫秒数比测试同学环境**系统性高约 155ms**。
- **因此本文件的数字只用于「同一脚本内的横向对比（哪个环节最贵）」，不用来跨环境比绝对值**；对外口径一律引用测试同学的 `baseline-20261102.json`。
- **禁跨窗口比较**：同一 OD 的 3 次采样之间可差 2 倍（关闸→澳科大热态三次 3917.8 / 6944.8 / 7527.8ms），跨窗口更可达 2 倍。任何「从 X 降到 Y」的结论必须同脚本、同窗口、优化前后各跑一次。

### 2.3 四条必须写进结论的实测事实

**事实 1：静态缓存的 60s TTL 短于真实访问间隔，导致「每个会话首访都付 1.7–3.2s」。**
12 个采样里有 3 次 `staticMs` 明显非零：**1725 / 2197 / 3162ms**（其余为 0）。
`TTL_MS = 60_000`（`src/lib/nav/nav-service.ts:149`）、`STATIC_TTL_MS = 60_000`（`src/lib/recommend/query.ts:239`）。
本项目是个人项目、请求稀疏 ⇒ 60s 的窗口大概率已经过期。也就是说：**用户每次打开应用，第一批请求大概率要付一遍静态重建**。

**事实 2：缓存的真相是「一半已好、一半没写」，而且 `Cache-Control` 头不能用来判断是否命中。**

我最初根据 `Cache-Control` 断言「所有静态接口都没命中 CDN」，**这是错的**，测试同学用 `X-Vercel-Cache: HIT` 与源码订正了我。复核后的真相：

| 端点 | 源码是否写了 s-maxage | `X-Vercel-Cache`（连测 3 次） | `Age` | 浏览器可见 `Cache-Control` |
|---|---|---|---|---|
| `/api/stations?include=lrt` | **有**（`stations/route.ts:182`：`public, s-maxage=3600, stale-while-revalidate=86400`） | **HIT** | 1172 → 1185 | `public`（s-maxage **被边缘剥离，不下发**） |
| `/api/route-stops?code=MT1` | **有**（`route-stops/route.ts:27`：`public, s-maxage=3600, stale-while-revalidate=600`） | **HIT** | 1181 → 1185 | `public`（同上） |
| `/api/route-shapes?code=MT1` | **没有**（`route-shapes/route.ts` 全文无 `Cache-Control`） | **MISS**（3/3） | 0 | `public, max-age=0, must-revalidate` |
| `/api/route-lines` | **没有**（`route-lines/route.ts` 全文无 `Cache-Control`） | **MISS**（3/3） | 0 | `public, max-age=0, must-revalidate` |
| `POST /api/nav/detail-body` | 无（`no-store`） | MISS | — | `no-store` |
| `/api/station/eta` | 无（`no-store`） | MISS | — | `no-store` |

**两条必须记住的教训**：
1. **`X-Vercel-Cache: public` ⇏ 未命中。** Vercel 会把 `s-maxage` 从**浏览器可见**的响应头里剥掉，只留 `public`；真正的缓存决策看 `X-Vercel-Cache` 与 `Age`。**用 `Cache-Control` 推断命中会得出完全相反的结论**（我这次就错在这里）。
2. **HIT 判定必须看 `Age > 0` 且多轮一致**，单次 `MISS` 可能是该 URL 首次经过这个 POP（我用 `&v=2` 首次请求就是 `MISS / Age: 0`）。

⇒ 真正需要修的只有 **`route-shapes` 与 `route-lines`**（源码里漏写响应头）。`stations` / `route-stops` 已经是对的，不要再动（测试同学基线里的 `stations 热 73ms` 是**真 CDN 命中**，不是函数实例热）。

**本机测量地板（解释一切绝对值偏差）**：用 `/_next/static/*.png`、`/manifest.webmanifest`、`/robots.txt` 这些「必然 CDN HIT 的小文件」测出本机 TTFB 地板 **157–180ms**（含本地 HTTP 代理与 TLS）。⇒ 我的所有绝对毫秒数都比测试同学的环境**系统性地高约 155ms**，两组数字**只能比同一脚本内的差值，不能跨环境比绝对值**。

**事实 3：`detail-body` 用 3 秒换 1.6KB，且它挡在 route-shapes 前面。**
`detail-body` 响应体 1591–2242 字节，耗时 2438/3158/3371ms。归因（读码 + 实测）：
`route.ts:184` 已并行（`Promise.all([loadStatics, buildOverviewLegs])`），但 `route.ts:193` 的 `foldDataOfCard` 会**无条件**去查「本站台其他线路」实时报站：
`detail-fold.ts:103` → `foldLiveAt` → `fetchStationLive` → `queryBusBucket`（DSAT 报站）→ `fetchLocSegments`（DSAT 位置修正，`LOC_FIX_TIMEOUT_MS = 1500`），且 `BUCKET_TIMEOUT_MS = 3000`。
实测返回非空（`foldLive: {"55":"还有 1 站 · 约 1 分钟"}`）但耗时 ≈ 2 个 DSAT 串行往返 + 超出预算的等待。

而 `useRouteOverview.ts:62,87-108` 是**先 `useDetailBody` 就绪、再并行拉 route-shapes** ⇒ 这条链被强制串行。实测链中位 **3847.5ms**。

**事实 4：多策略补查（s=7/s=8）的耗时完全没进埋点，却在最慢的 OD 上是最大单项。**
`nav-service.ts:443` 先算出 `transitMs`（只覆盖 s=0），`nav-service.ts:452-457` 的 `fetchMultiStrategySeeds` 才发起 **2 次额外高德调用**（`strategy 7/8`，`MULTI_STRATEGIES`），而这段 await 落在 `transitMs` 之外 ⇒ 全部计入「未埋点」。
证据是上面那张分层表：只要 `strategiesUsed` 含 7/8，未埋点就从 **59–741ms 跳到 817–4022ms**。
触发条件：`bridgedSeeds.length < MULTI_STRATEGY_WHEN_BELOW`（= 3，`nav-service.ts:241`）。「关闸→澳科大」的 `bridged` 只有 2 ⇒ 必然触发。
⇒ 这条同时是一个**诊断缺口**（看不见）和一个**优化机会**（补查可以不挡首屏），详见 §3 第 13 项。

### 2.4 首次 GPS 定位（必须诚实标注）

`src/components/nav/useUserFix.ts:102`：
```ts
{ enableHighAccuracy: true, timeout: 10_000, maximumAge: maxAgeRef.current }  // 导航态 maxAge = 0
```

**能测到的**（`gps-firstfix.mjs`，本机 Chrome 无 GPS 硬件、定位 provider 不可用 ⇒ 走的是**失败路径**）：

| 取法 | 观测 | 5/5 次结果 |
|---|---|---|
| `getCurrentPosition(enableHighAccuracy:false, maximumAge:600000, timeout:3000)` | **3013ms** 触发 `code=3 Timeout` | 全部超时 |
| `getCurrentPosition(enableHighAccuracy:true, maximumAge:0, timeout:10000)` | **10015ms** 触发 `code=3 Timeout` | 全部超时 |
| `watchPosition(enableHighAccuracy:true, maximumAge:0, timeout:10000)` | **10009ms** 触发错误 | 全部超时 |

**结论（可迁移的部分）**：`timeout` 就是**用户最坏等待上限**。当前设置下，「定位假死」时用户要**干等 10 秒**才看到失败；低精度 3s 档把最坏等待压到 **3 秒**。
**不可迁移的部分**：真机（手机 + 户外）首次定位的绝对毫秒数**本机测不出来**，我不编造。给出真机测量协议，交由 Phase 3 执行：

1. 手机开飞行模式 → 冷启动应用（清后台）→ 关飞行 → 点「开始导航」，秒表记到**蓝点首次出现**；
2. 同上但先开 WiFi 定位（不等 GPS 锁定），记「低精度先出」与「高精度修正」两个时刻；
3. 室内（商场）与户外路侧各 5 次，取中位。

这三步能直接判定「分级定位」值多少毫秒；在拿到数之前，只把「最坏等待 10s → 3s」作为保守收益。

### 3.1 推荐组合与累计收益（保守估计）

按「改动小、风险低、不改对外结果」优先排序，Phase 3 建议分两批：

**第一批（改配置与缓存头，互不冲突）**：#1 + #2 + #3 + #7 + #8 + #13（只加埋点那一半）
- 冷态 `/api/nav` 关闸→澳科大 **15.3s → 预计 4–6s**

- 首页冷 573ms → 同量级或更低（首页冷热已接近，说明它主要吃边缘+源站两段固定成本）
- 补埋点后，「未埋点 59–4022ms」第一次可被解释，第二批的收益估算才能收敛

> 注意：第一批**不再包含 `stations` / `route-stops`** —— 它们已经命中 CDN，动它们无收益且有引入回归的风险。

**第二批（改前端结构与数据新鲜度，需要验收口径）**：#5 + #6 + #4 + #10 + #13（流式那一半）+ #14

## 4. 导航稳定性缺陷清单

> 逐条给：触发条件 · 用户可见现象 · 代码位置 · 根因 · 修法 · 风险等级
> 每条都在本机读码核实过；「全项目 0 处」类结论用 `grep` 复核，命令见 §4.9。

### D1 切后台再回前台，车辆位置不刷新（P0）

- **触发条件**：导航中切到别的 App / 锁屏，超过 ~1 个轮询周期后返回。
- **现象**：车图标停在上一次位置；「还有 N 站」不动；要等下一个 12s 周期（甚至更久）。
- **位置**：`src/components/nav/useRideTracking.ts:742-764`（候车轮询）、`:773-778`（乘车轮询）。
- **根因**：两处都是裸 `setInterval(..., 12_000)`，**effect 依赖里没有可见性/网络状态**。后台时定时器被节流（Chrome 隐藏标签 5 分钟后降到 1 次/分钟）或被系统冻结（iOS Safari）；回到前台后**没有立即补一次请求**，只能等下一个 tick。
- **修法**：抽一个 `useResumeRefresh(onResume)`：监听 `visibilitychange`（`visible` 时）+ `online` + `pageshow`（`persisted`），回调里立即执行一次 `fetchFrame`，并重置节流计时。三处（riding / boarding / 车辆查看）共用。
- **风险**：低。唯一要防的是「回前台连发」—— 用一个 2s 去抖 + 复用已有 5s `useCooldown`。

### D2 定位假死：长时间无回调，无人重订阅（P0）

- **触发条件**：iOS Safari / 安卓 WebView 在后台停留较久后返回；或定位 provider 短暂不可用。
- **现象**：蓝点不动、上车判定一直「暂停」、地图不再跟着走；**用户只能杀进程重进**。
- **位置**：`src/components/nav/useUserFix.ts:77-108`（`doWatch`）、`:146-160`（可见性处理）。
- **根因**：可见性处理只做「隐藏 → `clearWatch`；可见 → `doWatch`」一次。`doWatch` 里有 `if (watchRef.current != null) return;` 的幂等保护，但**没有任何「多久没收到回调就重订阅」的看门狗**。`maximumAge: 0` + `enableHighAccuracy: true` 在恢复瞬间最容易长时间不给帧（实测：provider 不可用时**必等满 10015ms** 才报错）。而错误回调只有 `setDenied(true)`，**不重试、不重订阅**。
- **修法**：
  1. 看门狗：每 10s 检查 `Date.now() - lastCallbackTs`，超过 25s ⇒ `clearWatch` + 重新 `doWatch`（指数退避，最多 3 次）；
  2. 错误分类：`err.code === 1 (PERMISSION_DENIED)` 才置 `denied` 并停；`2 (POSITION_UNAVAILABLE)` / `3 (TIMEOUT)` 只记「信号弱」，触发看门狗重订阅；
  3. 恢复时先低精度快出（与 #11 同一条改动）。
- **风险**：中。重订阅会触发一次「定位中」的视觉抖动；需保证不去重弹权限（`clearWatch` 后再 `watchPosition` 不会重弹，权限已授权）。

### D3 断网/弱网时静默失败，且没有连通性感知（P0）

- **触发条件**：WiFi ↔ 移动数据切换、地铁/隧道、电梯。
- **现象**：`fetchFrame` 失败只写一句「车辆数据获取失败，稍后自动重试」，随后**等满 12s** 才重试；连点刷新也被 5s 冷却挡住。切换网络后没有任何自愈动作。
- **位置**：`useRideTracking.ts:662-663`（`catch { setNote(NOTE_FETCH_FAIL) }`）、`useRouteVehicles.ts:148-152`（`setError("车辆位置获取失败")` + `setVehicles([])`）。
- **根因**：① 失败即 `return`，无退避重试；② **全项目没有任何 `online` / `offline` 监听**（§4.9 复核：0 处）；③ `useRouteVehicles` 失败还会 `setVehicles([])`，把上一帧的车**清空**（比留着旧数据更糟）。
- **修法**：
  1. 失败保留上一帧数据 + 打「数据已 N 秒未更新」标记，**不清空**；
  2. 重试退避：1s → 2s → 4s（上限 8s），最多 3 次；成功后复位；
  3. 监听 `online` ⇒ 立即重试一次并清退避。
- **风险**：低。

### D4 断网后「最后已知位置」被清掉（P1）

- **触发条件**：`enabled` 变 false、或调用 `stop()`、或卸载重挂。
- **现象**：回到前台/重进导航时蓝点从零开始，用户看到「定位中」而不是「上次在这里」。
- **位置**：`useUserFix.ts:119`（`stop()` 里 `setFix(null)`）、`:123-129`（`enabled=false` 时 `setFix(null)`）。
- **根因**：`fix` 只有「有/无」两态，没有「陈旧但可显示」态。
- **修法**：保留 `lastFix`（不因 `stop` 清空），另加 `fixAgeMs`；UI 侧在 `age > 30s` 时把蓝点画成「半透明 + 环」并标注「约」。
- **风险**：低（但会改变蓝点视觉，需过 UI 文案门禁 `check-ui-copy.mjs`）。

### D5 「新鲜度」被 GPS 帧污染 —— 数据已 3 分钟没更新，界面显示「刚刚更新」（P1，沉默逻辑错误）

- **触发条件**：车辆接口连续失败，但 GPS 正常。
- **现象**：面板上的「上次更新：N 秒前」一直是 0–3 秒，用户以为车在更新，实际车的坐标是 3 分钟前的。
- **位置**：写入 `useRideTracking.ts:857`（在 **GPS 驱动 effect** 里 `setLastUpdateTs(Date.now())`，且该行在 effect 内是**无条件**执行的）；读取 `src/components/nav/RouteSheet.tsx:155-156`（`dFreshSec`）→ `RouteSheet.tsx:181` 传给 `NavTrackBar` → `NavTrackBar.tsx:162` 渲染成 **「上次更新：N 秒前」**。
- **根因**：`lastUpdateTs` 同时被「车辆帧」和「GPS 帧」写入，但读取方把它当「车辆数据新鲜度」用。这类错误**不报错、不崩溃、只是悄悄算错**，属于最贵的一类。
- **修法**：拆成两个字段：`lastVehicleTs`（只由 `fetchFrame` 成功时写）与 `lastFixTs`；UI 分别用于「车辆数据」与「定位」。
- **风险**：低，但要同步改 `RouteSheet` 的展示口径与观测钩子。

### D6 `useRouteVehicles`（线路查看模式）同样无可见性/网络处理（P1）

- **位置**：`src/components/nav/useRouteVehicles.ts` 全文（237 行）。
- **根因/修法**：同 D1 / D3，复用同一个 `useResumeRefresh`。
- **风险**：低。

### D7 失败后候选列表被清空，导致「不是这辆」翻不到车（P1，与 §6 同源）

- **触发条件**：上车后才点「开始导航」，且中途有一次车辆请求失败。
- **现象**：点「不是这辆」无反应或直接退回等车态。
- **位置**：`useRideTracking.ts:619-624`（候车候选只取 `filterPassed` 后的结果）、`:1248-1252`（`onNotThisBus` 找不到就 `onNotBoard`）。
- **根因**：候选池口径见 §6.1；失败时 `candidates` 不更新也不保留。
- **修法**：见 §6.8。
- **风险**：中（改的是判定入口）。

### D8 无 Service Worker：断网即白屏级降级（P2）

- **现状核实**：`public/manifest.webmanifest` 存在（`display: standalone`），**但全项目 0 个 Service Worker**（§4.9）。
- **现象**：断网时打开应用 → 浏览器错误页（不是「离线，显示上次结果」）。
- **根因**：PWA 只做了 manifest 与图标，没做离线壳。
- **修法（层 2，见 §5）**：注册 SW，预缓存应用壳 + 静态 chunk；`/api/nav` 的 GET 走 network-first + 5 分钟兜底缓存。
- **风险**：中-高。iOS 对 SW 限制多（存储上限、7 天未使用清理、`navigationPreload` 不支持）；缓存版本管理写错会「永远拿到旧版本」——必须用 `skipWaiting` + `clients.claim` + 版本号迁移，并提供「强制刷新」入口。

### D9 iOS 加入主屏后切后台的行为差异（P2，需真机确认）

- **现状**：`manifest.display = "standalone"` ⇒ 独立窗口运行。iOS 独立模式下切后台，JS 定时器几乎立即冻结（比 Safari 标签页更激进），且后台定位不可用。
- **影响**：D1/D2 在「主屏启动」时更严重。
- **处理**：层 1 的「回前台立即补刷 + 看门狗」必须覆盖 `pageshow`（`event.persisted`）路径，而不只是 `visibilitychange`。真机上「主屏模式」与「Safari 标签页」要各测一遍。

## 5. 三层修复方案（供决策）

| 层 | 内容 | 工程量 | 风险 | 效果 |
|---|---|---|---|---|
| **层 1（推荐先做）** | 回前台/网络恢复立即刷新 + 定位看门狗 + 断网保留最后位置并标注过期 + 新鲜度拆分（D1–D7） | 新增 1 个 hook（~90 行）+ 改 3 个文件；预计 1.5–2 人日 | 低 | 覆盖用户描述的全部三个现象：拿不到定位、蓝点不更新、巴士位置不更新 |

## 6. 车辆匹配算法设计（本次最重）

### 6.1 现状与根因（先定位病灶，不是调参数）

调用链：`start()` → `phase="boarding"` → 候选 = `rankBoardingVehicles(list, boardMain, boardPos, { filterPassed: true, stopMains, anchor })`。

`filterPassed: true` 会剔除**已越过上车站**的车（`track.ts:182-207` 的 `passedBoardOf`）。「上车后才点开始导航」时：

1. 用户坐的那辆车**已经离开上车站** ⇒ 被 `passedBoardOf` 剔除；
2. 排在后面的车也大多已过站 ⇒ 候选池 **0 辆**；
3. `candidates = []` ⇒ `note = NOTE_NO_VEHICLES`（「这条线现在查不到车」）—— **归因错了**（车在，只是不在上车站附近）；
4. 自动判定 R2 其实**会**命中（用户确实在动），但它是**晚且无名**的：
   - 时序下界 = `SWITCH_COOLDOWN_MS` 20s（`start()` 里 `lastSwitchTsRef = Date.now()`，`useRideTracking.ts:982`）+ 45s GPS 窗口（`R2_WINDOW_MS`）+ 需 3 次连续命中（`R2_STREAK_ALONE`）⇒ **最短约 65 秒**才切到 riding；
   - 且 `autoBoardOf` 只在 `aux.strong`（车刚从**本站**开走）时才锁牌（`boarding-detect.ts:372`）。车已走远 ⇒ `aux.strong=false` ⇒ `lockedPlate=null` ⇒ `progressSource="gps"`；
   - 也就是说：**用户要盯着「正在确认」等一分钟，最后拿到的是一辆没有车牌的车**。这正是「无法匹配到正确车辆」的直接体感。
5. 无车牌 ⇒ `mapVehicles` 为空（`useRideTracking.ts:392`：`if (!plate) return []`）⇒ 地图上**看不到自己坐的车**；
6. 点「不是这辆」→ `onNotThisBus`（`:1248-1252`）在空 `candidates` 里找不到别的车 → `onNotBoard` 退回等车态 → 又从空池开始。

**所以真正要修的是「候选池口径」，而不是把阈值放宽。** 放宽 R2 只会让判得更早，仍然没有车牌。

**正确的候选池定义**：该线路、该方向、**当前全部在途车**。实测该池很小：

| 线路 | dir | 在途车 | 行驶中 | 带 progress |
|---|---|---|---|---|
| MT1 | 0 | 4 | 2 | 2 |
| 25 | 0 | 10 | 2 | 2 |
| 26A | 0 | 5 | 3 | 3 |
| 26A | 1 | 6 | 2 | 1 |
| 52 | 0 | 4 | 3 | 3 |

⇒ **候选 0–10 辆、行驶中 1–3 辆**。这个规模下「不显示候选列表、全自动锁定」完全可行：不需要用户做选择，只需要算法在 ≤3 个假设里挑一个。
（顺带说明：`progress` 覆盖率 10/12 ≈ 83%，缺失要能降级，见 §6.6 的 `mileM`。）

### 6.2 业界与学术做法（可引用，含适用条件）

| 方法 | 出处 | 适用条件 | 本项目可用性 |
|---|---|---|---|
| **几何投影（point-to-curve）** | Quddus 等 2007 综述里的 geometric 类；Chao 等综述"projects each trajectory point to the geometric-closest edge" | GPS 密集且准确、附近无平行道路 | **已在用**（`nearestOnPath` / `perpDistM`）。澳门路窄、单行多 ⇒ 仅用它必错 |
| **曲线对曲线（Fréchet 距离）** | Chao 等综述："the Fréchet distance is the most common measure" | 整段轨迹已知、可与候选线形比对 | 可用作**短窗口**形状比对，但对离群点敏感（"one bad GPS record can dominate"） |
| **HMM + Viterbi（Newson & Krumm 2009）** | Newson & Krumm, *Map Matching with HMM*, GIS 2009；Valhalla Meili 采用同一方法 | 有路网拓扑、允许少量延迟（online 变体"match each record after a short delay"） | **部分可用**：本项目只有「一条已知线路」，路网退化为一条链 ⇒ 状态空间是「沿线里程」，HMM 可简化为 1-D 滤波（见 §6.3） |
| **卡尔曼 / 粒子滤波** | Quddus 综述的 advanced 类 | 需要运动模型 + 连续观测 | 可用：1-D 里程上的卡尔曼滤波，天然给出置信区间 |
| **序列证据累积（SPRT / CUSUM）** | Wald 1947（SPRT）；Page 1954（CUSUM）；工程综述见 CUSUM 的 k=δ/2、h=4σ~5σ 经验取值 | 需要「逐帧累积证据、控制误报率」 | **最贴合**：把「假设我在 X 车上」的似然比逐帧累加，达到阈值才锁定（替代当前的「连续 N 帧」硬计数） |
| **数据关联（NN / GNN / MHT）** | 多目标跟踪标准做法 | 多个候选、单传感器 | **正是本问题**：「一束候选车 × 一条用户轨迹」的单传感器数据关联 |
| **公交上车检测（传感器法）** | Rajput 等 2020（加速度计 + GPS 判别上车事件）、TransitSense（BLE + GNSS + 加速度计 HAR，投票窗口 70% 阈值） | 需要 IMU / BLE 信标 | **本项目不做**：PWA 拿不到可靠 IMU，也没有车内 BLE。仅作方法论参考（"Voting Window" 思想 = 多帧投票） |

**结论**：不要照搬 HMM 路网匹配。本问题的结构是「**已知道路（一条链），未知车辆**」，属于**单传感器多假设数据关联 + 序贯证据累积**。核心是把用户轨迹与每辆候选车轨迹都投影到**同一条沿线里程轴**上，再做「里程-时间」曲线的一致性检验。

### 6.3 设计：以用户定位为主锚的里程轴匹配

#### 6.3.1 统一到一个标量：沿线里程 `d`（米）

- **用户侧** `dU(t)`：`nearestOnPath(leg.colored, fix)` → `cumDistM` 取值。
  已有实现可直接复用：`advanceLrt`（`lrt-progress.ts:105-191`）已经给了可信门（离线 ≤120m、精度 ≤100m）、迟滞 `H`、速度合理性 `[8,80] km/h`、单帧最多推进 1 站、连续 2 帧一致才采纳。**新算法不改这套，只是把它的 `distNow` 当作 `dU`。**
- **车辆侧** `dV(t)`：服务端 `progress` 已含 `segFrom/segTo/p/segLenM` ⇒ 用站点里程阶梯换算
  `dV = ladder[segFrom] + p × (ladder[segTo] − ladder[segFrom])`。
  `ladder` 用 `buildLrtLadder(leg.colored, stops)` 建（同一份实现，站坐标来自 `/api/stations`，已在 `ensureStationMap` 里缓存）。
- **关键前提已验证**：`route_station_mileage` 的 **111 个线路方向全部严格单调**（非单调间隙 0 个）⇒ 里程轴是良定义的，按里程投票可行。

#### 6.3.2 候选集合

```ts
// 伪代码（Phase 3 落地到 src/lib/nav/match-vehicle.ts）
const pool = vehicles.filter(v =>
  (v.status === "moving" || v.status === "stopping" || v.status === "terminal") &&
  v.plate !== excludedPlate           // 「不是这辆」用
);
```
**不再**用 `passedBoardOf` 过滤。`passedBoardOf` 只保留给「候车态提示错过班次」这一条既有逻辑（`NOTE_NO_VEHICLES` 的语义不变）。

#### 6.3.3 打分（五项，全部可解释、可观测）

对每个候选车 `i`，取最近 `T = 90s` 的窗口，计算：

| 项 | 公式 | 直觉 | 权重 |
|---|---|---|---|
| **S1 位置一致** | `exp(−|dV_i(t) − dU(t)|² / (2σ_p²))`，`σ_p = max(60, 1.5×accuracy)` | 我沿线到哪，车也应该沿线到哪 | 0.40 |
| **S2 速度一致** | `exp(−(vU − vV_i)² / (2σ_v²))`，`σ_v` 取实测段速离散度 | 我随车动的速度应与车的速度一致 | 0.20 |
| **S3 方向一致** | `sign(ΔdU)·sign(ΔdV_i)` 一致记 1，否则 0 | 同向行驶 | 0.15 |
| **S4 曾经经过我** | 存在 `t' ∈ [t−120s, t]` 使 `|dV_i(t') − dU(t)| ≤ 120m` 且 `dV_i(t') ≤ dU(t)`（车从后方来） | 我上车时车确实经过了我 | 0.15 |
| **S5 时间可达** | 以 `p50` 单跳 105s 计，车与我之间的里程差折算时间 ≤ 该区间中位时长 × 2 | 物理上追得上/被追上 | 0.10 |

`score_i = Σ w_k · S_k`，取 `argmax`。

> **S4 的冷启动**：车辆历史靠 12s 帧累积，进入候车态的第 1 帧没有任何历史 ⇒ S4 **既不算 0 也不算 1，而是「不参与」**（把 0.15 权重按比例分给 S1/S2/S3/S5）。12s 后第 2 帧起 S4 才生效。这保证「刚打开就判」不会因为缺历史而系统性压低所有候选。
>
> **为什么用五项而不是一个综合距离**：五项各自对应一种可观测的失败模式（位置/速度/方向/经过/可达），出问题时能直接说「因为方向判负」而不是「分数低」。这也让 Phase 3 的验收可以逐项打点（见 §6.7 的 `data-match-score`）。

> **注意 S5 的方向语义**：车在**我前方**（`dV > dU`）时，「我本应在车上」⇒ 差距必须 ≤ 该窗口内车辆可能推进的最大里程（用 `TRAVELED_MAX_SPEED_MPS = 20` × 经过时间 + 余量）。车在**我后方**且距离在增大 ⇒ 不可能是我坐的车，直接判负。这一条是防「后车误锁」的关键。

#### 6.3.4 置信度分级与决策（回应「不要候选列表」）

用 **SPRT 式证据累积**替代当前的「连续帧计数」，因为后者无法表达「证据强度」：

```
L_i += log( P(观测 | 假设=车i) / P(观测 | 假设=无车) )      // 逐帧
```

- **高置信（自动锁定，静默）**：`L_i ≥ 3.0`（≈ 20:1 优势比）且 `score_i ≥ 0.75` 且 `margin = score_i − score_2 ≥ 0.20`。
  → 直接 `switchToRiding(plate)`，`progressSource="vehicle"`。**用户零操作**。
- **中置信（锁定但标注不确定）**：`1.0 ≤ L_i < 3.0`，或 `margin < 0.20`。
  → **仍然锁定**（因为需求方明确不要候选列表），但文案改为「已开始跟踪 25 路 · 粤A·12345（车牌待确认）」，并在站条来源标注为「定位推算」。
  → 一旦后续帧把 `L` 推过 3.0 或 `margin` 拉开，自动去掉「待确认」。
- **低置信（不给列表，给两个动作）**：
  1. **延迟锁定 + 继续累积**：不立刻切换，保持「等车态」但文案改成「正在确认你坐的是哪辆车」；每 12s 重新打分，最多等 60s；
  2. 60s 后仍低置信 ⇒ 进入 **`progressSource="gps"`**（就是现在这条路径，进度由 GPS 推），并在面板上给一句**单一动作**：「车牌对不上？点这里核对」—— 点开是一个**车牌输入/选择面板**（不是候选列表，是用户主动打开的核对界面，最多 3 个 + 「都不是」）。
  3. 复用既有「不是这辆」纠错入口：**纠错后重算整个池**（见 §6.8），而不是在空池里找下一个。

> 这样满足三条硬约束：① 不主动给候选列表；② 主路径全自动；③ 出错时用户有且只有一个明确动作。

#### 6.3.5 误判防护（逐条对应风险）

| 风险 | 表现 | 防护 |
|---|---|---|
| **环线（49.5% 的方向）** | 同一路段正反两遍走过，`dU` 在空间重合处跳变 | 复用 `monotonicCut` 的单调游标（`track.ts:395-460`）与 `TRAVELED_STALE_MS` 长间隔放行；候选打分用 `d` 的**增量**而非绝对值 |
| **平行线路** | 两辆不同线的车在同一条路上并排 | 候选池**只含本线路本方向**（`/api/route-vehicles?code=&dir=` 已保证），平行线不进入池 ⇒ 天然免疫 |
| **双向重叠（同一条路两个方向）** | 反向车被当成同向 | 候选池按 `dir` 过滤；再加 S3 方向一致 |
| **GPS 漂移 / 隧道 / 室内失锁** | `dU` 突跳或长时间不动 | 复用 `advanceLrt` 的可信门 + 「连续 2 帧不可信 ⇒ 冻结」；冻结期间**不更新证据**（不惩罚也不加分） |
| **用户步行（还没上车就被判上车）** | 见下方专项说明 | 速度门 + 位移门（已有）+ **新增「与候选车速一致」一项**：步行 1.4 m/s 与车速 4 m/s 打分必然低 |
| **用户冲刺赶车被误判「已上车」** | 见下方专项说明 | 新算法的 S2 把对照对象从「固定门槛」换成「候选车实测速度」；并加「无车速佐证时位移门不得低于一个站距」 |
| **两辆同线车相距很近** | `margin` 小 | 中置信分支；用 S4（谁刚经过我）+ 12s 后的下一帧拉开差距 |
| **`progress` 缺失（约 17%）** | 该车无法算 `dV` | 服务端新增 `mileM` 字段（见 §6.6），把缺失率降到 ~0；仍缺失则该车不计入池并记观测钩子 |

**专项：「冲刺赶车」与「乘车」在速度上不可分（用本项目自己的分档表算出来的）**

`R2_SPEED_MIN_KMH_FLEX = 8`（`boarding-detect.ts:61`）的注释说「8 是步行与车速的分界」。但本项目自己的分档表 `SPEED_RATIO`（`src/lib/recommend/types.ts:72-78`）写明：

| 档 | 速度 | 换算 km/h |
|---|---|---|
| 1 全力冲刺 | 3.6 m/s | **12.96** |
| 2 小跑 | 2.0 m/s | 7.2 |
| 3 正常走（基准） | 1.4 m/s | 5.04 |

⇒ **档 1（冲刺 12.96 km/h）落在 (8, 80] 的速度带内**，与实测段速 p50 = 14.8 km/h 几乎重叠。
也就是说：**单靠速度门，无法区分「用户在冲刺赶车」与「用户坐在低速行驶的车上」**。当前唯一在起作用的是 45s 窗口的**持续性**（冲刺通常撑不到 45 秒）。
这不是调阈值能解决的（把门槛提到 13 km/h 会把 p25 = 9.6 km/h 的真实乘车全部误杀）。
**正确解法在新算法里**：S2 的对照对象不是常数门槛，而是**候选车的实测沿线速度**；S1 的对照对象是**候选车的沿线里程**。冲刺时用户与其前方那辆车的里程差会**持续拉大**（车 190m/45s vs 人 162m/45s），`margin` 判负 ⇒ 不锁定。

| 参数 | 取值 | 依据 |
|---|---|---|

| 速度一致 σ_v | 6 km/h（待标定） | 实测段速分布 p25=9.6 / p50=14.8 / p75=23.1 km/h（`params-20261102T1305.json#segmentSpeedKmh`）；四分位半宽 ≈ 6.8 |
| 窗口 T | 90s | 与 `FIX_KEEP_MS = 90_000`（`useRideTracking.ts:55`）一致；也覆盖 3 个 12s 车辆帧 |
| S4 时间窗 | 120s | 覆盖「上车 → 点开始导航」的典型操作延迟；等于 `GPS_PAUSE_MS × 2` |
| 站距先验 | p50 420m / p05 126m / p95 1219m | 实测 2468 个邻接站距（`#stationGapM`） |

| 锁定所需最小帧数 | 3（有车速佐证）/ 4（无） | 复用 `R2_STREAK_WITH_VEHICLE=2` / `R2_STREAK_ALONE=3` 再加 1 帧（因为多了打分维度，需更多帧才能拉开 margin） |

### 6.5 与既有 R1/R2 的兼容策略（不能破坏「上车前开始导航」）

**需求方的原话是「上车前那条是准的」，因此纪律是：不变量优先。**

1. **R2 的位置不变**：`r2Of` 与 `autoBoardOf` 的既有判据（投影/位移/速度/连续帧）**一行不改**。「上车前开始导航」走的还是这条路径。
2. **新算法只在「已判定上车」之后接管车牌识别**：
   - 现在：`autoBoardOf` 命中 → `lockedPlate = aux.strong ? aux.plate : null`；
   - 之后：`plate === null` 时**不再直接落到 gps 驱动**，而是先跑一次 `matchVehicle`，得分够就带牌进入 riding，不够就 gps 驱动 + 后台继续匹配（每 12s 一次，最多 60s）。
   ⇒ 对「上车前开始导航」的路径，行为差异只有一处：**原来锁不到的牌现在能锁到**（增益，不是回归）。
3. **`aux.strong` 的特权保留**：若 `aux.strong` 成立（车刚从本站开走且唯一），仍然直接锁牌，**优先级高于**新算法（因为那是站序层面的硬证据）。
4. **`filterPassed` 只保留给候车提示**：`rankBoardingVehicles({filterPassed:true})` 继续用于「候选中没车（可能错过班次）」这条文案；新算法的池子另算，两者不共用一个数组。
5. **回归护栏**：`scripts/test-boarding-detect.ts` 现有断言（含 ⑭ 组 4 条）**必须全部保持绿**；新增 `test-match-vehicle.ts` 覆盖 §6.3.5 的 7 个风险场景。

### 6.6 需要的接口改动（新增字段，零额外计算）

`src/lib/nav/progress.ts` 的 `attachProgress` 里已经算出了**绝对沿线里程 `m`**（`projectMile(shape, [v.lng, v.lat])`，第 173 行），但**丢掉了**，只输出区间内的 `p`。

建议（Phase 3）：

```diff
  export interface VehicleProgress {
    p: number;
    remainSecD: number;
    mdSec: number;
    w: number;
    segFrom: string;
    segTo: string;
    segLenM: number;
+   /** 绝对沿线里程（米）—— 车辆匹配算法的唯一标尺；由 projectMile 直接给出，零额外计算 */
+   mileM: number;
  }
```

同时把 `attachProgress` 的「只算 moving」放宽为「有坐标就算」（停靠车用 `atStation` 的站里程补齐），把覆盖率从 83% 提到 ~100%。
**风险**：极低（纯新增字段；`mileM` 只对 `?progress=1` 的调用方可见，现有消费方忽略即可）。
**注意**：`/api/route-vehicles` 文件已到 300 行门禁上限，改动必须落在 `progress.ts`，不能往 route.ts 堆。

**机器可读契约**：`docs/迭代-导航优化-20261102/04-API契约增量-mileM.yaml` —— 只登记本次增量（`VehicleProgress.mileM`、`detail-body` 的可选 `fold` 参数、以及 `matchVehicle` 纯函数签名与 4 条不变量），不重写全量契约（避免在性能迭代里混入大范围改动）。

### 6.7 观测钩子（**已与产品/测试定稿的契约对齐，不另起一套**）

PM 与测试已把钩子契约定稿在 `docs/迭代-导航优化-20261102/03-测试-基线测量与场景复现.md` §3.4，本节**只做两件事**：① 说明匹配算法如何落到那套钩子上；② 申明一条命名红线。

**契约已有的（直接复用，不新增同义属性）**

| 钩子 | 取值 | 与匹配算法的关系 |
|---|---|---|
| `body[data-geo]` | `ok` / `low_acc` / `stale` / `denied` / `unavailable` / `timeout` | 由 `useUserFix` 直接映射；`low_acc` 与 `stale` 正交、**同时发生时 `low_acc` 优先**（测试已定稿）。匹配算法在 `data-geo != ok` 时**不得**从 `high` 置信降级为锁定 —— 见 §6.5 的冻结语义 |
| `body[data-veh]` + `body[data-veh-age]` | `fresh` / `stale` / `failed` / `open`；age = 整数秒 | `data-veh-age` 必须由**车辆帧**驱动（见 D5 的 `lastVehicleTs` 拆分）；这正是 D5 修好后才能成立的前提 |
| `body[data-user-fix]` | `"ts,acc"`（**不写经纬度**） | 匹配算法读这里判断用户锚是否新鲜，不额外造属性 |
| `.nav-actions[data-board-match]` | `none` / `auto` / `confirmed` / `corrected` / `manual` | 匹配结果落点：`auto` = 高置信自动锁定；`confirmed` = 中置信（已锁定但标注待确认）；`corrected` = 经「不是这辆」纠错后重锁 |
| `.nav-actions[data-match-source]` | `gps` / `gps+vehicle` / `manual` | = 既有 `progressSource` 的对外投影 |
| `[data-switch-list]` + `[data-switch-reason]` | 条目数；`wrong_vehicle` / `not_boarded` | §6.8 纠错后候选池重建的可断言证据 |

**命名红线（引用契约原文）**：**禁止合成 `data-net`**。理由是它会把「网络连通」与「车辆数据新鲜度」两个轴粘回一个，并诱导实现依赖不可靠的 `navigator.onLine`（MDN 明确说它本质不可靠，只能给提示、不能据此禁用功能）。网络故障只用 `body[data-veh]=failed` 表达。

**我的算法若还需诊断量，只允许追加（不改契约语义）**，且挂在已有元素上：
| 追加属性 | 取值 | 用途 |
|---|---|---|
| `.nav-actions[data-match-pool]` | 整数 | 候选池大小 —— 验收断言「上车后池子不得为 0」 |
| `.nav-actions[data-match-score]` | `"<score>,<margin>"`（2 位小数） | 便于判断「分数都低」还是「分不开」 |
| `.nav-actions[data-match-reasons]` | 逗号分隔，如 `S3:direction` | 逐项判负原因，避免只能看到"没锁上" |

> **关于 `data-match-source` 的一个口径澄清（防止验收标准写错）**：ADR-108「定位主导」约束的是**上车判定的触发器**（不得由车辆信号**单独**触发上车），**不约束判定之后的进度来源**。锁定车牌后 `progressSource` 本就是 `"vehicle"`（现状即如此，`useRideTracking.ts` 的 `switchToRiding(plate)`）。因此验收断言应写「**不得出现『仅有车辆信号就触发上车』**」，而不是「`data-match-source` 不得出现 `gps+vehicle`」——后者会把现有的正常路径判成违规。

### 6.8 「不是这辆」纠错后的候选池重建

现状：`onNotThisBus` 从 `candidates`（上车站口径）里找 → 空池 → `onNotBoard`。

改法：
1. `excludedPlates: Set<string>`（本次 riding 生命周期内累积）；
2. `onNotThisBus` → `matchVehicle({ excluded: excludedPlates ∪ {currentPlate} })`：
   - 池 = 全在途车 − 已排除；
   - 若有明确的次优（`score_2 ≥ 0.6`）⇒ 直接 `repick(plate_2)` 并**重算 ladder**（`clearTraveled` + `ensureLadder`，照 `repick` 现有逻辑，`:1060-1069`）；
   - 若无 ⇒ 文案「暂未识别出其他车辆 · 已改用定位推算」，并把 `progressSource` 切到 `gps`（**不回等车态** —— 回等车态会让用户丢失已走过的进度）。
3. 若 `excludedPlates.size ≥ 全池大小` ⇒ 说明全部都不是，此时才提示「可能不在本线路上」并给「改用定位推算」单选项。

> 关键区别：**「不是这辆」不再等于「我没上车」**。现在它退化成 `onNotBoard`（回等车态），这是语义错误 —— 用户明确说的是「我在车上，但不是这辆」。

### 6.9 硬性验收要求：定位不可用 ≠ 导航不可用

这是团队明确要求必须成立的一条，也是本项目最容易写错的地方。**禁止「任一轴失败 ⇒ 整页降级」**。

把两个轴的四象限写死（`data-geo` × `data-veh`）：

| 定位 `data-geo` | 车辆 `data-veh` | 允许降级的东西 | **不允许降级的东西** |
|---|---|---|---|
| ok | fresh | — | 全部正常 |
| ok | stale / failed | 车图标位置、报站读数（标「数据陈旧」） | 站条四态、**「还有 N 站」由 GPS 推算继续给**、下车提醒（基于 GPS 里程越过下车站）、蓝点 |
| low_acc / stale | fresh | 蓝点精度（画精度圈或灰点） | **「还有 N 站 · 约 X 分钟」必须照常**（走车辆驱动）、自动下车提醒、站条四态 |
| denied / unavailable / timeout | fresh | 蓝点（不显示）、走向车站距离、上车自动判定 | **「还有 N 站 · 约 X 分钟」必须照常**（车辆驱动）、自动下车提醒、站条四态、车牌 |
| denied / unavailable | stale / failed | 实时数字（改为计划值 + 「数据未更新」） | 沿途站序、**计划时长**、下车提醒（按计划到站时刻兜底，并标注「按计划」） |

**实现要点（都是小改动，但漏一条就会整页降级）**
1. `useRideTracking` 的 `progressSource` 是**两条独立通道**：`vehicle`（有车牌）与 `gps`（无车牌）。当前 `!plate ⇒ mapVehicles=[]` 只是**不画车**，不应牵连站条与文案 —— 需逐处确认没有把 `plate === null` 当成「数据不可用」。
2. **判定暂停 ≠ 导航暂停**：`detectPausedOf` 只控制「自动上车判定」与那一句提示，`track.prog` 与下车提醒不得读它。
3. 下车提醒的兜底链必须是三段：`车辆 nextIdx` → `GPS 里程越过下车站` → `计划到站时刻`。**现在只有前两段**（`alight-detect.ts` 只有 `atIdx === lastIdx` 与 `dNow >= dAlight + 30` 两个触发，`NavAlarmOverlay`/`AlightBanner` 也无按时刻的兜底）⇒ 双轴都坏时**不会自动提醒**，用户只能自己盯站条。这是本条验收要求里唯一需要新增代码的地方。
4. 验收断言（可直接写成自动化）：在 `data-geo=denied` 且 `data-veh=fresh` 下，`[data-eta-remain]` 元素仍存在且文本匹配 `/约 \d+ 分钟|即将到站/`。
