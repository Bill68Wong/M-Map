## 1. Q1 核实 Claim 1（基石）

### 1.1 沿线位移取的是什么 ——【直读】

`src/lib/nav/boarding-detect.ts:178-185`（**该文件自 v3.8.0 至今零改动**，见 §2）：

```ts
const cum = cumDistM(colored);
const projs = win.map((f) => nearestOnPath(colored, f));
if (projs.some((p) => p.distM > tol)) return false;

const i0 = projs[0].idx;
const i1 = projs[projs.length - 1].idx;
const disp = Math.abs(cum[i1] - cum[i0]);      // ← 顶点里程差，不是实际移动距离
if (disp < displace) return false;
```

`nearestOnPath`（`src/lib/nav/route-overview.ts:186-200`）取**最近的顶点**，返回 `{idx, distM}`。
⇒ **位移 = 窗口首末帧"最近顶点"的累计里程之差**，与用户实际移动了多远**无直接关系**。

### 1.2 `colored[0]` 恒为 board 这条契约是否还成立 ——【直读】重新核过

需求 4 刚改过 `route-overview.ts`（+228 行），所以按你的要求重核，不凭记忆：

- `cutColored`（`:217-228`）**一行未改**（`git diff` 里只出现在注释）⇒ 恒返回 `pts.slice(iBoard, iAlight+1)` ⇒ `colored[0] = pts[iBoard]`。
- 需求 4 新增的 `pickTripPair` 只改**选哪一个 `iBoard`**，候选集来自 `nearestTrips(pts, board, tolM)`（`:168-190`）⇒ 新 `iBoard` 距 board **仍 ≤ tolM(80m)**。
- ⇒ **`colored[0]` 距 board ≤ 80m 的契约成立**，需求 4 没有破坏它。

再看 `autoBoardOf` 的准入（`boarding-detect.ts:326-327`）：

```ts
const geomOk = input.colored.length >= 2 && !input.legDegraded;
if (!geomOk) return noHit();
```

而 `buildColoredLegs`（`route-overview.ts`）里 `degraded === false` 的出口**只有两个**：
- **分支⑤（正常切割）**：`colored = cutColored(...)` ⇒ `colored[0] ≈ board` ✔
- **分支④（起终点同站，`distM(board,alight) ≤ 50m`）**：`colored = gray = 整条 shape`、`degraded = false` ⇒ **`colored[0]` = 线路首站，不是 board** ✘

### 1.3 Claim 1 的严格证明（分支⑤）——【推断，基于 1.1+1.2 的不等式】

设末帧投影里程 `cum[i1] = alongM`（自 `colored[0]` 起算），首帧 `cum[i0] ≥ 0`：

```
disp = |cum[i1] − cum[i0]| ≤ cum[i1] = alongM
displace 门 = max(R2_DISPLACE_MIN_M, (8/3.6)·dt) ≥ 60
⇒ 若 alongM < 60 ⇒ disp ≤ alongM < 60 ≤ displace ⇒ r2Of 必失败
```

而未到站的用户，所有帧都投影到 `idx = 0`（`alongM = 0`）——因为 `colored[0]` 就是上车站，"站在站前"在折线上没有对应顶点，只能被钳到起点。

⇒ **「还没走到上车站的人」在分支⑤ 下绝不可能命中**。Claim 1 **成立**，而且是**数学必然**，不是"跑了几次没命中"。
顺带：若站前距离 > tolM(80m)，连 `projs.some(distM > tol)` 那道门都过不了 ⇒ 双重挡住。

### 1.4 但 Claim 1 有一个真实例外（分支④）——【实测】

`buildColoredLegs` 分支④（起终点同站，50m 内）给出 `degraded=false` 但 `colored=整线`。此时 `colored[0]` 是线路首站，`boardPos` 在中段 ⇒ **站前位置能正常落到中段顶点，位移会累积**。

`.verify/_q6-branch4.mts`（colored=3000m 整线，boardPos 在 +1000m，用户从 +800m 以 10km/h 走近并停在站台）：

```
k=0  d=800 idx=80 along=800m distM=0.0
k=5  d=842 idx=84 along=840m distM=1.7
k=10 d=883 idx=88 along=880m distM=3.3
⇒ 27s 触发          ← 人还没到站就被判已上车
```

⇒ **Claim 1 在分支④ 下不成立。** 但可达性极低：需要 `板-降` 两站相距 ≤50m 的**退化行程**（例如 C652↔C653 这种 20m 双台的一站车）。真实推荐里几乎不会产生这种卡。

**这一条应作为 Claim 1 的限定条件写进 FINDING**，不要写成无条件成立 —— 否则将来有人按"站前绝不可能命中"去删某道护栏，会踩这个洞。

### 1.5 Q1c：92a8912 当年「跑 24s 被误判」是怎么来的 ——【直读】+【实测】

**口径没变过。** `git diff 2806627..HEAD -- src/lib/nav/boarding-detect.ts` 输出为**空** ⇒
`r2Of` 的位移口径从 v3.8.0 → v3.9.0 → v3.10.0 → HEAD **一个字符都没改**。
⇒ 不是"前后两套测试在测不同东西"的**代码**问题，而是**夹具几何**问题。

**根因：老夹具把 colored 向站前延伸了 400m，违反 `colored[0] = board` 契约。**

`scripts/test-boarding-detect.ts:64-69`：

```ts
const PATH: LL[] = Array.from({ length: 1001 }, (_, i) => {
  const m = -400 + i * STEP_M;        // ← 从 −400m 起
  return [BASE_LNG + m * DEG_PER_M_LNG, BASE_LAT] as LL;
});
```
而基准输入 `boardPos = { ...atM(0) }`（`:94`）⇒ **`colored[0]` 在站前 400m**。
夹具注释自己写了原因（`:60-62`）：

> 「路径向**西**多留 400m：`fixesOf` 的早帧落在起点以西，否则投影距离超 tol 假失败。」

他们为了消掉"早帧投影超 tol"的假失败而延长了路径 —— 副作用是**把"站前位移"变成了可测量量**，而这在生产上不可能出现（生产 `colored[0]` 就是上车站）。
且 `fixesOf(0, 20, 3, 10000)` 这类用例的**末帧就在站台上**、早帧在站前 ⇒ 恰好是"跑到站台"的形态 ⇒ 在夹具里能命中，在生产里不行。

**92a8912 的注释其实自己声明了这一点**（`useRideTracking.ts` 当时的加严说明）：

> 「为什么是 2 而不是 1（**实测数据，理想直线 + 完美精度的下界**）」

"理想直线 + 完美精度的下界" = 假定"沿线位移 = 实际走了多远"，这正是被顶点钳位否掉的那一步。

⇒ **谁对：实现方的 FINDING 对。** 92a8912 的「跑 24s 误判」在真实函数上复现不出（我的 `.verify/_q6-claim1.mts` 场景 D：站前 200m 跑 10km/h 到站台停住，v380 也不触发，与加严无关）。
⇒ 由此得出一条更重的结论：**v3.10.0 的 `+2 帧` 对它所声称防护的场景从未生效过，却对真实乘车造成了 +6s 代价** —— 这正好解释了需求 6 的全部症状。

## 2. Q2 区② 到底守住了什么

先把区② 的定义抄准（`useRideTracking.ts:398-416`）：

```
区① dToBoard ≤ 40m                  ⇒ baseNeed
区② dToBoard > 40m 且 alongM < 60m   ⇒ baseNeed + 2
区③ alongM ≥ 60m                     ⇒ baseNeed
```

### 2.1 无车辆佐证时：**数学死区，零价值** ——【推断自 1.3 + 实测】

无佐证 ⇒ `displace 门 = max(60, …) ≥ 60`。而区② 的定义就是 `alongM < 60`，由 1.3 的不等式 `disp ≤ alongM < 60` ⇒ **必失败**。
⇒ 区② 在无佐证时**不可能对命中帧生效**，`+2` 永远无事可做。

【实测】`.verify/_q6-band.mts`：
```
无佐证：过站到 +50m 停住（along<60）  v380=不触发  zone=不触发    ← 连 v380 都不触发
无佐证：过站到 +200m 停住（along>60） v380=18s     zone=18s  Δ=0s  ← 区③，不受影响
```

### 2.2 有车辆佐证时：确有真实价值，但极窄 ——【实测】

有佐证 ⇒ `displace 门 = 60 × R1_ACCEL_DISPLACE_FACTOR(0.6) = 36m`（`boarding-detect.ts:71`、`:357`）。
此时 `alongM ∈ [36, 60)` 这条 **24m 带**里，`disp` 可以达到 36~60 ⇒ **能命中** ⇒ 区② 的 `+2` 真正生效。

`.verify/_q6-prevent.mts` 全量扫描 **80 组**（2 种佐证 × 4 个速度 8.5/10/12/20 km/h × 10 个停点 20~200m）：

```
区② 只延后：18 组
区② 真阻止：10 组   ← 只有这一类才算"有价值"
无影响/都不触发：52 组
```

**真阻止的 10 组全部集中在**：
```
有佐证 8.5km/h 停 55m
有佐证 10km/h  停 40/45/50/55m
有佐证 12km/h  停 40/45m
```
⇒ 区② 的价值画像非常清晰：**「车站旁跑步赶车 / 沿路跑过站台，在过站 40~55m 处停下」这类误判，且必须有车辆佐证把位移门放宽到 36m**。

**但要注意一个反向事实**（同一批实测）：这个带里也包含**真乘客**——
「公交刚出站、在 40~55m 处遇红灯停住」在形态上与"过站跑步停下"**无法区分**，区② 同样会让他多等 6s（`有佐证 20km/h 停 40~55m ⇒ 延后 6s`）。
⇒ 区② 是一个**双向代价**的窄带护栏，不是纯收益。

## 5. Q4 我的推荐：**(a) 接受现状（保留 60m）**

理由按权重：

1. **区② 已被证明有真实价值**（10/80 组真阻止），且集中在"过站 40~55m 停下"这个 92a8912 原本想防、但位置判断错了的形态。删掉它会放走这批误判 —— 我们不能一边说"不放松防误判"，一边删掉唯一真正生效的那道护栏。
2. **区② 的代价有界且可解释**：只在「有佐证 + 触发时 alongM ∈ [36,60)」时 +6s，属窄带；而最常见的"站台起"形态 **Δ=0s**（需求 6 的症状已修好）。
3. **(b) 会把最常见形态打回原形**（12s→18s），(c) 会重新引入 `walkActive` 误加严 —— 两者都与需求 6 的立项理由冲突。
4. **它现在近乎"免费"**：无佐证时数学上不生效 ⇒ 大部分行程根本不经过它的判断。

**同时建议加一条观测钩子（不改行为，只为将来取数）**：
在 `boardNeedOf` 返回 `baseNeed + 2` 且 `res.hit` 成立时，累计一个计数并写到 `body[data-board-zone2]`（形如 `n/m`：区②生效次数 / 判定总次数）。理由：我们现在**没有任何真实数据**能回答"区② 到底多久生效一次、生效时是乘客还是跑者"。有了这个数，下一轮才可能做真正的取舍，而不是继续用合成场景争论。

### 5.1 若一定要动，我给出的次优路径（不是推荐）

**先取数，再收窄**：如果观测显示区② 生效的绝大多数是"乘客遇红灯"而非"跑者过站"，那么正确方向是**收窄而不是扩大** —— 例如把区② 的判据从"alongM < 60"改成"alongM ∈ [36, 60) **且** 该帧速度 ∈ [8, 13] km/h"（乘客在红灯前已停，速度会掉到 8 以下；跑者不会）。但这需要真实数据支撑，**现在做等于用合成场景调参**，我不建议。
