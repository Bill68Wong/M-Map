## 0. 结论摘要

1. **基线可复现**：`.verify/perf/measure-nav.mjs` 同口径可重跑出可比数据；本次三采样结果存 `.verify/perf/baseline-20261102.json`（逐次样本 + stats 分项 + 缓存头 + `outsideMs` + 时间戳）。**跑前必须确认无并发测量**，否则 p50 失真（本轮已遇，见 §2.5）。
2. **性能瓶颈已定位（供架构师参考，非功能结论）**：
   - **冷态瓶颈 = 高德路径规划（`stats.transitMs` 3.4–6.4s）与 DSAT 实时（`stats.liveMs` 1.7–2.9s）串行叠加**，冷 p90 达 **6.2–17.3s**、且**方差极大**（同一 OD 样本间可差 2×）。
   - **热态瓶颈 = DSAT 实时 `liveMs`（744–1177ms）仍在关键路径**，命中 `transit_cache` 后 `transitMs` 降到 232–1549ms，但热 p50 仍 **1.1–3.3s**。
   - **函数外固定开销 `outsideMs` ≈ 294–316ms 且极稳定**（见 §2.3）—— 这是「边缘 POP 香港 hkg1 → 函数 iad1（美东）」的建连+排队+跳转成本，服务器内部再怎么优化也去不掉，只有「迁区域 / 边缘缓存命中」能削。
   - **关键线索**：氹仔内 OD `localCandidates=240` 但 **`localKept=0~1`** —— 本地近站候选几乎未承担路径计算，全打高德；跨岛（关闸→澳科大）`localKept=56~62` 说明机制本身可用，只是氹仔内没触发。需求①最值得深挖处。
3. **缓存现状（硬证据，§2.4）**：`stations` **有 `s-maxage=3600`、实测 CDN `HIT`（age=864）** ⇒ 其「热 73ms」是真边缘缓存，非函数热；`route-shapes` **无 s-maxage（`must-revalidate`）、恒 `MISS`** ⇒ 其「热 525ms」是函数实例热，非 CDN。二者不可混为一谈。
4. **稳定性场景**：在负责人 12 场景基础上，吸收 PM「定位×车辆两维度状态模型」补齐到 **18 项**；其中 **9 项可自动化**（Playwright + CDP），**3 项部分自动化+真机补验**，**6 项必须真机**（§3）。
5. **观测钩子**：`body[data-nav-phase]`、`.nav-actions[data-track-state|data-board-detect]`、`[data-sheet-state]`、`data-nav-leg`/`data-nav-legkind`、`body[data-vehicle-layer]`、`[data-nav-z]` 已就绪。**建议新增的钩子契约见 §3.4**（两维度分开：`data-geo` / `data-veh` / `data-veh-age`，**禁止合成 `data-net`**；定位仅写 `data-user-fix="ts,acc"` 不写坐标；需求③ `data-board-match` / `data-match-source` / `data-switch-*`；需求① `data-result-stage` / `data-card-pending`（分层出结果可断言））。**无「最后更新时间戳」断言会让「数据陈旧」缺陷在自动化里隐形**（PM 提示，已纳入 §4）。

**读法**：
- 冷 → 高德 `transitMs`（3.4–6.4s）是主耗时，`liveMs` 叠加其上；`gate` 冷态 `transitMs` 达 6.4s（高德当次慢），整体 15s。

- `localCandidates=240 / localKept=0~1`（氹仔内）：本地候选几乎不被采用，全交高德。

### 2.3 函数外开销 `outsideMs`（墙钟 − `stats.ms`）

| OD | 冷 outside p50 | 热 outside p50 |
|---|---:|---:|
| home→school | 302 | 306 |
| taipa→school | 316 | 310 |
| gate→school | 301 | 305 |
| hengqin→gate | 294 | 297 |

**结论**：`outsideMs` 在所有 OD、冷热下都稳定落在 **294–316ms**，是**固定成本**（边缘 hkg1 → 函数 iad1 的建连 + 实例排队 + 跳转）。含义：
- 服务器内部（transit/live/model）再怎么优化，**至少有 ~0.3s 的墙钟地板**。
- 削它的唯一手段是「**迁函数区域到 sin1/hkg1**」或「**让请求命中 CDN（根本不到 iad1）**」。这也是 §2.4 缓存矩阵对优化收益测算的关键。

### 2.4 缓存头矩阵（硬证据 · 决定「哪条优化手段值钱」）

| 端点 | `Cache-Control`（**线上实测，非源码**） | `X-Vercel-Cache` | `Age` | 判定 |
|---|---|---|---:|---|
| `/api/stations` | `public`（源码含 `s-maxage=3600`，被 Vercel 剥离） | **HIT** | 864 | **真 CDN 命中**（热 73ms 是真边缘缓存）|
| `/api/route-stops` | `public`（源码同上） | **HIT** | ~1185 | 真 CDN 命中（架构师实测）|
| `/api/route-shapes` | `public, max-age=0, must-revalidate` | **MISS** | 0 | 无边缘缓存；热 525ms 是**函数实例热** |
| `/api/route-lines` | 无 `Cache-Control`（仅 `force-dynamic`） | **MISS** | 0 | 无边缘缓存（同 route-shapes）|
| `/api/route-vehicles` | `no-store` | MISS | 0 | 实时，无缓存 |
| `/api/nav` | `no-store` | MISS | 0 | 实时，无缓存 |

`X-Vercel-Id: hkg1::iad1::…` ⇒ **POP 在香港、函数在 iad1（美东）执行**，每次动态请求需跨太平洋往返（对应 §2.3 的 ~300ms）。

> **方法论要点（务必记住，否则会看反）**：`Cache-Control` **不能**用来判断是否 CDN 命中——**Vercel 会把 `s-maxage` 从浏览器可见的响应头剥离，只留 `public`**，但缓存决策在内部照常生效。判命中只能看 **`X-Vercel-Cache` + `Age > 0`**。（架构师最初 curl 见 `public` 无 s-maxage 就误判「无缓存」，即栽在此。）
> **范围钉死**：「静态接口无缓存」只对 **`route-shapes` / `route-lines`** 成立（二者源码全文无 `Cache-Control`，仅 `force-dynamic`，恒 MISS）；`stations` / `route-stops` **确会 CDN 命中**。

> **跨脚本比较铁律**：不同测量环境（本机 HTTP 代理/TLS）有系统性偏差（架构师环境实测地板 TTFB 157–180ms，比我高约 155ms）。⇒ **绝对毫秒数一律以 `baseline-20261102.json` 为准**；跨脚本只用「同环境内的差值」横向比，绝不直接比绝对值。

## 3. 表二 · 稳定性场景复现矩阵（需求② + ③观测）

### 3.0 状态模型（吸收 PM：拆两维度，不要合成一个「报错」）

导航失效由**两个独立维度**共同决定，场景与断言应分开设计：

- **维度 A · 我的定位**（`data-geo`）：`ok｜low_acc｜stale｜denied｜unavailable｜timeout`
- **维度 B · 车辆数据**（`data-veh`）：`fresh｜stale｜failed｜open`（`open`=熔断中）

平台依据（可写进用例前置条件）：页面隐藏后浏览器停发 rAF、节流 `setTimeout`，隐藏超 30s 进预算节流；Web 无「始终允许」后台定位。`GeolocationPositionError.code`：`1=PERMISSION_DENIED`（用户可自修）/ `2=POSITION_UNAVAILABLE`（隧道室内）/ `3=TIMEOUT`，**三者文案必须互不相同**。

> **观测命名（PM 定稿，硬约束）**：两维度用两个**独立**只读属性 `body[data-geo]` 与 `body[data-veh]` 表达，**禁止合成单一 `body[data-net]`**。合成会诱导实现依赖 `navigator.onLine`（MDN 明确其不可靠），且会让 #14「连 WiFi 无外网」无法验证「是否偷偷依赖了 onLine」。

轮询/定位常量（用于设定断言窗口）：
- 车辆轮询 `POLL_MS = 12_000`（`useRideTracking.ts:51`）；乘车追踪 5s tick。
- 定位节流 `gpsIntervalMs` = 乘车 1500 / 导航中 3000 / 空闲 10000（`NavShell.tsx:341`）。
- `watchPosition`：`enableHighAccuracy:true, timeout:10_000, maximumAge:0`；`visibilitychange→visible` 触发重新取位（`useUserFix.ts:149`）。
- 手动刷新冷却 `COOLDOWN_VEHICLE_SEC = 5`（`useCooldown.ts:24`）。

### 3.3 模拟手段能力对照（Playwright / CDP 原语）

| 原语 | 能模拟 | 局限 |
|---|---|---|
| `context.setOffline(true/false)` | 断网/断连恢复 | 只切「有/无网」，不能模拟射频切换、IP 变更、丢包 |
| `CDP Network.emulateNetworkConditions` | 延迟/带宽/丢包、3G | 单连接级；packetLoss 需较新 Chromium |
| `CDP Emulation.setGeolocationOverride` | 坐标 + 精度 accuracy | 只能给「有 fix」，**不能模拟硬件失锁/GPS 完全无信号** |
| `CDP Page.setWebLifecycleState` | frozen/active（近似切后台） | Chromium 语义 ≠ iOS 真实挂起 |
| `page.clock` | 虚拟时间前进（30s/2min/5min）、触发定时器 | 不影响真实网络/系统生命周期 |
| `page.evaluate` override `visibilityState`+dispatch | 触发可见性切换逻辑 | 需 override 只读属性；不代表 OS 真实切后台 |
| `CDP Browser.setPermission / resetPermissions` | 中途改定位权限 | Chromium 可信；iOS 真机权限须真机 |
| `page.route(...).fulfill/abort` | 制造接口失败/停更（连续 N 次、旧时间戳）| 仅网络层，测不到原生崩溃 |

### 3.4 建议新增的观测钩子契约（advisory，交前端/架构师评估）

> 命名原则（PM 定稿）：两维度**分开成独立只读属性**，**禁止合成单一 `data-net`**（理由见 §3.0）。以下为**事实型状态枚举**，不绑定任何具体视觉（Q3 的 A/B/C 三种拍板结果都能跑）。

| 钩子 | 取值域 | 语义 |
|---|---|---|
| `body[data-geo]` | `ok｜low_acc｜stale｜denied｜unavailable｜timeout` | 维度 A 定位。`stale`=**曾拿到过 fix**但超阈值无新帧；`unavailable`=从未拿到或报错；`low_acc`=有 fix 但 accuracy 超门（与 `stale` 正交，同时发生时 **`low_acc` 优先**，因为「有数据但不准」比「没数据」更该显示精度圈）。**精度门 150m、`stale` 阈值 30s**；首页刚进入、未点「开始导航」前为 `unavailable`（诚实表达）⇒ **断言 `ok` 的用例必须先授定位 + 等到一帧** |
| `body[data-veh]` | `fresh｜stale｜failed｜open` | 维度 B 车辆数据。**优先级 `open > failed > stale > fresh`**；`stale`=有数据超阈值未更新（阈值 30s）；`failed`=最近一次请求失败（可选 `body[data-veh-fail]=n` 连续失败次数）；`open`=熔断中（**当前无数据源、为预留值**，本阶段验收不覆盖熔断路径）|
| `body[data-veh-age]` | 整数秒 | 随停更递增，拿到新数据归零 —— #16 的直接断言目标 |
| `body[data-user-fix]` | `"ts,acc"` | 每次 accept 的 fix 写入。**只 ts 与 acc，不写经纬度**：多数断言只需时间单调/精度变化，坐标用 `.user-dot` 屏幕位移代替；避免把用户坐标带进 DOM（截图/共享屏幕/录屏不外泄位置）|
| `.nav-actions[data-board-match]` | `none｜auto｜confirmed｜corrected｜manual` | 需求③匹配态。**口径（team-lead 最终裁决）**：`auto`=自动判定（**含高置信锁定与中置信待确认**）、`confirmed`=**用户确认过**（Q5 轻确认界面，本期未实现 ⇒ **本期恒不出现，断言标 SKIP 不标 FAIL**）、`corrected`=「不是这辆」重锁、`manual`=手动标记/选车、`none`=无。**中置信不得占用 `confirmed`**：它用 `auto` + `data-match-pending="1"` 表达——否则将来落 Q5 时同值同时代表「系统不确定」与「人已确认」两件相反的事，验收与排障再也分不开 |
| `.nav-actions[data-match-pending]` | `"1"` 或缺失 | 需求③中置信标记（**建议新增**）：`"1"`=中置信待确认（配 `pendingPlate` 展示车牌、`plate` 仍 `null`、进度走 GPS）。与 `data-board-match="auto"` 组合即「中置信」 |
| `.nav-actions[data-match-source]` | `gps｜gps+vehicle｜vehicle｜manual` | 需求③匹配来源。`gps+vehicle`（`autoBoardOf` 定位命中且有车辆佐证，`boarding-detect.ts:266`）与锁车牌后的 `progressSource=vehicle` 都是**正常后置来源**，不得判违规；ADR-108 约束的是「**上车触发器**不得由车辆信号单独触发」（R1 只降门槛、不触发），故断言只查「无定位证据却判定上车」，**不查这些值的出现**。[注] 断言只挂在 `data-board-match` 的 `none→auto/confirmed` **跃迁瞬间**读本属性；稳态读到 `vehicle` 不断言。`data-board-match`（事件）与本属性（状态）语义不同轴，故必须是两个独立属性 |
| ~~`.nav-actions__src`（来源标注）~~ | ~~`实时定位｜依据车辆位置｜手动`~~ | **★ 2026-11-03 作废（负责人拍板）**：三种来源展示标签已从 `NavTrackBar` 删除（AC-23 作废），本选择器**不再承载来源语义** —— 它现只剩 `anomalyHint`（疑似还没上车/已下车）与 `NavStrip` 的 `waitSrc`（按班距估/按时刻表）两个消费方。来源改由数据层 `progressSource` + 独立观测属性 `data-match-source` 承担，断言见上一行。
| `pendingPlate`（辅助展示） | 车牌文本 + 「待确认」 | **非 data-* 属性**（组件 prop 渲染）：medium 时 `plate=null`、用车牌文本 + 「待确认」只做展示。AC3.8 据此判 medium，**不要断言 `plate` 非空** |
| `[data-switch-list]` 条目数 + `[data-switch-reason]` | 条目数 ≤3；reason∈`wrong_vehicle｜not_boarded` | 换车面板：断言「最多 3 辆、按距离排序、无自由输入框」|
| `[data-result-stage]` | `skeleton｜partial｜full` | **需求①分层出结果**容器阶段（Q1 选 A/B/C 都可用：B 下长期停在 skeleton，C 下 partial 即「估算卡」）。用于区分「先出的结构」与「后补的数字」|
| `[data-card-pending]` | 逗号分隔待补字段（如 `eta,walk`）；空=全部就绪 | **需求①**逐卡待补字段：断言「结构先出、数字后补」，且 `full` 后必须为空（防残留占位）|

> 需求④ 现成资源：`TierBadge` 已带观测钩子 `data-catch-hint="on"`（`src/components/RoutePieces.tsx:81`）⇒ AC4.1 直接定位该徽标断言文案，无需新增钩子。

> **阈值约束（不代替架构定参数）**：`stale` 阈值必须 **> 2×POLL_MS（=24s）且 ≤ 90s**（建议 30s），否则正常抖动会误报。
> **[注] `data-veh-age` 可信前提**：先修 D5——`useRideTracking.ts:857` 的 `setLastUpdateTs(Date.now())` 被 GPS 帧无条件写入，须拆出 `lastVehicleTs` 单独计时，否则 age 会被 GPS 帧一直刷成 0（架构师确认，净增 ≈0）。
> **落地状态（架构师 ADR C14）**：`data-geo` / `data-veh` / `data-veh-age` / `data-user-fix` **本轮做**；`data-board-match` / `data-match-source` / `data-switch-*` 随匹配算法一起交付 ⇒ **本文验收标准按「必须」写**。

### 3.5 定位错误码文案矩阵（PM，可断言但不绑原文）

| code / `data-geo` | 触发 | 期望文案方向 | 硬断言 |
|---|---|---|---|
| 1 `denied` | 用户拒绝/系统撤销 | 「去设置开启定位」+ 手动入口可用 | 三者**互不相同**；含语义词「设置」；**不得**含「正在检测车辆」这类正面语义 |
| 2 `unavailable` | 隧道/室内/无信号 | 「暂时无法定位（信号弱）」| 含语义词「信号」|
| 3 `timeout` | 取位超时 | 「定位超时，正在重试」| 含语义词「重试」|

> **断言方式（PM 定稿）**：除「三者互不相同」是硬要求外，**不做全字符串相等**（措辞随文案门禁 43 禁用词与版本调整）。改为「三者互不相同 + 各自包含关键语义词（设置 / 信号 / 重试）」，避免用例被文案门禁反复绊住。

### 3.6 组合语义：定位不可用 ≠ 导航不可用（升为独立 AC2.7）

最易漏、也最该写成断言的部分——防止实现把「某个轴坏」写成「整页降级」：

- `data-geo ∈ {denied,unavailable,timeout}` 且 `data-veh=fresh` ⇒ **仍正常显示「还有 N 站 / 约 X 分钟」与自动下车提醒**，只是无蓝点、无沿线跟随、`data-board-detect=paused`。
- `data-geo=ok` 且 `data-veh ∈ {stale,failed}` ⇒ 定位跟随正常，但到站数字降级为「最后更新 X 秒前」，**不得继续显示「实时」**。
- **两轴同时坏** ⇒ 才允许「导航不可用」级表达，且必须保留手动下车入口。
- 对应场景：#10/#12（单轴 A 坏）、#13/#16（单轴 B 坏）各补一条「另一轴正常时仍可用」断言。

## 4. 表三 · 验收标准建议（EARS，全部可机验）

> 格式：While/When/If + 系统 + 必须 + 行为。指标均可量化、可用 §3.1/§3.4 钩子或 network timeline 断言。
> 阈值基于 §2 基线 + 行业做法（PM 文档 Q2 建议 8s 超时）：**热态**要显著优于现状，**冷态**上限设在现状 P90 内并强制超时降级。

### 需求② 断网 / 切换网络 / 切后台稳定性

| 编号 | EARS 验收标准 | 断言方式 |
|---|---|---|

> **[关键口径] `frames` = 对齐成功的「用户帧数」，不是车辆样本数**（`match-mile.ts:126`，容差 `MATCH_ALIGN_TOL_MS = 6s`）。一条车辆值可与用户序列中落在 6s 容差内的**所有**用户帧配对 ⇒ 5s 采样得 2 帧、1Hz 得 6 帧。由此三条禁令：
> - **禁止** `expect(frames).toBe(1)` 验证「单帧车辆场景」；要构造 `frames=1` 必须同时让用户序列也只有 1 帧（`userHistory: []`）。
> - **禁止**假设「车辆样本少 ⇒ frames 少」；`frames` 大也不代表样本多（证据强度还看 `logL`）。
> - 「池子非空（`poolSize>0`）」**不能**推出「能锁定」；反之亦然——`poolSize` 与 `frames` 是两个独立维度。
> - 实测对照：同车同 90s 轨迹，`colored` 两端都传 ⇒ `frames=19`→`high`；录制侧漏传 ⇒ `frames=2`→`medium` + `gate:frames-high`。

> **[reason 枚举] `MatchResult.reasons` 有 4 个命名空间（不是只有 `gate:`）**。任何「reason ∈ 固定集合」断言必须覆盖全部 4 个，否则会假红或漏新增值：
>
> | 命名空间 | 值 | 说明 |
> |---|---|---|
> | ① `gate:`（8） | `gate:frames`（frames<2，连 medium 都不够）、**`gate:frames-high`（2≤frames<3，够 medium 不够 high）**、`gate:logl`、`gate:score`、`gate:margin`、`gate:diverging`、`gate:diverged`、`gate:evidence` | 决策层门禁 |
> | ② 硬门（6，**无 `gate:` 前缀**） | `switch:disabled`、`g1:geometry`、`g1:stop-mains`、`g2:no-user-anchor`、`g3:empty-pool`、`g4:no-scorable-vehicle` | **[注]** `g3`（池子真没车）与 `g4`（有车但全不可评）**不是同一件事** |
> | ③ 跳过（2，**带车牌后缀、动态串**） | `skip:no-mile:<plate>`、`skip:no-frame:<plate>` | 必须前缀匹配 `skip:`；`if (skipped < 3)` 截断 ⇒ **不能数 skip 条数推车数** |
> | ④ 逐项判负（`s*:`） | `s1:position`/`s2:speed`/`s3:direction`/`s4:not-passed`/`s5:unreachable`、`s1:diverging` | `s1:diverging`（证据层：残差在拉大）≠ `gate:diverging`（决策层：被判 medium 而非 high）|
>
> **[禁用] 不要用 `score` 判断帧数是否充足**：`combine` 对**未参与项按比例回填权重** ⇒ 单帧时权重分母从 1.0 缩到 0.5，均分被结构性抬高，实测单帧 `score≈1.0`、`logL≈2.36`（已过 medium 两道门）。⇒ **分数门测的是「已有证据有多一致」，帧数门才是唯一度量证据量的那道门**。
> **[禁用] 不要从 `low()` 分支读 `logL/score/frames` 反推内部打分**：`low()` 把它们**全部归零**（契约：无可信结论就不报帧数），读到 0 是归零结果、不是算出来的 0。要判某道门是否生效，只能看 `reasons`，或绕过 `matchVehicle` 下探 `scoreVehicle`。
> **[注] `gate:frames` 与 `gate:frames-high` 必须区分**：前者「证据太少」、后者「再多攒一帧就能升 high」，排查方向相反（新增前者曾把 `frames=2` 误报成 `gate:margin`）。
> 现有产物中**无 reason 白名单断言**（已 grep 确认）；后续若加，必须含全 8 值。
> **触发区间不重叠（静态可证）**：`gate:frames` ∈ frames `[0, MATCH_MEDIUM_MIN_FRAMES)`＝`[0,2)`；`gate:frames-high` ∈ `[MATCH_MEDIUM_MIN_FRAMES, MATCH_MIN_FRAMES)`＝`[2,3)`。前者在 `match-vehicle.ts:210` 直接 `return low`，后者嵌套在其后 ⇒ 隐含下界 ≥2，两区间天然不相交。契约脚本 J5a/J5b/J5c 已固化为静态守卫，并经**变异测试**证明非空转（改守卫常量 ⇒ J5b 红；把 `frames-high` 移出嵌套分支 ⇒ J5a 红）。
>
> **分层归属**：`gate:frames-high` 的**行为**用例由后端 `test-match-vehicle.ts` 第⑨组 B 段持有（61/61，且已加固为「另三道门 logL/score/margin 全部已达 high 门槛 + reasons 不含 gate:logl/score/margin」，真正证明"唯一未满足的是帧数"）；QA 侧只做上述**静态枚举漂移 + 区间守卫**，不重复造行为用例（保持测试作者与实现作者解耦）。
> **夹具脆弱点（写行为用例须注意）**：该用例的 `frames=2` 是「对齐容差 6s ÷ 用户采样 5s」的副产物；若夹具改成 1Hz 采样 ⇒ frames=6 ⇒ 直接 high、用例变红。要可控请直接约束 `userHistory` 帧数（给 2 帧用户历史 + 2 条车辆样本），与采样率解耦。

| AC5.9 | **入口—调用点配对（静态门）**：本轮新增/导出的能力（`matchVehicle`、`loadFold`、`observe-hooks` 导出、`remainingSec` 等）必须**至少 1 处非定义引用**；0 处即失败并**指名**哪个能力无调用点。 | 静态脚本 `.verify/check-entry-usage.mjs`（grep 能力名、排除定义行计数）；本类缺陷 **tsc/lint/build/单测全绿但功能为 0**，故须独立静态门，不能靠运行期发现 |

**健康检查字段（`/api/health`，验收可用）**

| 字段 | 含义 | 注意 |
|---|---|---|
| `cache.staticRows.status` | `ok / oversize-warning / skipped-oversize / error / not-run` | 本地必为 `error`，只认部署域名 |
| `cache.staticRows.sizeBytes` | 约 1.16MB（1,220,615 B） | 须 ∈ [0.8MB, 2MB) |
| `cache.transitCacheTtl` | 60 | RL4 |
| `cache.routeIndexAgeSec` | route-index 缓存龄 | **从未装载为 `null` 而非 0**（0 会被误读成"刚装载"）|
| `cache.warmRequested` / `cache.warmError` | 预热是否请求 / 失败原因 | 预热失败**不改状态码**，只回填 error |
| `regions` | `VERCEL_REGION` | 本地 `unknown` |

> **warm 陷阱（必须写进脚本）**：`/api/health?warm=1` 在本地 tsx 会 `status="error"` + `fallbackUsed=true`——**预期**（非 Next 运行时无 incrementalCache，`loadStatics` 回落直查）。**AC5.3 的 `status==="ok"` 只能在部署域名验，不能拿本地读数判红。**

> 验收门纪律：AC1.4/AC1.5 由 `measure-nav.mjs` 的确定性数字判定（实现者不可改阈值自证），AC2.x/AC3.x/AC4.x/AC5.x 由 DOM 钩子 + 时间戳 + 网络时间线断言，二者与人工真机复核互补。
>
> **[项目级测试纪律] 断言定位一律走 `data-*` 钩子，禁止用样式类**。理由（本轮实测教训）：①样式类随改版重命名，钩子不会（项目先例 `.nav-actions[data-*]`、`body[data-*]`）；②**结构陷阱**——同名样式类可能被「骨架屏 / 隐藏副本」复用（本轮 `.rc-list .card` 先命中 `aria-hidden` 的 `rc--skeleton` 骨架卡，`waitForSelector` 早已通过、`click` 永久超时，8 条用例全 SKIP）。核法：真卡出现后骨架会卸载，断言必须写**双条件**（骨架不存在 **且** 目标元素 >0），单断元素存在会被骨架期骗过。样式类只留给视觉回归类用例。

## 5. 自动化 vs 真机 分工总结

| 归类 | 场景编号 | 说明 |
|---|---|---|
| **可自动化（Playwright + CDP）** | 1,2,3,6(断连),7,8,9,13,14,16,17,18 | 切后台（Chromium 生命周期）、弱网、丢包、断网、接口失败/停更、WiFi 无外网、定位超时、定位漂移 |

| **必须真机** | 4,5,6(真实射频) + 10/11/12/15 真机兜底 | iOS Safari 挂起、PWA 独立模式、Wi-Fi/移动数据真实切换、锁屏时间真实性、系统级权限与 GPS 失锁 |

## 6. 风险与待确认

1. **需求③④交互未定稿**（PM 文档 Q1/Q2/Q5/Q6 待拍板）⇒ AC3.x/AC4.x 中「一次性确认条」「颜色是否保留」将随决策调整，待定稿后同步。**钩子契约（§3.4）按事实枚举写，三种拍板结果都能跑，不绑视觉。**
2. **`stations` 冷态无法用 `_cb` 复现**：`_cb` 只破 CDN，服务端/DB 已热；真冷需「CDN + DB 双冷」（等 `s-maxage` 过期或换冷实例）。切勿把 `_cb` 的 87ms 当作冷态基线。
3. **`/api/route-vehicles` 波动大**（DSAT 上游），单次不作结论，固定多次采样取 P90 并按时段（高峰/非高峰）分列。
4. **定位坐标与新鲜度无 DOM 钩子**（§3.4）：建议新增 `body[data-geo]` / `body[data-veh]` / `body[data-veh-age]` / `body[data-user-fix]="ts,acc"` 与需求③钩子；**不新增 `data-net`**（会诱使依赖 `navigator.onLine` 且使 #14 失效）。否则「数据陈旧」在自动化里隐形。
5. 本次为**非高峰时段**（澳门时间约 21:05）；高峰期基线需另测单列，避免混用。
6. **并发纪律**：任何前后对比必须单脚本、确认无其他成员同时打线上；本轮已实证并发可使同 OD 热态差 6×（8864 vs 1451ms）。
7. **AC2.3 三档文案（已派前端，待交付后验）**：`data-geo` 已区分 `denied/unavailable/timeout`（钩子层可断言）；界面三档文案由前端施工（`useRideTracking` 加 `geo` 入参 + note 三分支 + `NavShell` 传 `userFixR.geo`，约 20 行；约束：三档语义互异不绑字面 / `low_acc` 与 `stale` 不得走错误文案 / 跑文案门禁）。**不标 SKIP，按「待前端交付后验」处理**（断言用「各自含 设置/信号/重试 语义词 + 三者互不相同」，不逐字匹配）。
8. **`data-veh=open`（熔断）当前无数据源**：`/api/route-vehicles` 无熔断枚举，`open` 为预留值 ⇒ **熔断路径本阶段不可触发、验收不覆盖**，记为下轮待办。
9. **S3 匹配用例的运行前提**：`MATCH_VEHICLE_ENABLED` 默认 **`false`**（Spec §10 回滚手段），关闭时 `data-board-match` 恒为 `none`、`data-match-source` 恒为 `gps`。⇒ **AC3.1/AC3.8 必须在 `useRideTracking({ matchEnabled: true })` 或已翻开关的环境下跑**，否则一律 `none` 会被误判为"匹配未生效"。用例前置须显式写明；灰度时机由 team-lead 定。
10. **AC2.3 三档文案已落地**：抽为纯函数 `src/components/nav/geo-note.ts`（`noteOfPausedGeo(geo)` 无 React 依赖）⇒ **可在纯逻辑脚本里直接 import 断言**，不必起浏览器；渲染层（是否真出现在 DOM）由 Playwright 场景脚本覆盖。
