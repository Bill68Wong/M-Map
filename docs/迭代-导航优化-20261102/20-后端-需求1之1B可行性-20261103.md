## 1. 依赖可调性

### 1.1 签名与 Pool 依赖

| 依赖 | 签名 | 是否真用 `pool` | 缓存层 | 位置 |
|---|---|---|---|---|
| `loadStatics` | `async (pool: Pool, force = false): Promise<RecStatic>` | **否** —— 函数体第一行 `void pool;` | ① 跨实例 **Data Cache**（`unstable_cache`，`revalidate:60`，`tags:["rec-static"]`，key `rec-static-rows-v2`）② 进程内 60s（`g.__recStaticCache`） | `query.ts:343-351`、`:227-232` |
| `loadHeadway` | `async (pool: Pool, force = false): Promise<HeadwayIndex>` | **是**（冷路径 3 条 SQL） | 进程内 10min（模块级 `let cache`，**非 Data Cache**） | `headway.ts:72-77`、`:69` |
| `nowBucketOfHolidayAware` | `async (pool: Pool, ms: number): Promise<string>` | 是（冷路径 1 条 SQL） | 进程内 6h（模块级 `let cache`） | `holidays.ts:34-37`、`:11` |
| `buildStrips` | `(card: RecommendCard, ctx: StripBuildCtx): SegmentStrip[]` | **完全不需要 pool**（纯函数） | 无（纯） | `strips.ts:58` |

**结论：handler 里可以直接 `await loadStatics(getPool())`，不需要任何额外初始化。** `getPool()` 是 `globalThis` 单例（`db.ts:28-33`），`new Pool()` 在 node-pg 里是惰性的 —— 不调 `.query()` 就不建连。`loadStatics` 连它都不用。

> 一个容易误读的点：架构师文档把 `loadHeadway` 记为「`async (pool: Pool)` ⇒ server-only」（`headway.ts:72`）。这个结论**方向对，但理由要看清**：`headway.ts:23` 的 `import type { Pool } from "pg"` 是 **type-only**（编译后完全擦除，不会把 pg 打进客户端包）；它真正的「server-only」体现在**语义**上——一个 `await pool.query()` 的函数只能在服务端执行。
> ⇒ 这个结论**不构成 1-B′ 的障碍**：Route handler 本身就是服务端运行时，直接调没有额外门槛。

### 1.2 冷热路径实测

环境：本机 → Supabase `ap-southeast-1`（新加坡）。生产区域见 §1.4。

| 项 | 冷（本进程首次） | 热（缓存命中） |
|---|---|---|
| `loadStatics` | **713.4ms** | **0ms**（连续 20 次平均 0ms） |
| `loadHeadway` | **152.6ms** | **0.1ms** |
| `nowBucketOfHolidayAware` | **43.3ms** | **0ms** |
| 三者合计 | **≈909ms** | **≈0ms** |

DB 基线（用于拆解）：纯 RTT `SELECT 1` = **40.6ms**；`segment_stats` 全表单查 = **272ms**（14,951 行，传输是大头）。

⇒ 冷 713ms ≈ 最大单查 272ms（14 条并行，一个 RTT 窗口）+ 索引构建 ≈400ms（**推导值，未单独测**，见 §6-H2）。

每次请求的**纯计算**成本（这才是热路径的真实开销）：

| 操作 | 实测 | 折算 |
|---|---|---|
| `lookupHop` × 3000（整线 15 跳 × 200 轮） | 1.9ms | **0.0006ms/次** |
| `headwayAt` × 2000 | 2.4ms | **0.0012ms/次** |
| `buildStrips` × 200 | 1.7ms | **≈0.009ms/次** |

**⇒ 热路径下一次重算的服务端计算 ≈ 亚毫秒级。** 端到端 p95 将由 HTTP 往返与客户端网络主导，不是计算。

### 1.3 依赖链上的一个可省项

`loadHeadway` **只在卡有 ≥2 段载具时才需要**（第 2 段起的候车重估）。单段卡（澳门常见）完全用不到 `HeadwayIndex`。

⇒ 实现时应写成 `const headway = card.rides.length > 1 ? await loadHeadway(pool) : null`，单段卡省掉冷路径 152.6ms 与 3 条 SQL。

### 1.4 区域：`vercel.json` 已改为 `hkg1`，历史注释里的 iad1 数字不再适用

`vercel.json` 现为 `{"regions": ["hkg1"]}`（v3.7.0 · ADR C1）。而 `live.ts:22`、`db.ts:46` 等处的「iad1 → 新加坡 ≈230ms/次建连、staticMs=2335ms」是 **改动前的历史实测**。

⚠️ 读那些注释时不要直接外推。当前 hkg1 → 新加坡的地理延迟远小于 iad1 → 新加坡。**生产冷路径的真实水平需要用 §1.5 的方法复测，不能用历史数字，也不能用我这台本机的数字。**

## 2. 成本核实：确实不打高德、不打 DSAT

### 2.1 静态证明（逐个模块）

对 1-B′ 的完整 import 链逐文件统计外部调用痕迹（模式：`fetch(` / `axios` / `http(s)://` / `queryEta` / `getBusPositions` / `getBusLocations` / `fetchTransitPlans` / `fetchWalkingSteps`）：

| 模块 | 命中 |
|---|---|
| `recommend/query.ts` | 0 |
| `recommend/model.ts` | 0 |
| `recommend/enumerate.ts` | 0 |
| `recommend/segment-lookup.ts` | 0 |
| `recommend/headway.ts` | 0 |
| `recommend/catch-up.ts` / `score.ts` / `transfer-slack.ts` | 0 |
| `lrt/next-departures.ts` / `eta.ts` / `map.ts` / `pattern.ts` / `day-type.ts` | 0 |
| `dsat/route-index.ts` | **1 —— 但只是注释**（`:5` 提到 `queryEta` 的名字，无调用） |
| `rebuild/holidays.ts` / `buckets.ts` | 0 |
| `nav/strips.ts` | 0 |

**无模块级副作用**：以上文件均无顶层 `fetch` / `setInterval` / 顶层 `await`。

### 2.2 语义证明（为什么可以不打）

用户上车后，剩余时间轴的每一段都不依赖实时数据：

| 段 | 数据来源 | 外部调用 |
|---|---|---|
| 当前段剩余乘车 | `lookupHop(segIdx, …)` 或客户端 `segRemainSec` | 0 |
| 下游各段乘车 | `rideOfHops(segIdx, …)`（巴士）/ 常量（轻轨） | 0 |
| 下游各段候车 | `headwayAt(headway, route, 到达时刻)`（`route_frequency`） | 0 |
| 换乘步行 | `card.transfers[i].minutes`（`transfer_walks` 静态） | 0 |
| 末段步行 | `card.walkIn.minutes` | 0 |

关键：`model.ts` 里**只有第一段**强依赖 `ctx.live`（`:463` `ctx.live.get(first.route)`，取不到就整条剔除 `:465`）。而用户已上车 ⇒ 首段已成历史 ⇒ **1-B′ 不调 `modelOption`**，也就不会踩这个依赖。

### 2.3 唯一需要点名的「隐藏成本」

不是外部调用，而是**冷实例的 DB 冲击**：

- 一个冷实例的**首个**重算请求若 Data Cache 也 miss ⇒ 14 条并行 SQL（`loadStatics`）+ 3 条（`loadHeadway`）+ 1 条（`holidays`）。
- 多实例同时冷启动 ⇒ N × 14 条并发查询打向主库。
- 缓解：Data Cache 是**跨实例**的，且 payload 实测 **1.16MB < 2MB 上限**（探针读 `__staticCacheObs`），所以**生产环境会真的写入**、能挡住冷实例的 DB 直查。

> ⚠️ 探针里 `status=error fallback=true` 是**预期**：`tsx` 脚本不在 Next 运行时，`unstable_cache` 抛 `incrementalCache missing` ⇒ 按设计回落到直查（`query.ts:353-356` 注释明写此行为）。这不代表生产会 fallback。

## 3. `buildStrips` 加可选参数的兼容性

| ⑦-b 亚分钟小数 `minutes=0.04 waitMin=0.06` | PASS · 608 bytes 完全一致 |

```bash
node node_modules/tsx/dist/cli.mjs .verify/_strips-v2-equiv.ts   # 9 条 PASS / 0 FAIL
```

**为什么「无差异」是可以预期的（结构性理由，比实测更强）**：
- `buildStrips` **只读 `ctx` 的 3 处**（`strips.ts:60` `routeIdx`、`:74` `segIdx`+`nowBucket`、`:77` `nameOf`）；
- 函数体内**无时间源**（`Date.now` / `new Date` / `Math.random` / `performance.now` **全部为 0 处**）。

⇒ 它是 `(card, ctx) → strips` 的**确定性纯函数**。只要那 3 行不动，追加可选参数在结构上**不可能**改变缺省输出。

**⑧ 反向哨兵要如实说明**：这条断言当前**期望相等**，因为候选版只扩容了 ctx、还没接重估逻辑。它的价值是「证明候选版目前是惰性的」——**实现阶段接入逻辑后，本条必须改为「必须不等」**，否则就是「加了参数但没接」的死代码（本项目已踩过同类：`model.ts` 里曾有整块 `nx` 恒 `undefined` 的静默死代码，见 `model.ts:561-566` 的修正注释）。

### 3.2 ★ 一个与该文档相反的结论：**没有可用的对拍基线**

架构师 §2 第 6 项写「缺省时行为与现在逐字节一致（保护 `detail-body` 与**既有对拍脚本**）」。我核了，那句括号里的前提**不成立**：

| 脚本 | 状态 | 证据 |
|---|---|---|
| `scripts/test-route-overview.ts` | **不覆盖 `buildStrips`** —— 它测的是 `route-overview.ts` 的几何纯函数（`parsePolyline` / `cutColored` / `chooseLegs` 等） | 头部注释「覆盖：parsePolyline / nearestOnPath / cutColored / chooseShape / buildColoredLegs」 |

### 3.3 但更该选的方案：**不改 `strips.ts`，改「喂进去的 card」**

既然 `rideMin` ← `ride.minutes`（`:134`）、`waitMin` ← `t.waitMin`（`:118`），1-B′ 完全可以：

```
patchedCard = {
  ...card,
  rides[i].minutes    = 该段剩余乘车分钟（当前段用 segRemainSec，下游用 rideOfHops 求和）
  transfers[i].waitMin = 按新到达时刻 headwayAt 重估
  walkIn.minutes      = 重估后的末段步行
  totalMin / arriveAt = 新值
}
strips = buildStrips(patchedCard, ctx)      // ← strips.ts 一行不改
```

对比：

| | 改「card」 | 改「`strips.ts` 加参数」 |
|---|---|---|
| 改 `strips.ts` | **0 行** | 加 4 个可选项 + 组内分支 |
| 需要新回归基线 | 只需「同一 card 双跑」快照对拍 | 同左 + 需覆盖「参数存在」的 4 种组合 |
| 语义风险 | 无（`buildStrips` 不变） | 缺省分支被后来人改坏的风险 |
| 前端改动 | **0**（`NavStrip` 读 `strip.rideMin` 天然生效） | 0 |

⇒ **建议采用「patched card」路线**，§3.1 的对拍就退化成「快照对比」而非「双实现对比」，维护成本更低。若主理人坚持加参数，§3.1 已证明它同样安全。

## 4. 契约登记点

### 4.1 `src/lib/security/route-policy.ts`：**不需要改**

该文件只有三个常量，各自管辖明确的范围：

| 常量 | 值 | 新端点是否命中 |
|---|---|---|
| `PAGE_RETIRED` | `/timer` `/records` `/stats` `/free` `/finish` | 否（是页面） |
| `GONE_PREFIXES` | `/api/timer`、`/api/free` | 否 |
| `SAME_ORIGIN_PREFIXES` | `["/api/fav-routes"]` | 否 |

`PUBLIC_PREFIXES` 已随 ADR-106 拆除，`proxy.ts` 头部只保留了一段「若要重新上锁的 3 步」的**注释记录**（不是代码）。⇒ **新端点无需任何白名单登记**，`proxy.ts` 也不会拦（`/api/nav/remaining` 不命中任何一条规则，走 `NextResponse.next()`）。

**唯一需要动的是门禁脚本要求的「handler 内要有防护调用」**，见 4.2。

### 4.2 AC-50 门禁：`check-api-guards.ts`

判据（`:18-31`）：每个 `POST/PUT/PATCH/DELETE` 必须命中四类之一——

1. `GONE_PREFIXES` 覆盖（本端点否）；
2. `SAME_ORIGIN_PREFIXES` 覆盖 **且** handler 内真有 `acquireToken(`（本端点否）；
3. **handler 内真有** `hasInternalToken` / `requireInternalToken` / `acquireToken` / `acquireWithWait` / `isSameOrigin` 之一（`GUARD_CALLS`，`:127-131`）；
4. 显式 `ALLOWLIST` 豁免（现仅 3 条，新增需主理人批准，`:92-95`）。

**推荐走 ③ 的 `isSameOrigin(req)`**：纯字符串比较（`same-origin.ts`），**0 次 DB**。

⚠️ 三个门禁细节，踩了会返工：

- **切片匹配**：脚本按 handler 切片（`:163-181`），只在 `export async function POST` **自己的函数体**内找防护调用。写在模块顶层或别的函数里**不算**。
- **注释会被剥掉**（`stripNonCode`，`:139-153`）：写 `// TODO: 加 isSameOrigin` **不会**让门禁变绿（这是**设计如此**，`:52-54` 记了踩坑史）。
- **`export const` 是违规**：`ROUTE_EXPORT_ALLOW` 只放行 HTTP 方法 + 段配置（`runtime`/`dynamic`/`maxDuration`/`preferredRegion` 等，`:604-620`）。`export const CACHE_TTL_SEC = 5` **会被判违规**（tsc 不报、`next build` 才炸）。常量必须**不 export**。`export interface` / `export type` 可以（TS 擦除，`switch-plans` 已先例）。

门禁当前实测状态（我跑过，只读）：`通过 22 / 失败 0`、`错误码闭集：新增违规 0 · 遗留欠账 0`、`扫描 40 个 route.ts` ⇒ 新端点会成为第 41 个。

### 4.3 错误码闭集

对外 `error` 只允许 6 值：`unauthorized` / `forbidden` / `gone` / `rate_limited` / `bad_request` / `upstream_error`（`errors.ts:16-34`）。

门禁第二部门做**静态扫描**：每个 `route.ts` 里 `error: "字面量"` 必须是六枚举之一，或用 `API_ERROR.x`（三种写法都覆盖，实测输出「共扫 107 处」）。`KNOWN_DEBT` 是遗留基线，只应缩短（`:33-42`）。

1-B′ 的错误场景一律映射到已有枚举：

| 场景 | 响应 |
|---|---|

| 跨站或来源不明（`isSameOrigin` 失败） | `forbidden`（403） |
| `loadStatics` 抛错 | `upstream_error`（500），细节只进 `console.error` |

**禁止新增** `stale_card` / `remaining_unavailable` 这类第七个值（`route-stops` 曾因回 `route_not_found` 破闭集，见 `route-stops/route.ts:35-40` 的修正注释）。

### 4.4 openapi / 前端类型

- **无全量 OpenAPI。** 全仓唯一契约文件是 `docs/迭代-导航优化-20261102/04-API契约增量-mileM.yaml`，且明文规定「未在此处出现的端点/字段一律不得改动」（`:1-6`、`:12`）。新端点**必须**在此登记（`paths:` 下加 `/api/nav/remaining`）。
- **类型真相源**：`src/lib/recommend/types.ts`（client-safe，禁 import pg）。`SegmentStrip` 在 `:783`，`RecommendCard` 在 `:733`。
- **消费方 interface**：新 hook 内定义（照 `useDetailBody.ts:24-40` 的 `DetailBody` 写法）。
- **三处必须同步**：`types.ts`（若新增类型）→ 契约 yaml → 消费方 interface。漏一处 = 「服务端发了、前端看不见」的静默缺失。

### 4.5 契约字段建议（附一个易漏项）

响应建议同时给三个时间字段，理由不是「方便调试」：

| 字段 | 类型 | 为什么必须有 |
|---|---|---|
| `remainingMin` | number | 相对值，直接上屏 |
| `arriveAt` | number(ms) | **绝对锚**，客户端据此本地递减（`model.ts:879` 的 `arriveAt` 就是绝对 ms 轴） |
| `recomputedAt` | number(ms) | **服务端时钟锚**，供客户端算 `offsetMs = recomputedAt − Date.now()` |

`recomputedAt` 的必要性有**现成先例**：`/api/station/eta` 下发 `serverNowMs`，让客户端用 `depMs − (Date.now() + offsetMs)` 倒计时，注释写明动机是「旧口径 `etaSec` 是相对快照，命中 20s 缓存时会整体偏大（用户实测反馈时间不准确）」（`station/eta/route.ts:114-120`）。

⚠️ **只回相对值 = 把那个坑再踩一次**：命中服务端任何一层缓存时，`remainingMin` 会系统性偏大，表现就是「每次刷新跳一格」。

## 5. 限流与滥用

### 5.1 真实流量（先纠正一个数）

派单说「前端 5s 轮询」。实际是**两个不同周期**：

| 通道 | 周期 | 位置 |
|---|---|---|
| 自动轮询车辆帧 | **12s**（`POLL_MS = 12_000`） | `useRideTracking.ts:57`、`:1071` |
| 手动刷新冷却 | **5s**（`COOLDOWN_VEHICLE_SEC = 5`） | `useCooldown.ts:24`、`useRideTracking.ts:1654` |

⇒ 每个导航中用户：
- 常态 = **5 req/min**（12s 轮询）
- 极限 = **12 req/min**（手动连点，卡 5s 冷却）
- 若重算与刷新按钮**同一次点击各发一个请求**，则极限 **24 req/min**

### 5.2 现有设施盘点：只有 DB 令牌桶一种

| 设施 | 位置 | 成本 |
|---|---|---|
| `acquireToken(bucket, qps, capacity)` | `amap/rate-limit.ts:121` | **1 次 DB 事务**：`BEGIN` + 建行 + `pg_advisory_xact_lock` + 2×`UPDATE` + `SELECT` + `COMMIT`（`:130-161`） |
| `acquireWithWait(bucket, timeoutMs)` | `:189` | 同上 × 轮询次数 |
| 进程内缓存 | 6 处 `globalThis.__xxx` | 0 |

**没有进程内限流器**（全仓 grep `rateLimit|tokenBucket` 除 DB 桶外无命中）。

⚠️ 两点必须说清：
1. **不要用 `acquireToken`**。生产 iad1→新加坡单次记账往返实测 ≈230ms（`client.ts:45`）。在一个亚毫秒端点上加一次 DB 事务，p95 直接从「~0ms 计算」变成「≥230ms 网络」。这是**净负收益**。
2. **`route-vehicles` 目前根本没有任何服务端限流**（无 `acquireToken`，探针反向断言通过）。⇒ 「连点刷新」今天只靠前端 5s 冷却。新端点若也只靠 `isSameOrigin`，是**维持现状**而非引入新洞——但这一点要在安全口径里写明，不要让人误以为「有门禁 = 有限流」。

### 5.3 建议方案（三件套，按必要性排序）

**① 门禁：`isSameOrigin(req)` —— 必做**
- AC-50 合规（`GUARD_CALLS` 认得）
- 0 次 DB（纯 header 比较）
- 挡住「别的网站替用户发请求」

**② 进程内微缓存去重 —— 强烈建议**
- 目的不是防 CPU，是**合并「轮询与手动刷新撞在一起」**（同一次刷新点了两下、或按钮与 12s 定时器同帧触发）
- 键：`planId|legIndex|passedIdx|Math.floor(nowMs / 2000)`，TTL 2s
- 效果：24 req/min 的极限场景被压到 ≈12，且**不引 DB**

**③ 容量上限 + 周期清理 —— 必做（这一条最容易漏）**

现存 6 处缓存**全部无淘汰**，只看 `ts` 判断是否命中，**旧条目永不删除**：

| 缓存 | 键空间 | 淘汰 |
|---|---|---|
| `__switchPlansCache`（`switch-plans/route.ts:119-121`、`:320`） | `主码\|lng\|lat\|当前线路` | **无** |
| `__stationEtaCache`（`station/eta/route.ts:127-128`、`:485`） | 站主码 | **无**（键空间有限，风险低） |
| `__etaCache`（`dsat/eta.ts:130-132`、`:446`） | `站\|线路集\|方向\|终点` | **无** |

对**低频**端点，无淘汰基本无害。但 1-B′ 是**高频 + 键里带会持续变化的进度字段** ⇒ 每个用户每分钟产生多个新键，12s 轮询 × 多用户 ⇒ Map 单调增长 ⇒ **进程内存泄漏**。

⇒ 实现必须带：`if (map.size > MAX) { 清掉最早的一批 }`（或每 N 次写入 sweep 一次过期项）。**不要照抄 `__switchPlansCache` 直接 `set` 了事。**

### 5.4 不需要的东西（避免过度设计）

- **不需要** 新增 `dsat` / `transit` 之类令牌桶：本端点 0 外部调用，没有要保护的配额。
- **不需要** 新增 `purpose`：压根不进 `dsatPost()`（熔断跳过名单 `recommend`/`live_pos` 与本文无关，铁律 19 不受影响）。
- **不需要** 服务端去取车辆帧：那是 2 次 DSAT × 高频 = 24 次/分钟/用户，而 `DSAT_QPS=3`、capacity 30 是**全 Key 全局单桶**（`amap/rate-limit.ts:46-47`）⇒ 约 7 个并发用户就打满。**必须由客户端传 `legIndex` + 本段进度。**

## 附录增补 · 时间锚自洽性（2026-11-03 二轮，回应 team-lead 提问）

> 背景：team-lead 与前端都需要知道「`arriveAt` 与 `remainingMin` 是否自洽、残差多少秒」，
> 以便写 QA 容差断言。这里给可验证的答案，而不是口头保证。

### 1. 恒等式成立，残差恒为 **0ms**（不是"约等于"）

契约：`arriveAt === recomputedAt + remainingMin × 60_000`

**能恒等的原因是实现顺序**（`remaining.ts` 末尾）：
```ts
const remainingMin = round1(Math.max(0, (cursor - nowMs) / 60_000));   // 先定剩余
const arriveAtMs  = nowMs + Math.round(remainingMin * 60_000);          // arriveAt 由它**反推**
// 且 nowMs 就是 recomputedAt ⇒ 代入即恒等
```
`arriveAt` **不是**内部 `cursor` 直出，而是由四舍五入后的 `remainingMin` 反推 ⇒ 恒等式结构上必然成立。

**已锁成断言**（`scripts/test-remaining.ts` ⑫ 段，8 个用例）：有/无 `segRemainSec`、有 `nextIdx`、
最后一段、单段卡、晚点 clamp 到 0、亚分钟小数、奇数秒（13s，最易暴露取整）—— **残差全部 0ms**。
另在 handler 层锁一次（`.verify/_remaining-route-smoke.ts` ⑤ 段）：**命中微缓存时**残差也是 0ms。

### 2. 相对「真实到达时刻」的偏差上界 = **3000ms**

`remainingMin` 保留 1 位小数 ⇒ 最坏 0.05 分 = 3000ms。
实测样例（`segRemainSec=13`）：`exactMin=20.9167` → `remainingMin=20.9` → 偏差 **1000ms**。

⇒ **给 QA 的两条容差（请照抄）**：
| 断言 | 容差 |
|---|---|
| `arriveAt === recomputedAt + remainingMin*60000` | **必须精确相等（0ms）**，不是容差问题 |
| `arriveAt` vs「按卡内各段时间手工累加出的到达时刻」 | **≤3000ms** |
| 命中微缓存时 `remainingMin` 的陈旧量 | **≤ `CACHE_TTL_MS` = 2000ms**（客户端用 `staleSec` 扣） |

### 3. 缓存命中策略 = **方案 (a)**，不是 (b)

`{ ...hit.data, serverNowMs: nowMs }` —— **只刷 `serverNowMs`**；
`recomputedAt` / `arriveAt` / `remainingMin` **三者一律保持写入时的原值**。

- 选 (a) 的理由：`arriveAt` 是绝对时刻，**时间流逝不会改变到达时刻**，保持原值才是物理正确；
  同时它与 `remainingMin` 成对，恒等式不破。
- **(b) 会分叉**：若用「当前时刻 + 旧 `remainingMin`」重算 `arriveAt`，则 `arriveAt` 与
  `recomputedAt` 不再同源 ⇒ 恒等式被破坏，前端「总时长」与「到达时刻」会在同一屏上互相打架。
- 代码里已写**不变量注释块**（`route.ts` 缓存命中分支），并用 smoke 断言把「三者都不许单刷」锁死
  —— 注释会腐坏，断言不会。

### 4. `pool` 使用审计（回应「不要预热点」）

`route.ts` 内 `pool` 只有 3 个使用点，**无任何 `pool.query`、无预热点式无条件查询**：

| 调用 | 是否真建连 | 说明 |

| `loadStatics(pool)` | **否** —— 函数体首行 `void pool` | 参数仅为兼容签名保留 |

`getPool()` 本身不建连（`new Pool()` 惰性）。⇒ 单段卡冷路径只多 1 条 SQL（假期表），不是 4 条。

下面 §1 给出完整判定逻辑与残余风险。

### 1. `isSameOrigin` 判定逻辑（逐行，回应 team-lead 四问）

实现在 `src/lib/security/same-origin.ts`（纯字符串比较、0 DB、Edge/Node 通用）：

```ts
// own = 本站 host 候选集（OR 并集，任一匹配即通过）
const own = new Set<string>();
if (x-forwarded-host) own.add(firstHostOf(x-forwarded-host));  // 逗号列表取第一段
if (host)             own.add(firstHostOf(host));
if (nextUrl.host)     own.add(nextUrl.host.toLowerCase());

// 来源 host：Origin 优先（浏览器 POST 必带），缺失回落 Referer
const srcHost = hostOfUrl(origin ?? referer);
if (!srcHost) return false;        // ★ 两者都没有 ⇒ 拒绝（fail-closed，不是 fail-open）
return own.has(srcHost);           // 严格相等比较
```

**Q1 读哪几个 header、优先级？**
读 `x-forwarded-host`、`host`、`nextUrl.host` 三个。**不是优先级，是 OR 并集** —— 三个都进 `own` 集合，
`srcHost` 命中任一即通过。来源侧是 **Origin 优先、缺失回落 Referer**（不是两者都要）。
`Origin: null`（沙箱 iframe / file://）⇒ `hostOfUrl` 返回 `null` ⇒ 拒绝。

**Q2 Vercel 生产这三个值分别是什么？会不会 `Origin` 是自定义域名而 `nextUrl.host` 是 `xxx.vercel.app`？**
- 自定义域名访问时，正常情况三者**都是**自定义域名（Vercel 把原始 Host 透传给 `x-forwarded-host` 与 `host`）。
- **即使 `nextUrl.host` 被改写成部署域名，也打不穿** —— 因为 `own` 是并集，`x-forwarded-host`/`host` 仍带自定义域名。
  这正是「三个都收进 Set 而不是取单一值」的设计价值。
- 真正会失败的情形只有一种：**三个 host 全部读不到或全被改写** ⇒ fail-closed 403。
  这种情况属平台级异常（影响全站所有同源校验），不是本端点特有问题。

**Q3 主域 `macaomap.vercel.app` + 保留域 `musttoukou.vercel.app`，会不会其中一个全量 403？**
**不会，且不需要维护域名清单。** 判定基准是「**本请求自己的 host**」——
哪个域名进来的，`own` 就是那个域名，`Origin` 自然也是那个域名 ⇒ 自匹配。
`same-origin.ts` 头注释已明确写：「多域名部署 ⇒ 每个请求的 host 即自身域名，故只需与本请求的 host 比对，
不需要维护域名清单」。⇒ 新增/下线域名**无需改代码**。

**Q4 是否已在生产验证过？**
**是，但强度要说清**：
| 证据 | 强度 |
|---|---|
| `proxy.ts:94-95` 对 `/api/fav-routes*` 写请求实施，随 ADR-106 v3.6.0 上线 | 强（代码事实） |

⇒ 结论：**风险从「高（从未验证）」降级为「低（同函数、同 header 源、已上线且有双侧实机断言）」，

## 附录增补 · 六轮（纠正「双保险」误判 + 方法论沉淀）

### ★ 1. 纠正架构师修订 ⑪ 的一个事实错误：本端点是**唯一防线**，不是双保险

架构师在 17 号修订 ⑪ 写：「新增端点若在 handler 内也调一次，属**双保险而非唯一防线**」。
**这句对本端点不成立。** 实核：

```
route-policy.ts:42   SAME_ORIGIN_PREFIXES = ["/api/fav-routes"]
proxy.ts:94          if (WRITE_METHOD_SET.has(req.method) && underPrefix(pathname, SAME_ORIGIN_PREFIXES))
                     ⇒ /api/nav/remaining 不在该前缀内 ⇒ proxy **不做**同源校验
```

实测判定：
```
前缀: ["/api/fav-routes"]
路径: /api/nav/remaining
proxy 会做同源校验吗 => false
```

⇒ **`/api/fav-routes` 才是双保险**（proxy + handler 各一次）；`/api/nav/remaining` **只有 handler 这一次**。

**为什么这是设计如此、不能"顺手"补到前缀里**：
AC-50 规则 ② 的要求是「`SAME_ORIGIN_PREFIXES` 覆盖 **且** handler 内真有 `acquireToken`（A4 两件套）」。
若把本端点加进 `SAME_ORIGIN_PREFIXES`，门禁就会要求它也带 `acquireToken` —— 而
`acquireToken` 一次 DB 事务约 230ms，会把亚毫秒端点打穿（这正是我们当初否决限流方案的理由）。
⇒ 正确形态就是：**留在前缀外，靠规则 ③（handler 内真有 `isSameOrigin(` 调用）过门禁**。

**⇒ 风险评级据此调整（比此前表述更严）：**

| 项 | 此前表述 | 实况 |
|---|---|---|
| 防线数量 | 「双保险」 | **单层**（仅 handler） |
| proxy 层已生产验证（fav-routes） | 可部分外推到本端点 | **不可外推** —— 本端点根本不走 proxy 那条路径 |
| 残余风险 | 「两层 header 注入是否一致」 | **该风险前提消失**：本端点只有一层，不存在"两层不一致" |

**⇒ 结论变化（重要，且方向与之前相反）**：
- **好消息**：此前担心的「proxy 层与 handler 层 header 注入不一致」这个残余风险**对本端点不适用**（它只走 handler 层）。三连 curl 的 ② 若回 400，就说明函数层 header 完全可用，**无需再担心另一层**。
- **坏消息**：防线**只有一层，没有中间件兜底**。若将来有人误改 `same-origin.ts` 或给它加提前 `return true` 的短路，本端点会**直接裸奔**，没有任何第二道闸。
⇒ 这正是 `scripts/test-remaining-route.ts` ① 段（403 行为 + 日志存在）必须保留的原因：它守的就是这唯一一层。

| # | 断言 | 它挡住了哪种「偷偷改语义」 | 逼人去的方向 |

## 附录增补 · 九轮（判据宽度：变异测试验的不是「会红」）

### ★ 1. 前端一条纠正，改变了变异测试的正确用法

我此前说「变异测试证明两条断言都红 ⇒ 断言灵敏」。**结论方向对，但表述不精确。**

| 我以为它验证的 | 它实际验证的 |
|---|---|
| 「代码改坏时断言会红」 | **「断言的判据是否足够窄」** |

「代码改坏会红」是**天然属性** —— 任何真在断言的代码，改坏大概率会红。变异测试不可替代的价值在于
抓**过宽的判据**：

> 若断言写成 `logs.includes("ownHosts")`，把实现改回平铺数组它**仍然绿**
> （因为 `ownHosts=[a,b,c]` 也含 `ownHosts`）⇒ 这类"看起来在验证"的断言才是变异测试该抓的。

⇒ 正确表述：**变异测试验证「判据宽度是否匹配它声称守护的不变量」**，而非"验证断言有效"。

### ★ 2. 我按这个标准复审，发现自己又犯了同型缺陷（第二次）

前端举的例子**恰好就是我代码里的那一行**：

```ts
ok(!!hit && hit.includes("ownHosts="), "  日志含 ownHosts（否则无法判断是 host 不匹配还是缺 Origin）");
```

**两个问题**：
| # | 问题 | 说明 |
|---|---|---|
| 1 | **判据过宽** | `includes("ownHosts=")` 平铺数组也绿 —— 我做的变异测试只覆盖了「来源标签」「显式 null」两条，**没覆盖这条** |
| 2 | **标签过度承诺** | 标签说「否则无法判断是 host 不匹配还是缺 Origin」，但这条判据**只能证明字段名存在** ⇒ 标签声称的强于判据能保证的 |

第 2 点是本轮**第二次**出现同型缺陷（第一次是 403 日志注释承诺了可诊断性、实现只做一半）。
**区别只在载体：第一次是"注释→实现"没兑现，这次是"标签→判据"没兑现。**

**修法**：
- 标签改成它实际保证的事：`日志出现 ownHosts 字段（仅证字段名存在，格式是否可诊断看下一条）`
- 下一条（`origin=`）判据收紧为 `origin=<none>` 或 `origin=<具体值>` 二选一 ——
  因为缺失时打 `<none>`、有值时打域名，**两者都含 `origin=`**，原判据同样宽。

⇒ 结论：**"过度承诺"是一种跨载体缺陷**（注释、断言标签、文档表头都能承载），
不是只在注释里发生。凡"声称 A 但只验证 B"，都要按此检查。

### 3. 恒真断言只能靠静态检查抓，不能靠动态测试

前端指出：`X || !!hit` 的问题是**判据恒真**（短路后永远 true），变异测试对它**无效** ——
因为改坏代码它还是绿的，你会以为是"断言写错了"；若代码没改，你永远不会怀疑它。

⇒ **能抓恒真断言的只有静态检查。** 已用前端给的模式扫全仓：

```bash
grep -rnE '(ok|assert|check)\([^;]*\|\|\s*(!![a-zA-Z_]+|true|1)\s*[,)]' scripts/ .verify/
# 结果：空（无残留）
grep -rnE '\|\|\s*!![a-zA-Z_]+' scripts/
# 结果：1 处，是 test-strips-snapshot.ts:391 的注释正文（`openManual || !!nav`），非断言
```

⇒ `scripts/` 与 `.verify/` 内**无同类残留**。这条检查值得固化成一次性的，而非依赖人工审阅。

### 4. 抽 `remaining-log.ts` 的第三条收益（前端补的，我采纳）

我原说收益是「可复用 + 纯函数好测」。前端补了更实际的一条：

> **它把「日志格式」从"实现细节"变成"可断言的契约"。**

⇒ 这条同时印证三分法：`formatOwnHosts` 的形状断言是**契约型**（不需要"造错检出"）；
而「日志必须打出来」是**守护型**（需要）。

> **用户会成为第一个发现者。** 所以必须抢在用户之前验。

## 1. 三条命令 + **实测期望值**

以下期望值**不是推测**，是在本地对真实 handler 构造 `NextRequest` 实测得到的
（响应体与 header 原样抄录）：

### ① 没有 `Origin` ⇒ 必须 **403**

```bash
curl -sS -o /tmp/r1.json -w "status=%{http_code}\n" -X POST "$BASE/api/nav/remaining" \
  -H "content-type: application/json" \
  -d '{}'
cat /tmp/r1.json; echo
```

| 项 | 期望 |
|---|---|
| status | **403** |
| body | `{"ok":false,"error":"forbidden"}` |
| `cache-control` | `no-store` |

**含义**：同源校验**确实在跑**（不是"恰好没生效"）。

### ② 带同源 `Origin` + 空 body ⇒ 必须 **400**（★ 最关键的一条）

```bash
curl -sS -o /tmp/r2.json -w "status=%{http_code}\n" -X POST "$BASE/api/nav/remaining" \
  -H "origin: $BASE" \
  -H "content-type: application/json" \
  -d '{}'
cat /tmp/r2.json; echo
```

| 项 | 期望 |
|---|---|
| status | **400** |
| body | `{"ok":false,"error":"bad_request"}` |

**含义（这条是核心）**：`400` 说明请求**已经通过同源校验**、进到了参数校验阶段。
⇒ 证明「同源放行」在生产**函数层**正常工作。

> ⚠️ **若这条返回 403，就是同源校验在函数层误判** ⇒ 见 §3 处置指引。

### ③ 跨站 `Origin` ⇒ 必须 **403**

```bash
curl -sS -o /tmp/r3.json -w "status=%{http_code}\n" -X POST "$BASE/api/nav/remaining" \
  -H "origin: https://evil.example" \
  -H "content-type: application/json" \
  -d '{}'
cat /tmp/r3.json; echo
```

| 项 | 期望 |
|---|---|
| status | **403** |
| body | `{"ok":false,"error":"forbidden"}` |

**含义**：同源校验**不是**简单放行，跨站确实被挡住。

## 2. 判定口径（三条一组，不要单看）

| 结果组合 | 结论 |
|---|---|
| ①403 / ②400 / ③403 | ✅ **通过**，可发公告 |
| ①403 / ②**403** / ③403 | ❌ **同源误判** ⇒ 走 §3 |
| ①**200/400** / … | ❌ **同源校验没生效**（安全漏洞）⇒ 立即撤回 |
| ①403 / ②400 / ③**200/400** | ❌ **跨站没挡住**（安全漏洞）⇒ 立即撤回 |
| ①403 / ②400 / ③403 之外任何组合 | ❌ 按上表定位后处置 |

> ⚠️ **②400 是"通过"的必要条件，不是充分条件** —— 必须三条一起看。
> 只看 ②（见到 400 就以为好了）会漏掉 ③ 的跨站失效。

## 3. 若 ② 返回 403：处置指引

**先别撤回，也别改代码 —— 先取证。** 服务端在 403 时会有一条诊断日志，这条日志是
**唯一能区分「缺 Origin」与「host 不匹配」的依据**（客户端侧完全静默）：

**去哪看**：Vercel Dashboard → 该项目 → **Logs / Function Logs** → 过滤
`同源校验拒绝`（或 `[api/nav/remaining]`）→ 取最近 5 分钟内的条目。

**日志形态**（实测样例，字段含义附后）：

```
[api/nav/remaining] 同源校验拒绝（403）： ownHosts={"xfwd":"macaomap.vercel.app","host":"macaomap.vercel.app","url":"internal.vercel.app"} origin=https://macaomap.vercel.app referer=<none>
```

| 字段 | 含义 | 若与 `origin` 不一致说明什么 |
|---|---|---|
| `xfwd` | `x-forwarded-host`（代理链透传的原始 Host） | 代理链注入了外部域名 |
| `host` | `host` header | 上游覆盖了 Host（Vercel 配置问题） |
| `url` | `nextUrl.host` | **最可能的一种**：`nextUrl` 被改写成内部部署域名 |

三者一致时会打印成 `ownHosts="macaomap.vercel.app"(三方一致)`（合并形态，省日志行）。

**按日志分三种处置**：

| 日志显示 | 判断 | 处置 |
|---|---|---|
| `origin=<none>` | 我的 curl 没带 Origin | 补上 `-H "origin: $BASE"` 重试（不是代码问题） |
| 三个 host 全部 ≠ `origin` | 平台把三个来源都改写了 | **撤回**（fail-closed 会全量 403），本端点改走别种防护后再上 |
| 仅 `url` ≠ `origin`，`xfwd`/`host` 与 `origin` 相同 | 属预期内的改写，`isSameOrigin` 的**并集**设计应已覆盖 ⇒ 若仍 403 则说明并集没起作用 | 属真缺陷，**撤回**并上报（这是 `isSameOrigin` 的 bug，不是配置问题） |

**不撤回的前提**：只有第一种（`origin=<none>`，即 curl 自己没带）可以先不撤 —— 那是验证方法问题，不是产品问题。

## 4. 顺带一条（可选，非阻断）

若想同时确认「正式请求体也能通」，把 ② 的 body 换成一张真实 card（从浏览器 DevTools
复制一次 `/api/nav/remaining` 的真实请求体），期望 `200` 且响应含
`remainingMin` / `arriveAt` / `recomputedAt` / `serverNowMs` / `strips` 五个字段，
且 **`arriveAt === recomputedAt + remainingMin × 60000`**（残差必须 **0**，不是"约等于"）。

## 5. 这张清单为什么不能被"看日志"替代

| 手段 | 性质 |
|---|---|
| 三连 curl（本文） | **事前能拦** —— 公告前可执行、结果二值、可写进验收步骤 |
| 服务端 403 日志 | **事后能查** —— 进的是 Vercel 原始日志流，**无聚合、无 403 突增告警** ⇒ 仍需有人主动去翻 |

⇒ **「可观测」不等于「会被发现」。** 真正防线上事故的是本节这三条 curl。

## 2. ⇒ 因此风险评级不能按「已验证几个月」降级

原假设是「已在线上跑几个月 ⇒ 风险降级为已验证」。**这个前提不成立**，三点都不成立：

| 原假设 | 实况 |
|---|---|
| 跑了几个月 | **5 天** |
| 被大量真实用户调用 | 仅 `/api/fav-routes*` 的**写**请求（收藏保存），频次远低于任何读接口 |
| `route-vehicles` 等端点也在用 | **`route-vehicles` 完全不用**；`isSameOrigin` 全仓只有 **2 个**消费点 |

**⇒ 准确评级：函数本身「有生产运行史但很浅（5 天、单一端点、低频写路径）」；本端点是它首次用于函数层。**

这既不是「全新未验证」（函数体和 header 读取逻辑是既有的、已被 fav-routes 打过），
也不是「已验证几个月」。**新引入的风险面只有一个，且很具体：**

> **函数层（route handler）能否拿到与中间件层相同的 host/origin header。**

因为 `fav-routes` 的校验发生在 **proxy（中间件）**，而本端点发生在 **route handler** ——
这是 Vercel 上**两个不同的执行位置**。函数体一样，**注入的 header 集合是否一样，没有先例可推**。

## 3. 这个风险怎么闭合（唯一手段）

**只能部署后用三连 curl 验 ②**（`见上一节验收清单 §1-②`）：
- ② 回 **400** ⇒ 函数层 header 可用 ⇒ **该风险闭合**；
- ② 回 **403** ⇒ 函数层 header 不可用 ⇒ 撤回，改走其它防护。

⇒ 在 ② 跑过之前，**这条必须以「未验证」对待**，不能因为 `fav-routes` 在跑就推定可用。
这也是为什么验收清单里 §3 给了「按日志字段分支处置」的完整指引 ——
万一命中，要能立刻判断是哪种不匹配，而不是只看到"全 403"。

## 4. 一个诚实的补充：我无法证明 fav-routes 的校验在生产真的被触发过

`proxy.ts:95` 的代码路径存在，且 `.verify/_check-middleware-public.ts` ⑤ 段有**双侧实机断言**
（跨站 ⇒ 403 / 同源 ⇒ 不被 401/403/410 拒）。但：
- 该脚本需要 `VERIFY_BASE` 指向一个运行中的实例；
- **仓库里看不到它曾被指向 Vercel 生产跑过的记录**。

⇒ 所以严格说：「`isSameOrigin` 在中间件层有生产代码路径 + 有实机断言脚本」，
但「该断言曾对生产执行过」**我无法证明**。

不过对本端点而言，这一点**不影响结论** —— 因为第 3 节已经确定：
无论 fav-routes 在生产验过与否，**本端点走的是另一层，都必须单独验 ②**。

## 附录增补 · 十一轮（status→reason 对偶：词表相同 ≠ 映射正确）

### 1. 词表断言有一个它抓不到的漏洞

前端的 `data-remain-fail` 值形如 `403:forbidden`。我此前只验了「词表 ⊆」：

```
前端 reason 词表 ⊆ 服务端 API_ERROR 枚举
```

**但这条抓不到对偶错配**：

> 若前端把 `403` 映射成 `bad_request`（`bad_request` 也在枚举里），词表断言**照样绿**，
> 而用户看到 `data-remain-fail="403:bad_request"`、服务端日志写 `forbidden`
> ⇒ **两边说的不是同一个东西，且没有任何报错。**

⇒ 必须验**对偶**：服务端 `status → error` 与前端 `status → reason` **逐档一致**。
服务端权威映射取自 `errors.ts#DEFAULT_STATUS`（`API_ERROR.forbidden → 403` 的反向表）。

**实测结果（6 档全部对齐）**：
```
401:unauthorized  403:forbidden  410:gone  429:rate_limited  400:bad_request  500:upstream_error
```

### 2. 而我自己在这次改动里连犯两个错，都是同一病灶

| # | 错 | 性质 |
|---|---|---|
| 1 | 要求前端覆盖**全局六枚举**的每一档 ⇒ `FAIL 4/6` | **把「全局枚举」当成「本端点契约」** |
| 2 | `new Map(statusPairs).get(error)` 键方向反了 ⇒ 查到 `undefined` ⇒ 空数组 ⇒ **判据恒绿** | **假绿**（最隐蔽那种） |

**错 1 的纠正**：实核 `route.ts` 只引用三个 `API_ERROR`：`bad_request` / `forbidden` / `upstream_error`
—— 它**从不返回** 401 / 410 / 429。⇒ 前端不映射 401/410 是**正确的**，错的是我的判据。
那种断言会**逼前端加两档永远用不到的映射**（无用代码 + 误导后来人以为会返回）。

改为**从 `route.ts` 程序化提取**实际可达集：
```
可达 = bad_request,forbidden,upstream_error  → 状态 400,403,500
前端映射 = 400,403,429,500                    ⇒ 覆盖 3/3 ✓（429 是超集，无害）
```
⇒ 自我维护：将来 route 若真加了 `rate_limited`，断言会自动要求前端同步。

**错 2 的纠正**：加了一条**防空断言** ——
> 「可达状态全部能在 `DEFAULT_STATUS` 中找到」
> 理由：若查不到就是空数组 ⇒「无缺失」⇒ 上一条恒绿。**任何"从集合推导缺失项"的断言都必须先断言集合非空**，
> 否则集合推导一坏就静默变绿。

### ★ 3. 这轮又是「判据宽度」的第三次显形，但形态不同

| 次 | 病灶 | 显形 |
|---|---|---|
| 1 | 判据过宽（`includes("ownHosts=")` 平铺也绿） | 覆盖不足 |
| 2 | 判据恒真（`\|\| !!hit`） | 永远绿 |
| 3 | **判据依赖错误的集合推导**（Map 键反 ⇒ 空集 ⇒ 无缺失） | 永远绿 |

三者共同结构：**断言的"绿"不来自被验证对象，而来自断言自身的构造缺陷。**
⇒ 检查清单再加一条：**凡是「先构造集合、再判断缺失」的断言，必须断言集合本身非空/尺寸正确。**

### 4. 双向变异验证（这条对偶断言确实灵敏，且不过度）

| 变异 | 期望 | 实测 |
|---|---|---|
| A：前端把 `403` 映射成 `bad_request`（词表内、对偶错） | **红** | **FAIL**，打印「错配：403 服务端=forbidden 前端=bad_request」；而**词表断言仍绿** ⇒ 正好证明词表断言抓不到它 |

## 附录增补 · 十二轮（`fe !== undefined` 自审缺陷 + 两条新原则）

### ★ 1. 我交付的对偶断言自身有假绿（前端发现，我独立复现）

```js
const mismatched = statusPairs.filter(([st, err]) => {
  const fe = feMap.get(st);
  return fe !== undefined && fe !== err;   // ← 提取失败被当作"不算错配"
});
ok(
  statusPairs.length >= 6 && mismatched.length === 0,   // ← 分母用输入集合尺寸（恒 6）
  "★ status→reason 对偶一致",
  mismatched.length ? `错配：…` : `${statusPairs.length} 档全部对齐：…`,
);
```

**两处问题**：
| # | 问题 | 后果 |
|---|---|---|
| 1 | `fe !== undefined` ⇒ 提取失败被过滤 | `mismatched=[]` ⇒ **恒绿** |
| 2 | detail 分母用 `statusPairs.length`（恒 6） | 即使只比了 1 档，也**宣称"6 档全部对齐"** |

**只读模拟复现（完全复刻判据，不读源码、不改文件）**：

| 场景 | 原版 | 改后 |
|---|---|---|
| 正常（前端 4 档齐全） | PASS — "6 档全部对齐" | PASS — "比对 4/6 档" |
| 变异：只抓到 1 档（查表式重构） | **PASS — "6 档全部对齐"** ← 假绿 | FAIL — "比对 1/6 档" |
| **变异：feMap 完全空** | **PASS — "6 档全部对齐"** ← 假绿 | FAIL — "比对 0/6 档" |
| 变异：403 真错配 | FAIL ✓ | FAIL ✓ |

**「完全空也绿」这一档比「部分失败」更关键**（前端指出）：
- 部分失败 ⇒ 还能用"前端真的只映射了少数档"解释
- **完全失败 ⇒ 没有任何档被比对，却仍声称 6 档全对齐**
⇒ 这不是"覆盖不全"，是**"什么都没比对，但报告说都对了"**。

且 `feMap` 完全空的触发很容易：只要有人重构 `statusReasonOf`（改成查表 / switch / 用 `API_ERROR` 常量而非字面量），正则一条都抓不到，**且编译器不报警**（正则失败是运行时静默的）。

**当前整体仍安全**：覆盖度断言兜住了（`FAIL 前端缺 400,403`）⇒ 三绿不会红、线上无风险。
但这是「靠另一条兜底」，**不是对偶断言自己有效**。

### ★ 2. 为什么我加了防空断言还是漏了 —— 这一族有**两个入口**

我加防空断言时想的是「集合为空 ⇒ 恒绿」，于是验了 `reachableStatuses.length === reachable.length`。
但 `mismatched` 的空集来自**另一个入口**：

| 入口 | 机制 | 我是否防住 |
|---|---|---|
| A | 输入集合本身为空 | ✅ 防住了（防空断言） |
| B | **过滤条件把「查不到」当成「无需检查」** | ❌ **漏了** |

而 `fe !== undefined` 的字面读法「前端没映射这一档就不算错配」在业务上**完全合理**（前端确实不必覆盖 6 档）
⇒ **合理性掩盖了它同时吞掉"提取失败"**。

### ★ 3. 交付说明里应写的准确措辞（若本批不修）

不要写「由覆盖度断言兜底」——那听起来"还有一层保护"。应写：

> **对偶断言在「前端映射提取失败」场景下无效，当前安全性单点依赖覆盖度断言；
> 若该覆盖度断言被改窄或删除，对偶断言会退回恒绿（且不报错）。**

区别在于：前者让人以为有两层；后者说清**保护是单点的** —— 才会让人在改动覆盖度断言时犹豫一下。

### ★ 4. 「加固动作是审查的终止符」（本轮最深的一条，来自前端）

它比四种假绿形态更普适，因为解释的是**为什么会漏**，而不是**漏成什么样**：

> 1. 加了断言 ⇒ 主观上"这块我加固过了" ⇒ 后续复审**跳过**它
> 2. 跳过 ⇒ 没人发现加固只覆盖了入口 A
> 3. ⇒ **"我加固过了"这个念头本身，是审查的终止符。**

**自我强化**：没加固时至少还会有人多看一眼；加固后连那一眼都没了。

**三条防御（前端实践，我采纳）**：
| 做法 | 为什么有效 |
|---|---|
| 加固后**立刻**写变异自检 | 强制在"最自信的时刻"去证伪一次 |
| 变异覆盖**多个入口**，不只一个 | 本次就是只变异了"档位错配"，没变异"提取失败" |
| 断言输出带**实际比对量/总量** | 让"只比了 1/6"自己浮出来，**不依赖人去想** |

### ★ 5. 两条必须成对的断言纪律（合起来才闭合）

| 规则 | 防的是 |
|---|---|
| ① 「先构造集合再判缺失」的断言，必须断言**集合非空/尺寸正确** | 集合**为空** ⇒ 恒绿 |
| ② 断言的**输出分母**必须是**实际参与比对的数量**，不能是输入集合的尺寸 | 集合非空但**只用了其中一小部分** ⇒ 看起来全覆盖 |

**我此前只做了 ① 就以为做完了** —— 典型的「防住一个入口就当防住整族」。

### ★ 6. 「过度承诺」的第四种载体：断言的 detail 输出

| # | 载体 | 例子 | 特征 |
|---|---|---|---|
| 1 | 注释 | 403 日志注释承诺可诊断，实现只做一半 | 承诺 > 实现 |
| 2 | 断言标签 | 标签说"否则无法判断 host 不匹配"，判据只证字段名存在 | 标签 > 判据 |
| 3 | `data-*` 属性名 | 名不副实 | 名字 > 语义 |
| 4 | **断言的 detail 输出** | 本条：说"6 档全部对齐"，实际只比了 1 档 | **结论对，但证据夸大覆盖** |

**第 4 型最隐蔽**：`PASS` 本身没错——错的是那个 `6/6` 的数字。**人看结论，不会去核 detail 里的分母。**

### ★ 7. 判据值域不得窄于「运行时真实可能出现的值域」（前端原则，我采纳）

前端给的 `data-remain-fail` QA 判据建议：

> 形如 `^\d{3}:[a-z_]+$`，且**若** `status ∈ {400,403,429,500}` **则** reason 必须等于对偶表值。

这是「**条件对偶**」而非「白名单」：
- **白名单**：任何不在列表的值都算错 ⇒ **误伤**网关层状态码（`502:upstream_error` 等 httponly 由网关产生，handler 根本不产生）
- **条件对偶**：只对**已知可达**状态要求对偶 ⇒ 未知状态放行但保留真实码 ⇒ **可诊断性不丢且不误伤**

⇒ 可复用原则：**判据的白名单/值域，不能窄于「运行时真实可能出现的值域」。**
前者是"我以为会出现的"，后者是"我没预料但实际会来的"。**两者之差就是假红。**
