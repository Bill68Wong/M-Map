## 三、逐条定级（按真实可达性，不是 audit 原始严重度）

### 3.1 `next`（audit: critical｜真实: 需修，但当前配置下不可达）

`next` 一个节点挂了 **4 条 GHSA**，严重度不同、机制完全不同，必须拆开看：

| GHSA | 原始严重度 | 机制 | 修复版本 | 本项目可达性 |
|---|---|---|---|---|
| **GHSA-2464-fhr4-w9xw** | **critical (9.5)** | **Image Optimization API 未授权 RCE**；根因是上游 `sharp` 的 librsvg 内存漏洞（CVE-2026-96889），仅 glibc Linux 可致 RCE | 15.5.28 / 16.4.1 | **当前不可达**（见 §四 实测）；但 `sharp` 在生产包内，配置一改就打开 |
| GHSA-4jqv-mc3x-m676 | moderate (6.3) | SSG/ISR cache poisoning | 15.5.27 | **不可达** —— advisory 原文：*"Self-hosted Next.js applications that use the **Pages Router**..."*，"**Applications deployed on Vercel are not affected**"。本项目是 App Router + Vercel，双重不适用 |
| GHSA-mcj8-r9mp-w47p | moderate (6.3) | 跨用户内容替换 + 持久 DoS；需 **root-level catch-all page** + SSG/ISR | 15.5.27 | **不可达** —— 预渲染路由只有 3 个（`/_not-found`、`/about`、`/help`，见 `.next/prerender-manifest.json`），而仓库**没有 root-level catch-all**（唯一的 catch-all 是 `api/amap-service/[...path]`，在 `/api` 段下，不构成 root-level）。两个条件不共存 |
| GHSA-p3m5-59mp-jv5r | high | **Server Actions** DoS | 15.5.28 | **不可达** —— 全仓 `"use server"` **零命中**，未使用 Server Actions |

⇒ 对 `next` 的正确理解：**这条 critical 不是 Next 的 cache poisoning，而是「Next 打包了有漏洞的 sharp」**。而 Vercel 明确不受 cache poisoning 影响，Server Actions 未使用，所以 4 条里 3 条在本项目**结构上不可达**，唯一有现实意义的是 sharp RCE —— 而它当前被配置拦住了（§四）。

> **这条对负责人决策很重要**：Security 页面把它标成 critical，看起来像「整站可被 RCE」。实际是「一个因配置被挡住、但依赖确实在包里的上游漏洞」。**修它的成本是 1 个补丁版本，所以仍然建议修** —— 不是因为现在能被打，而是因为「防线只剩一行配置」。

### 3.2 `sharp`（audit: high｜真实: 在生产包内，当前不可达）

- 根因：`librsvg` 内存漏洞（CWE-416 use-after-free），CVSS 4.0 = 8.9，**`AV:L`（本地向量）**。
- 官方 workaround 两条：升到 `0.35.5`，或 `sharp.block({ operation: ["VipsForeignLoadSvg"] })`。
- **它是唯一进入生产函数包的漏洞依赖**（证据见 §四）。
- 当前不可达的理由：见 §四 的三条实测。

### 3.3 `postcss`（audit: high｜真实: 构建期，不在生产包）

4 条 GHSA，全部要求**处理攻击者可控的 CSS**：
- `GHSA-6g55-p6wh-862q` / `GHSA-fxqj-rqcc-2cmp` / `GHSA-r28c-9q8g-f849`：CSS 注释里 `sourceMappingURL` 可读任意 `.map` 文件（路径遍历）
- `GHSA-qx2v-qp2m-jg93`：stringify 时 `</style>` 未转义导致 XSS

本项目的 CSS 是**仓库内自写、构建期编译**，没有任何「用户提交 CSS / 运行时解析 CSS」的入口 ⇒ **无攻击面**。且 `.nft.json` 聚合命中 **0**（不进生产包）。
⇒ 真实等级：**低**。可修可延。

### 3.4 `source-map-js`（audit: high｜真实: 构建期，不在生产包）

- `GHSA-68fv-2mgg-jv7q`：索引式 source map 段偏移导致事件循环 DoS。
- 链路：`next → postcss@8.4.31 → source-map-js@1.2.1`（`npm ls` 已验）。
- 只在**生成/消费 source map** 时触发 ⇒ 构建期。`.nft.json` 命中 **0**。
⇒ 真实等级：**低**。`npm audit fix` 会顺带升到 1.2.2。

### 3.5 `brace-expansion`（audit: high｜真实: dev-only）

6 条 GHSA 记录，实为 **3 个不同问题**（每个按 1.x / 4.x-5.x 两条范围各记一次）：
- `GHSA-qhr7-859c-m2p7`（high）：嵌套花括号递归导致栈耗尽
- `GHSA-6j4f-fj2g-mc7p`（high）：`parseCommaParts` 递归栈耗尽
- `GHSA-q2hr-2g5m-vwhr`（moderate）：`{a},b}` 重写的二次时间复杂度

共同前提：**处理攻击者可控的 glob 模式**。本项目 glob 全部来自仓库内配置（eslint / next 的 ignore 列表），无外部输入。`.nft.json` 命中 **0**。
- 两处副本：`eslint → minimatch@3.1.5 → brace-expansion@1.1.18`（`audit fix` 不动）、`@typescript-eslint → minimatch@10.2.6 → 5.0.9`（`audit fix` 会升 5.0.12）
⇒ 真实等级：**低**（dev-only）。

### 3.6 `minimatch` + 13 个 eslint 家族（audit: moderate｜真实: dev-only）

- `GHSA-g3hv-75wg-m249`：`globparts` 放大型 DoS，范围 `<11.0.1`。
- `eslint@9.39.5` 依赖 `minimatch@3.1.5`（无法升到 11，因为 minimatch 11 是 ESM-only 且 api 变化）；`@eslint/*` / `@typescript-eslint/*` / `eslint-plugin-*` / `eslint-config-next` 的多数条目**不是自身有洞，而是「依赖了有洞的 minimatch/eslint」**（audit 的 `via` 字段是字符串依赖名，不是 advisory）。
- 全部为 `devDependencies` 及其传递依赖。`.nft.json` 命中 **0**。
⇒ 真实等级：**极低**。

**为什么这组建议「记录不修」**：修它需要 `eslint@10`（当前 latest 10.14.0），而 `eslint-config-next@15.5.28` 的 peer 是 `eslint: ^7.23.0 || ^8.0.0 || ^9.0.0` —— **不支持 10**。要修就得上 Next 16 + eslint 10，跨 2 个 major，风险远大于收益（这些包不进生产、不受外部输入驱动）。

## 四、决定性证据：谁是运行时依赖，谁不是

`npm audit` 只回答「有没有洞」，不回答「在生产里跑不跑」。这一节用**构建产物**和**线上探测**回答后者。

### 4.1 构建产物：node-file-trace 不会被主观判断骗

Next 构建产出 60 个 `.nft.json`（node file trace，即**实际打进生产函数包的文件清单**）。全量聚合：

```
$ node -e "…遍历 .next 下全部 *.nft.json，按关键字计数…"
nft 文件总数: 60
全部 nft 聚合: {"postcss":0,"sharp":23,"source-map-js":0,"brace-expansion":0,"minimatch":0,"eslint":0}
```

⇒ **只有 `sharp` 进了生产包（23 个文件）**。`postcss` / `source-map-js` / `brace-expansion` / `minimatch` / `eslint` **全部 0**。

这直接决定了分档：
- 进生产包 ⇒ 运行时可能被触发 ⇒ 按安全漏洞对待（`sharp` / `next`）
- 不进生产包 ⇒ 只影响构建机与开发机 ⇒ 按供应链风险对待，不是运行时漏洞

### 4.2 线上探测：`sharp` 虽然在包里，但 SVG 进不去

对自家 `macaomap.vercel.app` 做只读探测（三条，均为正常 GET/HEAD，无利用尝试）：

```
$ curl -s -o /dev/null -w "%{http_code} | type=%{content_type}\n" \
    "https://macaomap.vercel.app/_next/image?url=%2Ficon.svg&w=64&q=75"
400 | type=text/plain; charset=utf-8

$ curl -s "https://macaomap.vercel.app/_next/image?url=%2Ficon.svg&w=64&q=75"
Bad request

INVALID_IMAGE_OPTIMIZE_REQUEST
hkg1::xjm8r-1793680832925-9367317e627e

$ curl -s -o /dev/null -w "%{http_code}\n" \
    "https://macaomap.vercel.app/_next/image?url=https%3A%2F%2Fexample.com%2Fa.svg&w=64&q=75"
400
```

对照：**非 SVG 图片走优化器是通的**（说明 `sharp` 确实在工作，不是端点被关）：

```
$ curl -sI "https://macaomap.vercel.app/_next/image?url=%2Ficon-16.png&w=64&q=75"
HTTP/1.1 200 OK
Content-Disposition: attachment; filename="icon-16.png"
Content-Security-Policy: script-src 'none'; frame-src 'none'; sandbox;
Content-Type: image/png
```

以及静态 SVG 本身正常（202，不经 sharp）：

```
$ curl -s -o /dev/null -w "%{http_code} | type=%{content_type}\n" "https://macaomap.vercel.app/icon.svg"
200 | type=image/svg+xml
```

**三条防线共同保证 RCE 路径当前走不通**（`dangerouslyAllowSVG: false` + `remotePatterns: []` + `contentDispositionType: attachment`）：

| 防线 | 来源 | 实测效果 |
|---|---|---|
| `dangerouslyAllowSVG: false`（Next 默认，`.next/images-manifest.json` 已确认） | 配置默认值 | SVG 请求 → **400 `INVALID_IMAGE_OPTIMIZE_REQUEST`**，**不交给 sharp** |
| `remotePatterns: []`、`domains: []` | 未配置 | 外部 URL → **400**（攻击者无法自带 SVG） |
| `contentDispositionType: "attachment"` + CSP `sandbox` | next.config 未覆盖默认 | 即使 SVG 被返回也强制下载、禁脚本 |

**但要说清这层的脆弱性**：这三条**全是配置**，不是代码。任何人为了「图片支持 SVG」加一行 `images: { dangerouslyAllowSVG: true }`，RCE 路径立刻打开，而**没有任何测试或编译器会拦**。这与本迭代反复讨论的「防线只剩一行配置」是同一类风险。

## 五、升级方案

### 5.1 必须先说清：`npm audit fix --force` **不能碰**

`audit` 对 eslint 家族给出的「fix」是：

```
eslint            · fixAvailable={"name":"eslint","version":"4.0.0","isSemVerMajor":true}
eslint-config-next · fixAvailable={"name":"eslint-config-next","version":"12.0.4","isSemVerMajor":true}
```

`eslint@4.0.0` 是 **10 个 major 之前的版本**、`eslint-config-next@12.0.4` 是 **3 个 major 之前**。这是 npm audit 在「该漏洞在当前 major 线无修复版」时的典型行为：它去翻历史版本找一个"不含漏洞"的，给出**降级**建议。

⇒ `npm audit fix --force` 会把项目降级到 2022 年的工具链，**必然破坏 lint 与构建**。**明确禁止使用**。

### 5.2 非 force 的 `npm audit fix` 实跑（dry-run，未落盘）

```
$ npm audit fix --dry-run
change next 15.5.25 => 15.5.28
change @next/env 15.5.25 => 15.5.28
change @next/eslint-plugin-next 15.5.25 => 15.5.28
change @next/swc-win32-x64-msvc 15.5.25 => 15.5.28
change eslint-config-next 15.5.25 => 15.5.28
change sharp 0.35.4 => 0.35.5
change source-map-js 1.2.1 => 1.2.2
change brace-expansion 5.0.9 => 5.0.12
change @typescript-eslint/* 8.69.0 => 8.72.1（10 个包）
… 共 20 处 change / 25 处 add（@img/sharp-* 平台二进制）
```

关键点：
- **`next 15.5.25 → 15.5.28` 是补丁级**，且 `package.json` 写的是 `"next": "^15.1.6"` ⇒ 15.5.28 **本来就在允许范围内**，`package.json` **无需改动**，只动 `package-lock.json`。
- `sharp 0.35.4 → 0.35.5` —— 因为 `next@15.5.28` 的 optionalDependency 是 `sharp: "^0.34.3 || ^0.35.5"`，0.35.4 **两个分支都不满足**，npm 必须装 0.35.5+。这正是 advisory 说的「Fresh installs automatically get a fixed version of sharp」。
- **`postcss` 不在变更列表里** —— 因为 `next@15.5.28` 仍精确锁定 `postcss: 8.4.31`（`npm view next@15.5.28 dependencies.postcss` → `8.4.31`）。**升 next 不会修好 postcss。**

### 5.3 三套方案（供负责人选）

| 方案 | 动作 | 消除的漏洞 | 风险 | 建议 |
|---|---|---|---|---|
| **S1（推荐）** | `npm audit fix`（不带 force）+ 构建 + 视觉回归 | critical 1 / high 2（sharp、source-map-js）/ brace-expansion(5.x)；共 4-5 条 | **低** —— 补丁级、`package.json` 不变、无 API 改动 | **本次做** |
| S2 | S1 + `overrides: { "postcss": "^8.5.32" }` | 再加 postcss 4 条 | **中** —— next 精确锁 8.4.31，强制 8.5.x 属**未测组合**，可能改变 CSS 产物；必须做构建 + 逐页视觉回归 | 可选，看是否要 audit 清零 |
| S3 | 升到 Next 16.4.4 + eslint 10 | 全部 19 条 | **高** —— 跨 1 个 Next major + 1 个 eslint major，React 19 / App Router 行为需全量回归 | **不建议本轮**（与本迭代冻结冲突） |

**S1 后预计剩余**：约 15 条（14 moderate 的 eslint 家族 + minimatch + brace-expansion 1.x + postcss 4 条）。全部**不进生产包**，除 postcss 外全部 dev-only。
> 这个数字是推算，**执行时需以实际 `npm audit` 为准**。我未实际落盘执行。

### 5.4 S1 的验收清单（若要执行）

1. `npm audit fix`（**不带 `--force`**）
2. `node node_modules/typescript/bin/tsc --noEmit` → EXIT=0
3. `node node_modules/eslint/bin/eslint.js .` → 0 error 0 warning
4. `tsx .verify/test-match-vehicle.ts` → 71/71（确认匹配算法未受影响）
5. `next build` → BUILD_EXIT=0
6. **视觉回归**：`/help`（唯一 SSG）、首页地图、`/line/[code]` 三页与改前对比（下次 next 会影响 CSS/资源处理）
7. `npm audit` 复核实际剩余条数

> 注：S1 改的是 `package-lock.json`，属「依赖变更」而非「业务代码变更」，但**需要一次发布窗口**（铁律 34：push 与 deploy 合并算 1 次）。建议与下一次计划内的推送合并，不单独开窗口。

## 六、Code scanning（GitHub CodeQL）

### 6.1 现状：仓库侧无任何配置

```
$ ls -la .github
.github 不存在

$ find . -name "*.yml" -o -name "*.yaml" | grep -iE "codeql|github/workflows"
（仅 node_modules 内的第三方 workflow；仓库自身为 0）
```

⇒ **仓库里没有 CodeQL workflow**。若 GitHub「Security and quality」页面显示了 code scanning 结果，来源只能是 **GitHub 服务端的 Default setup**（由 GitHub 托管，无需仓库内文件）。

### 6.2 关键前提：仓库是公开的 ⇒ CodeQL 免费且合规

`https://github.com/Bill68Wong/m-map` **未登录即可完整浏览**（README、Issues、commit 历史、文件树全部公开；一条 commit 说明里也写着「移出公开仓库」）。

CodeQL Action 的许可条款是：**公开仓库免费可用**；私有仓库需所有者是已启用 GitHub Advanced Security 的组织。本项目是**公开仓库 + 个人账号** ⇒ **落在允许范围内，无许可问题**。

> 附带含义：**19 条依赖漏洞目前对公众可见**（公开仓库的 Security 页可读）。这不改变技术风险，但改变「观感」—— 若负责人介意，S1 可一次性把 critical 从页面上消掉。

### 6.3 若启用：建议用 Default setup，不是 workflow

**推荐 Default setup**（GitHub 仓库 Settings → Code security → Code scanning → Default），理由：
- 零仓库文件、零维护、自动跟随 GitHub 的查询集更新
- 无需管 action 版本漂移
- **不产生仓库内的 workflow 文件** ⇒ 不改变 `git` 内容、不占发布窗口的「改动面」

**若必须用 Advanced setup（workflow）**，配置如下（`javascript-typescript` 语言，v4 为当前主版本线，2026-10 时点最新为 4.39.x）：

```yaml
name: CodeQL
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  schedule:
    - cron: "0 3 * * 1"   # 每周一 03:00 UTC，兜住不常推的场景

permissions:
  contents: read
  security-events: write   # 上传 SARIF 必需（缺失是这类 workflow 最常见的失败原因）

jobs:
  analyze:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v4
        with:
          languages: javascript-typescript
          # JS/TS 是解释型，不需要 autobuild；init 后直接 analyze 即可
      - uses: github/codeql-action/analyze@v4
        with:
          category: "/language:javascript-typescript"
```

注意点（都是实际会踩的）：
- **`security-events: write` 权限必须显式声明**，否则 `analyze` 上传 SARIF 失败。
- JS/TS **不要加 `autobuild`**（该语言无编译步骤，加了反而空跑一轮）。
- 建议加 `paths-ignore`：`node_modules`、`.next`、`docs`、`scripts` —— 本仓 `scripts/` 是采集脚本，纳入分析只会产生噪声告警。
- **v4 与 v3 并行维护**（同日发版）。选 v4；若选 v3 需在升级时同步。

### 6.4 风控影响（铁律 34 / §3.0 自检）

| 维度 | 影响 |
|---|---|
| **发布窗口** | 添加 workflow 需要一次 **push** ⇒ 占 1 次发布窗口（与 Vercel deploy 合并算同一次）。**不能为「加 workflow」单独开窗口**，应与下一次计划内推送合并 |
| **GitHub Actions 额度** | 公开仓库 **Actions 免费无限额**（不消耗私有额度）。若走 Default setup 则完全不占仓库额度统计 |
| **单次耗时** | JS/TS CodeQL ≈ 2–5 分钟。按每日 1 次 push 估算 ≈ 60–150 分钟/月 —— 公开仓库无上限，**无额度风险** |
| **§3.0 G 自检** | 添加 `.github/workflows/*.yml` 属「设置变更」，需走 G1–G6。预判：G1 否 / G2 否 / G3 否（单次文件添加，非高频）/ G4 否 / G5 否（不含凭据）/ G6 视当日窗口 → **可放行**，但必须与推送合并、且当日未超限 |
| **对 Vercel** | 无影响（workflow 不改变构建产物；Vercel 只认 push，不看 Actions 结果） |

**结论**：Technical 上无风险、无额度压力。唯一约束是**它必须搭车在一次已有的发布窗口里**，不能单独推。

## 10.5 结论

**建议只做档 1（`npm audit fix`，补丁级、零代码改动），把「全部消除」立为独立专项排在导航迭代交付之后。**

理由：
1. 全消换来的仅是 **14 条不进生产包的 dev 漏洞 + 4 条构建期 postcss 漏洞** —— 均「理论存在、实际打不到」；
2. 有现实意义的 critical（sharp RCE）**在档 1 就已解决**；
3. 全消的真实成本是「换打包器 + 换 lint 引擎」两次架构级变更，其修复量无法预估。

**补充约束（非催办）**：**eslint 9 已于 2026-08-06 EOL**，不再有安全补丁。升 eslint 10 属「技术债到期」，迟早要做，但应排独立窗口，不应塞进正在收尾的迭代。
