## 需求 2 · 导航时地图上巴士实时位置图标消失

### 现状与根因

**已排除（v3.8.0 未改动的三处，逐一 diff 过）**：

| 位置 | 结论 |
|---|---|
| `useRideTracking.ts:497-509` `mapVehicles` useMemo | v3.6.1（`c93e849`）与 v3.8.0 **逐行相同**：`phase==="riding" && !plate ⇒ return []` |
| `NavMap.tsx:1598` `<VehicleLayer>` 挂载 | 未改动（`phase==="ready"` + `enabled` + `vehicles`） |
| `NavShell.tsx:1057` `vehicles={detailActive ? ride.mapVehicles : rv.vehicles}` | 未改动 |

**根因链（高置信，三条规则叠加成一个真空区）**：

1. `useRideTracking.ts:505` —— riding 态**没有车牌** ⇒ `mapVehicles = []`（既有规则，不是新改的）；
2. `useRideTracking.ts:1040-1080` 主轮询 effect —— 条件 `phase==="riding" && plate`，无牌 ⇒ **不轮询**；
3. `useRideTracking.ts:1095-1096` v3.8.0 S3 新补的「riding 无牌轮询」effect —— 第一行 `if (!matchOnRef.current …) return`，而 `MATCH_VEHICLE_ENABLED` **缺省 false**（`match-vehicle.ts`）⇒ 该 effect 在生产**永不启动**。

⇒ **riding 且无牌 = 零轮询 + 零显示**：车辆坐标冻结在候车最后一帧，`mapVehicles` 恒空，图标消失。

**为什么现在才爆发**：v3.8.0 S2 把候车期定位改为粗定位（`NavShell.tsx` `coarse: navActive && ridePhase !== "riding"`）+ 上车判定链路大改（锚定/过站过滤/里程轴），**自动锁牌（`rankBoardingVehicles` → `setPlate`）成功率可能下降** ⇒ 更多行程走 `switchToRiding(null, "gps")`（GPS 上车，`useRideTracking.ts:878-884` 允许 nextPlate=null）⇒ 落进上述真空区的概率升高。这是**组合效应**，不是某一行被改坏。

### 改动方案（三选一或组合）

- **方案 A（最小，立即恢复显示）**：`mapVehicles` useMemo 中 `if (!plate) return lites.map(withCompany);` —— riding 无牌时回落显示该线路全部在途车（与 boarding 态 `:504` 同口径）。1 行改动，风险低；缺点：显示的是全部车而非「本车」，与「锁定车辆」语义弱化（但本来就没锁上）。
- **方案 B**：解除无牌轮询的开关门控（`:1096` 去掉 `matchOnRef` 条件）——坐标能持续刷新，代价是每 12s 多一次 `/api/route-vehicles` 请求；S3 明示开关关闭的理由是「判据未经真车标定」，但**轮询本身只是取数，不涉及判据**，解除在语义上站得住。
- **方案 C**：排查自动锁牌率为何下降（coarse 定位对 `rankBoardingVehicles` 输入的影响）——治本，但需真机数据，工作量不可控。

**建议**：A+B 组合（显示恢复 + 坐标刷新），C 另立观察项。

### 澄清问题

1. 「图标消失」是**上车后全程没有**，还是**中途消失**？（前者 = 无牌 riding 真空区；后者可能是 `lites.find(plate)` 找不到锁定车，`:506-507` 车辆列表刷新后车牌瞬时不匹配也会闪空）——可用 `data-vehicle-shown` / `data-veh` 钩子在真机抓一次。
2. 无牌时显示「全部在途车」是否符合预期，还是宁可不显示（等方案 C 把锁牌修好）？

### 工作量与风险

- 方案 A+B：**小**（各 1-2 行）；风险：低。方案 A 改变的是「无牌时显示策略」，不触碰判定链。
- 方案 C：**中-大**，需真车数据，不建议本轮做。

## 需求 3 · 「怎么才能赶上车」标签在出发前不可见

### 现状与根因（**已实锤，且不是「隐藏条件太宽」**）

负责人的口径：「只有在用户走到站以后才隐藏」⇒ 推荐/详情界面（用户还没出发）必须显示。

实读结论——**这个标签现在对绝大多数路线根本不存在**：

1. **数据端**：`src/lib/recommend/model.ts:621` —— `catchHint: i === 0 ? lrtCatchHint : undefined`。
   `lrtCatchHint` 只有一条产生路径：`model.ts:532-534`，**且只在首段是轻轨**（`first.kind === "ltr"` 分支内）。
   **巴士分支（`model.ts:462-505`）从未生成过 `catchHint`** —— 巴士段的「可赶上」信息从来只存在于 `tierText`（档位文案）。
2. **渲染端**：v3.8.0 S4 把 `catchHintOf` 的回落分支删了（`RoutePieces.tsx:30`：`leg.catchHint ?? ""`，旧版是 `leg.catchHint ?? leg.tierText ?? ""`），`TierBadge` 收敛为 `if (!catchHint || !tierText) return null`（`RoutePieces.tsx:78`）。

⇒ S4 之前巴士路线显示档位文案（「全力冲刺有机会赶上」等）；S4 删档位文案后，**巴士路线的赶车提示整体蒸发**——推荐卡（`RecommendCard.tsx:253`）、导航详情（`NavDetailBody.tsx:353`）、计卡详情（`CardDetailClient.tsx:236`）三处调用端判 `firstHint.text` 为空、什么都不渲染。轻轨段（`lrtCatchHint`，档 1/2 且有时刻）不受影响。

`git show 2806627 -- src/lib/recommend/model.ts` 为空 ⇒ model.ts 在 v3.8.0 **没动过**——缺口是 S4（v3.7.0 批次，随 v3.8.0 一起上线）删回落分支时暴露的**既有数据空洞**，当时 S4 注释自己警告过「否则会把可赶上 HH:MM 一起隐藏掉」，但只防住了「轻轨 hint 被删」，没发现巴士段从来就没有 hint。

### 改动方案

1. **`model.ts` 巴士分支补 catchHint 生成**（AC-107 的巴士版）：档 1/2（`t0 === 1 || t0 === 2`）且本班有真实时刻时，产出 `走快一点可赶上 ${clock} 那班`。
   - 时刻来源：`chosen.loSec`（`pickBoardable` 选中班的到站秒），换算 HH:MM 需要基准钟（轻轨用的是 `lv.clocks[depIdx]` 现成字符串；巴士侧若接口只有相对秒数，需要用 `nowMs + loSec*1000` 走 `macauClock`）。
   - 注意 SSR 冻结问题：轻轨那处特意不把客户端倒计时冻结下发（`model.ts:538` 注释）；catchHint 是「绝对时刻 HH:MM」不是倒计时，无此问题。
2. **「走到站后隐藏」**：现状导航站条**本来就不渲染** TierBadge（`types.ts:640`「只在方案卡、不进导航站条」）⇒ 推荐卡/详情页恢复显示后，负责人口径即满足，无需新增隐藏逻辑。
3. 措辞与档位的关系需澄清（见下）。

### 澄清问题

1. 巴士段的措辞：原来巴士显示的是**档位文案**（v1.0.6 五档：「全力冲刺有机会赶上 / 小跑能赶上 / 正常走能赶上」），没有「可赶上 HH:MM」。补的是轻轨同款「走快一点可赶上 HH:MM 那班」——负责人认可的「怎么才能赶上车」是否就是这个形态？（大概率是，但需确认，因为涉及档 3「正常走能赶上」时**不**出提示的取舍：轻轨侧只在档 1/2 出，巴士是否一致？）
2. 「走到站后隐藏」的隐藏主体：导航进行中站条本来就没有这个胶囊 ⇒ 是否还有别的地方需要加「到站后隐藏」？（可能负责人指的是旧版步行折叠里的「走快一点…」——那处属于档位文案，S4 已按内容口径删除，不在恢复范围。）

### 工作量与风险

- **小**（model.ts 一个分支 + 补一条单测）；风险：低。
- 注意：`catchHint` 变化会进推荐接口响应体，缓存头（S1 加的 s-maxage）不影响（字段是请求时算的）。

## 需求 4 · 加载动画全站替换（rc-sk 骨架屏 → BrandRouteLoader）

### 现状：全站骨架屏完整清单（实搜）

| # | 位置 | 形态 | 性质 |
|---|---|---|---|
| 1 | `src/app/recommend/loading.tsx:30-35` | 整页级骨架（chip+3 line 卡片形） | **路由级 loading**（Next 约定文件，SSR 导航期间整页占位） |
| 2 | `src/app/recommend/page.tsx:111-116` | 同上形态 | **SSR fallback**（服务端组件，首次直出） |
| 3 | `src/components/card/page.tsx:97-99`（`src/app/card/page.tsx`） | 3 条 line | 计卡详情 SSR 占位 |
| 4 | `src/components/nav/RouteResultPane.tsx:56-64` | **3 张完整卡片骨架**（big+chip+2 line） | client `phase==="loading"`，推荐结果列表 |
| 5 | `src/components/nav/RouteDetailPane.tsx:101-107` | `cd-sk`（big+3 line） | client `phase==="loading"`，路线详情 |

（v3.8.0 已替换掉第 6 处：`NavMap.tsx:1628` 的 `rc-sk--big` → `BrandRouteLoader slot="map-cover"`。）

### 关键区分：等待指示 vs 布局占位（给负责人的澄清核心）

- **#4 / #5**：真 client loading 态，替换语义干净——但骨架是**卡片形状**（预告「这里将出现 3 张卡」）。换成单个转圈后：加载期间不再有「卡片数量与形状预告」，加载完成时内容**跳入**。若负责人只要求「不要灰色方块流水灯」，可以在每张卡片骨架的**中心位**放小 M（保留卡形底），或者整列中心放一个（接受跳入）——两种视觉都要负责人选。
- **#1 / #2**：路由级/SSR 整页骨架。`BrandRouteLoader` 是 client 组件，可以在 server 组件里渲染（`active` 传常量 `true`），但整页骨架换成一个转圈 = **丢掉整页内容预告**，且 `loading.tsx` 的骨架本身就是为了掩盖 SSR 延迟——这一处要不要换，**强烈建议澄清**（可能是负责人看到 #4/#5 时的迁移要求，未必包括 #1/#2）。
- **#3**：同 #1/#2 性质。

### 改动方案（按澄清结果两档）

- **保守档（仅 #4/#5）**：`RouteResultPane` / `RouteDetailPane` 的骨架区替换为 `<BrandRouteLoader active slot="request" label="加载中…" />`（`request` slot：GATE_MS=300，防快路径闪烁）。注意两处都是「列表/面板级」等待，`slot="request"` 语义吻合；`GATE_MS` 无需改。
- **全量档（#1~#5 全换）**：#1/#2/#3 的 server 组件内直接渲染 `<BrandRouteLoader active … />`（client 子组件，无 hydration 问题）；但需接受「整页预告消失」的后果。

### 澄清问题

1. 「全项目所有加载等待」是否包括 `recommend/loading.tsx`、`recommend/page.tsx`、`card/page.tsx` 这三处**整页/SSR 骨架**？（换掉 = 丢内容形状预告）
2. #4 三张卡片骨架：换成「保留卡形、卡内放小 M」还是「整列一个转圈」？（前者无跳入、后者更彻底）

### 工作量与风险

- 保守档：**小**（2 文件各 ~6 行）；全量档：**小-中**（+3 文件，需处理 server/client 边界）。
- 风险点：均低；唯一要防的是 `aria-hidden="true"` 的骨架容器换成 live 组件后 a11y 语义变化（`role="status"` 会播报，是改善但会改变测试基线）。

## 需求 5 · 路线详情删除「开始步行」按钮

### 现状与链路

- 按钮：`src/components/nav/NavDetailBody.tsx:248-254`（`rc-walkpreview__go`，文案「开始步行」，`onClick={() => onWalkStart?.(seg, pv.serverSteps)}`）。
- 链路：`onWalkStart` → `RouteSheet.tsx:518` `onWalkStart={walk?.active ? null : walk?.onStart}` → NavShell 步行状态机。
- 全自动推进已存在：`NavShell.tsx:422` 注释明示「推进规则（全自动，用户不再需要点开始步行）」——①「开始导航」即可进首段步行；②走到上车站自动交棒乘车；③下车自动进步行到达段；④到达收尾。
- `NavShell.tsx:740-750` `walkGhosts`：`walkSeg` 驱动，不依赖按钮。
- 按钮渲染条件：`pv.phase === "ready"`（步行预览取数成功）才出现；`:321` `:430` 两个折叠区（out/in）各有一个。

### 删除影响评估

- 主流程**不受影响**：①~④推进不经过该按钮；「开始导航」主按钮与 `walk.onStart` 的汇合点在 NavShell（实现时需确认主按钮 handler 是否复用同一函数——若复用，只删按钮 JSX 即可，prop 链保留）。
- 保留「步行步骤列表」（`WalkStepList`）与「全程 X 米 · 约 Y 分钟」——只删按钮。
- 边界：删除后用户在**详情页**失去「直接进入步行跟随」的手动入口（只能从「开始导航」进入）。按 NavShell 注释这是设计意图的收敛，但若首段步行很长，用户可能想跳过乘车先走——这是产品取舍，需负责人确认（大概率 OK，因为他就是要删）。

### 澄清问题

1. 「开始步行」按钮删除后，**步行预览折叠区本身保留**（步骤列表还在）对吗？还是折叠区也一并简化？
2. 需求原文「主页面开始导航 + 步行折叠处开始步行」——确认「开始导航」按钮本身不动。

### 工作量与风险

- **极小**（1 个 JSX 分支 + 确认 prop 链是否还有其他消费方）；风险：低。

## 需求 6 · 步行路径改主题绿实线（与巴士段一致）

### 现状（三块实读）

1. **圆点/虚线的出处**：`src/components/nav/nav-map-walk.ts:87-100` `common()` 写死
   `strokeStyle: "dashed"` + `strokeDasharray: [0.5, 12]` + `lineCap: "round"` —— 三者合成「圆点串」效果。
   三条线（done 灰 / now 绿 / ahead 绿细）与 ghost 全部经此函数 ⇒ **一处改，全量生效**。
   颜色已走 token：`--map-walk-ahead`（#0b6e4f 主题绿）、`--map-walk-done`（灰）——**颜色不用改**，只改线型。
2. **「走过涂灰」机制已有**：`donePath`（导航中随轨迹累积涂灰）+ ghost 的 `tone: "done"`（非当前段已走过）。
3. **未导航时不显示——这是现状，也是工作量主体**：
   - `NavShell.tsx:740-741`：`walkGhosts` 第一行 `if (!rsOpen || pane !== "detail" || !sessionLive) return null;`
     ⇒ **未开始导航（sessionLive=false）时两段步行走廊完全不画**；
   - `route-overview.ts`（ov.legs）**只有乘车彩段**，无步行几何（grep walk 零命中）；
   - 步行几何来源 `walkOutPath/walkInPath`（`NavShell.tsx:730` flatMap 自 `walkRoute.out/in.steps`）；
     `walkRoute = useWalkRoute(walkOds)`（`:496`），`walkOds`（`:473`）**只要详情打开且有起终点就构造**——即预取数据在未导航时就绪（`useWalkRoute` 是否在 idle 时自动 ensure 需实现时确认，`:694-696` 只见对 `in` 段的自动 ensure）。

### 改动方案

1. **线型（必做，一行级）**：`common()` 改 `strokeStyle: "solid"`，删 `strokeDasharray`。建议把线型也 token 化（`--map-walk-style`）以防将来再翻回。
   ⚠️ `lineCap: "round"` 注释自述「是圆点的唯一来源」——改实线后 round cap 保留（端点圆润，与巴士段一致），圆点效果自然消失。
2. **未导航显示（工作主体）**：`walkGhosts` 的 `!sessionLive` 门控放宽为「detail 打开且有几何就画」；未导航时两段全是 `tone:"ahead"`（绿）⇒ 天然呈现「绿-乘车色-绿」。
   - 需确认 `useWalkRoute` 在未导航时是否已拉取（若只在导航启动时 ensure，需补一个「detail 打开即 ensure」——注意 `/api/walk-route` 预算口径 AC-08a（单次导航 ≤4 次）是否要为未导航预取加豁免）。
   - 「走过的涂灰」未导航时不存在（没走过）⇒ 全绿即正确形态，导航后随 `tone` 翻灰——机制现成，只是门控放开。
3. **与巴士段视觉一致**：巴士彩段 z72 / 步行 ghost z68 / 三线 z69-73，层级不需动；宽度 token（w5/w7 vs ghost w4）建议按「与巴士段一致」统一，需设计师给数值或确认沿用现值。

### 澄清问题

1. 未导航时的步行预取会新增 `/api/walk-route` 调用（进入详情页即触发），是否接受这个请求开销？（现预算口径是否覆盖）
2. 「与巴士段显示一致」是否包含**线宽一致**（巴士段宽度 vs 现步行 w5/w7）？
3. 未导航时用户**还没开始走**，「走过的涂灰」只发生在导航后——确认「未导航全程绿」即可，无需预演灰色。

### 工作量与风险

- 线型部分：**极小**；未导航显示：**中**（门控 + 预取时机 + 请求预算确认）。
- 风险：中低。最大风险是未导航预取的请求量与 `useWalkRoute` 的 ensure 时机（实现前需一次小验证）。
