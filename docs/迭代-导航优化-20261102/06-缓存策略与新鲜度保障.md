## 1. A. 「收藏页旧数据」的真实根因

### 1.1 文档检索结果（先给证据，再推断）

我检索了 `docs/` 全部文档、`.workbuddy/memory/` 全部日志、以及 `git log` 全部提交说明。

**直接描述「收藏页旧数据」的条目：无。** 没有任何一份文档或提交说明以这个措辞记录过事故。

**但检索到三条同源记录，合起来足以还原根因：**

| 时间 | 记录 | 性质 |
|---|---|---|
| 2026-09-04 | `docs/刷新与缓存机制调研-20260904.md` | **同类问题的完整调研**。结论原文：「系统存在『打点/手动刷新命中 10s 缓存返回旧值』的竞态窗口 + Vercel 多实例缓存隔离导致数值横跳」。含用户当时的反馈「刷新后站距不对」「越刷越乱」 |
| 2026-09-21 | `.workbuddy/memory/2026-09-21.md` | **`force-cache` + CDN 钉住旧响应结构**。原文：「v2.10.0 起 `/api/stations` 才下发 `color/color2`，但旧响应被 `force-cache` + CDN 存住」⇒ 修法是 URL 加 `?include=lrt&v=2` |
| 2026-10-29 | 提交 `1f2290a` → `3b7096f` | **前端合并逻辑把上一次结果留在屏幕上**。`3b7096f` 原文：「阻断 ①：merge 无条件生效 ⇒ 废掉换 OD / 切偏好 / 切轻轨优先……否则服务端重排会被旧顺序覆盖、**旧目的地路线会残留**」 |

### 1.2 当年的候选链：`FavoritesClient` → 点击 → 结果

`docs/` 里的首页注释写明现行路径：`/favorites` 点「地点对」→ `/?<query>` → 首页解析出起终点预填，进「可出发」态（**不自动跳结果页**）。

⇒ 收藏页**本身不发导航请求**，它只做一次客户端跳转。所以「收藏页的旧数据」在**现行版本**上只可能来自两处：
1. **跳转后的首页沿用了上一轮的推荐结果**（组件状态）；
2. **某个缓存层返回了旧值**（数据源）。

关键在于「刷新才生效」这个描述 —— 它把两者区分开了：
- 若是**数据源缓存**（`transit_cache` / CDN / `force-cache`），**浏览器刷新也救不了**（旧副本还在），只有 TTL 到期或版本号变了才行 → 与「刷新就生效」矛盾；
- 若是**组件状态**，浏览器刷新 = 整页重挂 = 状态清空 → **立刻生效** → 与描述完全吻合。

⇒ **「刷新才生效」本身就是「问题在组件状态，不在数据源」的判据。**

（唯一例外是 09-21 那次：`force-cache` 的旧响应结构**刷新也不生效**，必须改版本号。用户当时的感受是「图标颜色一直不对」，不是「刷新才生效」，所以不是同一类。）

### 1.3 但「用了缓存之类的」这个直觉也不是错的 —— 它指对了另一半

`docs/刷新与缓存机制调研-20260904.md` 记录的是**真·数据源缓存**导致旧值：`globalThis.__etaCache`（TTL 10s→5s）命中时直接返回旧 `EtaResponse`，而前端手动刷新**不带 `force`** ⇒ 刷新也拿旧值。当时收藏 v2.x 的「方案子列表」正是走 `fetchLive`（读这份缓存），所以**收藏页确实显示过旧到站数**。

⇒ 完整结论：

> **当年是两个问题叠在一起**：① 收藏页方案子列表吃 `__etaCache`（5–10s 旧值，且刷新不带 force ⇒ 刷也白刷）；② 首页结果列表用了 merge/去重逻辑，把上一次请求的结果留在屏幕上（刷新整页才清空）。
> **修法完全不同**：① 是「缓存层要能被旁路 + 缩短 TTL」，② 是「请求去重窗口要有时效 + 查询键要含所有影响结果的输入」。把两者都归因成「缓存」会做错修复。

### 1.4 当前仍然存在的同类缺陷（**这是本期必须修的**）

`src/components/nav/useRecommend.ts:142-147`：

```ts
// 打开时（含首次）拉取；同一 query+prefs 只自动拉一次（关闭再开 = 秒显上次结果）
useEffect(() => {
  if (!open || !fullQuery) return;
  if (loadedQueryRef.current === fullQuery) return;   // ← 无条件跳过
  void load(fullQuery);
}, [open, fullQuery, load]);
```

`loadedQueryRef` **没有任何时间因素**。而 `queryOf`（`StepSheet.tsx:364-378`）生成的是**确定性字符串**（只有坐标/站码/标签，无时间戳）。

⇒ 后果，逐条可复现：

1. 用户在同一页面会话内搜 A→B（t0），拿到卡片（含车辆位置与到达时刻）；
2. 收起面板（`open=false`，hook 在 `RouteSheet` 内**不卸载**，`data` 保留）；
3. t0+20 分钟再点同一 OD → `open=true`，`loadedQueryRef.current === fullQuery` ⇒ **直接 return，一个请求都不发**；
4. 屏幕上显示的是 20 分钟前的车、20 分钟前的「还有 3 站 · 约 5 分钟」、20 分钟前的到达时刻；
5. 点刷新键 → 才更新（**【「刷新才生效」】**）；
6. 按 F5 整页重载 → 组件重挂 → 立刻正确（**【「刷新才生效」的另一种表现】**）。

**这完全复现了负责人的描述**，且它是**当前线上代码**，不是历史遗留。它同时直接违反 Spec 的 R3（「禁止复用上一次请求的结果」）。

> 补充：跨路由（`/favorites` → `/`）会重挂页面，`loadedQueryRef` 随之清空，所以**跨页面不触发**。触发条件是「停留在 `/` 上，同一 OD 关掉再开」—— 而这恰好是最常见的使用方式（看完结果去别处、过一会儿回来再走一趟）。

### 2.6 对「直接删除这 3 处 `force-cache`」裁决的评估（团队决策，我的结论：**同意，附 3 个条件**）

团队决定不补版本号，而是**删掉 B4–B6 的 `force-cache`**，改由服务端 `max-age`/`s-maxage` 单层管理。我的评估：

**为什么这个裁决比「补版本号」更好**
1. **消灭一层缓存，就消灭一类事故**。两层缓存（浏览器 + 边缘）各自有生命周期，"哪层给了旧副本"无法从外部判断 —— 09-21 那次排查就卡在这里。单层后，陈旧只有一个来源，**可判定**。
2. **版本号仍然是「靠人记得 +1」**，与本专项「不靠人守」的原则冲突（RL2 已改为形状自动派生）。删掉这一层，就不需要给每个 URL 设计版本段。
3. **成本可控**：见下。

**代价测算（这是团队担心的点）**

| 站点 | 现状 | 删除后 | 增量 |
|---|---|---|---|
| B4 `NavMap` 线路模式拉 shapes | 浏览器缓存命中 ⇒ **0 RTT** | 边缘命中（加 `s-maxage` 后）⇒ **约 40–80ms**（澳门→hkg1） | +1 次边缘往返 |
| B5 `useRouteOverview` 详情总览 | 同上 | 同上，每个 distinct route 一次（1–2 条） | +1~2 次边缘往返 |
| B6 `RouteLinesSheet` 线路列表 | 同上 | 同上，每次打开线路面板一次 | +1 次边缘往返 |

⇒ 最坏情况（打开详情 + 打开线路面板）**+150ms 左右**，相比之下 `route-shapes` 现从 iad1 取是 **525ms（热）/1924ms（冷）**。**判断：可接受。**

**必须同时满足的 3 个条件**

1. **顺序：先加 `s-maxage`，再摘 `force-cache`（同一提交或服务端先行）**。若先摘后加，请求会直达 iad1（525ms+），比现状明显退步。这一点是**唯一可能让裁决变错**的情形。
2. **范围：只摘 B4–B6 三处；`stations` 的 B1–B3 必须保留 `force-cache`**。理由：`stations` 是 **103KB**（最大载荷），服务**地图首屏**（每次进首页都要），且它的 `v=2` 是 09-21 事故后验证过的。摘掉它等于把那次事故的保护拆掉，且每次进首页多传约 25KB（br）。若团队的本意包含 stations，请先与我确认。
3. **实施时不得改变 `card` / `routeLine` 的引用稳定性**。我已核过当前实现是安全的：`ovExtra` 走 `useMemo`（`NavShell.tsx:282`）、`detailCard.card` 是 `useState`（`:178`）、`applyCamera` 是 `useCallback`（`NavMap.tsx:374`）、`routeLine` 来自 `rv.picked`（`useState`）⇒ effect 只在「选线路 / 打开详情」时触发一次，不会随渲染反复请求。**但若实施时把 `card` 或 `routeLine` 改成内联对象**，就会退化成"每次渲染一个请求"—— 这一条必须写进本次 review 清单。

**若实测发现回退明显（>300ms）**：替代方案不是退回 `force-cache`，而是由服务端下发 `staticVersion`（`/api/health` 或首屏 RSC 注入），前端把它拼进 URL（`&v=<version>`），版本**由数据形状派生**。这样保留 0 RTT 且自动失效，代价是多一次 bootstrap。**但优先用删除法**（更简单，且消掉了整层风险）。

## 3. C. 「从任何入口发起导航必然新鲜」的机制保证

**设计原则：不写「开发时注意」，写成「结构上做不到复用」。** 三层，每层单独成立，任何一层失效另两层仍能兜住。

### 3.1 第一层：类型层隔离（静态段与实时段不可混装）

新增 `src/lib/nav/freshness.ts`（纯类型 + 纯函数，client-safe）：

```ts
/** 发起时刻（品牌类型：防止把「今天零点」之类误当 issuedAt 传进来） */
export type IssuedAt = number & { readonly __brand: "issuedAt" };

/** 客户端「同一请求复用」的时效窗口 —— 超过即必须重发 */
export const FRESH_WINDOW_MS = 5_000;

export function isFresh(loadedAt: number, now: number, windowMs = FRESH_WINDOW_MS): boolean {
  return now - loadedAt < windowMs;
}

/**
 * 静态段：**类型上不允许出现任何时间推导字段**。
 * 用途：`getStaticRows()` 的返回类型、`RecStatic` 的字段约束。
 */
export interface NavStaticOnly {
  // 只允许「不含 now 的输入」派生出来的量：站序、站名、几何、里程、班距表、步行实测
  readonly __staticOnly: unique symbol;
}

/**
 * 实时段：**必须**带 issuedAt，且**禁止**进任何缓存。
 * 用途：`fetchLive()` 的返回、卡片里的 `liveText`/`waitMin`/`arriveAt`。
 */
export interface NavLiveOnly {
  readonly issuedAt: IssuedAt;
  readonly expiresAt: number;
}

/** 运行时哨兵：缓存写入前调用；命中禁止字段即抛错（不是 warn） */
export function assertNoLiveFields(payload: object, where: string): void;
```

`assertNoLiveFields` 的检查清单（与 R1 同源，只写一次）：
`liveText` / `liveMainMs` / `liveDepartures` / `stopsAway` / `etaMin` / `etaSec` / `waitMin` / `arriveAt` / `depMs` / `totalMin` / `minutes`（乘车段）/ `lat`+`lng`（车辆）/ `plate` / `progress`。

调用点（各一行，写在缓存**写**之前）：
- `recommend/query.ts` → `loadStaticsUncached()` 返回前：`assertNoLiveFields(rows, "getStaticRows")`；
- `nav-service.ts` → 任何 `*Cached()` 函数写 `globalThis` 之前。

> 为什么用**抛错**而不是 `console.warn`：`query.ts` 已经吃过一次「超限只 warn ⇒ 静默不写 ⇒ 三年没人发现」的亏（原注释原话）。同一类错误不能用同一种弱手段。

### 3.2 第二层：`issuedAt` 的**正确作用域**（★ 本节已修订，原设计会毁掉 S1）

> **修订说明（2026-11-02 二次审）**：本文初稿把 `issuedAt` 当作 `transit_cache` 的命中下界
> （`fetched_at >= to_timestamp(issuedAt/1000)`）。**这个设计是错的，且危害极大，已撤销。**
> 原因见下「为什么不能对 `transit_cache` 用 `issuedAt`」。若后端已按初稿动手，请立即停止。

#### 3.2.1 为什么不能对 `transit_cache` 用 `issuedAt`

`issuedAt` = 用户发起时刻。若要求 `fetched_at >= issuedAt` 才算命中，那么：
- 用户在 12:00:00.000 发起 ⇒ 只有 **12:00:00.000 之后写入**的条目才算命中；
- 而缓存条目是**上一次请求**写的，必然早于本次 `issuedAt` ⇒ **几乎 100% 不命中**；
- ⇒ 每次用户发起的导航都要真打高德：实测 `transitMs` 冷态 **2.9–4.7s**（关闸→澳科大 6196ms）。
- ⇒ **S1「热态 P50 ≤ 2000ms」直接归零**，并把高德配额从「偶发消耗」变成「每次导航必耗」。

根因是我初稿把 `transit_cache` 当成「实时值缓存」了。它不是：
它存的是**高德的方案拓扑 + 各区段时长估计**，属于「分钟级稳定的路线知识」；
真正的实时值走 `fetchLive` → `queryEta`，那一路本来就**只有 5s dedupe**（`dsat/eta.ts:112`），不存在「几十分钟不更新」的可能。

#### 3.2.2 三层的真实新鲜度上界（这是判据的基础）

| 数据 | 缓存 | 陈旧上界 | 是否够新鲜 |
|---|---|---|---|
| 高德方案（拓扑/时长） | `transit_cache` 60s | **≤60s** | 够（拓扑与分钟级时长不会有实质变化） |
| DSAT 报站/位置 | `queryEta` 的 `__etaCache` 5s | **≤5s** | 够（≤ 一个刷新周期） |
| 静态数据 | 进程内 60s + Data Cache 60s | ≤60s | 够（日更数据） |
| **客户端复用的上一轮结果** | **无任何上界**（`loadedQueryRef` 永不过期） | **可达数十分钟** | **不够 —— 这才是真问题（P1）** |

⇒ 三个服务端缓存的上界都在 60s 内，**不可能**产生负责人描述的「旧数据、刷新才生效」。
唯一没有上界的是**客户端复用**。所以机制保证的重心必须放在客户端 + live 层，**不是** `transit_cache`。

#### 3.2.3 修订后的 `issuedAt` 定位：诊断量，不参与命中判定

| 用途 | 是否保留 | 说明 |
|---|---|---|
| `transit_cache` 命中下界 | **撤销** | 见 3.2.1 |
| dedupe 缓存（`__etaCache` 5s / `__stationEtaCache` 20s / `__switchPlansCache` 20s）的**用户主动刷新旁路** | **已有，不新增** | `/api/nav?nocache=1`、`/api/dsat/eta?force=1` 已实现；这条本就是「用户说刷新就必须真刷」 |
| 响应里回带 `issuedAt` 供验收断言「这次结果不是上一轮」 | **保留（仅字段）** | `stats.issuedAt`，零风险，用于 AC5.4 的机验 |
| 客户端 5s 复用窗口的时间基准 | **保留** | 但那是**客户端本地**的 `at`，不需要传给服务端 |

**结论：不新增任何 SQL 条件、不改 `TransitCacheIo.get` 签名。** 第二层由「服务端下界校验」改为
「**服务端回带 `issuedAt` 供验收 + live 层 5s 上界 + 客户端 5s 窗口**」三者合力。

**唯一保留的服务端改动（1 行，零风险）**：`/api/nav` 响应 `stats` 里回带 `issuedAt`（= 本次 `planNav` 的 `nowMs`）。
用途只有一个 —— 让 AC5.4「三条入口各自独立」可以机验：断言三次请求的 `stats.issuedAt` 互不相同且递增。
它**不参与**任何命中判定，所以不会影响性能。

### 3.3 第三层：客户端「复用窗口」改为有时效（**这是本专项真正的主修复**）

`src/components/nav/useRecommend.ts:75-86,142-147` 的具体改法：

```ts
// 现在：loadedQueryRef 记录「拉过哪个 query」，永不过期
const loadedQueryRef = useRef<string | null>(null);

// 改为：记录「什么时候拉的」，只有窗口内才复用
const loadedAtRef = useRef<{ q: string; at: number } | null>(null);

useEffect(() => {
  if (!open || !fullQuery) return;
  const prev = loadedAtRef.current;
  if (prev && prev.q === fullQuery && isFresh(prev.at, Date.now())) return;  // 仅 5s 内复用
  void load(fullQuery);
}, [open, fullQuery, load]);
```

`load()` 内：`loadedAtRef.current = { q, at: Date.now() }`。用户主动刷新仍走既有的 `reload({nocache:true})`（已有能力，不需要新增参数）。

**关键约束（否则会引入新 bug）**：**不要把任何时间戳拼进 `fullQuery`**（`useRecommend.ts:99` 的 merge 键）。时间戳与 `nocache` 同类 —— 只改变「从哪拿数据」，不改变「这是哪一批方案」。若拼进去，merge 守卫永不命中，列表每次刷新都整体替换 ⇒ 违背「只刷数字不换路线」（这正是 `3b7096f` 修过的阻断）。

> 注意：本层是**唯一**能解决负责人所述现象的一层 —— 因为它管的是「客户端到底有没有去要新数据」。
> 其余两层（类型隔离、服务端 `issuedAt` 字段）都只是让「要了之后拿到的不是旧值」，管不到「不去要」。

### 3.4 三层的关系（为什么不能只做一层）

| 只做 | 会漏什么 |
|---|---|
| 只做第一层（类型隔离） | 类型管不住「同一个合法响应被复用两次」—— 数据本身不含时效字段，但它算出来的 `totalMin` 是 20 分钟前的 |
| 只做第二层（`issuedAt` 诊断字段） | 它**只用于验收断言**，不参与命中判定 ⇒ 运行时不提供任何保护 |
| 只做第三层（客户端 5s 窗口） | 5s 窗口内仍可能拿到别的入口刚写进 `transit_cache` 的方案；且窗口靠调用点自觉实现，容易漏 |

三层齐备时：客户端 5s 外必发（第三层）→ live 层 5s 上界 + `transit_cache` 60s 上界（第二层的真实载体）→ 静态/实时类型层保证静态缓存里没有时效字段可漏（第一层）。

**权重说明（别把力气花错地方）**：真正解决负责人所述现象的是**第三层**；第二层是「上界已知」的保障（60s/5s，本来就够）；第一层是防回归的护栏。⇒ 派工时优先第三层，其次第一层，第二层只需 1 行字段。

## 4. D. 拆包方案 —— **结论：不需要拆**

### 4.1 实测体积（推翻 Spec 的前提）

`Spec §5` 写「静态数据 payload 必须拆到单条 < 2MB；当前 3.07MB ⇒ 静默不写」。**这个前提已过期。**

我用与 `getStaticRows()` 相同的取数与编码方式逐表量了体积（`.verify/perf/static-split-probe.mjs`，只读）：

| 表 | 行数 | 原始 JSON | 入缓存形态（编码后） |
|---|---|---|---|
| `segment_stats` | 14,951 | 2.436MB | **0.768MB**（数组编码 `SEG_COLS`） |
| `stations` | 619 | 0.098MB | 0.098MB |
| `lrt_timetables` | 84 | 0.086MB | 0.086MB |
| `route_stations`（聚合成站序） | 123 组 | 0.026MB | 0.026MB |
| `plan_legs` | 64 | 0.013MB | 0.013MB |
| `lrt_station_biases` | 56 | 0.006MB | 0.006MB |
| `routes.color` | 100 | 0.003MB | 0.003MB |
| `station_walk_distance` | 37 | 0.003MB | 0.003MB |
| `walk_times` | 20 | 0.002MB | 0.002MB |
| `commute_plans` | 14 | 0.002MB | 0.002MB |
| 其余（`transfer_walks`/`places`/`lrt_api_stations`/`lrt_holidays`/`lrt_route_params`） | 合计 104 | 0.002MB | 0.002MB |
| **合计** | — | **2.68MB** | **1.008MB** |

换算成 Next 判定的 `itemSize`（`predictedItemSize` 复刻 `JSON.stringify({kind,data:{body}})` 的二次转义，膨胀系数 1.19）：

```
itemSize ≈ 1.008MB × 1.19 ≈ 1.20MB  <  2.00MB（上限）
余量 ≈ 0.80MB（约 40%）
```

> 口径说明：Next 用的是 `JSON.stringify(...).length`（UTF-16 码元数），我对的是 UTF-8 字节数。中文在 UTF-16 里占 1 个码元、UTF-8 里占 3 字节 ⇒ **UTF-16 长度恒 ≤ UTF-8 字节数**。既然 UTF-8 口径都已 1.008MB，UTF-16 口径只会更小。结论对两种口径都成立。

### 4.2 为什么变小的

不是运气，是 v3.6.1 已做过一次针对性优化：`segment_stats` 从「每行重复键名的对象数组」改成「按 `SEG_COLS` 的数组数组」，同一份数据从 2.436MB 压到 0.768MB（**-68%**），并把缓存键从 `rec-static-rows-v1` 换成 `v2`（不做编码分支，避免永久负担）。

⇒ **`Spec §5` 的「必须拆包」应删除；`§6` 的「`/api/health` 新增 `cache.staticRows`」保留（用于验证），但 `AC5.3` 的判据要改（见 §4.4）。**

### 4.3 仍然建议做的两件小事（不是拆包）

| 事项 | 理由 | 代价 |
|---|---|---|
| **给 `getStaticRows` 加体积断言** | 现在只有 `predictedItemSize` 的**观测**（写进 `__staticCacheObs`），没有**护栏**。将来某张表涨上去又会静默不写 | 3 行：`if (size > LIMIT) throw` |
| **把 `segment_stats` 的单行体积盯住** | 它占 76%（0.768/1.008）。它随「补采」增长：`docs/追踪数据分析` 记录每天约 +3.3k 段样本、9 个时段空格待补。按当前 14,951 行 → 若涨到 **38,000 行**就会触顶 | 在 `/api/health` 里报 `parts.segBytes`，配一条 cron 告警 |

按当前增速估算，触发上限大约还需要**数月**（受补采计划影响，不是自然增长），因此**本期不做拆包，但必须有护栏**，否则下次会以同样的方式静默失效。

### 4.4 `AC5.3` 的判据要改（原判据不可稳定通过）

原判据：`AC5.3 When 部署完成后访问 /api/health，cache.staticRows.status 必须为 ok 且 sizeBytes < 2097152`。

**问题**：`/api/health` 读的是**本实例**的 `__staticCacheObs`，而 Serverless **每个请求可能落到不同实例**。我实测：先打一次 `/api/nav`（该实例装载了静态数据），紧接着打 `/api/health`，读到的仍是 `status: "not-run", sizeBytes: 0` —— 因为 health 落到了另一个空闲实例。

⇒ 原判据会**大概率读到 not-run 而误判失败**（或反之，读到某个旧实例而误判通过）。

**改法（推荐）**：`/api/health?warm=1` —— 同一个请求内先 `await loadStatics(getPool())` 再读 `__staticCacheObs`，保证「观测」与「装载」在**同一实例**：

```ts
// src/app/api/health/route.ts
export async function GET(req: NextRequest) {
  if (req.nextUrl.searchParams.get("warm") === "1") {
    await loadStatics(getPool());   // 同实例强制装载
  }
  const staticCache = await getStaticCacheObs();
  ...
}
```

新判据：`GET /api/health?warm=1` 返回 `cache.staticRows.status === "ok"` 且 `sizeBytes` 落在 `[0.8MB, 2MB)`（下界防「读到 0 当通过」）。

### 4.5 若将来真需要拆（预案，本期不做）

只在 §4.3 的护栏触发时才启用。拆法按「访问频率 × 体积」而不是按表：

| 键（含版本号） | 内容 | 体积 | 何时读 |
|---|---|---|---|
| `rec-static-core-v3` | 站序 + 站表 + 线路色 + 方案库 + 步行/换乘 | ≈0.25MB | **每次请求都读** |
| `rec-static-seg-v3` | `segment_stats`（数组编码） | 0.768MB | 建模阶段才读（`modelOption`） |
| `rec-static-lrt-v3` | 轻轨时刻表 + 偏差 | ≈0.10MB | 仅含轻轨段时读 |

**读命中是内存级还是 RTT？** 这是拆包唯一的真实代价：Vercel Data Cache 的读**不是**同进程内存，每次 `unstable_cache` 未命中进程内缓存时是一次**边缘/区域存储往返**（量级 5–20ms，远小于一次 DB RTT，但不是 0）。所以拆成 3 条最多多 2 次这种往返（≈10–40ms），可接受；**拆成 10+ 条就会把省下的传输量换成往返次数**，这是「按表拆」的陷阱。

## 5. 五条红线的逐条评估

| 原条 | 评估 | 依据 |
|---|---|---|
| **R1** 缓存条目不得包含车辆位置、到站剩余秒数、等待时长、按当前时刻推算的任何数值 | **方向对，但过严且与 R4 自相矛盾** | 「按当前时刻推算的任何数值」把 `transit_cache` 也包含了 —— 它存的高德方案里 `amapDurationSec` 会在映射失败时**写进卡片**（`recompute.ts:216`）。R4 又明说它保持 60s ⇒ 两条互斥。且按字面读，`totalMin`（总时长本身就含等待）也算「推算值」，那卡片根本不该缓存任何东西。**必须收窄为「本项目自己计算的实时值」+ 显式列豁免** |
| **R2** 静态缓存键必须含 schema 版本，发版即整体失效 | **合理，但「发版即整体失效」做不到** | 键里的版本号是**手写的**，只有「改了数据形状的人记得 +1」才生效。真实机制是「改形状时必须 +1」= 靠人守，与本专项「不靠人守」的原则冲突。**修订：版本号 + 形状指纹自动派生**（见 R2'） |
| **R3** 任何入口发起导航，实时段必须重算，禁止复用上次结果 | **合理，是最核心的一条**。但判据要可机验 | 原判据「间隔 2 分钟后从收藏页进入，`stats.liveMs > 0`」无法验证「客户端有没有真的发请求」，也无法覆盖 §1.4 那个「压根不发请求」的缺陷。**修订：加客户端侧的 `data-result-stage` 与请求计数断言**（见 R3'） |
| **R4** `TRANSIT_CACHE_TTL_SEC` 保持 60 | **过度（但方向安全）** | 我实测 `transit_cache` 793 行里 319 个坐标对、148 个重复出现（46%）⇒ 60s TTL 让这 46% 的重复请求几乎全部白付高德往返（冷态 2.9–4.7s）。但**负责人的硬约束是「不许旧」**，而上调 TTL 就是换陈旧度。⇒ 保留 60s 是对的，但**应把它写成 R1 的豁免而不是独立红线**，并注明「若要提速，走 `issuedAt` 而非延长 TTL」 |
| **R5** `force-cache` 仅用于纯几何与站点清单，键必须带版本号；实时接口一律 `no-store` | **合理，且已发现 3 处现存违规** | 6 处 `force-cache` 中 `route-shapes`×2 与 `route-lines`×1 **没带版本号**（§2.5）。这不是「将来要注意」，是**现在就违规**，且与 2026-09-21 事故同形 |

**总评**：五条里 **R1 需收窄（含与 R4 的矛盾）· R2 需换实现 · R3 需换判据 · R4 应降级为豁免 · R5 直接可用且要补 3 处违规**。

## 6. E. 修订版红线（最终版 · 可直接写进 Spec）

> 编号 `RL1…RL9`。判据列全部可机验（脚本 / grep / SQL / 断言），不含「注意」「应当」这类靠人守的表述。
> 「违反后果」统一按 **阻断缺陷** 处理（不得合并、不得发版）。

| 编号 | 规则 | 判据（怎么机验） | 违反后果 |
|---|---|---|---|
| **RL1** | **本项目计算的实时值不得进任何缓存**：车辆坐标/车牌、到站剩余站数、到站剩余秒/分、等待时长、任何以「现在」为输入的推算值。**唯一豁免**：`transit_cache`（上游高德原始方案，60s，且其时长仅在本地无数据时作回落，并以 `provenance.usedAmapFallbackLegs` 可观测） | 缓存写入前调用 `assertNoLiveFields(payload, where)`；检查清单 = `liveText/liveMainMs/liveDepartures/stopsAway/etaMin/etaSec/waitMin/arriveAt/depMs/totalMin/minutes/plate/progress/lat+lng`。脚本 `.verify/perf/check-cache-redlines.mjs` 对每个缓存点注入哨兵字段，断言**抛错而非通过** | 阻断 |
| **RL2** | **缓存键的版本段必须由「数据形状」自动派生**，不靠手写递增：`<name>-v<sha1(cols+types)[0..7]>`。改了 SELECT 列/编码方式 ⇒ 键自动变 | 键构造处只能引用同一个 `shapeHash()` 产物；grep 禁止出现硬编码 `-v1`/`-v2` 字面量（`stations?v=2` 这类 URL 参数除外，见 RL5） | 阻断 |
| **RL3** | **服务端必须能自证「本次响应不是上一轮的结果」**：`/api/nav` 响应 `stats` 回带 `issuedAt`（= 本次 `planNav` 的 `nowMs`），且**每次请求递增**。⚠️ **`issuedAt` 不得作为 `transit_cache` 的命中下界**（那会让命中率≈0、每次导航多付 2.9–4.7s，直接毁掉 S1） | 同一 OD 连发 3 次（间隔 >1s）：三次 `stats.issuedAt` **严格递增**且 `transitFromCache` 允许为 `true`（拓扑缓存是好事）；断言响应里**不存在**任何以 `issuedAt` 为条件的 SQL 分支（grep `fetched_at >=`） | 阻断 |
| **RL4** | **客户端「同一请求复用」的窗口 ≤ 5s**；超出必须重发。禁止「同 query 永不复用刷新」这类无时效去重 | `useRecommend` 的 `loadedAtRef` 必须是 `{q, at}` 结构；脚本注入假时钟：`at = now - 6000` 时断言**必须**发请求（`fetch` 计数 +1） | 阻断 |
| **RL5** | 浏览器缓存不得与边缘缓存**双层并存**于同一资源：每个响应的陈旧只能有一个来源。**本期落法 = 删掉 `route-shapes`×2 与 `route-lines`×1 的 `force-cache`**，全部交服务端 `s-maxage` 单层管理；`stations` 的 3 处保留 `force-cache` 且 URL 必须带版本段（103KB 首屏载荷，浏览器缓存值钱）；实时接口一律 `no-store` | grep `force-cache`：允许清单只剩 `/api/stations?include=lrt&v=N` 三条；`route-shapes` / `route-lines` / `api/nav` / `route-vehicles` / `station/eta` / `nav/detail-body` 出现 `force-cache` 即失败 | 阻断 |
| **RL6** | **去重缓存（dedupe）与内容缓存必须可区分，且去重缓存必须暴露陈旧度**：TTL ≤ 一个刷新周期（≤20s），响应**必须**带 `cachedAgoMs`（= 数据写入时刻到当前时刻的差）。**仅刷新时间基准（`serverNowMs`）而不带 `cachedAgoMs` 视为违反** —— 那会让陈旧数据伪装成新鲜 | 构造「缓存命中」请求，断言响应体含 `cachedAgoMs ≥ 0` 且该值 ≈ 写入龄；断言命中路径**没有**只覆盖时间基准而不报龄的分支（`station/eta` 现状即属此类，需补字段） | 阻断 |
| **RL7** | **静态段与实时段在类型层不可混装**：静态缓存函数返回的类型不得含实时字段；实时值的类型必须携带 `issuedAt` | `assertNoLiveFields` 在 `getStaticRows()` / 各 `*Cached()` 返回前调用；`tsc` 层用品牌类型 `IssuedAt` 防误传 | 阻断 |
| **RL8** | **缓存可观测性必须与装载在同一实例内**：任何「读本实例缓存状态」的诊断端点必须支持先装载再报告（`?warm=1`），否则 Serverless 多实例会让观测恒为 `not-run` | `GET /api/health?warm=1` 返回 `status ∈ {ok}`；`GET /api/health`（不加 warm）**不得**作为验收依据（允许返回 `not-run`） | 阻断（仅验收场景） |
| **RL9** | **缓存体积必须有护栏而非仅观测**：静态载荷超限时**抛错**，不得 `console.warn` 后静默跳过 | `getStaticRows` 内 `if (itemSize > LIMIT) throw new Error(...)`；单测注入超大 payload 断言抛错 | 阻断 |

## 7. 我发现的、原风险清单里没有的坑

按严重度排序。前三条建议直接进 Spec。

| # | 坑 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| P1 | **`useRecommend.loadedQueryRef` 无时效** —— 同一 OD 关掉再开（同一页面会话）**一次请求都不发** | `useRecommend.ts:143-147`（`if (loadedQueryRef.current === fullQuery) return`）；`queryOf` 无时间因子（`StepSheet.tsx:364-378`） | **这就是负责人描述的现象本身**，且违反 R3/RL4 | 改为 `loadedAtRef {q, at}` + 5s 窗口（§3.3） |
| P2 | **`route-shapes` / `route-lines` 的 `force-cache` 无版本号** | `NavMap.tsx:1278`、`useRouteOverview.ts:92`、`RouteLinesSheet.tsx:40` | 响应结构一变就**永久钉住旧结构**，连清缓存都不一定救得了；2026-09-21 事故同形 | 团队已裁决**删除这 3 处**（而非补版本号），我的评估见 §2.6：同意，但须满足「先加 s-maxage 再摘」「不含 stations」「勿改引用稳定性」三个条件 |

| P4 | **`eta-smooth` 的 120s 记忆键不含 OD** | `eta-smooth.ts:33-41`，键 = `线路\|车牌\|等车站` | 同会话里先后看两条不同行程，同线路同车同站的平滑值会被复用（概率低但存在），表现为「还有 N 站」偏高不降 | OD 变更处调 `getSmoothMem().clear()` |
