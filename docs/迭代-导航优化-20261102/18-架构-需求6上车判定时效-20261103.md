## 1. 逐条回答

### Q1 `walkActive` 的定义、依赖、何时变 false

```ts
// NavShell.tsx:375-377
const [walkSeg, setWalkSeg] = useState<"out" | "in" | null>(null);
const walkActive = walkSeg !== null;
// NavShell.tsx:395  →  useRideTracking({ walkActive, ... })
// useRideTracking.ts:348-349
const walkActiveRef = useRef(walkActive);
walkActiveRef.current = walkActive;   // 每次渲染同步，读 ref 永远拿最新值
```

`walkSeg` 转 `null` 的**全部**出口（`grep setWalkSeg(null)` 只有 `endWalk`）：

| 出口 | 条件 | 位置 |
|---|---|---|
| ① 走到上车站 | `walkFollow.phase === "arrived"`（`remainM ≤ 30m`，`follow.ts:253-256`） | `NavShell.tsx:716-719` |
| ② 步行路线缺失/失败 | `!hasWalkOut \|\| walkRoute.out.phase === "failed"` | `NavShell.tsx:737` |
| ③ v3.10.0 新增：判定进入 riding 后 | `ride.phase === "riding" && walkSeg === "out"` | `NavShell.tsx:616-620` |

⚠️ ③ 发生在**判定成功之后**，对判定时机**零影响**（它只是清段，不参与准入）。

### Q2 正常路径的 `walkActive` 时间线

```
t=0    点「开始导航」→ startSession("out")：walkSeg="out"、ride.phase="boarding"、
       boardingStartedAtRef=now、lastSwitchTsRef=now（:1433 ⇒ 触发 20s 冷却，G3 硬门）
       ⇒ walkActive = true
t=0…N  步行（N = 步行时长，本 OD walkOut 仅 9.3m/0.1min，通勤场景常见 3~8 分钟）
       · userFix 每 3s 一帧（NavShell.tsx:341 `gpsIntervalMs = navActive ? 3000 : 10000`）
       · tryAuto 每帧被调用一次；walkActive=true ⇒ 门槛 need+2
       · 候车轮询 schedule(walkActive ? 60000 : 0)（:1082）
t=N    走进上车站 30m 内 ⇒ remainM ≤ 30 ⇒ walkFollow.phase="arrived" ⇒ endWalk()
       ⇒ walkSeg=null ⇒ walkActive = false
       ⇒ 轮询 effect 重跑（deps 含 walkActive，:1090）⇒ schedule(0) ⇒ round()
          ⇒ fetchFrame（车辆帧立即刷新）+ tryAuto
t=N+Δ  用户上车 ⇒ 此时 walkActive === false ⇒ need = 基准（3 或 2）
```

⇒ **严格正常路径上，+2 在上车时并不生效。** 这是与负责人体感矛盾的地方，必须用运行期证据判定（§4）。

### Q3 上车那一刻 `walkActive` 是 true 还是 false

- **只要 `arrived` 先触发 ⇒ false ⇒ +2 不生效。**
- **`arrived` 未触发 ⇒ true ⇒ +2 生效，并且叠加第二个拖慢（见 Q6）。**

`arrived` 未触发的四条具体机制（都是真实可达的，不是臆测）：

| # | 机制 | 证据 |
|---|---|---|
| A1 | **赶车提前上车**：公交比用户先到，用户在离站 30~100m 处跑上车 ⇒ 从未 `arrived` | `arrived` 阈值 `WALK_ARRIVE_M = 30`（`follow.ts:253`）；92a8912 自己的场景描述"10 km/h 跑 24s"正是这类 |
| A2 | **精度门冻结进度**：`acc > WALK_ACC_MAX_M(150m)` ⇒ `progressOnPath` 直接 `return {...fallback, lowAccuracy:true}`，`remainM` **永不下降** ⇒ `arrived` 永假 | `follow.ts:206-208`、`:48` |
| A3 | **走偏/未沿路线走**：`remainM` 靠「投影到从当前步起的拼接折线」得到（`flattenFrom` + `cumOnFlat`），若用户不沿该折线走（例如从另一条路直插站台），投影点被 clamp 在折线附近 ⇒ 里程不增 ⇒ `remainM` 冻结 | `follow.ts:218-240` |
| A4 | **步行路线仍在飞/取不到**：`following = walkSeg !== null && activeWalk?.phase === "ready"`（`NavShell.tsx:531`）⇒ 未 ready 时 `useWalkFollow` 的推进会 `if (!following || !steps.length) return;`（`useWalkFollow.ts:101`）⇒ `arrived` 永假。失败态由 ② 兜底，但**"慢"不是"失败"** ⇒ 会真空一段时间 | 同上 |

### Q5 `+2 帧` 的真实耗时（实测，不是估算）

`.verify/_q6-timing.ts`：10m 顶点走廊（与 `route_shapes` 同量级）、3s 一帧、45s 窗口、真 `autoBoardOf`。

| 场景 | need=3（基准） | need=5（+2） | 差值 |
|---|---|---|---|
| 站台静止 60s → 公交 20 km/h | 上车后 **24.0s** | **30.0s** | **+6.0s** |
| 零等待直接上车 → 20 km/h | 18.0s | 24.0s | +6.0s |
| 站台静止 60s → 堵车 12 km/h | 36.0s | 42.0s | +6.0s |
| 站台静止 60s → 30 km/h | 18.0s | 24.0s | +6.0s |

**⇒ 「+2 帧」= 精确 +6.0 秒（2 × 3s 帧间隔）。92a8912 注释里写的"拉长约 3s"算错了，它把 2 帧当 1 帧。**

**顺带量出两个更重要的数：**
- **结构性下界**：第一次 `hit` 出现在上车后 **18s**（20/30 km/h）到 **30s**（12 km/h）。这不是 streak 决定的，是 **45s 滑动窗口 + 位移门 `max(60, 8/3.6×dt) = 100m`** 决定的 —— 窗口里还混着站台静止/步行的帧，必须等车速帧占满到平均值 >8 km/h 且累计位移过 100m。**⇒ 用户"要好一会"里至少有 18~30 秒与 v3.10.0 无关。**
- **车辆佐证的价值**：有 `strong` 佐证时 need 3→2 且位移门 ×0.6（100m→60m）。实测 20 km/h 场景 **24s → 21s，只省 3s** —— 因为 P3 速度门不变、45s 窗口不变。**⇒ 佐证只值 1 帧，不是决定性因素。**（这一条修正了「先修佐证就能明显变快」的直觉）

### Q6 步行段降频轮询是否造成"双重拖慢"

代码：`schedule(walkActive ? POLL_MS * 5 : 0)`（`:1082`）⇒ 步行段 60s 一帧。**该行是 `ba96efb`（v3.9.0）引入的，不是 92a8912。**

两条调用路径分开看：

| 调用路径 | 步行段频率 | 对 streak 的影响 |
|---|---|---|
| `useEffect(..., [userFix, phase, tryAuto])`（`:1089` 附近） | **3s 一帧，不受降频影响** | **streak 的节拍由它决定 ⇒ 恒 3s/帧** |
| `round()` 之后（`:1054`） | 60s（步行）/ 12s（到站后） | 只是"额外"调用，不改变节拍 |

⇒ **降频不会让 streak 变慢**（3s 节拍由 GPS 帧保证），所以"双重拖慢"中的 streak 那一半**不成立**。

但它有**另一条真实影响**：`listRef.current`（车辆帧）在步行段可陈旧至 60s。若在上车瞬间它陈旧/为空 ⇒ `aux.strong=false` ⇒ need 3 而非 2、位移门不 ×0.6 ⇒ **多 3s**（实测 Q5）。这条**只在 `walkActive` 上车仍为 true 时才发生**（因为 `arrived` 会触发轮询 effect 重跑并 `schedule(0)` 拉新帧）。

⇒ **定论：不存在"双重"效应，但存在"6s（need+2）+ 3s（佐证丢失）= 最坏 9s"的叠加，且两者共享同一个前提 —— 上车时 `walkActive` 仍为 true。**

## 2. 待验证假设（必须用一条运行期证据判定）

### H6-A（唯一待验证项）负责人的「正常路径」在上车时 `walkActive === true`

若成立：`need+2` 生效 ⇒ +6s；且很可能伴随 `listRef` 陈旧 ⇒ 再 +3s ⇒ 合计约 9s，与"要好一会才跟踪到车牌"的体感吻合。

**为什么我不把它写成定论**：C4 的代码链显示"走到站台"应当先触发 `arrived`。两者矛盾，而矛盾点只有一条：**用户是否真的走到了步行路线的终点**。这一条**无法从代码判定**，必须实测。

**一条命令即可取证**（项目已有现成观测钩子，无需改代码）：

```js
// 安卓真机 + chrome://inspect，导航中执行一次
let prev = null;
setInterval(() => {
  const m = document.body.getAttribute("data-board-match");
  if (m !== prev) {
    console.log(Date.now(), "board-match →", m,
      "| legkind =", document.body.getAttribute("data-nav-legkind"),
      "| walk-step =", document.body.getAttribute("data-walk-step"),
      "| walk-off =", document.body.getAttribute("data-walk-off"));
    prev = m;
  }
}, 500);
```

判据（`data-nav-legkind` 由 `NavShell.tsx:750-758` 写入，取值 `walk-out` / `ride`）：

| 观测 | 结论 |
|---|---|
| 翻转瞬间 `legkind === "walk-out"` | **`walkActive === true` ⇒ +2 生效，H6-A 成立** |
| 翻转瞬间 `legkind === "ride"` | `walkActive === false` ⇒ +2 不生效 ⇒ 需另找原因（则问题只剩 C7 的结构性 18~30s，属"一直如此"而非"变差"） |

## 3. 修复方案选项（未选）

目标约束（负责人已定）：正常路径恢复到 v3.8.0 时效；不重新引入死锁；**不得靠降 8km/h 速度门或减 1 帧**这类会引入新误判的手段。

### 方案 6-A（推荐评估）：把「加严」的判据从 `walkActive` 换成「用户到上车站的沿线距离」——三区判别

**核心思想**：`walkActive` 是个**状态**，它回答"还有没有步行段"，但真正该问的是"**人现在相对上车站处在哪一侧**"。三区判别能同时满足三个目标：

```
设 fixNow = 当前定位；boardPos = 上车站坐标（useRideTracking 已有，已传给 autoBoardOf）
    dToBoard = distM(fixNow, boardPos)                      // 直线距离
    along    = 沿 leg.colored 从 colored[0](= 上车站) 起的里程  // colored[0] 恒为 board（route-overview 不变式）

区① 已到站/刚上车：  dToBoard ≤ 40m                ⇒ need = 基准（不加严）
区② 仍在走近站台：    dToBoard > 40m 且 along < 60m  ⇒ need = 基准 + 2（保守，防跑步赶车误判）
区③ 已随车离开：      along ≥ 60m                  ⇒ need = 基准（不加严；人已在线路下游，不可能是走路赶车）
```

- **正常路径**：上车点就在站台 ⇒ 区① ⇒ **恢复 v3.8.0 时效**。
- **异常路径（车上点开始导航）**：人已在线路下游（区③）或就在车上位置 ⇒ 不加严，且 `walkActive` 不再参与 ⇒ **不死锁**。
- **防误判不放宽**：只有区②（真的在路上跑向站台）才 +2 ⇒ 「10 km/h 跑 24s」这类误判仍被抑制。**速度门 8、位移门 60、窗口 45s 全不动。**
- 代价：改 `useRideTracking.ts` 的 `need` 计算一行 → 变成 3~5 行（需 `distM` + 沿线路程，两者都已在 `route-overview.ts` 导出、`leg.colored` 已在手）。
- 风险：低。唯一新增依赖是「`colored[0]` 恒为上车站」这条既有不变式（`route-overview.ts:78-88` 的 JSDoc 已把它写成契约；需求4 的修复要保住它，两者一致）。
- **额外收益**：区③ 的判据与需求 4 的 D4-3 同源（都用「沿线路程」而非「最近顶点」），修需求 4 时可共用工具函数。

### 方案 6-B（最小改动）：`need+2` 仅在「仍在走近站台」时生效，其余情形一律基准

即 6-A 的简化版，只判距离、不做沿线路程：
```
need = 基准 + (walkActive && dToBoard > 40 ? 2 : 0)
```
- 代价：一行改动。
- 风险：中。「跑步赶车但已冲到站台 40m 内」这一种边缘场景会退回基准门槛（误判面比现在略大），但仍是"沿线路移动 ≥100m 且均速 >8 km/h"才命中，误判概率很低。
- 适用：想今天就止血、不想动判别模型时选它。

### 方案 6-C（治本，但动面大）：把 `arrived` 的判据从「沿步行折线投影」改为「到上车站的直线距离」

- 做法：`NavShell` 的 `endWalk` 触发条件加一条并集：`walkFollow.phase === "arrived" || distM(fix, boardPos) ≤ 40`。
- 效果：A1（赶车提前上车）/ A3（走偏）/ A4（步行路线慢）三类"`arrived` 不来"的场景**从根上消失** ⇒ `walkActive` 在站台必然为 false ⇒ `need+2` 自然不生效，**不用改判定门槛**。
- 代价：改 `NavShell.tsx:716-719`（+3 行）+ 需要 `boardPos` 在 NavShell 可得（`ov.body.legs[0].board` 已有）。
- 风险：中。`endWalk` 提前触发会让步行横幅提前消失（用户可能还在站台 40m 外就被切走）⇒ 需要产品确认「站台 40m 内算已到」是否可接受。**A2（精度冻结）它修不了**（精度差时距离也不准），但那种情况下 `dToBoard` 抖动也不会持续 ≤40m。
- **它与 6-A 不冲突可叠加**：6-C 修"清段太晚"，6-A 修"加严判据错位"。若只想改一处，选 6-A（它不改变任何用户可见的段切换时机）。

### 不建议的两类做法（明确排除）
- 把 `+2` 降为 `+1` 或去掉：直接回到「10 km/h 跑 24s 后站着等车」的误判，92a8912 的实测数据已证明这是真实场景。
- 降速度门 8 → 6/7：会把快走判成乘车（`boarding-detect.ts:54-61` 注释已双向实测），误判面更大。
