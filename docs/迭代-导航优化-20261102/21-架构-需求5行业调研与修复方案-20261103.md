## 0. 结论摘要

1. **业界没有"让 PWA 在后台继续跑"的魔法。** 高德 App / Google Maps / Citymapper / 车来了 全部是原生 App，靠 Android **前台服务（foreground service，`foregroundServiceType="location"`）**在熄屏后继续拿位置。**Web 平台等价物不存在**：Service Worker 无法访问 Geolocation，Periodic Background Sync 生产环境最小间隔 **12 小时**。⇒ 「别的软件切后台回来就正常」的真正原因**不是**它们有更好的恢复机制，而是**它们的定位在后台从来没停过**。
2. **但他们的"恢复"确实比我们多一步**：原生 App 从后台回来时是"**流还在、只是补一帧**"；我们是"**流断了、要重新搭**"。要在 Web 上追平体验，唯一可行路径是把「**重建链路**」做得又快又必定成功 —— 而不是让后台继续跑。
3. **找到了一条决定性的外部证据链**：`phoenixframework/phoenix` issue #6804 是一份**安卓已安装 PWA（WebAPK）+ Android 15 + Chrome 151** 的**设备端 trace**，完整复现了我们的症状，并给出三条硬结论：
   - 页面在 **`hiddenFor=60`（≤60 秒）就被 `freeze`**，不是官方文档说的 5 分钟；
   - 解冻时 **`resume` 事件到了**（`resume vis=visible`），但 **`visibilitychange` / `pageshow` / `pagehide` 一个都没发**；
   - **`visibilitychange` 直到 14 秒后才补发**（且疑似由后续交互触发）。
4. **而我们的代码全仓 `resume` / `freeze` / `focus` / `wasDiscarded` 监听数量为 0**（已 grep 确认）。这是需求 5 最关键、也最便宜的缺口。
5. **同时验证了一条反向结论**：同一份 issue 明确写「**attaching DevTools prevents Chrome from freezing the page**，freezing 是复现的前提」—— 这**解释了我上一轮 Playwright 复现为什么失败**，也意味着**CDP 无法证明真机上的事件会到**。验收设计必须据此分层（§5）。
6. 推荐方案：**三层自愈（6-A'）** —— ① 事件矩阵补 `resume` + `focus`（并修掉 `visibilityState==='hidden'` 这道会误杀 `resume` 的守卫）；② **时间戳哨兵**兜底（不依赖任何事件）；③ **请求超时 + `inFlight` 时间戳自愈**（消灭 H5-B）。三层分别覆盖不同失效面，缺一层就留一条永久冻结路径。

### 1.3 事实（决定性）：安卓已安装 PWA 的设备端 trace

来源：`phoenixframework/phoenix` issue #6804（https://redirect.github.com/phoenixframework/phoenix/issues/6804）。
环境自述：Motorola moto g power 5G (2024)，**Android 15，Chrome 151.0.7922.171，已安装 PWA（WebAPK），不是浏览器标签页**。

原始 trace（照抄，仅换行）：

```
04:42:43.076  visibilitychange  vis=hidden  conn=open      -> pageHidden = true
04:42:48.614  sock:close        code=1006   pageHidden=true
04:43:43.096  freeze            vis=hidden  conn=closed   hiddenFor=60
04:46:35.274  resume            vis=visible conn=closed   hiddenFor=232
              pageHidden STILL true   (no visibilitychange, no pageshow, no pagehide)
04:46:35.310  pageHidden = false
04:46:49      visible (3s)      visibilitychange fired, pageHidden cleared
04:46:54      hidden -> 04:46:55 visible  visibilitychange fired
```

四条可直接引用的事实：

- **F11**：`freeze` 在 **`hiddenFor=60`** 就发生了 —— 即熄屏/切后台约 **1 分钟**后整页被冻结。这与用户实测「熄屏 1~2 分钟」**精确对撞**。（对照：官方文档口径是"隐藏较久后"，未承诺 5 分钟；F7 的 5 分钟是**节流**档位，不是 `freeze` 档位 —— 两者常被混为一谈。）
- **F12**：`resume` 触发时 `document.visibilityState` **已经是 `visible`**，但 **`visibilitychange` 事件没有发**。⇒ 「监听 `visibilitychange` 就够」的假设在安卓 WebAPK 上**不成立**。
- **F13**：`visibilitychange` 在 **14 秒后**才补发一次，且后续出现连续的 `hidden→visible`（1~3 秒级）—— 与原 issue 猜测"由后续交互或短暂切出触发"一致。
- **F14**：原 issue 明确记录「**attaching DevTools prevents Chrome from freezing the page**, and freezing appears to be a precondition for the failure. I could only capture this by instrumenting the page over CDP, **detaching**, reproducing, and then reattaching to read a log persisted to localStorage. **With the debugger attached throughout, it never reproduces.**」
  ⇒ **任何挂调试器/Playwright 的会话都无法复现该 freeze**。这一条直接决定验收方案的设计（§5），也是我上一轮 `_q5-resume.mjs` 拿到「零 `visibilitychange`」却**无法判定线上**的原因。

### 1.4 业界共识的工程做法（与具体产品无关，属平台级最佳实践）

| # | 做法 | 来源 |
|---|---|---|
| F15 | 时间用**墙钟差值**算，**不数 tick**：「Compute from wall-clock time, never from callback counts」「A client that counts heartbeat timer ticks… miscounts badly when ticks arrive a minute apart. The robust design compares wall-clock times」 | https://kellymears.me/knowledge/web/background-tab-throttling ；https://aicassindra.com/blogs/bidi/sse_client_lifecycle_and_visibility.html |
| F16 | 「回去之后**从真相源重新同步**，而不是假设什么都没变」；「re-sync from the source of truth rather than assuming nothing changed」 | 同上 kellymears |
| F17 | 连接类应用的标准姿势：`visibilitychange` 恢复 + `pageshow(persisted)` 重开 + `online` 重连 + **墙钟看门狗**（`staleMs` 超过阈值即判定连接已死并重连） | SSE Client Lifecycle 一文给出的 `ResilientStream` 实现（staleMs 默认 45s、每 10s 跑一次 watchdog，并注明"may fire late in hidden tabs"） |
| F18 | **不要只看 `visibilitychange`**：「PWA 应用应该正确处理 freeze/resume 事件来管理后台同步」；Chrome 官方示例把 `resume` 列入必有监听 | https://www.ud5.com/tool/page-lifecycle-demo/faq ；F9 |

### 1.5 我的推断（不是事实，标注清楚）

- **I1**：高德 App / Google Maps / Citymapper / 车来了 之所以"回来就正常"，主因是 **F4 前台服务让定位从未中断**，加上客户端本来就把「最后一帧 + 时间戳」持久化，回前台只是"补一张图"。**他们的"恢复"次数是 0，我们是 1**。⇒ 我们不缺"恢复机制"，缺的是"恢复要必定成功且足够快"。
- **I2**：用户实测的「完全冻结」最可能的完整因果链是：
  `熄屏 → 约 60s 后 freeze（F11）→ 冻结期间用户/车都在动 → 亮屏 resume（F12）但 visibilitychange 缺席 → 我们的两条恢复链（`useResumeRefresh` / `useUserFix`）都没被 `resume` 唤醒 → 14s 后迟到的 visibilitychange 终于 fire → kick() 被 H5-B 的 `inFlight=true` 当场吞掉 → 之后再无事件 ⇒ 永久冻结`。
  ⇒ **H5-A 与 H5-B 不是二选一，而是"必须同时修"**：只修 H5-A 会被 H5-B 吞掉；只修 H5-B 则根本没人去 kick。
- **I3**：`useUserFix` 的 20s 看门狗（`WATCH_IDLE_MS=20_000`，巡检 5s）理论上能在 freeze 结束后 25s 内自愈 GPS —— 但它**也依赖定时器**，而 resume 后最先到期的一批定时器会集中触发；若其间 `permDeniedRef` 或 `watchRef.current == null` 任一成立就会 `return`（`useUserFix.ts:237-238`）。**这条需实测**，见 §6。

| 维度 | 业界基线 | 本项目现状 | 差距判定 |
|---|---|---|---|
| 恢复事件矩阵 | `resume` + `pageshow` + `focus` + `visibilitychange`（F9/F18） | `useResumeRefresh.ts:51-61` 只挂 `visibilitychange` / `online` / `pageshow`；`useUserFix.ts:263-275` 只挂 `visibilitychange` / `pageshow(persisted)`；**全仓 `resume`/`freeze`/`focus`/`wasDiscarded` 监听数 = 0**（已 grep） | **缺 2 个最重要的事件**：`resume`（F12 证明它是唯一会来的）与 `focus` |

| 请求健壮性 | 超时 + 重连（F17 的 `staleMs`/backoff） | `useRideTracking.ts:714-718` `fetch(...)` **无 `AbortSignal.timeout`**；`inFlight` 是**布尔闭包**（`:1050-1056`/`:1105-1111`/`:1173-1179`），`finally` 一旦因冻结未执行 ⇒ 永久 `true` | **H5-B 完整成立** |

| 后台继续采集 | 原生：前台服务；Web：**不可能**（F1/F2/F3） | 不存在 | **不追**（这不是差距，是平台边界） |

## 3. 方案选项

> 三者互不排斥，差别在"改几处 / 覆盖哪一层"。**六项具体手段的评估见 §3.4**。

### 方案 6-A'：三层自愈（推荐）

| 层 | 内容 | 覆盖 |
|---|---|---|
| L1 事件矩阵 | `useResumeRefresh` 加 `document.addEventListener("resume")` + `window.addEventListener("focus")`；`fire()` 改为按来源门控（显式恢复事件不看 `visibilityState`，仅 `online` 保留该守卫）；`pageshow` 去掉 `e.persisted` 限制、改为"首 5s 内的 pageshow 忽略" | H5-A 的主路径 |
| L2 墙钟哨兵 | **复用仓库已有的 1s 单例心跳**（`observe-hooks.ts:175-196` `retainVehTicker`，`VEH_TICK_MS=1000`；导航态已挂在 `useRideTracking.ts:1216-1219`、线路查看挂在 `useRouteVehicles.ts:243-245`），在 `tickVeh()` 里加一句：`Date.now() - lastFrameAt > 30_000` ⇒ 调一个注册进来的 `kick`。**不新增定时器、不计数、不依赖任何事件**；被节流到 1 次/分钟也终会执行 | H5-A 的兜底（**唯一不依赖事件**的一层） |
| L3 请求自愈 | `fetch` 加 `AbortSignal.timeout(8000)`；`inFlight: boolean` → `inflightSince: number`（`>15_000` 强制重置）；三条 effect 同形改 | H5-B |

- 改动量：3~4 个文件、约 50~70 行（含注释）。**L2 不新增定时器**（复用既有 1s 心跳）。
- 覆盖 H5-A：**是**（L1 主路径 + L2 兜底，两条独立路径）。覆盖 H5-B：**是**（L3）。
- 风险：低。L2 在既有心跳上加一句判断（心跳本来就每秒跑，无新增 CPU/功耗）；L1 的 `focus` 在输入框聚焦时会触发，靠既有 2s 去抖 + L2 的 `lastFrameAt` 判定吸收。
- 可回归性：**最好**。三层各自可用纯函数/合成事件独立验证（§5），不依赖真机。

> ⚠️ **L2 的一个实现陷阱（必须先说清）**：`observe-hooks` 里已有的 `lastVehTs` 只在**帧内容变化**时才前移（`noteVehFrame` 内 `key !== lastFrameKey` 才更新时间戳，`:141-145`）。**哨兵绝不能用它** —— 车没动、`fetchedAt` 不变时它不前进，会把"数据没变"误判成"数据过期"，导致每 30s 白刷一次。
> 正确的锚是 `fetchFrame` 里那句**无条件**的 `setLastVehicleTs(Date.now())`（`useRideTracking.ts:736`）—— 它表达的是"上一次成功往返的时刻"，与内容是否变化无关。需要把它同步进一个模块级 ref 供 `tickVeh` 读取。

### 方案 6-B'：恢复即全量重置（reset-on-resume）

在 6-A' 的 L1 之上，把回前台的动作用"丢弃旧状态、重建"替代"增量补刷"：

- 重置 **网络/定时器态**：`inflightSince=0`、清 `timer`、重新 `schedule(0)`；
- 重置 **定位订阅**：`stopWatch()` → `doWatch()`（`useUserFix` 已有 `resume()` 做这件事，只需接到 `resume`/`focus` 事件上）；
- **不重置判定累积**（`boardStreakRef`、`fixesRef`）—— 这一点必须写清：
  - 若一并重置 streak，**上车判定要重新等 3 帧（+9s）**，会让需求 6 的时效变差。这是本方案最容易踩的坑。
- 改动量：约 80~100 行。
- 覆盖：同 6-A'，且对"半死连接/悬挂请求"更彻底。
- 风险：中。重置面大 ⇒ 容易出现"回前台下一次判定变慢"的次生回归（正是需求 6 的形态）；需要回归 `data-board-match` 时序。
- 可回归性：中（时序类断言更容易受环境影响）。

### 方案 6-C'：最小止血（只加 `resume` 监听 + 请求超时）

- 2 处改动、约 20 行：`useResumeRefresh` 加 `resume`；`fetch` 加 `AbortSignal.timeout`。
- 覆盖 H5-A：**部分**（依赖 `resume` 会到；F11-F12 的机型上够用，但**若某机型连 `resume` 也不发，就完全没有兜底**）。覆盖 H5-B：**是**。
- 风险：最低。
- 可回归性：好。
- 定位：可作为 6-A' 的第一刀（L1 的 `resume` 部分 + L3），**不含 L2 哨兵**。

### 3.4 六项具体手段的逐项评估

| 手段 | 评价 | 理由 / 注意 |
|---|---|---|
| **时间戳哨兵兜底** | **必须做（推荐 L2）** | 唯一不依赖事件、不依赖可见性的自愈层（F15/F17 明确背书）。⚠️ 注意两点：① **它自己也会被 freeze 冻住** —— 它的价值不是"冻结期间发现"，而是"**解冻后第一次 tick 立刻发现缺口**"，所以判定必须写"现在 vs 上一帧"，不能写"连续 N 次 tick 无变化"；② 间隔别太长（5s 优于 15s），否则解冻后要等一个周期才检。 |
| **请求超时 + 自愈门** | **必须做（推荐 L3）** | `AbortSignal.timeout(8000)` 把"悬挂的 fetch"变成"确定失败"；`inflightSince > 15s` 强制重置把"冻结导致的 `finally` 未执行"变成可自愈。两者互补：只有超时、没有时间戳门，仍可能因冻结错过 `finally`。 |
| **补事件矩阵** | **必须做（推荐 L1）** | `resume` 是 F12 里**唯一真正到达的**恢复信号。`focus` 在安卓 WebAPK 上是否发**待验证**，但成本近零。⚠️ 关键细节：**现有 `fire()` 的 `visibilityState === "hidden"` 守卫必须按来源放开**，否则加了监听也可能被吞（这是我读代码发现的、调研前没预料到的坑）。`pageshow` 去 `persisted` 限制要配"首 5s 忽略"护栏，否则首次加载会多刷一次。 |
| **重连即全量重初始** | **部分采纳（只重置网络态，不重置判定态）** | F16 的精神对（"从真相源重新同步"），但**全量重置会伤需求 6**：streak 清零 ⇒ 上车判定重新计时 9s。所以只重置 `inflightSince` / timer / 定位订阅，**保留 streak 与 fixes 窗口**。 |
| **Wake Lock** | **不改，只提示** | 已实现且符合 F5（隐藏自动释放、可见重申请）。但重申请挂在 `visibilitychange` 上 ⇒ F12 场景下不会重申请 ⇒ **屏幕可能在导航中再熄灭**。这是产品决策（导航中是否强制常亮），我只提不建议：若产品要"导航中不熄屏"，需把重申请也挂到 `resume`/`focus`；否则现状可接受（位置冻结与屏幕熄灭是两件事，前者由 L1~L3 解决）。 |
| 后台继续采集（SW / Periodic Sync） | **明确不做** | F2：SW 无 Geolocation。F3：Periodic Sync 生产最小 12 小时且仅 Chromium。**这两条要写进文档，避免下一轮再有人提"用 Service Worker 后台保活"。** |

## 4. 明确推荐

**推荐 6-A'（三层自愈），分两批落地；不单独采纳 6-B'，只吸收其"重置网络态"的部分。**

理由（按权重）：

1. **三层覆盖三种互不重叠的失效面，缺一层就留一条永久冻结路径**：只补事件 ⇒ 某机型事件不发就死；只加哨兵 ⇒ 若 `inFlight` 卡住，哨兵 kick 也被吞（I2）；只修 `inFlight` ⇒ 没人去 kick。**这三层不是"三选一"，是"三个都必须有"**。
2. **它是三层里唯一能"不依赖任何事件"的一层**（L2），而外部 trace 已证明事件会迟到 14 秒甚至要等交互（F13）。用户感受的是"1~2 分钟熄屏回来就冻住"，14 秒的迟到在体感上等于永久。
3. **风险最低**：不改判定阈值（不与需求 6 冲突）、不改 API 契约、不改数据模型、不动 `model.ts`。6-B' 的 streak 清零风险是**已知会伤需求 6** 的具体坑，不值得为"更彻底"付这个代价。
4. **可回归性最好**：三层都能在无真机条件下被确定性验证（§5），符合负责人"不做真机实验"的要求。

**"如果不这么做会踩什么坑"**：
- 只做 6-C'（加 `resume` + 超时）：在 F11 那台机型上够用，但一旦遇到"`resume` 也不发"的容器（安卓 WebView 壳、部分 OEM 省电模式），症状原样复发，且**没有任何兜底能发现** —— 排查成本比现在更高（因为看起来"已经修过了"）。
- 做 6-B' 的全量重置：会把需求 6 的上车判定时效打回去 9 秒，等于一个 P0 换一个 P0。
- 试图用 Service Worker / Periodic Sync 保活：F2/F3 已证不可行，白花时间且会引入新的失败面。

## 5. 无真机验收设计

### 5.0 先说清一个硬事实（决定验收边界）

F14：**挂调试器（含 Playwright/CDP）会让 Chrome 不 freeze**，因此 **CDP 无法证明"真机上事件会不会到"**。它能证明的是：「**当事件按某种顺序到达时，我们的代码会正确恢复**」以及「**即使一个事件都不来，哨兵也会自愈**」。这正好覆盖我们真正能改的部分 —— 事件到不到不归我们管，**代码响不响应归我们管**。

⇒ 验收分三层，全部可在无真机条件下执行：

### 5.1 L1 纯函数/假时钟（最快、最确定）

把哨兵判定与 `inFlight` 门抽成纯函数，直接单测（沿用项目现有 `scripts/test-*.ts` + `tsx` 习惯）：

```ts
// src/lib/nav/freshness.ts（新增，纯函数）
export function shouldForceRefresh(o: {
  lastFrameAt: number;   // 0 = 从未成功
  nowMs: number;
  staleMs: number;       // 30_000
  lastKickAt: number;    // 去抖
  debounceMs: number;    // 2_000
}): "stale" | "fresh" | "debounced";

export function inflightGate(d: { inflightSince: number; nowMs: number; forceMs: number }):
  { blocked: boolean; renewed: boolean };   // forceMs=15_000
```

断言（`.verify/_q5b-units.ts`）：
- `lastFrameAt=0`（从没成功）⇒ `stale`（不能因为是 0 就一直等）；
- 缺口 `29_999ms` ⇒ `fresh`；`30_001ms` ⇒ `stale`；
- `stale` 但距上次 kick `1_999ms` ⇒ `debounced`（防请求风暴，对齐既有 AC2.5）；
- `inflightSince` 已过 `15_000ms` ⇒ `blocked=false, renewed=true`（自愈生效）。

### 5.2 L2 合成事件断言（验证"接线"，不验证浏览器）

Playwright 注入后**手动派发事件**，断言**是否真的发出了 `/api/route-vehicles` 请求**（这就是"接线对不对"的唯一真相）：

```js
// .verify/_q5b-wiring.mjs（骨架）
// 1. 打开详情 → 进入 boarding（若线上进不去，用本地 dev + 直接 mock 卡片）
// 2. page.route('**/api/route-vehicles**', r => { hit.push(Date.now()); r.fulfill({json:{vehicles:[]}}) })
// 3. 逐个派发，每次断言 3s 内新增一次请求：
for (const [target, type] of [
  ['document', 'resume'],        // ← 当前代码不会通过（全仓无此监听）
  ['window',   'focus'],
  ['document', 'visibilitychange'],   // 需先把 visibilityState 置为 visible（CDP Emulation 或 Object.defineProperty）
]) {
  const before = hit.length;
  await page.evaluate(([t, ty]) => (t === 'document' ? document : window)
    .dispatchEvent(new Event(ty)), [target, type]);
  await page.waitForTimeout(3000);
  assert(hit.length === before + 1, `${type} 未触发补刷`);
}
```
> 判据：三条全绿 = 事件矩阵接对了。**若 `resume` 一条红，就是需求 5 的直接证据**（可直接给负责人看，无需真机）。

### 5.3 L3 时间跳跃 + 请求挂起（验证哨兵与自愈门）

用 Playwright 的 `clock` API（或 CDP `Emulation.setVirtualTimePolicy`）做**确定性时间跳跃**，并用 `page.route` 把请求挂住：

```js
// A. 哨兵：无任何事件，也要自愈
await page.clock.install();
await page.clock.pauseAt(new Date());
// 让页面认为"90 秒过去了，但期间一个 tick 都没跑" —— 等价于 freeze
await page.clock.fastForward(90_000);
await page.clock.resume();
// 断言：解冻后 ≤6s 内必须出现 /api/route-vehicles（哨兵 5s 周期）
expect(requestsAfter > 0).toBe(true);

// B. 请求挂起 + 自愈门（消灭 H5-B）
await page.route('**/api/route-vehicles**', async (route) => {
  await new Promise(r => setTimeout(r, 60_000));   // 永不 fulfill，模拟冻结导致悬挂
});
// 触发一次 kick → 等 9s（>8s 超时）→ 再触发一次 kick
// 断言：第二次 kick 仍然真的发出请求（说明 inflightSince 已自愈 / 或被 timeout 释放）
expect(secondRequestSeen).toBe(true);   // 当前代码此断言会失败（inFlight 恒 true）
```
> 这两条是**唯一能在无真机条件下证明"修好了"的断言**，且它们的失败/通过完全确定，不受网络与机型影响。

### 5.4 可选：被动日志（0 成本，非实验）

若将来想要一次真实证据，**不需要做实验**：在 `freeze` 里 `localStorage.setItem` 一行 "freeze@ts，hiddenFor=…"，`resume`/`visibilitychange`/`focus`/`pageshow` 各记一行，用户正常用一天后我们把日志读出来即可（F14 里作者正是这么做的）。**这属于埋点，不属于真机实验**，且能一次性回答"这台机上哪个事件真的会来"。是否要做请负责人定，我**不推动**。
