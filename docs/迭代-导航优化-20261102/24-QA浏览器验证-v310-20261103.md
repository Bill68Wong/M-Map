## 3. `track.prog` 为空的**直接原因**（team-lead 点名要这句）

### 3.1 先排除一个假设：与 `useNavRemaining` 的 gate **完全无关**

`useNavRemaining` 是 `/api/nav/remaining` 的**剩余行程重算**通道（写 `data-remain-*` / `data-recompute-seq`），**不产生 `track.prog`**。`prog` 由 `useRideTracking` 的车辆/GPS 两条路径写。两者是独立链路 ⇒ **「`useNavRemaining` 的 gate 写错」这个假设不成立**（它的 gate 我另测过：`24 PASS / 0 FAIL`，含 boarding no-op 与 riding 重算）。

### 3.2 `prog` 只有两个写入点，各自的前置条件

| 路径 | 代码位置 | 前置条件 | 本次是否满足 |
|---|---|---|---|
| ① 巴士车辆帧 | `useRideTracking.ts:950` | `const v = list.find(x => x.plate === lockPlate) ?? null;` → `if (!v) { missRef++; return; }`（`:951-955`）；命中后才 `setProg(progressOf(stopMains, v))`（`:975-976`），且 `progressOf` 需返回 `at`/`between`（非 `lost`），并要求 `stopMains.length >= 2` | **不满足**（该帧车辆列表为空 / 无锁牌车命中） |
| ② GPS 里程阶梯 | `useRideTracking.ts:1419` | 需 `ladderRef.current` 非空；ladder 由 `ensureLadder()` 建，首行 `if (!leg \|\| leg.colored.length < 2) return;`（`:792`） | **不满足**（本次为绕开步行段「提前点开始导航」，`legs` 尚未就绪） |

### 3.3 生产上会不会满足：**会**

- **自动判定路径**（设计主路径）：`switchToRiding(res.plate, res.source)` 会把车牌锁进 `plate` ⇒ ① 的 `find` 能命中 ⇒ `prog` 有值。
- **手动标记上车路径**：`board()`（`:1622-1678`）自身会拉一次 `/api/route-vehicles`，`if (!ranked.length) { setNote(NOTE_NO_VEHICLES_BOARD); return; }`，否则 `setPlate(ranked[0].plate)` + `setProgressSource("vehicle")` ⇒ **也会锁牌** ⇒ ① 能命中。
- 实时数据实测（本轮 `code=` 正确参数）：`56→3 台、25→14、50→4、52→3、55→2、26→6、2A→5` ⇒ 接口与数据都正常。

⇒ **结论：`track.prog` 为空是本次测试路径造成的**（e2e 在 detail body/legs 就绪前就点了手动上车 + 当次车辆帧读空），**不是产品 bug**。

### 3.4 但有一条真实风险要产品确认（不是缺陷，是预期）

若用户在真机上「手动标记上车」时，**该线路此刻没有可锁的车**（`ranked.length === 0` 会留在 boarding；若 `leg.kind!=="bus"` 则 `switchToRiding(null,"gps")` **plate 为 null**），那么 `prog` 会长期为空 ⇒ 纵条无进度、无「距下车站还有」。

- 这是**既有设计**（手动上车 ≠ 锁车），线上 v3.8.0 行为一致，本批未引入。
- 但建议产品确认预期：**「GPS 源（无牌）乘车时，纵条是否应有进度？」** 如果应该有，那是需求缺口，不是测试问题。

### 3.5 想 100% 定位需要一行日志（本轮未加，避免改 `src/`）

在 `board()` 的 `if (!ranked.length)` 分支与 `progressOf` 调用处各打一条 `console.debug`（`ranked.length` / `progress.kind` / `stopMains.length`），下次跑一次即可唯一确定是哪个子条件。**本轮因三绿已过、不动 `src/`，只记录。**
