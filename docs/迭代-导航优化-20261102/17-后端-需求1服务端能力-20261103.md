### 1.1 「刷新」当前实际打的是哪个接口

- `refreshNow()` → `fetchFrame(plate)` → `GET /api/route-vehicles?...&progress=1`（`useRideTracking.ts:704-715`）⇒ **一次刷新 = 2 次 DSAT**。
- 响应只更新「车辆位置 → `prog.passedIdx` / `segProgress.segRemainSec`」⇒ 前端只重算**当前腿**的「还有几站」「约几分钟」。
- `strips` 不来自该接口 ⇒ 纵条 `车上约 N 分` 不动；`card.totalMin` / `card.arriveAt` 更是规划时算定的死值（`model.ts:817`、`:879`）。

## 2. 关键判断：现有接口能否「只重算时间」

### 2.1 `detail-body` 的入参里有没有位置/已过站/已用时？

**没有。** 入参只有 `card` 与 `fold`（`detail-body/route.ts:168`、`:192-193`）。服务端拿到 `card` 后只做三件事：`loadStatics` 解站序、`buildStrips` 出纵条、`foldDataOfCard` 出折叠栏（`:195-204`）。**全程没有「用户在哪」这个概念。**

一个容易误判的点：`detail.body` 里确实有时间数字（`rideMin` / `minToNext` / `waitMin`），所以「detail-body 无时间字段」这句话只在**顶层**成立。真实机理是：
- `rideMin` ← `card.rides[i].minutes`：客户端回传的同一份 card ⇒ 前后两次调用**逐字节相同**；
- `minToNext` ← `lookupHop(segIdx, route, from, to, nowBucket)`：只随**时段桶**（5 桶）变化；
- `transferAfter.waitMin` ← `card.transfers[i].waitMin`：同 card ⇒ 不变。
⇒ **`detail.reload()` 对纵条数字在绝大多数时刻是 no-op。** 这与架构师 §0 复核 A 一致，我独立复核成立（探针 B1/B2/B3）。

### 2.2 服务端是否已有「按站序推算剩余各段用时」的逻辑？

**有零件，没有装配。** 三段用时分散在四个模块，且**没有任何一处是按「从中间某站起算」写的**：

| 时间段 | 计算位置 | 依赖 | 是否纯函数 | 能否单独重算 |
|---|---|---|---|---|
| 首末步行 | `model.ts:321 walkView()` → `lookupWalk(walkIdx)` 或 `ctx.walkResolver`（`recompute.ts:70/96`）→ `amap/walk-fix.ts walkMinutes()` | 静态 `walk_times` / `walk_cache` / 高德几何 | 是 | 能（`card.walkOut/walkIn.minutes` 直接可用；首次步行已花掉要扣） |
| 换乘步行 | `model.ts` `transferMinutes` + `recompute.ts:144 overlayTransferIndex()` | 静态 `transfer_walks` / 高德 `distanceM` | 是 | 能（`card.transfers[i].minutes`） |
| 候车 · 第 1 段 | `model.ts` 首段块（`:463` `ctx.live.get(first.route)`） | **DSAT 实时 / 轻轨时刻表** | 否 | 用户已上车 ⇒ 该段是**已发生成本**，不需要重算 |
| 候车 · 第 2 段起 | `model.ts:733 headwayAt(ctx.headway, next.route, cursor)` + `headway.ts:230 conservativeWaitMin()` | 静态 `route_frequency`（10min 内存缓存，`headway.ts:69`） | 是 | 能（只需重算 `cursor`） |
| 乘车 · 巴士 | `model.ts:586 rideOfHops(segIdx, route, hops, nowBucket)` → `segment-lookup.ts:124 lookupHop()` | 静态 `segment_stats`（已进 `loadStatics`） | 是 | 能，且能做「剩余跳前缀和」 |
| 乘车 · 轻轨 | `model.ts:576-586` `LRT_RIDE_SEC_FIXED` / `LRT_HOP_SEC` | 代码内常量 | 是 | 能 |
| 区间剩余秒数 | `progress.ts:184 attachProgress()` / `:252 locateSegmentOf()` | `route_shapes` + `route_station_mileage` + `route_hop_stats`（120s/600s 内存缓存，`progress.ts:84-88`） | 是（读库但已缓存） | 能；**但只回答「一辆车到下一站还要多久」，不回答「到目的地还有多久」** |

**关键洞察（这是本报告最有价值的一句）**：**用户上车之后，剩余的每一个时间段都不依赖 DSAT 与高德。** 这决定了整个方案的可行性边界——重算可以做到零外部调用。

## 3. 数据可用性

### 3.1 「已过几站」服务端能否从 DSAT 车辆帧 + `route_stations` 站序推出来？

**能，而且已有生产实现在跑。** 三层事实：

1. `route_stations` 提供站序：`(route_id, dsat_dir, seq, station_code)`，唯一键 `(route_id, dsat_dir, seq)`（`db/schema.sql:111-118`）；运行时由 `loadStatics().routeIdx` 建内存索引（`dsat/route-index.ts`）。
2. 车辆帧：`/api/route-vehicles` 并行发两个 DSAT 请求——`getBusLocations`（给坐标）+ `getBusPositions`（给挂载站 + status）。**两者结构互补、无法合并**（`route-vehicles/route.ts:13-18`、`:148-151`）。`status='0'` 表示刚离开挂载站、正驶向下一站 ⇒ `interval={from, to}` 直接给出「车在哪两站之间」。
3. 「已过几站」已有两条现成实现：
   - `progress.ts:184 attachProgress()`：坐标投影到 `route_shapes` → 沿线里程 → 用区间两端站里程锚求 `p`（0=刚离站，1=即将到站）→ 位置模型剩余秒 `md × h[段型][1−p]`；
   - `progress.ts:252 locateSegmentOf()`：**无需已知 from/to**，直接在线路全部站里程链里找包含车辆里程的最小间隔（等车场景用，`live.ts:377` 已在调）。

**但**：「用户在哪一段 / 已过几站」这个判断目前在**客户端**做（`useRideTracking.ts` 的 `prog.passedIdx`、`segProgress`），服务端手里只有「一辆车的进度」，没有「这张卡的用户走到第几段了」。⇒ **服务端要算，必须由请求告诉它 `legIndex`**；`passedIdx` 可以由客户端传，也可以让服务端用「车牌 + 2 次 DSAT」自算（不划算，见 §4.3）。

表结构支持情况：**支持**。「已过站点」不需要新表——站序在 `route_stations`，里程在 `route_station_mileage`，跳时长在 `route_hop_stats`，几何在 `route_shapes`，全部已有生产数据。

### 3.2 各表提供什么

| 表 | 提供 | 谁在用 | 备注 |
|---|---|---|---|
| `route_stations` | 线路 × 方向 × 站序 | `loadStatics().routeIdx`（站序、方向、站名） | 唯一键 `(route_id, dsat_dir, seq)` |
| `route_shapes` | 线路 × 方向 × `polyline`（GCJ-02） | 画线、`progress.projectMile()` | 唯一键 `(route_code, dsat_dir)`；**运行时禁实时查高德**，只读本表（`migrate-v2900.ts:76-80`） |
| `route_frequency` | 线路 × `day_type` × 时段 × `freq_lo/freq_hi` | `headwayAt()`（第 2 段起等车、slack 风险项） | `special` 不参与自动匹配；≈512 行全量进内存 |
| `lrt_timetables` | 轻轨 站 × 线 × 方向 × 班别 → `minutes` JSONB | `queryLrtDepartures`（零 DSAT） | 首末班为**当日分钟偏移**，可 >1440 |
| `route_station_mileage` | 站 → **沿线里程（米）**，**多行制** | `progress.getMiles()`；`/api/route-stops` 的 `mileM` | 环线同站两候选（里程 0 与 L），运行时消歧 |
| `route_hop_stats` | 线路 × 邻接站对 → `p50_sec` / `avg_sec` / `samples` | 进度模型 `md` | 不按时段分层（实测更稳） |
| `segment_stats` | 线路 × 站对 × `weekday` × `time_bucket` × `arrive_kind` → `avg/p50_minutes` | `lookupHop()` 的七级回落 | 时段桶口径来源 |

### 3.3 「沿线路程（里程）」有没有现成字段？

**有，而且是两条现成出口，不必按几何现场算：**
1. 表：`route_station_mileage.mile_m`（`db/migrate-v3400.ts:45-56`），主码级、多行制；
2. API：`GET /api/route-stops` 已把它作为 `mileM` 下发，且做了**沿站序贪心消歧**（`load-route-stops.ts:59-70`、`:143-157`），表缺失时 `mileM: null` 而非整页失败（`:18`）。

⇒ 「剩余各段用时」**不需要里程**（`lookupHop` 直接给分钟）；里程只在要展示「还剩 N 米 / 已走 x%」时才需要，且已现成。**不要**为了重算时间去现场投影几何。

### 3.4 「已用时间」这个输入缺失——但可以反推，不必新增状态

`card` 里没有 `sessionStart`，但有两条恒等式：

```
model.ts:817   totalMin = (cursor − nowMs) / 60_000
model.ts:879   arriveAt = cursor           // cursor 是绝对 ms 轴
⇒ 规划时刻 = arriveAt − totalMin × 60_000
⇒ 已用时长 = now − (arriveAt − totalMin × 60_000)
```

⇒ **不需要新增「会话起始时刻」字段**，也不需要 localStorage。这一点我复核成立，与架构师 §1 Q2 一致。`arriveAt` 是常量锚，页面刷新 / bfcache / 熄屏回来都天然自洽。

⚠️ residual（与架构师一致）：`arriveAt` 是**规划时刻**算的，车晚点后它不会更新（`model.ts` 无回写）。⇒ 它只支撑「第一个数字的正确倒计时」，不支撑「晚点后的正确剩余」。后者必须靠「当前腿 `segRemainSec` + 下游 `headwayAt` 按新到达时刻重估」。

## 4. 成本与约束

### 4.1 重算一次会打几次 DSAT？

| 方案 | DSAT | 高德 | 说明 |
|---|---|---|---|
| **重算（本文两个选项，客户端传进度）** | **0** | **0** | 用户已上车 ⇒ 首段候车是历史；其余全是静态索引 + 内存缓存 |
| 参照：现有「刷新」一次 | **2** | 0 | `route-vehicles` 位置 + 报站（`:148-151`） |
| 参照：`/api/nav` 一次 | 约 9~13 | 1（+2 条件） | `switch-plans/route.ts:132-133`、`live.ts:25` |

**结论：重算比现在的「刷新」更省**（0 < 2）。这是本方案最硬的一条可行性依据。

### 4.2 `purpose` 分档与熔断隔离（铁律 19）

- 现有 `DsatPurpose = "timer_grab" | "poll" | "sync" | "recommend" | "live_pos"`（`dsat/client.ts:20`）。
- 跳过熔断判定的只有 `recommend` 与 `live_pos`（`:93`）——铁律 19 的落地形态就是这一行。
- **本方案不新增 purpose**：重算端点 0 次 DSAT，压根不进 `dsatPost()`。⇒ 无熔断风险、无新登记项。
- **若将来改成「服务端自取车辆帧」**（不信任客户端传的进度）：一次刷新 2 次 DSAT、5s 轮询 = **24 次/分钟/用户**；而 `DSAT_QPS=3`、`DSAT_BUCKET_CAPACITY=30` 是**全 Key 全局单桶**（`amap/rate-limit.ts:46-47`）⇒ **约 7 个并发用户就打满**，且必须把新 purpose 加进 `skipBreaker` 白名单否则会撞开全局熔断、静默计时器主流程 30 分钟。**这条属「结构上不可行」，不是调参能解决。** 建议写进设计约束：**重算端点禁止服务端拉车辆帧。**

### 4.3 缓存层：点刷新时该走 nocache 还是复用？

分三层，各自结论不同：

| 层 | 现状 | 重算时应该怎样 |
|---|---|---|
| `transit_cache`（高德 OD，60s） | 只服务 `/api/nav` | **完全不碰**（不打高德） |
| Next **Data Cache**（`unstable_cache`，`revalidate:60`，tags `rec-static`；`query.ts:227-232`） | 静行走跨实例边缘缓存 | **复用，不要绕过**。这是 Hobby 计划下的正解（`preferredRegion` 在 Hobby 不生效，本项目记忆已有此条；`live.ts:22-27` 亦有实测记录） |
| 进程内缓存（`STATIC_TTL_MS=60s`、`headway 10min`、`holidays 6h`、`progress 120s/600s`） | 已有 | **复用**。重算不需要「更新鲜的静态数据」——静态数据 60s 不变不影响分钟级预测 |

⇒ 「点刷新」应当**复用缓存**，而不是 `nocache`。理由：重算的输入变化全部来自**客户端上报的进度**与**当前时刻**，不来自服务端静态数据。缓存新鲜度不是这条链路的瓶颈。

⚠️ 一个必须先说清的坑（Data Cache 的已知缺陷）：`StaticRows` 序列化后 ≈1.2MB，超过 Next 单条 2MB 上限时**生产静默跳过写入**（`query.ts:245-256` 有完整考证与 `oversize-warning` 观测）。⇒ 新端点的 p95 存在「缓存命中」与「缓存未写入、直连库」两种量级，不能只测一次就下结论。

### 4.4 会不会撞高德配额（搜索类 5000/月，超限静默空）？

**不会。** 重算端点不 import 任何高德搜索路径，也不进 `search` 桶（`poi.ts` 的 `inputtips` / `placeText` 是唯一两个记账点；熔断在 `quota.ts:74 circuitState()`）。静态可证，无需实测。

同时也不碰 `transit` / `walking` 桶——本次不新增任何高德调用。

### 4.5 出口限流：新增端点要不要令牌桶？

| 选项 | 门禁成本 | 每次请求的额外 DB |
|---|---|---|
| `isSameOrigin()`（纯 header 比较，`same-origin.ts`） | 0 | **0** |
| `acquireToken(bucket)` | 0 | **1 次事务**（`BEGIN` + advisory lock + 2×UPDATE + SELECT + `COMMIT`，`rate-limit.ts:130-161`） |

重算端点是纯计算、不写库、不打外部 ⇒ **推荐 `isSameOrigin()`**。它是 `GUARD_CALLS` 认可的防护之一（`check-api-guards.ts:127-131`），且不引入 DB 往返（生产 iad1→新加坡单次 ≈230ms，见 `client.ts:45` 的实测记录 —— 这一跳会把「100~300ms」的预期直接打穿）。

⚠️ 副作用需登记：`route-vehicles` 目前**没有任何服务端限流**（探针 E3 通过）。若重算端点也用 `isSameOrigin`，则「连点刷新」在两个端点上仍只有前端 5s 冷却一道闸。这是**现状**，不是本方案引入的新风险，但应在安全登记里写明。

## 5. 契约风险

### 5.1 扩展现有接口入参，是向后兼容还是破坏性变更？

**选项 A（扩 `detail-body`）：技术上向后兼容，但语义上要写清。**
- 新增入参全部**可选**、缺省行为不变（⇒ 老前端零改动，可逐字节对拍）；
- 新增出参全部**可选**（`remainingMin?` / `arriveAt?` / `recomputedAt?`），老前端忽略即可；
- **但**「同一个端点在不同入参下 `strips` 数值可能不同」是一条**语义变更**，必须写进契约，否则将来有人会拿「两次 detail-body 的 strips 不一致」当 bug 查。
- 判定依据：本项目已有同类先例——`fold` 就是「可选入参 + 缺省不变」的加法（`04-API契约增量-mileM.yaml` 的 `/api/nav/detail-body` 段），且明确写了「响应结构不变 ⇒ 老前端不崩」。照这个范式走即可。

**选项 B（新增端点）：纯新增，零契约影响。**

### 5.2 前端类型/契约定义在哪？

- **没有全量 OpenAPI 文件。** 全仓只有一个契约文件：`docs/迭代-导航优化-20261102/04-API契约增量-mileM.yaml`，且开宗明义「只登记本迭代要动的**增量**；未在此处出现的端点/字段一律不得改动」（`:1-6`、`:12`）。
- 类型定义的**唯一真相源是 `src/lib/recommend/types.ts`**（`RecommendCard` :733、`RideLegView` :543、`SegmentStrip` :783），前后端共用（client-safe，禁 import pg）。
- 客户端消费子集的形状写在 hook 的本地 interface 里，如 `useDetailBody.ts:24-40` 的 `DetailBody`。
⇒ **任何新字段必须三处同步：`types.ts`（如新增类型）→ 契约 yaml → 消费方 interface。** 漏一处就会出现「服务端发了、前端看不见」的静默缺失。

**一条容易漏的契约细节（建议照抄现成做法）**：重算响应应带 `recomputedAt`（服务端 `Date.now()`）。理由不是"方便调试"，而是**时钟偏移校正**——`/api/station/eta` 已经这么做了：它下发 `serverNowMs`，客户端算 `offsetMs = serverNowMs − Date.now()`，再用 `depMs − (Date.now() + offsetMs)` 倒计时，从而**不受网络往返与服务端缓存延迟影响**（`station/eta/route.ts:114-120` 的口径，注释里写明「旧口径 `etaSec` 是相对快照，命中 20s 缓存时会整体偏大，用户实测反馈时间不准确」）。

重算端点若只回 `remainingMin`（相对值）而不回锚点，5s 轮询下用户会看到「每次刷新跳一格」；回 `recomputedAt` 后客户端可把「预计到达时刻」做成绝对锚 + 本地递减，与现有 `arriveAt` 的做法一致。⇒ **响应同时给 `remainingMin`（相对）与 `arriveAt`（绝对）+ `recomputedAt`（服务端时钟锚），三者缺一都会退化成旧问题。**

### 5.3 安全策略要登记在哪？

- **`src/lib/security/route-policy.ts` 不需要改。** 该文件只有三类常量：`PAGE_RETIRED`（下线的页面）、`GONE_PREFIXES`（退役接口 410）、`SAME_ORIGIN_PREFIXES`（`["/api/fav-routes"]`，只有它）。新端点不属于任何一类 ⇒ 无需登记。
- `PUBLIC_PREFIXES` 白名单已随 ADR-106 拆除，`proxy.ts` 头部保留了「若要重新上锁的 3 步」作为设计记录（探针 G3 只断言「不存在 `export const PUBLIC_PREFIXES`」，注释块里的提及不算违规）。
- **真正要过的是 AC-50 门禁 `scripts/check-api-guards.ts`**（规则见 `:18-31`）：每个 `POST/PUT/PATCH/DELETE` 必须命中四类之一——① GONE 前缀覆盖；② SAME_ORIGIN 前缀 + `acquireToken` 两件套；③ handler 内真有 `hasInternalToken` / `acquireToken` / `acquireWithWait` / `isSameOrigin` 调用；④ 显式 allowlist。
  - 新增豁免是「门禁上唯一的洞」，当前只有 3 条（`cron/rebuild`、`amap-service`、`poi/suggest`），且**新增必须主理人批准**（`:92-95`）。**本方案不建议走豁免。**
  - 走 ③ 的 `isSameOrigin()` 即可通过，且成本为 0 DB。
- **本条已实测确认**（2026-11-03 跑门禁，只读）：`通过 22 / 失败 0`；`错误码闭集：新增违规 0 · 遗留欠账 0`；`扫描 40 个 route.ts`。⇒ 现存 40 个 handler 全绿，选项 B 会变成第 41 个，且**不加防护调用必然 FAIL**（不是"可能"，是门禁判据明文）。

### 5.4 为什么不能做成 GET（绕开 AC-50）

GET 不在 AC-50 校验范围（`:31`「GET 不校验」）。但**重算必须携带 `card`**：
- `RecommendCard` 含 `strips` 级信息与 5 张卡的完整结构，序列化后远超 URL 长度上限；
- 服务端**没有**任何「按 planId 取回 card」的存储（`planId` 是 `planNav` 内部分配，`OptionSeed` 上带，无落库）——`detail-body/route.ts:8` 明文写着「planId 不参与定位」「card 直传，不经过 planId 重算」。

⇒ **只能 POST** ⇒ **必须带防护调用**。这一点在选端点形态时是硬约束，不是偏好。

### 5.5 错误码闭集

- 对外 `error` 只允许 6 值：`unauthorized` / `forbidden` / `gone` / `rate_limited` / `bad_request` / `upstream_error`（`errors.ts:16-34`）。
- `check-api-guards.ts` 第二部门是**静态扫描**：每个 `route.ts` 里 `error: "字面量"` 必须是六枚举之一，或用 `API_ERROR.x` 标识符；`KNOWN_DEBT` 是遗留基线，只应缩短（`:33-42`）。
- 历史事故：`route-stops` 曾回第七个值 `route_not_found`，当时「没有任何自动门禁看得到它」（`:36-40`，`route-stops/route.ts:35-40` 有修正注释）。
⇒ **新端点的错误场景一律映射到已有 6 枚举**：
- 缺参 / 结构非法 / `legIndex` 越界 → `bad_request`(400)
- 静态数据装载失败 → `upstream_error`(500)，细节只进 `console.error`
- 若加桶 → `rate_limited`(429) + `Retry-After`
- **不得新增**如 `stale_card` / `remaining_unavailable` 这类码。
