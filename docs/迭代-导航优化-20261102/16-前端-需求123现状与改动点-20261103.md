### 1.3 为什么「刷新什么都不变」——根因（三条，缺一不可）

1. **数据结构层**：`POST /api/nav/detail-body`（`src/app/api/nav/detail-body/route.ts:206-215`）响应体 = `{ok, strips, otherRoutes, foldLive, stationLabel, legs}`——**没有 card，也没有任何时间字段**。所以 `detail.reload()` 无论调多少次，①②都不可能变。
2. **计算层**：`card.totalMin/arriveAt` 是 `modelOption()` 在**规划时刻**用 `nowMs + walkOut + wait + ride + transfer + walkIn` 串行累加出来的**一次性快照**（`model.ts:421-889`），之后**没有任何代码路径回写它**。全仓 grep `recompute|reroute|ladder` 无「剩余行程重算」实现（`src/lib/nav/recompute.ts` 名字像，实际是"高德骨架时间补丁"，不是剩余行程重算）。
3. **触发层**：`refreshNow()` 只做 `fetchFrame`，它更新 `prog`（站游标）与 `segProgress`（本段剩余秒），**不产生任何跨段汇总**。

### 7.3 「时间数字会自己动」——需求 1 的验收噪声源，第一部分未点明

`NavDetailBody.tsx:151-176` 的机制是「**校准值 − 本地流逝**」：

```
etaBaseMin  ← 帧到达时重算（segProgress.segRemainSec / 60，或按 minToNext 求和）
remainMin   ← max(0, etaBaseMin − (now − base.ts)/60000)   ← 每 15s 因 etaTick 重渲染一次
```

两个后果，**直接决定验收怎么做**：
1. **`约 X 分钟` 自己每 15s 就掉一次**（与点不点刷新无关）⇒ 「点刷新后数字变了」在现状下**无法证伪也无法证实**。验收必须引入**未递减的校准锚点**（建议新增 `data-eta-base`），否则任何「刷新前后差值」断言都会被本地 tick 噪声吞掉。
2. `:366-367` 与 `:174` 都用了 `Math.max(1, …)` ⇒ **「约 X 分钟」永远不小于 1**，到站前不会出现 0。若改成「剩余总时长」，需同步决定是否沿用这个地板（沿用 ⇒ 到站时显示 1 分而非 0）。

另补一条被忽略的事实：`segProgress` 的 `uSec` 是在 **fetchFrame 内部**用 `Date.now()` 一次性累加的（`useRideTracking.ts:848-864`），**帧间不推进** ⇒ `segRemainSec` 本质是「上一帧时刻的剩余」，其"实时性"完全依赖轮询频率（12s）。这解释了为什么「多刷一次」在体感上确实会变、但幅度很小。

## A.6 ⚠️ 已知边界：`boarding` 相位的 ①② 是规划快照（本轮不修）

### 现象

`boarding`（在站台等车、尚未上车）时，详情头的 ①② 显示的是**规划时快照**

### 固有偏差

规划快照假设「**你能赶上规划时的那一班车**」。若那班车已走、用户仍在站台等：

- **真实剩余会变长**，而快照不变 ⇒ **偏乐观（偏小）**

⇒ 在 boarding 期调用该端点会**反方向出错**（漏算候车 3~9 分钟，显示偏短），比不调用更糟。

因此本轮采用「boarding 不调用该端点」（`useNavRemaining` 的 `enabled` 收窄为 `phase === "riding"`），

```
误用偏差 = rides[legIndex].waitMin          ← 精确等式，不是「大概 5~10 分钟」
```

实测（`waitMin = 7.5` 分）：

| 断言 | 结果 |
|---|---|
| 当前腿 `waitMin=7.5` **完全不计入**剩余 | `remainingMin = 22.7`（boarding 语义应为 `30.2`） |
| ⇒ 误用偏差 | `30.2 − 22.7 = 7.5`（**分毫不差**） |
| `waitMin` 7.5→0 ⇒ `remainingMin` **不变** | `22.7 → 22.7` ⇒ **该字段在时间轴里根本没有位置** |

第三条是**结构性**证据（不是量级证据）：它证明的不是"漏算了 7.5 分"，而是
**`recomputeRemaining` 的时间轴里压根没有这一项**。
这个区别在防回归上很关键 —— 若将来有人改成 `curRemainMin += waitMin * 0`
（假装消费但乘 0），前两条数值断言可能仍绿，只有第三条能抓出来。

> **给下一位维护者的提醒**：**不要**因为"boarding 显示的数字看着还行"就认为它是准的。
> 它只是"没更糟"。偏差 = `rides[legIndex].waitMin`（**精确值**，不是区间估）：
> 班次越稀疏、`waitMin` 越大，偏差越大（26A、N2 这类线路的 `waitMin` 常在 8~15 分）。
> 若要做对，走上面的「未上车时间轴」，**不要**在客户端把卡面 `waitMin` 加回去 ——
> 卡面值是**规划那一刻**算的，若那班车已走，加回去仍偏乐观。

## A.7 前后端契约对拍结果（2026-11-03 与后端联合验证）

### A.7.1 恒等式的**精确**形式（后端确认，比"约等于"更强）

后端实现保证：

```
arriveAt === recomputedAt + remainingMin × 60000     ← 残差恒 0ms，不是约等于
```

原因：`arriveAt` **不是**内部 `cursor` 直出，而是**由四舍五入后的 `remainingMin` 反推** ⇒ 结构上必然恒等
（后端已锁 8 个用例断言，含 13s 这类奇数秒最易暴露取整误差的场景）。

代入 `remainServedOf` 的式子：

```
remainingMin − staleSec/60 − (now − serverNow)/60
  = remainingMin − (serverNow − recomputedAt)/60000 − (now − serverNow)/60000
  = remainingMin − (now − recomputedAt)/60000
  = (arriveAt − recomputedAt)/60000 − (now − recomputedAt)/60000
  = (arriveAt − now)/60000                              ✓ 恒等
```

⇒ **两条派生路径（`remainingMin` 基准 / `arriveAt` 反算）数学恒等，不是"近似相等"。**

### A.7.2 `staleSec` 分子不变量的守护（后端已锁成 smoke 断言）

`staleSec = (serverNowMs − recomputedAt)/1000` 成立的前提是：**缓存命中时 `recomputedAt` 不刷新**。
这个不变量没有任何编译期保护，改坏了只会「静默偏大」。

后端已在 `.verify/_remaining-route-smoke.ts` 锁 5 条：

```
命中微缓存：recomputedAt 保持原值（staleSec 的分子，不得刷新）
命中微缓存：serverNowMs 已刷新为新时刻
命中微缓存：remainingMin 复用（与 recomputedAt 成对）
命中微缓存：arriveAt 也保持原值（与 remainingMin 成对，不得单刷）
★ 恒等式 arriveAt === recomputedAt + remainingMin×60000 在命中缓存时仍成立（残差 0ms）
```

**注释会腐坏，断言不会** —— 谁刷新 `recomputedAt`，smoke 立刻变红。

### A.8.1 批 1：`data-remain-fail` 观测属性（已实现）

**为什么做**（不只是"可观测性"）：负责人主诉是「点了刷新按钮有反应但不知道刷新了什么」。
若 403 被静默吞掉，用户看到的是「**点了完全没反应**」——**同款失败模式的更严重版本**。
修了主诉却留这个洞，等于没修完。

**静默点在哪（关键）**：**不在 `catch`**。`fetch` 对 4xx/5xx **不抛**
（只有网络层错误才抛）⇒ 403 走的是 `if (!r.ok)` 分支，旧实现里那条路**零痕迹**：
无 console / 无 `data-*` / 无 UI ⇒ 故障表现与「本来就不需要重算」完全无法区分。

**实现**：

| 档位 | 触发条件 | `data-remain-fail` 值 |
|---|---|---|
| HTTP 4xx/5xx | `!r.ok` | `403:forbidden` / `400:bad_request` / `429:rate_limited` / `500:upstream_error` |
| 200 业务失败 | `j.ok === false` | `200:<服务端枚举>` |
| 时间锚非法 | `remainingMin`/`arriveAt`/`serverNowMs` 任一非有限 | `200:bad_payload` |
| 网络层异常 | 非 abort 的 `catch` | `0:net` |
| 换卡/换代的 abort | `signal.aborted` | **不记**（否则每次换卡闪假失败） |
| 成功一次 | — | **清空**（属性不输出） |

**成功时不输出**：`data-remain-fail={liveRemainFail ?? undefined}` ⇒ React 不渲染该属性。

**QA 断言写法**：点刷新后 `[data-remain-fail]` 的属性值**不得**以 `403` 开头；
无该属性 = 最近一次成功（正常态）。

**清场规则**：`enabled` 变 false（下车 / 退出详情 / 换卡）时一并 `setLastFail(null)`
—— 否则「上车时 403 一次」的过期值会**永久挂在 DOM 上**，误导 QA 断言与线上排障。
