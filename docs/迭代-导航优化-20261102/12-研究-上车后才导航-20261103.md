## 〇、结论摘要（先看这段）

**负责人描述的现象成立，但 team-lead 给的一个前提需要更正：**

> ❌ team-lead 判断：「`boarding-detect.ts` 现有上车判定算法，`grep speed|velocity|km/h` **零命中**，说明目前**完全没有速度维度**」

**实测有 9 处速度相关代码，且是一套完整的速度判定**：

```
$ grep -rc 'speed\|velocity\|kmh' src/lib/nav/boarding-detect.ts
9
```

关键常量（`boarding-detect.ts:52-65`）：

| 常量 | 值 | 作用 |
|---|---|---|
| `R2_SPEED_MIN_KMH_FLEX` | **8** | 巴士速度下限 =「步行/车速」契约分界（注释详述为何不能用 5.5） |
| `R2_SPEED_MAX_KMH` | 80 | 漂移上限 |
| `R2_LRT_SPEED_MIN_KMH` | 12 | 轻轨（起速快） |
| `R2_WINDOW_MS` | 45_000 | 速度/位移计算窗口 |
| `R2_DISPLACE_MIN_M` | 60 | 沿线位移下限 |
| `R2_STREAK_ALONE` | 3 | 纯定位判定所需连续命中帧 |

`r2Of`（`:164-208`）同时校验**四个门**：投影 ≤80m（自适应精度）+ 沿线位移 ≥60m + 平均速度 ∈ (8, 80] km/h + 采样 ≥3。这是一套比行业常见做法更完整的判据（详见 §四）。

**⇒ 真正的根因不是「没有速度判定」，而是「速度判定永远执行不到」。**

死锁链（详见 §三）：

```
用户在车上点「开始导航」
  ⇒ startSession("out") ⇒ walkSeg="out" ⇒ walkActive=true
  ⇒ useRideTracking.ts:940  if (walkActiveRef.current) return;   ← tryAuto 被硬封
  ⇒ 速度判定 r2Of 永不被调用（它在 tryAuto 内部）
  ⇒ 而 walkSeg 唯一出口是 walkFollow.phase === "arrived"
  ⇒ arrived(remainM) = remainM ≤ 30m（需沿步行路径走到终点 30m 内）
  ⇒ 用户在车上不沿步行路径走 ⇒ remainM 永远 > 30 ⇒ 永不 arrived
  ⇒ 死锁：永远是步行段，且横幅显示「已偏离路线 N 米」
```

这与 v3.8.1 修的「步行段不轮询车辆」（`e300b87`）**是同一族缺陷**：v3.8.0 的 T1 把会话起点从「站在站台」提前到「出门就走」后，所有「假设用户在站台」的旧门控（轮询、上车判定）全部失效。

## 一、场景还原核实

team-lead 的场景还原**准确**，逐条对应到代码：

| team-lead 描述 | 代码证据 |
|---|---|
| 「开始导航」⇒ 进步行出发段 | `NavShell.tsx:598-618` `startSession("out")`：`freezeOrigin()` + `rideStart()` + `walkRoute.ensure("out")` + `setWalkSeg("out")` |
| `walkSeg` 与 RidePhase 是两套状态机 | `NavShell.tsx:375` `useState<"out"\|"in"\|null>(null)`；`:394` 注释「★ T1：步行活跃 ⇒ 引擎内 `tryAuto` 早退（真互斥，不是靠调用方不渲染）」 |
| 系统自动进 boarding | `startSession` 内 `if (seg === "out" && ridePhaseNow === "off") rideStart()` |
| 地图显示步行路线 | `walkActive && activeWalk?.phase === "ready"` ⇒ `WalkTurnBanner` + 地图 walk 三线（v3.9.0 改绿实线） |
| 显示「偏离路线」 | `WalkTurnBanner.tsx:8` 「`off` 偏离 > 50 米：黄底 + 「已偏离路线 N 米」」；阈值 `follow.ts:57` `WALK_OFF_M = 50`、`:59` `WALK_OFF_CONFIRM = 2`（连续 2 帧） |
| 无法自动切到车程 | §三 死锁链 |

**补充一条 team-lead 未提到的**：boarding 态**已经有手动出口**——`NavTrackBar.tsx:217-228` 渲染「手动标记上车」按钮（点击 ⇒ `board()` ⇒ `switchToRiding`）+ hint「上车后自动开始跟踪」。所以用户**并非完全无路可走**，问题是：
1. 按钮文案是「手动标记上车」，在"我在步行导航"的语境下不像该点的东西；
2. 用户注意力在顶部 `WalkTurnBanner`（「已偏离路线」），根本不会看底部 sheet 的按钮；
3. 系统没有任何「你可能已经在车上」的信号。

**这一点影响方案选择**：可能不需要新增"自动上车"能力，只需要在正确时机把用户注意力引到已有按钮上，或让系统代劳。

## 二、现有判定条件链（完整，带行号）

### 2.1 三层结构

`useRideTracking.tryAuto()`（`:933-960`）→ `autoBoardOf()`（`boarding-detect.ts:316-393`）→ 三个子判据：

```ts
// useRideTracking.ts:933-960（当前实际代码）
const tryAuto = useCallback(() => {
  if (phase !== "boarding" || !active) return;      // ① 只在候车态判
  if (walkActiveRef.current) return;                // ② ★ 步行段硬封（死锁点）
  const leg = legs[legIndex];
  if (!leg) return;
  const boardMain = stopsBoard(strips, legIndex) || mainOf(anchors?.[legIndex]?.board?.code ?? "");
  const res = autoBoardOf({ legKind, legDegraded, colored, boardMain, boardPos,
                            vehicles: listRef.current, fixes: fixesRef.current,
                            lastSwitchTs, nowMs, autoUsed, streak });
  boardStreakRef.current = res.streak;
  if (!res.hit) return;
  if (res.streak >= res.need) switchToRiding(res.plate, res.source);
}, [...]);
```

### 2.2 `autoBoardOf` 的五个硬门（`boarding-detect.ts:316-393`）

```ts
/* ① 硬门 G3：总开关 / 单次会话 / 冷却 */
if (!AUTO_BOARDING_ENABLED) return noHit();              // :322  = true
if (input.autoUsed) return noHit();                       // :323  单会话单次
if (nowMs - lastSwitchTs < SWITCH_COOLDOWN_MS) return noHit();  // :324  20s 冷却

/* ① 硬门 G1：几何缺失 ⇒ 不判（旧版退化成 R1-only 是误判来源） */
const geomOk = colored.length >= 2 && !legDegraded;       // :328

/* ① 硬门 G2：定位主导 ⇒ 帧不够不判 */
const fixes = trustedFixes(input.fixes);                  // :334  过滤 accuracy > 150m
if (fixes.length < R2_STREAK_ALONE) return noHit();       // :335  需 ≥3 帧

/* 巴士段：定位主导 + 车辆辅助降门槛 */
const aux = auxOf(vehicles, boardMain, boardPos);
const assisted = aux.strong || aux.weak;                  // :361  车辆只降门槛，不单独触发
const need = assisted ? R2_STREAK_WITH_VEHICLE : R2_STREAK_ALONE;  // 2 或 3

const hit = r2Of(fixes, colored, { tolM, displaceM, speedMinKmh: R2_SPEED_MIN_KMH_FLEX, ... });
if (!hit) return noHit();

const lockedPlate = aux.strong ? aux.plate : null;         // :372 ★ 只有 A1（车刚离站且唯一）锁牌
return { hit: true, plate: lockedPlate, source: lockedPlate ? "vehicle" : "gps", ... };
```

### 2.3 为什么「人在车上但已过站」不触发

**不是"已过站"的问题，是 `:940` 早退根本没让它判。** 假设早退被解除，`r2Of` 会怎么表现？逐门核对：

| 门 | 用户在公交车上（20 km/h，沿线路） | 判定 |
|---|---|---|
| 帧数 ≥3 | 步行段 GPS 间隔 **3s**（`NavShell.tsx:341`），45s 窗口内约 15 帧 | ✅ |
| 投影 ≤80m | 公交沿公交线路走 ⇒ 投影接近 0 | ✅ |
| 沿线位移 ≥60m | 20 km/h ⇒ 60m 需 10.8s | ✅ |
| 速度 ∈ (8, 80] | 20 km/h | ✅ |
| streak ≥3 连续调用 | 每帧 GPS 调用一次 ⇒ 约 9s | ✅ |
| 几何 `colored.length ≥ 2` | `ov.legs[k].colored` 正常 | ✅ |
| 冷却 20s | `lastSwitchTs = 0`（刚 startSession） | ✅ |

**⇒ 解除早退后，约 11–20 秒即可自动切入 riding。** 算法本身不需要改一行。

## 三、死锁机制（核心，完整证据链）

```
① startSession("out")                          NavShell.tsx:598-618
     ⇒ setWalkSeg("out")                        NavShell.tsx:617
     ⇒ walkActive = walkSeg !== null            NavShell.tsx:377
② walkActive 传给引擎                           NavShell.tsx:395  walkActive,
     ⇒ walkActiveRef.current = true             useRideTracking.ts:349
③ 所有 tryAuto 调用点                                （共 2 处）
     · userFix 帧到位                            useRideTracking.ts:1050（每 3s）
     · 候车轮询 round 内                          useRideTracking.ts:1014（步行段 60s，v3.8.1 降频）
     ⇒ 两处都被 :940 硬封                        useRideTracking.ts:940
④ 速度判定 r2Of 在 tryAuto 内部 ⇒ 永不被调用
⑤ walkSeg 唯一出口                             NavShell.tsx:684-688
     if (walkSeg !== "out") return;
     if (walkFollow.phase !== "arrived") return;
     endWalk();
⑥ arrived 判据                                 lib/walk/follow.ts:253
     export const WALK_ARRIVE_M = 30;
     export function arrived(remainM) { return remainM <= thresholdM; }
     ← remainM = stepsTotalM - doneTotalM（沿步行路径已走距离，follow.ts:240）
⑦ 用户在车上不沿步行路径走 ⇒ doneTotalM 几乎不增长 ⇒ remainM 恒 > 30

```

**「偏离路线」同时被点亮**：`walkFollow.offRoute` = `offStreak >= WALK_OFF_CONFIRM`（`follow.ts:59` = 2），`offRouteM > 50` 连续 2 帧即成立 ⇒ 横幅切 `state="off"`（`NavShell.tsx:1196`）⇒ 用户看到「已偏离路线 N 米 · 回到路线」。

**这个提示在死锁下是"正确但无用"的**：它说"你偏了"，但真实情况是"你不该走"，用户按它走会越来越错。

## 四、速度判定可行性

### 4.1 数据源与采样率（比 team-lead 估计的好）

| 项 | 实测 | 依据 |
|---|---|---|
| GPS 采样间隔（步行/候车段） | **3 秒** | `NavShell.tsx:341` `const gpsIntervalMs = ridePhase === "riding" ? 1_500 : navActive ? 3_000 : 10_000;` |
| GPS 采样间隔（riding） | 1.5 秒 | 同上 |
| 定位精度门 | accuracy ≤ 150m 的帧才可信 | `boarding-detect.ts:48` `R2_FIX_MAX_ACC_M = 150`；`trustedFixes()` 过滤 |
| 精度自适应容差 | `tol = max(80, accuracy × 1.5)` | `:42-46` |
| 已有纯速度函数 | `gpsSpeedKmh(fixes, windowMs)` | `:216-226`，两帧位移/时间差，**不依赖线路投影** |
| 是否用 `coords.speed` | **否**（0 处） | `grep '\.speed\b' src/components/nav/useUserFix.ts` 无命中 |

⚠️ **一个需要注意的隐患**：候车期（含步行段）开着**粗定位** `coarse: navActive && ridePhase !== "riding"`（`NavShell.tsx:351`），即 `maximumAge = 30_000` + `enableHighAccuracy = false`（`useUserFix.ts:71` `COARSE_MAX_AGE_MS = 30_000`）。后果：
- `maximumAge` 允许浏览器返回最多 30s 前的缓存坐标 ⇒ **两帧可能是同一个物理点** ⇒ `gpsSpeedKmh` 会算出 0；
- `enableHighAccuracy=false` ⇒ 城市峡谷/车内定位误差可能 50–150m。

对 45s 窗口内的多帧判定，这些噪声会被"投影容差自适应"和"streak 3 次连续"吸收；但如果要基于速度做**快速**判定（几秒级），当前粗定位会明显拖慢。⇒ 若采用"速度闸门"，建议在闸门激活窗口内临时切回高精度（`coarse=false`），否则第一帧可能不可靠。

### 4.2 阈值：现有 8 km/h 与行业一致，不需要改

| 来源 | 阈值 | 方法 |
|---|---|---|
| **本项目** `R2_SPEED_MIN_KMH_FLEX` | **8 km/h** | 投影 + 沿线位移 + 平均速度 + streak；注释记录了 5.5 km/h 会把快走误判为已上车（架构已双向实测） |
| MDPI Sensors 2017（首尔，3 部手机实测 GPS 抖动） | **9.6 km/h** | 静止时 GPS 位移噪声实测 ≈ 9.6 km/h ⇒ 以此为"非步行"下限 |
| Politecnico di Bari（CEUR Vol-1099） | **7.2 km/h**（2 m/s） | 速度门 + **与公交线路重合率 ≥0.8** |
| Dawarich（开源轨迹分类） | Walking 1–7 / Running 7–20 / Cycling 7–45 / **Bus 10–100** | 纯速度分档，并明确承认「Bus vs Driving 无停站模式数据时难分」 |

**三条结论**：
1. 项目现有 **8 km/h** 落在行业区间（7.2–9.6）内，**阈值无需调整**；
2. 单靠速度**无法**区分公交 / 跑步（7–20 重叠）/ 骑行（7–45 重叠）——但项目已有第二判据（**线路投影 ≤80m**），这是 Politecnico 方案（速度 + 重合率 0.8）的同构做法；
3. 行业普遍需要**连续确认**（MDPI：连续两次识别相同才确认；项目：streak ≥3）与**停站容忍**（MDPI：车辆识别后出现静止 <3 分钟则忽略）——项目 45s 窗口天然容忍短停。

### 4.3 判定延迟估算

| 车速 | 位移门 60m 所需 | streak 3 帧所需 | 实际首次判定 |
|---|---|---|---|
| 20 km/h | 10.8s | 9s（3s/帧） | **≈ 11–20s** |
| 30 km/h | 7.2s | 9s | ≈ 9–15s |
| 12 km/h（慢速/拥堵） | 18s | 9s | ≈ 18–30s |
| 5 km/h（堵车蠕行） | 43s | 9s | ≈ 43s+（可能一直判不出） |

⇒ **拥堵蠕行是最坏情况**：速度可能长期低于 8 km/h，算法判不出（这也是行业共识——低速时速度判据天然失效）。

## 五、方案（3 个，标出需拍板的取舍）

### 方案 A（保守）：速度闸门 ⇒ 提示用户确认，不自动切

**做法**：在步行段检测「疑似在车上」（`gpsSpeedKmh` > 8 持续 ≥3 帧 **且** 投影 ≤80m），把 `WalkTurnBanner` 的 `state` 从 `off` 改为一个**新增的**「你似乎在车上？」提示（或把底部「手动标记上车」按钮高亮 + 文案改「已检测到你在移动 · 点此标记上车」）。用户点确认 ⇒ `board()` ⇒ 正常 riding。

- **改动量**：小。新增一个速度检测 effect（约 30 行）+ 横幅一个 state/文案 + 按钮高亮样式。
- **误判代价**：**零**（只提示，不改变状态）。
- **优点**：不破坏任何既有判定链；跑步/骑行误判只是"多看到一个提示"，用户忽略即可。
- **缺点**：多一步交互；用户可能在颠簸/分心中错过提示，仍卡在死锁。
- **需要拍板**：提示用横幅还是按钮？文案「你已在车上？」是否需要更中性（如「检测到你在移动」）？

### 方案 B（激进）：速度闸门 ⇒ 自动解除步行段，交给既有 tryAuto

**做法**：步行段检测到「疑似在车上」⇒ `endWalk()`（`NavShell` 侧）⇒ `walkActive=false` ⇒ `tryAuto` 早退解除 ⇒ 下一次 GPS 帧（≤3s）由既有 `r2Of` 走完整判定 ⇒ 连续 3 帧命中 ⇒ `switchToRiding`。**算法与阈值零改动**。

- **改动量**：**最小**（核心约 10 行：一个 effect，条件满足调 `endWalk()`）。
- **误判代价**：中。用户在跑步（7–20 km/h）且沿公交线路跑时会被自动切到车程 ⇒ 需要"回到步行"的回退路径，而**当前没有**（`startSession("out")` 有反向 gate `if (ridePhaseNow === "riding") return`，要走 `onNotBoard()` 再 `startSession` 两步，UI 上无此路径）。
  - 缓解：切 riding 后走安全网——`anomalyOf` 的 A1「疑似未上车」（`autoSwitched && v60 < 2 && advanced && 离线>250m`）会提示「我没上车」，但**前提是"离线 >250m"**（`projDistM > 250`），跑步沿线路时不成立 ⇒ **安全网抓不到**。
- **优点**：用户零操作；体验最顺。
- **缺点**：跑步/骑行误判无自动化兜底；需新增回退路径。
- **需要拍板**：能否接受"偶发误判 + 需手动纠正"？若接受，是否同时加一条「识别到在车上 · 不对？点此回到步行」的撤销入口？

### 方案 C（折中，推荐）：速度闸门 + 高置信自动切 + 低置信提示

**做法**：分两档置信度，复用既有阈值不新增魔法数：

- **高置信 ⇒ 自动切（走 B 的路径）**：速度 > 8 km/h **持续 ≥3 帧** + 投影 ≤80m **+ 有车辆佐证**（`auxOf` 的 `strong`，即本段有车刚离开上车站或就在附近）。此时"在车上"的证据是双源的（用户自己在动 + 车也在），跑步时不会同时满足。
- **低置信 ⇒ 只提示（走 A 的路径）**：只有速度+投影，无车辆佐证 ⇒ 用户自己判断。

- **改动量**：中（速度 effect + 分支 + 提示 UI + 撤销入口）。
- **误判代价**：低。高置信档要求双源证据，跑步时段很难恰好有车辆佐证。
- **优点**：自动化的顺滑 + 保守的安全。
- **缺点**：实现最复杂；车辆帧在步行段是 **60s 一帧**（v3.8.1 降频）⇒ `auxOf` 的车辆佐证可能过期/缺失 ⇒ 高置信档命中率下降，多数情况会落到"只提示"⇒ 退化为 A。**这是本方案的实际风险，必须实测车辆帧时序。**

### 方案对比

| 维度 | A 保守 | B 激进 | C 折中 |
|---|---|---|---|
| 改动量 | 小 | **最小** | 中 |
| 误判代价 | **零** | 中（无自动兜底） | 低 |
| 用户操作 | 1 次点击 | **0** | 0 或 1 次（看置信度） |
| 拥堵蠕行场景 | 仍卡（速度判不出） | 仍卡 | 仍卡 |
| 需要新增回退路径 | 否 | **是** | 是（仅高置信档） |

**⚠️ 三个方案都解决不了「拥堵蠕行」**：速度 < 8 km/h 时无任何方案能判出"在车上"。这需要单独决策——是否接受（用户可手动点按钮），或增加"上车站周边 + 车辆停靠"的辅助判据（复杂度显著上升，不建议本期做）。

## 六、隐藏坑：riding 无牌时的**数据供给缺口**（team-lead 问题 5 的答案：链路不成立）

team-lead 假设：「走跳过步行直接 riding，此时无牌 ⇒ 依赖 v3.9.0 刚修好的无牌显示在途车（`e300b87`）。这条链路要核实成立。」

**核实结论：不成立。`e300b87` 只修了「显示」，没修「供给」。**


riding 无牌时，两条轮询全灭：

**影响**：方案 B/C 自动切到 riding 后，地图上的车会静止在旧位置不再更新。用户会看到"进车程了但车不动" ⇒ 比卡在步行段更困惑。

**修复建议（若采用 B/C，必须一并做）**：把 `:1107` 的守卫从 `!matchOnRef.current` 改为「**只看是否需要帧**」——即无牌 riding 就轮询（不跑匹配算法，只更新 `listLiteRef` 供 `mapVehicles` 用），匹配仍受 `MATCH_VEHICLE_ENABLED` 控制。这是**把"数据供给"与"匹配算法"解耦**，与 v3.8.1 修 `mapVehicles` 的思路一致。

工作量：约 5 行（守卫拆分）。但需确认不违反「关闭匹配时不多发请求」这条既有约定（`match-vehicle.ts:25` 注释）——**这条约定本身需要重新审视**：在"无牌 riding"这条路径上，不发请求的代价是"地图车不动"，比多发几次请求更糟。

## 七、「偏离路线」提示的处理（team-lead 问题 4）

**结论：不需要单独处理，它会自然消失。**

- 横幅渲染条件：`walkActive && activeWalk?.phase === "ready"`（`NavShell.tsx:1192`）
- 一旦 `endWalk()` ⇒ `walkActive=false` ⇒ 整个 `WalkTurnBanner` 卸载（含 `state="off"` 的「已偏离路线」）
- 同样，`WalkPane.tsx:76` 的 `.walkoff`（「已偏离路线 N 米，正在重新规划」）也在 walk pane 内，随 `walkSeg` 清空消失

⇒ 方案 A（不结束步行段，只提示）时横幅**仍然显示偏离**，需要在 `state` 上做分支（`off` vs 新增的 `onboard?`）。方案 B/C（结束步行段）时自动消失。

**一个细节风险**：`offRoute` 的自动重算通道（`NavShell.tsx:663-671`，偏航自动 1 次重算）会在死锁期间把**唯一一次自动重算额度**用掉——用户真正需要重算时已无额度。这是死锁的次生损害，修复死锁即消除。

## 九、验证手段（现成观测钩子）

v3.8.0/v3.9.0 已埋全套钩子，真机一次导航即可归因：

| 钩子 | 正常值 | 死锁时 | 说明 |
|---|---|---|---|
| `body[data-walk-step]` | 递增 | **停在 0/1** | 步行进度不推进 = 没在走步行路径 |
| `body[data-walk-off]` | 无 / 小值 | **持续 >50** | 偏航距离 |
| `data-walk-acc` | — | — | 精度分档 |
| `data-board-detect` | `on` / `paused` | `on`（但永不触发） | 判定是否在跑 |
| `data-vehicle-shown` | ≥1 | 步行段 60s 才有帧 | 车辆数 |
| `data-board-match` / `data-match-source` | `auto`/`vehicle` | **`none`/`gps` 永不变化** | 从未判定成功 |

**判别方法**：若导航中 `data-walk-step` 停滞 + `data-walk-off` 持续 >50 + `data-board-match` 恒 `none` ⇒ 即本死锁。

**建议新增一个闸门专用钩子**（若做方案 A/B/C）：`body[data-onboard-gate]` = `speed:12.3|proj:8m|hits:2/3`，用于真机确认闸门是否被正确触发。

## 十、需要负责人拍板的取舍点（汇总）

1. **要不要自动切？**（A 零误判但多一步 / B 零操作但有误判风险 / C 折中）
2. **跑步/骑行的误判**：用户沿公交线路跑步（8–20 km/h）会被判成"在车上"——是否接受？若接受，是否需要「我没上车，回到步行」的撤销入口？
3. **拥堵蠕行**（< 8 km/h）三个方案都判不出——是否接受"用户手动点按钮"作为兜底？还是要求本期必须解决（需引入车辆停靠判据，复杂度显著上升）？
4. **数据供给缺口**：是否同意"无牌 riding 也轮询（只更新地图车位置，不跑匹配）"？这会打破既有"关闭匹配时不多发请求"约定，代价是 DSAT 请求量增加（同线路同方向，12s 一帧）。
