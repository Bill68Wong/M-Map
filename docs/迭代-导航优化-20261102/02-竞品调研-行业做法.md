## 1. 维度一：路线搜索的等待体验

### 1.1 行业做法清单

| 做法 | 具体表现 | 来源 | 等级 |
|---|---|---|---|
| **不许空白等待** | "Show something as soon as possible… 如果让人等到加载完成才显示任何东西，用户会把'没内容'理解成'应用出问题了'"；并明确"等待期间要让人能做别的事（在后台加载）" | Apple HIG · Loading | [官方文档] |
| **按等待时长选控件** | 0.1s = 即时感；1s = 思路不中断；10s = 注意力极限。骨架屏适用 2–10s；**超过 10s 必须给进度/时长预估 + 取消**；<1s 不要盖骨架（一闪而过反而像闪烁） | NN/g · Response Times / Skeleton Screens 101 | [官方文档] |
| **骨架必须"像真的"** | 骨架屏的价值 = 提前展示版面结构；尺寸/位置与真实卡片不一致会造成布局跳动，反而扣分。"帧式骨架"（只有页头页脚 + 空白）等于没有进度信息，不要用 | NN/g · Skeleton Screens 101 | [官方文档] |
| **分层流式：先出壳，再补内容** | Suspense/流式渲染的官方口径：立即给出 loading 状态 → 内容完成后自动替换；**共享布局保持可交互**；导航可中断 | Next.js `loading.js` 文档 | [官方文档] |
| **首屏不阻塞在"规划结果"上** | Transit 主界面是"离站看板"（`GO in X minutes`），先回答"我这一站下一班什么时候来"，路线结果在二级页面 | seattlebuses 对比评测 | [二手] |
| **规划=先选方案，再开始导航** | Moovit 三段式：搜索目的地 → **选一条路线** → 点 Start / Navigate 进入 Live Directions（帮助中心不同版本文案不一致，语义一致）。规划结果是一次性完整返回的列表，不是流式补全 | Moovit 帮助中心 · Plan a Trip / Live Directions | [官方文档] |
| **GO 依赖"已规划好的行程"** | Citymapper 的 GO 是"对已有 trip 的实时副驾"：先有 trip，再 hit GO，进入逐步导航视图 | Citymapper · GO 介绍页 | [厂商博客] |
| **规划结果页的信息组织** | 高德 PC 端：输入起终点 → 自动计算 → 结果页给方案列表（距离、预计用时、红绿灯数）+ 点选高亮 + 偏好切换（推荐/躲拥堵/少收费） | 高德地图帮助中心 · 路线规划 | [官方文档] |
| **等待期文案** | 高德/百度/Google 在 App 内的**逐字加载文案**，公开文档未收录 | — | [未验证] |

补充说明（诚实标注）：主流地图 App 在"输入起终点 → 出结果"这段的**具体文案与是否有分步提示**，官方文档均未公开，我也没有做录屏取证，因此不下结论。可确认的是**结构性事实**：Apple/Google 的设计规范要求"先给点东西"，NN/g 要求"按时长升级反馈"。

### 1.2 对本项目的可借鉴点

1. **把"一种等待表达"升级成"三段式"**。现状只有骨架 + 不确定进度条，缺少"升级路径"。按 NN/g 的门槛可分三段：<300ms 什么都不显示（避免闪烁）→ 300ms~3s 骨架 + 一句人话文案 → >3s 在骨架之上叠加"进行到哪一步"（例如"正在取候选路线 → 正在取实时到站 → 正在算步行"），并把已完成的部分**先渲染出来**。
2. **"部分结果先出"在本项目有天然抓手**。卡片是按线路组织的，`mergeCardsStable` 已能"只刷数字、不换顺序"；因此可以先把**结构**（线路号、上车站、下车站、步行距离）落地，把**会变慢的数字**（实时到站、总时长）留空并标"计算中"。这与 Next.js 的 Suspense 分层是同一思路，不需要改架构方向。
3. **等待期必须可操作**。Apple 的原话是"让人在等待时能做别的事"。本项目最低成本的落实：搜索面板不做全屏遮罩，地图仍可拖动缩放、起终点仍可改；一旦用户改条件，旧请求作废。这比"加一个取消按钮"更符合"用户在手机上其实是边走边查"的场景。
4. **文案要写"正在干什么"，不要写"加载中"**。NN/g 的结论是进度感来自"系统在工作"的可感知证据。对一个公交产品，最有信息量的一句话是"正在查 XX 站下一班车"。

### 1.3 不建议照搬的做法

| 做法 | 为什么不适合本项目 |
|---|---|
| 10 秒以上的百分比进度条 | 本项目请求是"几路并发 + 数据库查询"，没有真实百分比可算；假进度条一旦走满但结果没来，信任损失比不显示更大。用"步骤名 + 已完成步骤打勾"更诚实 |
| 骨架屏无限延长 | 若最终失败，长时间骨架会让用户以为"再等等就好"。必须有"超过 N 秒仍未出结果"的兜底（降级为"用估算值先出一条方案"或明确报错） |
| Moovit 式"必须先选路线才能导航" | 本项目的核心卖点是"全自动上下车"，把导航入口绑在"先规划"上会退化成普通地图 App，且与需求③冲突 |
| 把路线结果做成一次性"all or nothing" | 这是现状问题的根源之一。用户等待的是"第一张能看的卡"，不是"全部卡" |

## 2. 维度二：断网 / 切换网络 / 切后台的处理

### 2.1 先说平台硬约束（这一条决定产品只能做"恢复"，不能做"维持"）

| 事实 | 依据 | 等级 |
|---|---|---|
| 页面隐藏时，浏览器**停止发 `requestAnimationFrame`**、**节流 `setTimeout`**；隐藏超过 30s 后进入预算节流（Chrome 为 10s 起） | MDN · Page Visibility API（"Policies in place to aid background page performance"） | [官方文档] |
| `visibilitychange` 是唯一可靠的"回到前台"信号；`blur/focus` 不可靠（不等于页面被隐藏） | MDN · Page Visibility API | [官方文档] |
| Web 平台**没有**"始终允许"的后台定位；页面隐藏/锁屏后 `watchPosition` 停止，Service Worker 也拿不到定位 | 从业者长文 + iOS PWA 能力盘点（两篇互相印证） | [二手] |
| `navigator.onLine` **"本质不可靠"**：连上局域网就算 online，可能根本没有外网；官方建议"只用来给提示，不要据此禁用功能" | MDN · Navigator.onLine | [官方文档] |
| 定位失败有三类可区分原因：`PERMISSION_DENIED(1)` / `POSITION_UNAVAILABLE(2)` / `TIMEOUT(3)`；`message` 字段仅供调试，**不应直接展示给用户** | MDN · GeolocationPositionError | [官方文档] |

结论：**"断网时继续实时导航"在产品上是不成立的承诺**（PWA 做不到）。可行目标只有一个：**回到前台 / 网络恢复后，5 秒内让画面重新可信，且不让用户看到一次跳跃式错乱**。

### 2.2 行业做法清单

| 做法 | 具体表现 | 来源 | 等级 |
|---|---|---|---|
| **把"定位陈旧"做成一等状态** | Mapbox 导航 SDK 的路线进度状态枚举里，除 `LOCATION_TRACKING` 外还有 `LOCATION_STALE`（"定位更新缺失导致对进度失去信心"）与 `ROUTE_UNCERTAIN`（"已在跟踪、但路线吸附暂时失去信心"）；**UI SDK 会按状态更换定位图标的绘制样式**，且提供 `staleStateTimeout` 配置"多久没更新算陈旧" | Mapbox · Route progress / LocationComponentOptions | [官方文档] |
| **定位不确定用"圈"而不是"文字"** | Google 地图：浅蓝圆 = 位置不确定，圈越小越确定；**蓝点变灰 = 找不到当前位置，改为显示"上次到过的位置"** | Google 地图帮助中心 · 定位精度 | [官方文档] |
| **区分"我的位置过期"和"精度低"** | 同上帮助页的排查表把 `Location is out of date`（→关飞行模式）与 `Location accuracy is low: weak GPS/Wi-Fi`（→换位置）**分成两条**，处理建议不同 | 同上 | [官方文档] |
| **区分"车辆数据停更"** | 百度实时公交 SDK 回调里有 `onGetLocationTimeOut`，文档定义为"**查询后 5 分钟没有更新实时位置**，且没有调用停止接口" ⇒ 厂商把"数据源停更"当作独立事件，而不是网络错误 | 百度地图开放平台 · 实时公交查询 | [官方文档] |
| **不依赖 online 标志做功能开关** | MDN 原文建议"只提供提示，不要基于在线状态禁用功能" | MDN · Navigator.onLine | [官方文档] |
| **断网时的具体横幅文案** | Google/高德/百度在导航中的断网提示原文，未取得一手材料 | — | [未验证] |
| **回前台是否"补一帧"、是否有跳动** | 各厂均未公开；Mapbox 只提供了"定位动画时长倍率"这类平滑参数 | Mapbox · LocationComponentOptions | [未验证] |

### 2.3 对本项目的可借鉴点

1. **引入"两个独立的新鲜度"而不是一个"报错"。** 现状把"定位不动"和"车辆不动"混在一起，用户只看到"卡住了"。行业做法是分开：
   - **我的定位**：正常 / 精度差（给圈）/ 陈旧（灰点 + "定位暂停"）/ 权限拒绝（明确文案 + 引导）；
   - **车辆数据**：正常 / 陈旧（"最后更新 32 秒前"）/ 失联（"暂时取不到车辆位置"）。
   两个维度组合出 6~9 种状态，但用户只需看懂 3 种视觉结果：正常、降级可用、不可用。
2. **用"最后更新 X 秒前"代替"实时"。** 这是最省成本、也最诚实的一招。项目的 ETA 本来就有"区间/约"的表达习惯，加一个"最后更新"时间戳与之同构，且能被真机验证（截图即可断言）。
3. **回前台的恢复协议要有明确顺序**，这是产品可验收的行为，不是技术细节：`visibilitychange → visible` 时，(a) 立刻补一帧定位、(b) 立刻重取车辆位置、(c) 用平滑过渡把蓝点挪过去而不是瞬移、(d) 卡片**顺序不动**、只更新数字。第 (d) 条尤其重要：用户回到前台时看到的第一个变化如果是"卡片换了位置"，会直接判定为"又乱了"。
4. **网络切换不当作事件，当作"下一次请求可能失败"的常态。** 由于 `onLine` 不可靠，产品侧不应该有"检测到断网 → 进入离线模式"的显式切换；应该是"请求失败 → 保留旧数据并标注陈旧 → 退避重试"。用户视角只有一句话："有点卡，但还能用"。
5. **权限拒绝必须与"没信号"分开说。** `PERMISSION_DENIED` 用户自己可修（去设置里打开），`POSITION_UNAVAILABLE` 用户修不了（隧道/室内）。同一句"定位失败"会浪费用户一次无效排查。

### 2.4 不建议照搬的做法

| 做法 | 为什么不适合 |
|---|---|
| 断网后弹模态框 / 强制打断导航 | 巴士乘客在车上往往只有几秒注意力，模态框要求"确认"是纯负担。用非阻塞的细条 + 图标降级即可 |
| 学 Google 的"位置过期就切到停车/步行模式" | 本项目没有多模态回退，切换模式会造成语义混乱（用户明明在车上） |
| 把 `navigator.onLine` 当作开关做"离线模式" | 官方文档明确说它不可靠；且本项目离线时没有可用数据，做"离线模式"是空承诺 |
| 后台持续高频轮询"保活" | 平台会节流，且违背项目既有的 DSAT 调用纪律（见项目风险规则：页面打开才查、关闭即停） |

## 3. 维度三：公交/地铁场景的「我在哪辆车」

### 3.1 行业做法清单

| 做法 | 具体表现 | 来源 | 等级 |
|---|---|---|---|
| **打开即"猜"你在哪辆车上（不要求先规划）** | Transit 的 AutoGO：**"你一打开 Transit，我们就猜你正在哪辆附近的车上。猜对了就提示你立刻开始一次 GO"**；目标是"去掉学习成本"；已有 100 万+ 次 GO 是由 AutoGO 启动的 | Transit 官方博客 · How we turned public transit into a multiplayer game | [厂商博客] |
| **"中途已经在车上"被明确列为支持场景** | Transit 5.17.21 发布说明：现在可以在**"你已经坐在车上的时候"**匹配到车辆，**一次点击**就能开始 GO，"不用先规划行程、也不用手动选线路" | Transit 发布说明（经市政网站与镜像页转载） | [二手] |
| **猜错时的成本设计 = 一次点击** | AutoGO 的产品取舍是"我先猜 + 你一键确认/否掉"，而不是"给你一个候选列表让你认车牌" | 同 Transit 博客 | [厂商博客] |
| **用运动特征确认"你确实在车上"** | Transit 工程博客描述：用加速度计做运动分类，区分"走路（约 2Hz）"与"乘车（约 5Hz）"，用机器学习判定"是否在移动的车厢里"，以此在**没有可靠 GPS**（地铁隧道）时也能推断位置 | Transit 工程博客（原文链接已 404，见转载全文） | [二手] |
| **"先规划再导航"是另一派的做法** | Citymapper 的 GO 依赖已存在的 trip；Moovit 的 Live Directions 必须先选路线 | Citymapper / Moovit 官方页 | [官方文档] |
| **用"站点订阅"替代"车辆身份绑定"** | 百度实时公交 SDK 提供"指定站台**订阅上车提醒**、指定站台**订阅下车提醒**" | 百度地图开放平台 · 实时公交查询 | [官方文档] |
| **车辆位置是"参考图层"，不是"绑定对象"** | 高德把"车辆动态 / 实时公交"做进路线步骤里的按钮，点开是车辆位置图层，而不是要求用户"确认我上了哪辆车" | 第三方教程（未获官方文档确认） | [二手] |
| **纠错是否提供"换车/车牌选择"** | 未找到任何主流产品公开"不是这辆 → 循环切换候选"的交互 | — | [未验证] |

### 3.2 用户心理：什么情况愿意多点一下，什么情况必须全自动（推断，标注依据）

这一节没有直接的行为学研究，以下是**基于行业产品取舍的推断**，请在真机上验证：

1. **"确认"可接受，"辨认"不可接受。** AutoGO 让用户做的是"是 / 不是"（一次判断），成本是一次点击；而"从候选里认出我的车牌"要求用户抬头看车、记住车牌、在手机上比对——车上拥挤、站牌背光时做不到。这解释了为什么"不是这辆 → 点下一个"在本项目会失败：它把"确认"退化成了"逐条辨认"。
2. **决策窗口在关门前后那几秒。** 用户上车后 3~10 秒内注意力在"找位置、刷卡、站稳"，任何需要读文字的交互都会被打断。因此"自动 + 事后可撤销"优于"上车前先选"。
3. **错误必须"可撤销且不计成本"。** 如果纠错需要三步（打开面板 → 找换车 → 选车牌），用户会直接放弃整个导航功能，而不是纠正它。行业普遍把"退出/重来"作为最后兜底，而不是把"逐条切换"当主路径。
4. **全自动失效时，用户的真实反应是"不再信任自动"。** 因此"手动入口"必须常驻可见，而不是藏在二级菜单——这与项目 ADR-108 的结论一致（漏判上升用"明示 + 手动入口 + 可断言钩子"承接）。

### 3.3 对本项目的可借鉴点

1. **把"匹配"从"选候选"改成"猜 + 一次性确认"。** 用户已经在车上时，最有信息量的信号不是"上车站附近有哪几辆车"，而是"我正沿着这条线路在移动"。这正是 ADR-108 已经确立的方向（定位主导），但**还缺一个"从当前移动状态反推车辆"的入口**：现在是"先判上车、再绑车辆"，而需求③的场景是"人已在车上，系统却还在等上车判据"。
2. **纠错入口改成"我不是这辆 → 从当前线路的在途车里选一辆"。** 现实现的"换候选第 1"在语义上是"帮我翻页"，不是"让我指出正确的车"。可选做法：按与用户当前位置的距离排序、显示"车牌 + 距我 N 米 + 还有几站到我的下车站"，最多 3 个；仍不允许自由输入车牌（澳门车牌对用户不是记忆项，输入成本高于选择成本）。
3. **给"未确认"一个体面的状态。** AutoGO 的话术是"猜对了就提示开始"；猜错/猜不出时应该明确"没认出你在哪辆车上"并给手动入口，而不是让用户停在"正在检测车辆"（现状 `NavTrackBar.tsx:110` 的硬编码文案已被 ADR-108 点名）。
4. **把"站台订阅"作为降级路径。** 百度用"订阅上车/下车提醒"绕开了"识别车辆"这个难题。本项目可以保留一个纯站台维度的兜底：即使不知道车牌，也能给出"你这一站下一班几点 + 到你的下车站还有几站"。

### 3.4 不建议照搬的做法

| 做法 | 为什么不适合 |
|---|---|
| 让用户从候选列表里认车牌（含"下一辆"翻页） | 这是现状失败的直接原因：车上无法辨认车牌；且候选基于"上车站附近"，用户离站后排序失效 |
| 手动输入车牌 | 澳门巴士车牌不是用户记忆项，输入成本高于收益；还引入输入校验与错误匹配风险 |
| 用加速度计做运动分类（Transit 路线） | Transit 的目的是"在没有 API 数据时生成众包定位"；本项目有 DSAT 官方车辆位置，做传感器分类投入产出比低，且 Web 端传感器精度/权限不可控 |
| 要求"先规划行程才能开始导航" | 与需求③场景（已在车上）直接冲突 |

## 4. 附带说明：需求④（隐藏步行速度分档）的行业参照

这一项不是"要不要做"，而是"做到哪一层"。行业没有"隐藏速度档"的现成案例，但有一条通用原则可参照：**信息分层 = 拿走判断，保留结果**。

- 现状：`TierBadge` 的同一个胶囊里，"档位色 + 档位文案"与"可赶上 HH:MM"共用槽位（`RoutePieces.tsx:29` 注释、`:81` 的 `rc-tier--{tier}`）。
- 由此产生一个容易被忽略的问题：**若只删文案、保留色块，"隐藏"就只是换了个通道**——用户仍然能看到"这班要跑"的暗示（颜色梯度），而色觉障碍用户反而丢失了信息（原来有文字兜底）。这与"不想让用户被评判走路速度"的初衷相悖。
- 参照做法：结果型提示保留且唯一化——只保留"可赶上 18:40 那班"（有真实时刻才出现），速度语义不再单独成标签；胶囊在导航三态中退化为中性样式（不编码档位）。**是否连颜色一起去掉，是需要拍板的问题（见 Q6）。**

## 5. 决策问题清单（待负责人拍板）

> 每条格式：问题 → 为什么问 → 选项（短标题 + 完整说明）→ 推荐 → 理由。
> 这些问题会直接决定架构与设计的工作量，因此建议在技术方案冻结前定。

### Q1 路线结果的呈现方式：是否允许"部分结果先出、再原地刷新"？

**为什么问**：这是"加载慢"的两种解法——"让等待变短"（性能）和"让等待不难受"（呈现）。只做性能，用户仍会在慢网络下看到空白 6 秒；只做呈现，慢网络下会出现"数字先给后改"的可信度问题。两者都要做，但**先后与边界必须定**。

- **选项 A｜分层出结果**：先出卡片结构（线路、上下车站、步行距离）+ 灰字"正在取实时到站"，实时数字到位后原地补上，卡片顺序不变。用户第一眼就有内容。
- **选项 B｜维持骨架屏，只加文案与取消**：等到全部数据齐了再一次性出卡，但骨架期给分步文案（"正在取实时到站…"）+ 可取消。
- **选项 C｜估算优先**：先用历史规律给一个"约 X 分钟"的结果，实时数据到了再改成精确值，并标注"估算/实时"。

**推荐**：A 为主、C 作为兜底（超过 N 秒没拿到实时数据时，把"约 X 分钟（估算）"顶上），B 的文案与取消作为基础层一并做。

**理由**：NN/g 的门槛说明"1 秒后用户就需要系统在工作的证据"，而本项目的慢点在"实时数据"这一段，不是"有没有路线"；Apple 的规范也要求"先给占位内容、到位再替换"。A 能复用既有的 `mergeCardsStable`（只刷数字不换顺序），风险最低。C 单独用会有"数字改两次"的信任成本，只适合当兜底。

### Q2 用户等待多久算"失败"？超时后给什么？

**为什么问**：如果没有超时兜底，"分层出结果"会退化成"永远转圈但永远不报错"，这比直接报错更伤。超时阈值还决定服务端要不要做"快速失败"。

- **选项 A｜8 秒**：8 秒未出首屏可用结果 ⇒ 降级为估算结果 + 一条"实时数据暂时取不到"的提示，后台继续重试。
- **选项 B｜15 秒**：给足重试机会，但用户已经离开。
- **选项 C｜不设超时**：一直等到成功。

**推荐**：A（首屏可用结果 8 秒；单次请求 15 秒硬超时后报错并给重试）。

**理由**：NN/g 的 10 秒注意力极限；且本项目典型的"两手准备"（实时 + 估算）已经存在，降级是有内容可给的，不需要空手报错。

### Q3 断网/切后台的表达：是否引入全局"新鲜度"状态？

**为什么问**：现状是"某个数字不动了"，用户无法归因。要做"最后更新 X 秒前"，就必须决定它是**一个数字**、**一个图标状态**，还是**一整条顶部提示**——三者的工作量与视觉侵入度差别很大。

- **选项 A｜双维度状态机，弱视觉**：定位（正常/精度差/陈旧/权限拒绝）× 车辆数据（正常/陈旧/失联），只用一个**小图标 + 一行灰字**（"最后更新 32 秒前"）表达，不弹条、不遮罩。
- **选项 B｜单一"离线/在线"条**：只要是请求失败就出顶部灰条"网络不稳定"，恢复即消失。
- **选项 C｜什么都不加，只保证恢复**：不加任何状态表达，只做"回前台自动补齐"。

**推荐**：A。

**理由**：Mapbox 官方 SDK 把 `LOCATION_STALE` 当一等状态并据此换图标；Google 用"灰点 + 上次位置"表达同一含义；百度把"5 分钟没更新"单独定义为一个回调。三家一致的做法都是"区分两种失效"，而 B 把两种失效合成一种（用户仍然不知道是"我的位置没动"还是"车的位置没更新"），C 会让用户把"数据旧"误判成"产品坏了"。

### Q4 回到前台时，画面允许"跳"吗？

**为什么问**：这是最容易被忽略但用户最敏感的一点。补帧必然带来坐标变化；如果卡片同时重排，用户会觉得"整个页面乱了一下"。

- **选项 A｜只跳蓝点，不跳卡片**：定位用 300ms 左右平滑过渡过去，卡片只更新数字、顺序与结构不动；若阶段判定发生变化（例如"候车→乘车"），用一个明确的过渡提示告知，而不是悄悄改。
- **选项 B｜静默重排**：允许卡片按最新数据重新排序（可能换位），不做提示。
- **选项 C｜弹提示再刷新**：回前台先弹"数据已更新，是否刷新"，用户点才更新。

**推荐**：A。

**理由**：Apple/NN-g 的"避免布局跳动"原则；且本项目既有 `mergeCardsStable` 就是"保留旧顺序、只覆盖数字"的设计意图，A 与既有实现方向一致。C 把恢复的责任推给用户，在"上车后 3 秒注意力窗口"里最不可行。

### Q5 上车后开始导航的匹配：全自动 + 事后纠错，还是自动 + 一次确认？

**为什么问**：需求③的诉求是"全自动、不要候选列表"，但完全无确认的自动有一个必然结果：猜错时用户只能依赖纠错入口，而纠错入口是"事后"的。是否给"一次轻确认"决定了错判的止损速度，也决定交互工作量。

- **选项 A｜静默自动 + 常驻纠错**：系统直接进入"乘车中"，不打断；纠错入口常驻（"不是这辆 / 我没上车"）。
- **选项 B｜自动 + 一次性确认条**：判定后出一个 2.5 秒自动消失的轻提示"26 路 · MW-12-34，对吗？"，不点即为默认正确；点了就进入换车选择。
- **选项 C｜自动 + 薄候选（最多 2~3 辆）**：给出"你可能是这几辆"，让用户点一个。

**推荐**：B。

**理由**：Transit 的 AutoGO 是"先猜，猜对了提示你开始"——**猜本身就是一次显式确认**，只是做得极轻（一键）。A 的问题在于猜错时用户毫无察觉（继续按错车算到站，风险是把人坐过站）；C 已经接近用户明确否掉的"候选列表"。B 取中间：不打断、但给一次 2.5 秒的撤销窗口，符合"确认可接受、辨认不可接受"的推断（§3.2）。

**同时建议明确纠错的形态**（附注：这属实现约束，不是产品决策）：纠错应从"换候选第 1"改为"从**当前线路在途车**里按距离排序选一辆，最多 3 辆，显示车牌 + 距我 N 米 + 还差几站到我的下车站"，且不再支持自由输入车牌。

### Q6 隐藏速度分档时，颜色要不要一起去掉？

**为什么问**：用户要的是"别评判我走路快慢"。如果只删文案保留颜色梯度，等于把信息挪到颜色通道——用户仍能感知"这班要跑"，色觉障碍用户反而失去兜底。这是"是否真的达成目的"的问题。

- **选项 A｜文案与颜色一起去掉，只留时刻**：导航三态中该胶囊退化为中性（不编码档位），只显示"可赶上 18:40 那班"；没有真实时刻时不显示任何赶车提示。
- **选项 B｜只去文案，保留颜色**：视觉上仍能区分"轻松 / 要跑"。
- **选项 C｜整体去掉该胶囊**：导航三态里连"可赶上 HH:MM"也不要。

**推荐**：A。

**理由**：与需求原文一致（保留"可赶上 HH:MM"、去掉档位）；且避免"隐藏只换了通道"的自欺。C 会丢掉用户真正需要的决策信息（那班车几点），不建议。

**需一并确认的边界**：仅在"到站 / 等车 / 上车后"三态隐藏，还是**推荐列表与详情页也一并隐藏**？（推荐列表是"选方案"阶段，速度档在那里是决策依据；导航中是"执行"阶段，才是评判感最强的地方。建议只改导航三态，列表保留。）

## 附：观测钩子契约（advisory · 交架构评估，非本轮阻断项）

> 目的：让"数据陈旧""匹配失败"这类缺陷在自动化里**可见**。现状探针只断言 pageerror 与 HTTP 状态，这两种缺陷完全隐形（测试已把这条列为纪律，见 `03-测试-基线测量与场景复现.md` §4）。
> 约定：只读、字符串、挂 `body` 或既有容器；**只表达事实，不表达视觉**（视觉未拍板，绑视觉会让用例随视觉一起红）。

### A1 定位维度（维度 A）

| 钩子 | 取值域 | 语义 |
|---|---|---|
| `body[data-geo]` | `ok` / `low_acc` / `stale` / `denied` / `unavailable` / `timeout` | `stale` = 曾拿到过 fix 但超阈值无新帧；`unavailable` = 从未拿到或直接报错；`low_acc` 与 `stale` 正交，同时发生时 `low_acc` 优先 |
| `body[data-user-fix]` | `"ts,acc"`（整数秒, 整数米） | 每次 accept 的 fix 写入；**不写经纬度**（断言只需 ts/acc，坐标可用 `.user-dot` 屏幕位移替代，避免把用户坐标留在 DOM 里） |

### A2 车辆数据维度（维度 B）

| 钩子 | 取值域 | 语义 |
|---|---|---|
| `body[data-veh]` | `fresh` / `stale` / `failed` / `open` | `open` = 熔断中 |
| `body[data-veh-age]` | 整数秒 | 距最后一次成功取数的时长；停更时递增，成功即归零 |
| `body[data-veh-fail]` | 整数（可选） | 连续失败次数 |

**明确不做 `data-net`**：`online|offline|stale` 把两个轴合成一个值，会诱导实现写"offline 就不显示实时"的耦合；且 MDN 已明确 `navigator.onLine` 本质不可靠，把它升格为可断言状态等于给它背书。网络故障只以 `data-veh=failed` 体现，"是否偷依赖 onLine"则用「`navigator.onLine === true` 且 `data-veh === failed`」这个组合来断言。

参数约束（只给边界，具体值由架构定）：`stale` 阈值 **> 2×POLL_MS（12s）且 ≤ 90s**，否则正常抖动会误报。

### A3 车辆匹配（需求③，目前完全无钩子）

| 钩子 | 取值域 | 语义 |
|---|---|---|
| `.nav-actions[data-board-match]` | `none` / `auto` / `confirmed` / `corrected` / `manual` | `auto` 与 `confirmed` 必须可区分，否则测不出"一次性确认条是否出现过" |
| `.nav-actions[data-match-source]` | `gps` / `gps+vehicle` / `manual` | ADR-108 已禁止纯 `vehicle`，此钩子可直接断言"不得出现" |
| `[data-switch-list]` + `[data-switch-count]` | 条目 / 整数 | 断言"最多 3 辆、按距离排序" |
| `[data-switch-reason]` | `wrong_vehicle` / `not_boarded` | 区分两种纠错入口 |

### A4 组合语义（建议升为独立验收项）

**定位不可用 ≠ 导航不可用**：

- 维度 A 坏、维度 B 好 ⇒ 仍须显示"还有 N 站 / 约 X 分钟"与自动下车提醒，只是无蓝点、无沿线跟随、`data-board-detect=paused`；
- 维度 A 好、维度 B 坏 ⇒ 定位跟随正常，到站数字降级为"最后更新 X 秒前"，不得继续显示"实时"；
- 两轴同时坏 ⇒ 才允许"导航不可用"级表达，且保留手动下车入口。

反例风险：实现常见做法是"任一维度失败 ⇒ 整页降级"，这会把"没定位但在车上"的用户直接推进不可用状态。

### A5 开屏动画（开屏/加载动画线新增，含互斥规则）

> v2（2026-11-02 负责人裁决后修订）：开屏改为**每次页面加载都播**，版本门方案全部作废 ⇒ 不再有任何 cookie/localStorage 记账钩子。
> v3（同日终裁）：枚举 **4 值** `playing / skipped / done / reduced`。挂载点定根 `layout.tsx`、`sessionPlayed` 标记已删除 ⇒ 客户端路由不重挂、bfcache 还原时容器已移除 ⇒ **无任何场景需要"已播但未播"标记，`blocked` 删除**。

| 钩子 | 取值域 | 语义 |
|---|---|---|
| `body[data-splash-state]` | `playing` / `skipped` / `done` / `reduced` | 开屏动画生命周期（纯客户端页面生命周期轴；与 A1/A2 的定位、车辆数据轴正交） |
| `[data-splash-root]` | 属性存在性（覆盖层唯一实例） | splash 覆盖层容器的**专用钩子**，专供选择器定位；跳过/播完后移除，`document.querySelector('[data-splash-root]')` 必须为 `null`。**不得复用样式类**做定位（样式类会随改版重命名，钩子不会）。**因退出末帧带 `pointer-events: none`，遮挡缺陷"完全无感"——每例 setup 后断此钩子为 null 是唯一抓手，不可省** |
| `[data-loader-root]` | 属性存在性 | 加载态（小尺寸循环 + 分步文案）容器专用钩子。**补于 2026-11-02**：原实现只有样式类 `.brand-loader` + `role="status"`，导致 P7（动画结束但内容未就绪须接加载态）无法机验 |
| `[data-loader-mode]` | `loop` / `static` | 加载态形态（`loop` = 循环动画；`static` = 将来静态呼吸变体）。**不设 `data-loader-state`**：该属性会恒为 `"loading"`（`!active \|\| !visible` 时组件 `return null`，"未加载"在 DOM 里没有节点），断言它永远绿、零信息量 |
| `[data-loader-slot]` | `map-cover` / `request`（**以实现为准，2026-11-02 修正**：原稿写 `boot`，实现取 `map-cover`） | 消歧用：`map-cover` = 地图容器内 loading 位（`.nav-map__cover` 内，随地图 `phase === "loading"` 出现）；`request` = 原生文行左侧内联位（带 label）。目前只落了 `map-cover` 一处，`request` 预留。未来两处同时存在时，断言必须指定 slot，否则 `querySelectorAll('[data-loader-root]').length` 含混 |
| `body[data-app-version]` | 构建期注入的版本字符串 | 保留（架构裁定）。只读、零运行时成本，用于验收脚本记录版本与线上排障；**不参与任何门判定**，P 组用例不依赖它 |

**互斥优先级（必须成文，否则断言会抖）**：`skipped > done > reduced > playing`，仅约束**同一挂载实例内**的终态竞争。

- 用户点击跳过 ⇒ `skipped`（无论是否 reduced-motion）；
- reduced-motion 下正常结束 ⇒ `reduced`（"播完"这个事实对 reduced 用户没有区分意义）；
- 正常播完 ⇒ `done`。
- 暖启动 / 应用内客户端路由均不产生挂载，验收只断言 `[data-splash-root]` 不出现、且 `playing` 全程只出现一次（见 06 P1c/P2）。**无 `blocked` 值**——挂 layout 后无场景需要它。

**已播标记：一条都不留（2026-11-02 终裁）**。挂载点定在根 `layout.tsx` ⇒ 客户端导航不重挂是**结构事实** ⇒ 不需要任何"已播标记"。全部禁止：内存变量、sessionStorage、cookie、localStorage。理由：① 持久化媒介会跨加载留存，构成真正的频次控制；② 内存标记（`sessionPlayed`）是 `next dev` 下遮挡层永不移除的根因（StrictMode 双调用时第二遍 effect 提前返回，跳过监听与兜底重建）；③ 代码里不留可用钩子，将来想加回去必须新写代码——这是 P10 防回潮的实现层保障。注意：若有人把挂载点挪回 `page.tsx`，客户端路由就会重播，届时才需要标记，而标记会带回 StrictMode 类缺陷 ⇒ **不要挪回去**。

**配套断言规则（缺一不可）**：

1. 跳过时 splash 容器必须从 DOM **移除**（禁止 `visibility:hidden` / `opacity:0` / `pointer-events:none`）。「点击后 100ms 内首屏可交互」的断言 = `data-splash-state === "skipped"` **且** `document.querySelector('[data-splash-root]') === null`。单靠状态值证明不了遮挡层已不在。
2. **负向断言（防回潮）**：页面加载完成后，**cookie / localStorage / sessionStorage 三者**均不得新增任何开屏相关键——加载前后快照 diff 应无可归因于开屏的变化。**sessionStorage 是重点**（同 tab 跨刷新保留，最像"内存标记"实则破坏"每次都播"）。这条替代了原「版本键必须带版本」纪律：现在没有持久标记，任何重启记账逻辑的改动都应在这一条上被判红。
3. 保留通用纪律（对将来任何「是否做过 X」的标记仍适用）：**持久标记的键里必须带版本，禁止裸布尔**——本次开屏不需要持久标记，故不适用，但这条纪律不撤销。
