### ★ 我新增的两条关键复核（改写选型结论）

**复核 A：`detail.reload()` 对纵条数字是 no-op。**

`buildStrips` 的两个数字来源决定了这一点（`src/lib/nav/strips.ts`）：

```ts
// :78  逐跳分钟 —— 时段桶静态（5 桶），桶不变则输出逐字节相同
minToNext: hop ? hop.minutes : 0,     // hop = lookupHop(segIdx, route, from, to, nowBucket)

// :111-118  换乘等车 —— 来自**客户端 POST 上来的 card**
const transferAfter = t ? { ... waitMin: t.waitMin ?? null } : null;
```

而 `detail-body` 的 `card` 是**客户端传回来的那一份**（`detail-body/route.ts:169` `body?.card`、`:201-207` `buildStrips(card, …)`）。

⇒ `reload()` 前后：`waitMin` 来自同一份 card ⇒ **完全不变**；`minToNext` 只在跨 5 桶边界时才可能变。
⇒ **「静默 reload 拿最新 minToNext 修正」在绝大多数时刻是 no-op**。前端 1-C 的这一半假设不成立。

**复核 B：`detail.reload()` 会**把地图彩段清空再重建**，不是"静默"。**

`useRouteOverview.ts:84-89`：

```ts
if (!open || !card || detail.phase !== "ready" || !legsInput) {
  setLegs([]); setBox(null); setGeomReady(false); return;
}
```

`reload()` 使 `useDetailBody` 置 `phase="loading"`（`useDetailBody.ts:76`）⇒ 上面分支命中 ⇒ `legs=[]`、`box=null`。
而取景 effect 的依赖含 `frameBox`，`frameBox` 又依赖 `ov.box`/`ov.legs`（`NavShell.tsx:802-806`、`:845`）⇒ `box=null` 时执行 `frame({ mode: "none" })`（`:840`），回来后再 fit 一次。

⇒ **1-C 的"不闪骨架"只对了文字部分；地图会**先清线、放弃取景、再重画重取景**（一次可见的跳动）。这比闪骨架更糟 —— 用户在导航中被地图跳视野，会以为定位漂了。

## 1. 三问回答

### Q1：三者能否满足「纵条每段也一起刷、整屏一致」？

**先看纵条的数字到底由谁算**（这是判据，不看这一点就是在猜）：

| 纵条上的数字 | 数据源 | 活/死 | 代码 |
|---|---|---|---|
| `车上约 N 分` | `strip.rideMin` ← `card.rides[i].minutes` | **死**（规划时算定） | `NavStrip.tsx:171-182`、`types.ts:804-805` |
| 换乘行 `等车约 N 分` | `strip.transferAfter.waitMin` ← `card.transfers[i].waitMin` | **死** | `strips.ts:111-118`、`NavStrip.tsx:112-114` |
| 逐站 `N 分` | `stops[k].minToNext` ← `lookupHop(..., nowBucket)` | **半死**（只在跨时段桶时变） | `strips.ts:78`、`NavStrip.tsx:138-141` |

★ 另外一条常被忽略的事实：**导航态下逐站 `N 分` 根本不显示** —— `NavStrip.tsx:138` 的条件是 `!end && s.minToNext > 0 && !nav`，有 `nav` 时整块隐藏。导航中用户看到的纵条数字只有 **`车上约 N 分`** 与 **换乘行 `等车约 N 分`**，两者都是死值。

**逐候选判定：**

| 候选 | 纵条能刷吗 | 整屏一致吗 | 为什么 |
|---|---|---|---|
| **1-A 客户端纯函数** | **不能** | **不能（假一致）** | 派生层只能替换 `NavDetailBody.tsx:278`（`card.totalMin`）与 `:282`（`macarriveAt`）这两处。纵条数字在 `ov.body.strips` 里，是**服务端 `buildStrips` 产物**；客户端要重算它需要 `lookupHop`（`SegmentIndex` 来自 DB 静态索引）与 `headwayAt`（`HeadwayIndex` 来自 `route_frequency` 表，`loadHeadway` 是 `async (pool: Pool)` ⇒ **server-only**，`headway.ts:72`）。⇒ 顶部倒计时在动、纵条 `车上约 12 分` 不动 = **一眼可见的自相矛盾** |
| **1-B 服务端端点** | **能（但必须返回整份 strips，不是只返回一个总时长）** | 能 | 服务端同时握有 `segIdx`（`loadStatics`）、`headway`（`loadHeadway`）、到达时刻 ⇒ 唯一能在服务端把「下游候车按到达时刻重估」算出来的地方 |
| **1-C 派生 + 静默校准** | **不能** | 不能 | 见复核 A（reload 对 strips 是 no-op）+ 复核 B（reload 会清地图线并放弃取景） |

**⇒ 结论：只有 1-B 能满足"纵条每段一起刷、整屏一致"，且 1-B 的响应体必须是「整形替换 `strips`」，不能是「一个 `remainingMin` 数字」。**
若 1-B 只返回总时长，它就退化成 1-A 加一次往返，同样不满足负责人已拍板的"整屏一致"。

### Q2：「会话起始时刻」怎么落地？—— 我的结论：**不要引入它，用 `card.arriveAt` 当锚点**

前端把「缺失输入：会话起始时刻」列为前置依赖，但**这个依赖是可以消掉的**：

```
model.ts:817   totalMin = (cursor - nowMs) / 60_000
model.ts:879   arriveAt = cursor
⇒ 规划时刻 = arriveAt - totalMin * 60_000
```

即 **`arriveAt` 本身就是绝对锚点**，`剩余 = arriveAt - now` 直接可算，**零新增 state**。

| 场景 | `arriveAt` 锚 | 「新加 sessionStart」锚 |
|---|---|---|
| 单页会话内导航 | 正确（常量，不参与时钟） | 正确（需维护 ref） |
| 页面刷新 | **天然安全** —— card 丢失（`useDetailBody.ts:18` 注释「card 直传，不经过 planId 重算」）⇒ 详情 pane 一并重建，无需恢复"已花时间" | **必须持久化**（localStorage/sessionStorage）+ 反序列化 + 处理过期，且 card 已失、锚点孤立无意义 |
| bfcache 还原 | **天然正确** —— 常量；恢复瞬间派生值自动跳到正确值（顺带修掉"数字冻在熄屏时刻"） | 需在 `pageshow` 里重算偏移 |
| 熄屏回前台 | **天然正确**（同上） | 同上 |
| 换 OD / 换卡 | 自动跟随新 card | 需手动重置，容易漏 |

**同源可靠性排序**：`card.arriveAt`（已在卡里，绝对） > `/api/nav` 顶层 `generatedAt`（有，但要额外透传进卡） > 新加 sessionStart（最差：多一份要持久化、要恢复、要处理过期）。

**唯一 residual**：`arriveAt` 是**规划时刻**算的，车晚点后它不会更新（`model.ts` 无回写）。⇒ `arriveAt` 只能支撑**第一个数字的正确倒计时**，不能支撑**晚点后的正确剩余**。后者必须靠 `segProgress.segRemainSec`（当前腿）+ `headwayAt`（下游候车），且必须在服务端算 —— 这正好是 1-B 的职责。

⇒ **推荐分工**：`arriveAt` 负责"总时长/到达时刻的即时倒计时"（客户端，0 成本、0 新状态）；服务端 1-B 负责"晚点/下游变更后的真实剩余"（含纵条整形）。

### Q3：明确推荐

**推荐：`1-A′`（arriveAt 锚的薄派生层，立即做）+ `1-B′`（服务端整形 strips，本周做）；不采纳 1-C。**

分两步，因为两步的收益与风险完全不同，可以分别验收：

**第一步 `1-A′`（半天，可单独上线）**
- 收益：总时长从"冻结的 `19.3`"变成真倒计时；到达时刻保持绝对（本来就对）；**且这一步顺带修掉需求5的一部分症状**（熄屏回来数字不再冻住 —— 这是纯时间函数，不依赖任何网络帧）。
- 代价：1 个新文件 + 1 个组件 2 处渲染 + 1 个"已到达"文案分支。
- 风险：低。唯一要防的是**倒计时归零后的表现**（车晚点时会走到 0）—— 必须 clamp 到 0 并把文案切成"即将到达/已过预计时刻"，**不得出现"-3 分钟"**。

**第二步 `1-B′`（2~3 天，满足"整屏一致"）**
- 收益：纵条 `车上约 N 分` / 换乘 `等车约 N 分` 一并刷新，顶部与纵条同源同帧 ⇒ 真正整屏一致；晚点场景正确。
- 代价：新端点 + `strips` 重算入口 + 2 个组件接新数据 + 节流轮询。
- 风险：可控，但**必须纠正一个量级误判**：前端把风险写成"多一次往返（本项目冷启动实测 2~3s）"。那 2~3s 是 `/api/nav` 的代价（要打高德 transit + 9~13 个 DSAT 桶）。`/api/nav/remaining` **不打高德、不打 DSAT**，只读已缓存的 `loadStatics` + 内存计算 ⇒ 预期 **100~300ms**。若真按 3s 估，会得出"不可做"的错误结论。<br>⚠️ 这条「不打 DSAT」是**硬约束而非可选项**：服务端自取车辆帧会把全局单桶打满（约 7 并发用户）并可能撞开全局熔断 —— 详见 §2.1 修订 ②。

**不采纳 1-C 的理由**：复核 A（对 strips no-op）+ 复核 B（会清地图线并放弃取景，产生可见跳动）。它是三者里**唯一会引入新副作用**的方案 —— 用户没要求地图跳，我们不该送他一个。

**「不这么做会踩什么坑」**
- 只做 1-A：用户会看到"上面 18 分→17 分在走，下面纵条写着车上约 12 分一动不动" ⇒ **比现在更不可信**（现在至少两处一致地冻着）。这正是负责人拍板"纵条也要一起刷"的原因，前端候选里只有 1-B 能做到。
- 做 1-C：地图彩段被清空重画 + 取景重算（`frame({mode:"none"})`）⇒ 导航中视野跳一次，用户会怀疑定位漂了，可能触发"我以为走错路"的次生投诉。
- 都不做：`totalMin` 永远停在规划值，导航 20 分钟后仍显示"19.3 分"，这是最直接的"不达标"。
