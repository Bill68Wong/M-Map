## 2. 最终算法（三层判据 + 三条硬保证）

### 2.1 数据流

```
GET /api/route-shapes?code=X
   └─ shapes[] = { dir, polyline, stations: [{code, seq}] }   ← 新增 stations
        │
        └─ useRouteOverview（未改）
             └─ buildColoredLegs(legs, shapesByRoute)          ← 未改签名，内层接线
                  ├─ ① 容差门（未改）：任一窗口 > TOL_M(80m) ⇒ 该方向不合格
                  ├─ ② 外层选向（未改）：score = dBoard + dAlight 最小，并列优先正向
                  ├─ ③ 内层配对（★ 新增 pickTripPair）：站序 + 几何联合定 (iBoard, iAlight)
                  └─ ④ cutColored（未改）：按索引切片
```

### 2.2 `nearestTrips(pts, p, tolM)` — **按趟聚类，不是「全部顶点」**

这是实现过程中被实测推翻的第一版设计。第一版返回「全部 ≤ tolM 的顶点」，结果 25 号靶子选中 `iBoard=541 / iAlight=639`（弧长 3504m）—— 因为最短弧会在簇内随手挑一个偏了点。**锚点语义要求取簇内最近点**，否则验收靶子直接错位。

- 逐顶点扫描，命中（≤ tolM）即入簇；
- **离上一命中顶点累计路程 > `PASS_CLUSTER_GAP_M`(120m) ⇒ 另起一趟**（按里程而非索引间隔：各线顶点密度差 2 倍以上）；
- 每趟输出 `{ idx（簇内最近点）, distM, from, to }`。

### 2.3 `arcMiles(pts, iFrom, iTo, loop, cum?)` — 沿索引累计里程差分

- 非环线：`|cum[iTo] − cum[iFrom]|`（`reverse()` 不改变点集长度）；
- 环线 `iTo < iFrom`：`cum[n−1] − cum[iFrom] + **distM(pts[n−1], pts[0])** + cum[iTo]`
  —— **闭合边必须计入**，否则「评分用的弧长」比「真正画出来的长度」少十几米（实测 16m），评分与绘制就会打架；
- 只算**索引递增**那条弧（`cutColored` 从不产生反向弧，只评能画出来的）。

### 2.4 `pickTripPair` — 三层判据

| 层 | 判据 | 依据 |
|---|---|---|
| ① **方向** | `wantIdxUp = iAlight0 ≥ iBoard0`（取自**旧解的索引序**）。非环线只保留同向候选 | 它回答「shape 是正向还是逆向**存储**的」，与站序位置无关 ⇒ 不受「同站多次经过」干扰 |
| ② **可信下限** | `arc ≥ max(直线距离 − 两端投影距离, 0.55 × 跳数 × 平均站距)` | 前半是**三角不等式**（几何上可证明的下界，无需调参）；后半是线路自身站距经验（平均站距 = shape 全长 ÷ 停靠数） |
| ③ **最短弧** | 只接受**比旧解更短**的候选，取最小 | 更长的候选没有意义 |

**三条硬保证**
1. **旧解恒为候选** —— 判据只筛「更短的替代方案」，不筛旧解本身。
2. **永不变长** —— 结果恒 ≤ 旧解弧长（全量 9476 段实测 `变长=0`）。
3. **站序不可用即逐字节回落** —— 无 `stations` / 站码不在站序 / 站码出现多次 / 两站序位相同 / 全部候选被剔 ⇒ 返回旧解。

### 2.5 范围闸门：只巴士段吃站序

```ts
const pickShapes = leg.kind === "bus"
  ? shapes
  : shapes.map((s) => (s.stations ? { ...s, stations: null } : s));
```

理由：轻轨段的 `colored` 另有四个消费者（`buildLrtLadder` 里程阶梯、`cutAt` 安全网投影、`youAt` 纵条用户点、自动下车阈值），改它等于动另一套推进系统的基准。实测轻轨确实会变（氹仔线 `LRT-OCH→LRT-JCK` 772m→678m，方向上是变准），但**本轮不顺手改**。接口对轻轨照常下发 `stations`，放开只需删这个三元（一行、可逆）。

## 3. ★ 偏离说明：为什么 `cutColored` 没有改

**你的第 4 条**：非环线 `iBoard > iAlight` 的 `reverse()` 分支改为「先用站序判断方向，方向与索引相反才 reverse」。

**我不是"没做"，是把同一件事做在了更有约束力的位置**，理由三条：

1. **`cutColored` 的索引比较在新不变量下与「按站序判方向」等价。**
   `wantIdxUp` 已经把「shape 是否逆向存储」判出来了（取自旧解索引序），配对层又只保留与其同向的候选。于是在产出侧恒成立：
   「`iBoard > iAlight`」 ⟺ 「shape 逆向存储」 ⟺ 「需要 `reverse()`」。
   两者不再可能给出不同答案 —— `cutColored` 的旧规则恰好就是站序规则的推论。

2. **改 `cutColored` 会破坏一条跨模块契约。** 它必须保证 `colored[0] === board`、`colored.at(-1) === alight`（`ColoredLeg.colored` 的 JSDoc 明写，`nav-map-overview.ts` 的 `grayIsWhole` 也依赖引用相等）。若按「站序方向」而非「索引顺序」决定是否反转，在「站序前向但索引前向」的矛盾输入下会产出**首尾颠倒**的点列 —— 地图形状不变但方向箭头全反，且违反契约。

3. **会打红既有对拍用例 ③④⑤。** 它们直测 `cutColored` 三种切片语义（正向 / `reverse` / 环线环绕）。用例 ④ 就是 `cutColored(pts, 3, 1, false)` 断言「反转后首点=board」。改了语义 ⇒ 这三组必红，且是**契约级**改动，不该夹在需求 4 里做。

**如果你仍要改 `cutColored`**：请把它作为独立条目，并同时重写 ③④⑤ 与 `ColoredLeg.colored` 的契约说明 —— 我不建议在本轮做。

## 6. 实施中被实测推翻的 4 个设计（供后续参考）

| # | 第一版做法 | 实测症状 | 修正 |
|---|---|---|---|
| 1 | 站序位置用 `Map` 取**首次出现** | 环线多次经过同一站 ⇒ 把「第 40→41 位」误判成「第 40→5 位」⇒ **146 段过长回归** | 站码出现多次 ⇒ **整段回落**（不冒险） |
| 2 | 弧长区间 `[0.4×, 2.5×] × 跳数 × 平均站距`（**双侧**） | 上界误伤正常短程（`51B T375→T379`：平均站距 855m、实际 609m 被拒 ⇒ 反而选出绕行 4293m） | **删上界**，只留下限；「不变长」改用显式比较保证 |
| 3 | `nearestTrips` 返回**全部** ≤tol 顶点 | 最短弧在簇内随手挑点 ⇒ 25 号靶子 `iBoard` 从 539 漂到 541、弧长 3549→3504，**验收断言直接错位** | **按趟聚类**，每趟取簇内最近点为代表 |
| 4 | 拍脑袋的「每跳最小米数」常量 | 与线路尺度强相关，换一条线就不成立 | 换成**三角不等式**（可证明下界）+ 线路自身站距经验 |
