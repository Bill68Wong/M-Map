## 1. 根因定论（有证据）

### 1.1 需求4：地图巴士段几何画错

#### 结论 D4-1（几何来源）巴士段 polyline 来自 `route_shapes` 的**整条线路走向**，前端按「上/下车站坐标」投影后**自行切片**

- 数据来源：`GET /api/route-shapes?code=` → `src/app/api/route-shapes/route.ts:100-118`，读表 `route_shapes`，`polyline` 为 **GCJ-02**（`route.ts:6-20` 段注释明确「直接喂高德，不要再转」）。
- 绘制链路（三跳，全部在前端）：
  1. `src/components/nav/useRouteOverview.ts:99-122` —— 并行拉每条线路的 shapes，然后 `buildColoredLegs(legsInput, shapesByRoute)`；
  2. `src/lib/nav/route-overview.ts:170-208` `chooseShape()` —— 选方向 + 用**最近顶点**定位上/下车站索引 `iBoard` / `iAlight`；
  3. `src/lib/nav/route-overview.ts:217-228` `cutColored()` —— 按索引切片出「彩段」；
  4. `src/components/nav/nav-map-overview.ts:25-72` `drawOverview()` —— 灰底线（整线虚线 z68）+ 彩段（乘车区间实线 z72）。
- ⇒ **不是按「整条 shape」直接画**，而是「整条 shape 当灰底线 + 投影切片当彩段」。用户看到的那条绕路的线**是彩段**。

#### 结论 D4-2（锚点定位方式）上车站用**经纬度最近顶点**定位，不看站名、不看站码、不看站序

`src/lib/nav/route-overview.ts:127-139`：

```ts
export function nearestOnPath(pts: LL[], p: { lng: number; lat: number }): { idx: number; distM: number } {
  let idx = 0; let best = Infinity;
  const q: LL = [p.lng, p.lat];
  for (let i = 0; i < pts.length; i++) {           // 全量线性扫描
    const d = distM(pts[i], q);
    if (d < best) { best = d; idx = i; }           // 只保留全局最小
  }
  return { idx, distM: best };
}
```

`chooseShape()` 对它的用法只有一条容差门（`route-overview.ts:181-184`）：

```ts
const nb = nearestOnPath(pts, board);
const na = nearestOnPath(pts, alight);
if (nb.distM > tolM || na.distM > tolM) continue;   // TOL_M = 80 米（:40）
```

**没有**任何「该顶点对应哪个站码」「该顶点在 shape 上是第几趟经过」的判别。

#### 结论 D4-3（★ 核心：为什么起点像「安顺大厦」）金峰南岸 C653 与安顺大厦 C652 在库里只相距约 20 米，shape 上这两站各有**一趟**经过，最近顶点落在了 C652 那一趟

DB 直读（`.verify/_q4-1.mjs` 输出，WGS84）：

```

C653  金峰南岸/金譽峰    lat 22.128178  lng 113.558600     ← 两点相距 ≈ 20 m
```

但在站序上二者相距 6 站（`route_stations`，`.verify/_q4-seq.mjs`）：

⇒ 巴士从 C652 那一侧经过 → 绕行 → 从对侧回到 C653。**同一条路两侧各一个站台，物理相距 20 米，站序相差 6 站。**

实测（`.verify/_q4-25.ts`，线上真实 shape，25 号线 913 点、闭合环）：

> 这就是用户原话「地图上显示的巴士路线是从对面的安顺大厦上车」的机制：不是站名匹配错，而是**几何最近点恰好落在对侧站台的轨道顶点上**。

#### 结论 D4-4（★ 核心：为什么「绕到路环一大圈」）闭合环的两条弧没有长度比较，只按索引大小决定环绕方向

`cutColored()` 的环线分支（`route-overview.ts:226-227`）：

```ts
return pts.slice(ib).concat(pts.slice(0, ia + 1));   // 索引小 ⇒ 一律往后环绕
```

#### 结论 D4-5（文字与地图是否同源）**站码同源，几何锚点不同源**

| 用途 | 数据来源 | 证据 |
|---|---|---|
| 文字「在金峰南岸上车」 | 推荐引擎 `card.rides[].board = "C653"` | `.verify/_q4-nav.json`：`planId 1 … board "C653" boardLabel "C653 金峰南岸/金譽峰"`；`hints[0]`「在 C653 金峰南岸/金譽峰 上车，乘 26A」 |

`POST /api/nav/detail-body` 确实用**站码**下发坐标（`src/app/api/nav/detail-body/route.ts:151-155` `coordOf(r.board)`，`:84-85` `mainCodeOf`），坐标取 `stations` 表 + `wgs84ToGcj02`（`:96-108`）。**到这一步仍是同一份数据**。

⇒ **定论：文字用「站码」，地图彩段用「坐标→最近顶点投影」。两者同源不同径；当两个站台相距 ~20m 时，投影会越界到对侧站台，而渲染层与文字层各自都不知道对方说的是哪个站。** 这就是「文字对、图画错」的结构性原因。

#### 结论 D4-6（`loopSkipBoardOf` 是否影响）本 OD **未触发**，但它是同类问题的放大器

`src/lib/nav/graph-search.ts:299-332` `loopSkipBoardOf()`，调用点 `:422-432`（只改**首段**）。

- 机制：若 `board` 之后沿站序绕 ≥ `LOOP_MIN_RIDE_M`（300 m，`:287`）回到 ≤ `FAMILY_RADIUS_M` 内的**同族站**，就把上车站改到下游那个同族站。
- 本 OD 实测：`board C653`（25 号线 seq30）→ `alight T306`（seq36），下标区间内**没有**任何与 C653 相距 ≤ 半径的同族站（C652 在 seq24，在 board **之前**）⇒ `loopSkipBoardOf` 返回 `null`，**未改写**，`card.rides[].board` 仍是 C653（与 `.verify/_q4-nav.json` 一致）。
- ⚠️ 但它把「C652 ↔ C653 这对相距 20m 的同族站」**制度化**了：正是这个函数的存在证明产品口径承认这两个站可以互换。它一旦命中，就会把上车站**在文本上**改成下游站，而几何投影仍然可能落在**上游**那趟经过（D4-3 同一机制）—— 于是文字说「在金峰南岸上车」、图画成「从安顺大厦出发」。⇒ **它不是本次直接原因，但它与本 bug 共享同一个失效前提（站码语义 vs 几何最近点不对齐），修 D4-3/D4-4 时必须一起回归它。**
- 顺带证伪：`92a8912`（v3.9.0 `walkActiveRef` 解死锁）与 `51561d8` 的环线跳站**都不在**这条渲染链路上（渲染链 = `useRouteOverview` → `route-overview.ts` → `nav-map-overview.ts`），**本地 4 个未推 commit 不影响本 bug**。

#### 结论 D4-7（非环线也会画反）`iBoard > iAlight` 时走 `reverse()`，几何方向反了但没人校验

`route-overview.ts:222-225`：


实测 26A `dir=0`：`iBoard=471 > iAlight=342`（`.verify/_q4-loop.ts` 输出「⚠ 非环线但 iBoard > iAlight ⇒ 走 reverse 分支」），反转后的彩段**首点仍是安顺大厦附近顶点**。本 OD 因为 `dir=1` 得分更优（1.9m vs 16.8m）而未选中，但**只要方向判据稍有变化，就会画成「从对侧站出发、倒着开」**。

### 1.2 需求5：熄屏回前台位置冻结

#### 结论 D5-1（调用点）`useResumeRefresh` 只有 2 个挂载点，内部覆盖 4 条轮询；**没有漏接**，但「三个调用点」的说法与代码不符

`grep -rn useResumeRefresh src/` 结果：

| 挂载点 | 文件:行 | 回调里刷什么 | `enabled` 条件 |
|---|---|---|---|
| `useRideTracking` | `useRideTracking.ts:1021-1026` | `resumeKickRef.current?.()` | `active && (phase==="boarding" || phase==="riding")` |
| `useRouteVehicles` | `useRouteVehicles.ts:239` | `resumeRefresh` → `fetchVehicles()`（线路查看模式车辆） | `!!picked` |

`resumeKickRef` 的写入者共 **3 条** effect（全部在 `useRideTracking.ts`）：

- 候车轮询 `:1031`（`deps [phase, active, legIndex, walkActive]`）→ `resumeKickRef.current = kick` @ `:1083`
- 有牌乘车轮询 `:1096`（守卫 `:1100`；`deps [phase, plate, active, fetchFrame]`）→ @ `:1131`
- 无牌乘车轮询 `:1161`（守卫 `:1169`；`deps [phase, plate, active, fetchFrame]`）→ @ `:1199`

**代码级核过三个问题，均无缺陷**：
1. 三条 effect 互斥（`boarding` / `riding+plate` / `riding+!plate`），且 cleanup 有 `if (resumeKickRef.current === kick)` 身份校验（`:1087`、`:1135`、`:1203`）⇒ 后挂载的不会被先卸载的清掉；
2. 手动刷新走的是 `vehicleCooldown`（`:1660-1676`），**`kick()` 直接调 `round()/pull()`，不经过冷却** ⇒ 补刷不会被 5s 冷却吞；
3. `useResumeRefresh` 的 2s 去抖是**每实例独立** `firedAtRef`（`useResumeRefresh.ts:37`），熄屏 1~2 分钟后首次事件必然通过（`now - 0 > 2000`）。

#### 结论 D5-2（12s 轮询是否立即补一次）**会立即补一次**，且补完才重置 12s

```
useRideTracking.ts:1074-1079   kick(): void round().then(() => schedule(POLL_MS))   ← 立即打，不等 tick
useRideTracking.ts:1066-1073   schedule(ms): clearTimeout 旧 timer 后重排           ← 取消待触发的那一次
```
同形实现见 `:1123-1129`、`:1187-1195`。「等下个 tick」的旧行为已被 v3.7.0 S2 的 `setTimeout` 链替换（`:1061-1065` 注释）。

#### 结论 D5-3（GPS 是否重新激活）`useUserFix` 有**独立**的一条 `visibilitychange → clearWatch + watchPosition` 复位链，实测探针证明重订阅确实发生

代码：`src/components/nav/useUserFix.ts:253-280`

```ts
const onVis = () => {
  if (document.visibilityState === "visible") { if (startedRef.current) resume(); }
  else { stopWatch(); }                       // 隐藏时释放监听
};
const onPageShow = (e: PageTransitionEvent) => { if (e.persisted && startedRef.current) resume(); };
```

`resume()`（`:255-262`）先重置 `dogBaseRef`（避免看门狗误判假死）再 `doWatch()`。

真浏览器探针证据（`.verify/_q5-resume.out.txt`，本机 Chrome + 线上站点）：

```

           ["clear",…823165],["watch",…823165,0,true],["cb",…823167,22.12525,113.56366]]
data-geo=ok  data-user-fix=1793706823167,12
```

⇒ `clearWatch` + 重新 `watchPosition` + 新回调确实发生了（本次是**看门狗**在 20s 空闲后触发的，见 `:236-245`，不是 `visibilitychange` —— 见 D5-4）。

**另外**：`useUserFix` 有 20s 空闲看门狗（`WATCH_IDLE_MS = 20_000`，`:66`；巡检 5s，`:64`；`:236-245`）——即使 `visibilitychange` 完全不来，只要 JS 定时器还在跑（哪怕被节流到 1 次/分钟），GPS 侧**最多 1 分钟内会自愈**。这一点是「用户蓝点也该自己恢复」的反证依据，见 §2 H5-C。

#### 结论 D5-4（`pageshow(persisted)` 在本场景天然失效）安卓熄屏属 resumed，不属于 bfcache 还原 ⇒ `persisted === false` ⇒ 被过滤

- 代码：`useResumeRefresh.ts:54-57` —— `if (e.persisted) fire();`；`useUserFix.ts:270-273` —— 同样 `if (e.persisted && …)`。
- 实测（`.verify/_q5-resume.out.txt`）：整个会话**只收到一次** `pageshow`，且 `persisted=false`：

```
vis 事件全量: [[1793706803140,"pageshow:persisted=false"]]
```

⇒ **定论：这条入口对「熄屏 1~2 分钟」场景永远不触发。该场景的全部补刷能力 100% 押在 `visibilitychange` 一条路径上。**

#### 结论 D5-5（图层重绘）**不是**「数据没变所以不重绘」——两个图层都由 state 变化驱动

- `UserDotLayer.tsx:192`：`}, [enabled, map, amap, fix, smoothMs]);` —— 每次采纳新 `fix`（`useUserFix.ts:174` `setFix(f)` 新建对象）就重跑。
- `VehicleLayer.tsx:291`：`}, [vehicles, recompute]);` —— `listTick` 递增触发 `mapVehicles` 重算（`useRideTracking.ts:490-519`）。
- 且 `fetchFrame` 成功即 `setListTick((t) => t + 1)`（`useRideTracking.ts:736`）—— 即使车辆坐标一字未变，帧号也会变。

⇒ **定论：「数据回来了但不重绘」这条假设可以排除。用户看到的「完全冻结」必然是「没有新数据进来」。**

#### 结论 D5-6（Turbopack / effect 双跑）无证据支持，且架构上不成立

- `useResumeRefresh` 的监听器注册在 `useEffect(..., [enabled, debounceMs])`（`useResumeRefresh.ts:67`），cleanup 完整移除三个监听（`:62-66`）⇒ 双跑即「注册→移除→注册」，稳态只有一份。
- `firedAtRef` / `cbRef` 是 `useRef`，跨 effect 重建保留（`:34-37`）—— 注释明确写了这是为「解绑重绑不会造成二次连发」。
- `92a8912`（`walkActiveRef` 解死锁）改的是 `tryAuto` 内的门槛（`:1005` `res = res.need + (walkActiveRef.current ? 2 : 0)`），**不碰任何监听器注册**。

⇒ **定论：Turbopack effect 重放不是本 bug 的原因**（未发现任何证据）。

## 2. 待验证假设（无证据，禁止当结论使用）

### H5-A（首要，最能解释「两张图同时冻结」）：安卓 standalone 熄屏→亮屏时 `visibilitychange` 未按预期到达

- 若成立：`useResumeRefresh` 与 `useUserFix` 的**唯一**恢复入口（D5-6 已证明 `pageshow(persisted)` 不触发）同时失效 ⇒ 蓝点与车辆图标一起冻结，UI 仍渲染旧帧 —— 与用户描述完全一致。
- 为什么怀疑：`document.visibilityState` 在部分安卓 WebAPK / 独立窗口 + 屏幕熄灭场景下被报为 `visible`（页面自认为可见），或熄屏只触发 `freeze`（Page Lifecycle）而不发 `visibilitychange`。**本机 Playwright 复现出的正是「`bringToFront` 后 `visibilityState` 仍是 visible」这一现象**（虽属 harness 缺陷，但说明该 API 在真实环境断言不可靠）。
- **验证方法（真机，5 分钟）**：安卓 + 已加主屏的构建，导航中熄屏 60s 后亮屏，用 `chrome://inspect` 远程 DevTools 的 Console 跑：
  ```js
  document.addEventListener('visibilitychange',()=>console.log(Date.now(),document.visibilityState));
  document.addEventListener('freeze',()=>console.log('FREEZE'));
  document.addEventListener('resume',()=>console.log('RESUME'));
  document.addEventListener('pagehide',e=>console.log('PAGEHIDE',e.persisted));
  ```
  判据：亮屏后 1s 内是否出现 `visible` 日志。

### H5-B（次选，症状强吻合）：`fetchFrame` 的 `inFlight` 闭包标志在熄屏中途被打断后永久为 `true`，之后每轮轮询在门口就 `return`

- 代码位置：`useRideTracking.ts:1050-1056`（候车）、`:1105-1111`（有牌）、`:1173-1179`（无牌）三处同形：
  ```ts
  const round = async () => { if (inFlight) return; inFlight = true; try { await fetchFrame(null); } finally { inFlight = false; } }
  ```
- 风险机制：`fetchFrame` 里的 `fetch("/api/route-vehicles…")` **没有 `AbortSignal.timeout`、没有超时兜底**（`useRideTracking.ts:714-718`）。若页面在请求在飞时被冻结、恢复后该 promise **既不 resolve 也不 reject**（射频休眠导致的请求悬挂），`finally` 永不执行 ⇒ `inFlight` 永久 `true` ⇒ 之后**每一次** `round()/pull()` 都在第一行 return ⇒ **完全冻结，且不会再自愈**。
- 为什么比 H5-A 更值得查：它解释「为什么恢复后 1~2 分钟里连看门狗（20s）都没救回车辆帧」——但**不能**解释蓝点为什么也冻（蓝点由 `useUserFix` 独立驱动，见 D5-5）。⇒ **单独不足以解释全症状，需与 H5-A 并列验证或排除。**
- **验证方法**：在 `round()` 的 `if (inFlight) return;` 前加一行临时 `console.debug`，真机复现后看是否每 12s 打一行 debug 而无网络请求（Network 面板无 `route-vehicles`）。

### H5-C：`active`（`navActive = rsOpen && pane === "detail"`）在恢复后变 `false`，导致三条轮询 effect 全部卸载

- 若成立：`resumeKickRef` 被 cleanup 置 `null`（`:1087`/`:1135`/`:1203`）⇒ 即使 `visibilitychange` 到达也无 `kick` 可调。但此时 UI 会退回「推荐列表」而非停在旧地图 —— 与用户「还卡在熄屏时刻的状态」略有出入。
- 附带反证：`useUserFix` 的 `enabled` 也挂在导航态上；若 `active` 变 false，蓝点会被 `setFix(null)`（`useUserFix.ts:211-217`）**移除**，用户会看到「蓝点消失」而不是「蓝点卡住」。⇒ **优先级最低，但仍应顺手排除。**

### H5-D：`wakeLock` 在亮屏后重申请失败（无手势）—— 与本 bug 无关，仅记录

`useRideTracking.ts:659-674` 在 `visibilitychange→visible` 时重申请 wake lock。失败被静默吞掉（`:646-650`）。即便失败也只会导致「屏幕会再自动熄灭」，不会冻结位置。⇒ **排除。**

## 3. 最小修复方案选项（供出选择题，**未选**）

### 需求4

#### 方案 4-A：给 `chooseShape` / `cutColored` 加「站序校验 + 最短弧优先」（后端/纯函数层，推荐评估）

- 做法：`route-overview.ts` 的 `nearestOnPath` 改为返回**所有 ≤ tolM 的顶点趟次**（而非单一全局最小）；对每个 `(iBoard, iAlight)` 组合算出彩段沿线路程，取**最短**；环线时两条弧都算，取短弧。可选再叠一层「彩段里程 ≈ 站序累计里程（`route_stations` seq 差 × 平均站距）」的一致性校验。
- 代价：改 1 个纯函数文件（`route-overview.ts`）+ 更新 `scripts/test-route-overview.ts` 对拍用例（现成脚本，已覆盖环线场景）。**不动 API、不动 DB、不动 UI。**
- 风险：低—中。「取最短弧」在「公交故意绕行」的少数线路上会与真实运营里程不符（但 MVP 的展示目标就是「别画错方向」，可接受）；需回归 26/25 环线 + 21A/26A 非环线 + 起终点同站（分支④）。
- 影响面：只影响详情/导航态的地图彩段与灰底线。

#### 方案 4-B：用 `route_stations` 的站序直接决定投影趟次（数据驱动层）

- 做法：把 `legs[]` 里再加上 `boardSeq` / `alightSeq`（服务端从 `route_stations` 读），前端用「沿 shape 的第 n 趟经过」与站序差做匹配；或更彻底：**离线预计算** `route_shapes` 的「站点在 shape 上的索引」表（`fetch-route-shapes` 时一并写入），前端直接查索引，不再做几何投影。
- 代价：要动 `db/` 迁移 + `scripts/fetch-route-shapes.ts` + `/api/route-shapes` 契约 + `detail-body` 契约。工作量约为 4-A 的 3 倍。
- 风险：中。契约变更需前后端同步；离线表若未覆盖全部 92 线会引入新的降级面。
- 收益：一次修好「投影越界」这一类问题（含 C652/C653 这种 20m 双台），并且 `loopSkipBoardOf` 的语义也能对齐。

#### 方案 4-C：只做「上车站视觉锚点对齐」的止血（UI 层，最小改动）

- 做法：彩段起点顶点若距**文字上车站**坐标 > N 米（如 30m），把彩段首点**强制替换**为该站的 `/api/stations` 坐标；同时若彩段沿线路程 > 直线距离 × K（如 2.0），改画「整线灰虚线 + 起终点连线」降级。
- 代价：改 `nav-map-overview.ts` / `route-overview.ts` 十余行。
- 风险：低技术风险，但**治标不治本** —— 绕路的那一段仍然绕（只是首点对齐了），用户仍会觉得「路线画错」。适合作为「先止血、后重构」的第一刀。

### 需求5

#### 方案 5-A：给恢复补刷加「无事件也自愈」的兜底 tick（最小、最稳）

- 做法：在 `useRideTracking` 加一个 `lastFrameTsRef`；新增一个 15s 定时器：`if (Date.now() - lastFrameTsRef.current > 30_000) resumeKickRef.current?.()`。因为定时器即便被节流到 1 次/分钟也终会执行 ⇒ 无论 `visibilitychange` 是否到达，**最多 1 分钟内一定补刷**。
- 代价：改 1 处（~10 行），不动任何契约，不动监听器。
- 风险：极低。代价是隐藏期间会多发极少量请求（节流下 1 次/分钟，且服务端有配额记账）。**注意**：若 H5-B 成立（`inFlight` 永久 true），本方案会被同一道门挡住 ⇒ **必须同时做 5-C**。

#### 方案 5-B：补齐「恢复」事件矩阵（`visibilitychange` + `focus` + `pageshow(任意)` + `resume` + 轮询心跳）

- 做法：`useResumeRefresh.ts` 增加 `window.focus`、`document.resume`（Page Lifecycle）监听；`pageshow` 去掉 `e.persisted` 限制（改为「首次加载后 3s 内的 pageshow 忽略」）。再给 `document.visibilityState` 加一条「`Date.now() - lastFire > 60s` 且当前 `state === 'visible'` 即放行」的兜底判据。
- 代价：改 1 个 hook（~20 行），单测可用现成 `.verify` 脚本扩展。
- 风险：低—中。`focus` 在输入框聚焦时也会触发（会误刷）⇒ 需与去抖配合；`pageshow` 去掉 persisted 过滤要小心首帧重复刷。

#### 方案 5-C：给 `fetchFrame` 的请求加超时 + 把 `inFlight` 改成带时间戳的可自愈门

- 做法：`fetch(..., { signal: AbortSignal.timeout(8000) })`；`inFlight` 从 `boolean` 改为 `inflightSince: number`，判据改成 `if (inflightSince && Date.now() - inflightSince < 15_000) return;` 后强制重置。
- 代价：改 3 处同形闭包 + `fetchFrame` 的 fetch 调用（~15 行）。
- 风险：低。**前提是先验证 H5-B**：若真机日志显示「无 `route-vehicles` 请求但 12s 心跳在打」，则 H5-B 成立，本方案就是主修复项；若不成立，本方案仍是值得做的防御（悬挂请求在移动网络上是常态）。

#### 建议的验证顺序（不改代码，先取证）

1. 真机按 **H5-A** 的 Console 片段跑一次熄屏/亮屏 → 先确定「事件到不到」。
2. 若事件到不到 ⇒ 走 5-B（+5-C）。
3. 若事件到了仍不刷 ⇒ 按 **H5-B** 加 debug 看 `inFlight` → 走 5-C。
4. 无论如何都建议先上 5-A（成本最低、与 1~3 的结论互不冲突）。
