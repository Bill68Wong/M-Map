## C1 函数执行区域：iad1 → hkg1

**问题**：所有 API 都从香港边缘转到美东（iad1）执行，固定多付 305ms，且每个上游（Supabase 新加坡 / 高德中国 / DSAT 澳门）都跨洋。

**选项**
- **A. `vercel.json` 加 `"regions": ["hkg1"]`（不改套餐）**
- B. 加 `"regions": ["sin1"]`（和数据库同区）
- C. 升 Vercel Pro 再锁区域
- D. 不动区域，只做缓存（C2/C3）

**推荐：A**

**理由**
- 官方文档：函数区域「Runs in a single region by default (iad1), which you can change」；套餐限制表里 Hobby = **Single region**（限 1 个，但**可改**），Pro = 5 个。项目记忆里「Hobby 下 `preferredRegion` 不生效」是**对的**（`preferredRegion` 是 Next 的 route 段配置，实际取的是项目 region 设置），但结论「必须升 Pro」**不成立**。
- 选 hkg1 而非 sin1：本项目 **transit（高德，中国）+ live（DSAT，澳门）** 的耗时（冷态 3.3–7.3s / 0–4.7s）远大于 DB 耗时（`staticMs` 命中时 0）。hkg1 离用户、离澳门、离高德都更近；DB 也顺带从「跨太平洋」变成「香港→新加坡」（约 3,300km）。
- 选 Pro **无额外收益**：本项目不需要多区域，`maxDuration` 30s 已够（当前最慢 13.1s）。

**代价**：1 行配置 + 清理各 route 里已无效的 `preferredRegion`；重新部署一次。

**风险与验证**：全站函数一起搬 ⇒ 先部署 Preview 域名，跑 `.verify/perf/measure-gaps.mjs`（把 `PERF_BASE` 指向 preview）对比，再上生产。若 Supabase pooler 拒绝新来源区域，会整体 5xx —— 这是唯一需要提前确认的点。
**若 Hobby 实际拒绝该配置**（部署在 build 前失败，报「more regions than your plan allows」）：退回「C2 + C3 + C4」组合（收益约为 C1 的 1/2），再单独评估是否值得为 C1 付 Pro。这条必须在 Preview 上**先验证再拍板**。

**影响面**：全部 API 的 wall time；不改任何响应内容。

## C2 给 `route-shapes` / `route-lines` 补 CDN 缓存

**问题（已订正）**：我最初判断「所有静态接口都没命中 CDN」，**这是错的**。`stations`（`stations/route.ts:182`）与 `route-stops`（`route-stops/route.ts:27`）都写了 `s-maxage=3600` 且**真的命中**（连测 3 次 `X-Vercel-Cache: HIT`，`Age` 1172→1185）。
真正漏写的只有两个：`route-shapes` 与 `route-lines` —— 这两个文件**全文没有 `Cache-Control`**，只有 `dynamic = "force-dynamic"` ⇒ Next 默认 `max-age=0, must-revalidate` ⇒ 恒 MISS。

> **教训（值得写进项目记忆）**：`Cache-Control` **不能**用来判断是否 CDN 命中 —— Vercel 会把 `s-maxage` 从浏览器可见头里剥掉，只留 `public`。判命中只能看 `X-Vercel-Cache` + `Age`。我按 `Cache-Control` 推断，得出了与事实相反的结论。

**选项**
- **A. 只给 `route-shapes` 与 `route-lines` 加 `public, s-maxage=3600, stale-while-revalidate=600`（照抄 `route-stops/route.ts:27`）**
- B. 连 `stations` / `route-stops` 一起重写（**不要**：已经是对的，动它只增加回归面）
- C. 不动

**推荐：A**

**理由**：`route-shapes` 是「开始导航」链上 detail-body 之后唯一的静态项（热 525ms、冷 1924ms），且每张卡的每段线路都要拉一次；`route-lines` 564ms 恒 MISS。收益是这两个唯一还没拿到 CDN 的静态接口。

**代价**：2 个文件各加 1 行常量。

**风险**：线路几何/线路色最多陈旧 1 小时（改道才变）；`?v=` 可强制绕过。

## C3 服务端缓存 TTL：60s → 10–15min

**问题**：`staticMs` 实测有 1725 / 2197 / 3162ms 的尖峰，因为 TTL 只有 60s 而真实访问间隔更长。

**选项**
- **A. 静态 60s → 600s，并让每日 cron 顺带预热**
- B. 只把 `transit_cache` 延长（C7），静态保持 60s
- C. 保持 60s

**推荐：A（静态部分）+ C7 单独议**

**理由**：这些静态数据的上游是「每日 Cron 重算」的派生表 ⇒ 60s 与 10min 对**正确性**没有区别，只对**成本**有区别。而项目是个人项目、请求稀疏 ⇒ 60s 窗口大概率已过期，用户付的是全额重建。

**代价**：2 个常量 + 一条预热调用。

**风险**：极低（数据源本身日更）。回滚 = 改回常量。

## C4 DSAT 报站结果缓存 12–15s

**问题**：`liveMs` 0–4687ms，是「关闸→澳科大 6.9s」的主因；`src/lib/dsat/client.ts:130` 是 `cache:"no-store"`，零缓存。

**选项**
- **A. 进程内 + Data Cache，键 `(station,dest,routes)`，TTL 15s，`purpose` 参与熔断排除**
- B. TTL 30s（更省，更旧）
- C. 不做（保持每次直查）

**推荐：A**

**理由**：DSAT 自身刷新节奏与官方页 10–15s 轮询同量级 ⇒ 15s 内的缓存不引入**额外**陈旧。这是唯一能让最慢 OD 掉下来的手段（transit 只能在 C7 里省）。

**代价**：新增一层缓存（约 60 行，放 `src/lib/recommend/live.ts` 或新模块）。

**风险（需负责人确认口径）**：这是**唯一会改变对外数值**的一项 —— 「还有 N 站」最多旧 15s（可能多算 1 站）。若负责人不接受任何读数陈旧，选 C，并把期望值改成「最慢 OD 约 7s」。

**联动**：必须同时满足铁律 19（新增 `purpose` 不得进熔断判定），否则高频缓存穿透会撞开全局熔断。

## C5 `detail-body` 的「本站台其他线路」改按需

**问题**：1.6KB 的响应要 3.1s，且它挡在 route-shapes 前面，把「开始导航」链拉到 3.8s。

**选项**
- **A. 拆出折叠栏数据，折叠展开时再取（新端点或 `?fold=1`）**
- B. 保留但缩短 `BUCKET_TIMEOUT_MS`（3s → 1.2s），超时就返回空
- C. 不动

**推荐：A + B 组合**

**理由**：A 消除 2.7s；B 是 A 落地期间的止血（即使展开，也最多等 1.2s）。折叠栏本来默认折叠（代码注释明确），为不展示的内容付 3s 没有道理。

**代价**：新端点或参数（约 40 行）+ 前端 `StationReachFold` 加一次取数。

**风险**：折叠栏从「立刻有」变「展开后 0.5s 内到」；需要一次骨架/加载态。

## C6 首页静态壳化

**问题**：`/` 是 `force-dynamic`，且 `loadRouteColors()` **每请求查一次库**；首页 TTFB 526ms 热 / 2.1s 冷。

**选项**
- **A. 去掉 `force-dynamic`，`?fromLng…` 回放参数改客户端 `useSearchParams` 解析；`loadRouteColors` 改 `unstable_cache`**
- B. 只把 `loadRouteColors` 缓存（保留 `force-dynamic`）
- C. 不动

**推荐：先 B，观察一周；若首页仍是首屏瓶颈再做 A**

**理由**：B 改动极小（1 个函数包一层），能省一次 DB。A 的收益更大（CDN 命中 ≈ 0.1s）但引入两个真实风险：`AMAP_JS_KEY` 变 build-time（env 改动需重部署）、`?` 回填有一次客户端跳变。而首页 526ms 已经不是链路里最慢的一环（导航链 3.8s、`/api/nav` 6.9s 更慢）。

**代价**：B = 5 行；A = 中改（约 60 行 + 一次真机回归）。

## C7 `transit_cache` TTL 与 OD 粗化

**问题**：TTL 60s，OD 键是「4 位小数坐标（≈11m）+ 15min 桶」。实测 319 个坐标对里 **148 个（46%）** 被重复请求过 ⇒ 这些重复几乎全部白付高德往返（冷态 3.3–7.3s）。

**选项**
- **A. TTL 60s → 300s，坐标取整 4 位 → 3 位（≈110m）**
- B. 只延长 TTL，不改坐标精度
- C. 只在「非服务时段边界」延长（05:00–07:00 与 23:00–01:00 保持 60s）
- D. 不动

**推荐：C（= B + 时段豁免）**

**理由**：改坐标精度会**改变结果**（首末步行的起终点变了，虽然只差 110m），不该在性能迭代里顺手动。而 TTL 只影响陈旧度。服务时段边界（首末班）对旧方案最敏感，这两段保持 60s 即可避开主要风险。

**代价**：1 个常量 + 1 个时段判断。

**风险**：中（陈旧方案可能含已收班的线路）。**这项建议等 C1 落地后重估** —— 若 hkg1 让 transit 从 4s 降到 1.5s，收益就不值得这个风险。

## C9 首次定位是否分级

**问题**：`enableHighAccuracy:true, maximumAge:0, timeout:10000` ⇒ 定位假死时用户**干等 10 秒**（实测 10015ms）。

**选项**
- **A. 先 `getCurrentPosition(低精度, maximumAge:600000, timeout:3000)` 快出，再 `watchPosition` 高精度修正**
- B. 只把 `timeout` 从 10s 改成 5s（不改取法）
- C. 不动

**推荐：A（但只在「候车/浏览」档启用；`riding` 档保持高精度直出）**

**理由**：riding 时蓝点精度直接影响「我该在哪下车」的判断，不能先给一个误差数百米的点。而候车/浏览时用户要的是「我在不在附近」，低精度够用且能立刻响应。

**代价**：`useUserFix` 内约 30 行。

**风险**：**会短暂改变可见结果**（蓝点先粗后准）。需要 UI 配合：粗点用半透明/带环，并在 `accuracy > 200m` 时不画吸附到线路的蓝点（避免吸到错的线）。

**待确认**：真机毫秒数尚未测（见主文档 §2.4 的测量协议）。若真机显示低精度也要 3–5s，本项收益就有限。

## C10 匹配算法的接入方式

**问题**：新算法是替换 `rankBoardingVehicles` 的候选口径，还是叠加一层？

**选项**
- **A. 叠加：`rankBoardingVehicles` 一行不改（继续服务候车提示），新增 `matchVehicle` 只在「已判定上车但无车牌」时接管**
- B. 替换：直接把候选池改成全在途车
- C. 只改「不是这辆」的候选来源

**推荐：A**

**理由**：需求方的硬约束是「上车前开始导航那条是准的，不能破坏」。A 的语义边界最清楚 —— 既有路径零改动，新逻辑只补「原本会落到 gps 驱动」的那条分支。C 太小（仍解决不了自动锁牌）。

**代价**：新增 `src/lib/nav/match-vehicle.ts`（纯函数，可单测）+ `useRideTracking` 接一处。

**风险**：中（新逻辑锁错车 ⇒ 报错站）。护栏：中置信标注「车牌待确认」、低置信退回 gps 驱动、「不是这辆」始终可用、`test-boarding-detect.ts` 现有断言全绿。

## C11 低置信时给什么（需求方明确「不要候选列表」）

**选项**
- **A. 延迟锁定 60s；仍失败则切 GPS 推算，并给**一个**「车牌对不上 → 核对」入口，点开才是最多 3 个 + 「都不是」的核对面板**
- B. 延迟锁定 60s；仍失败就静默使用 GPS 推算，**不给任何入口**
- C. 低置信直接显示候选列表（违背需求方要求）

**推荐：A**

**理由**：B 的风险是「用户永远无法纠正一个错判」—— 这是不可恢复的。A 把「列表」从「系统主动塞给你选」降级为「你主动点开才看到」，符合需求方「不要候选列表」的本意（反对的是**默认要求用户做选择**，不是禁止用户纠错）。

**需负责人一句话确认**：这个「核对入口」是否可接受。

## C12 需求 4 的隐藏范围

**问题**：现在「速度分档」（`TIER_TEXT`：全力冲刺有机会赶上 / 小跑能赶上 / 正常走能赶上 / 慢慢走能赶上 / 爬过去都能赶上）与「可赶上 HH:MM」（`catchHint`）共用同一个胶囊组件 `TierBadge`（`src/components/RoutePieces.tsx:65` 起），靠 `data-catch-hint` 区分。

**选项**
- **A. 只在导航态隐藏速度分档（`NavDetailBody.tsx:343`），推荐结果页与收藏页保留**
- B. 导航态 + 卡片详情态都隐藏（`CardDetailClient.tsx:236/260/294`）
- C. 全站隐藏速度分档，只留「可赶上 HH:MM」

**推荐：A**

**理由**：「全力冲刺有机会赶上」这类标签的价值在**出门前的决策时刻**（推荐结果页）—— 它回答「我现在跑还来不来得及」。用户一旦点进导航，人已经在路上或已在车上，这个信息只剩噪音。C 会削掉推荐页的核心决策信息。

**技术实现（一处改动，四种界面受益）**：给 `TierBadge` 加 `hideTier?: boolean`，导航态传 `hideTier={!firstHint.isHint}`，即「不是赶车提示就整块不渲染」。
**注意**：`catchHint`（可赶上 HH:MM）必须保留 —— 判据是 `firstHint.isHint`，不是 `tier !== null`。改完要跑 `.verify/check-ui-copy.mjs`（文案门禁）。

**需负责人确认**：`NavStrip` / `NavTrackBar` 目前不渲染速度分档（已核实），所以「到站/等车/上车后」三个状态实际只影响 `NavDetailBody` 一处。**若需求方期望的是「连详情页也不显示」，选 B。**

## C13 多策略补查（s=7/s=8）怎么处理

**问题**：`transitMs` 只统计 s=0，`fetchMultiStrategySeeds` 的 2 次额外高德调用落在埋点之外。实测只要 `strategiesUsed` 含 7/8，「未埋点」就从 **59–741ms 跳到 817–4022ms**（关闸→澳科大最差）。这段耗时目前**完全不可见**。

**选项**
- **A. 只补埋点（`multiMs`）+ 加预算上限（如 1.5s 超时即放弃补查）**
- B. 补查不挡首屏：先返回 s=0 的结果（3 张），补查完成后再推一次完整列表
- C. 提高 `MULTI_STRATEGY_WHEN_BELOW`（3 → 2），减少触发次数
- D. 不动

**推荐：A 先做，B 作为独立小迭代**

**理由**：A 零行为变化、成本极低，且它是**第二批所有收益估算的前提** —— 不把这段拆开，「未埋点」就永远是一笔糊涂账。B 的收益最大（0.8–4.0s）但会让列表「先 3 张后 5 张」，属于产品体验决策，不宜与性能修复混在一起。C 会降低补漏质量（研究报告里漏线率 20.5%→8.6% 正是靠补查换来的），不该为性能牺牲。

**代价**：A ≈ 10 行；B 需前端支持二次渲染（约 40 行 + 一次体验评估）。

**风险**：A 无；B 有「卡片跳变」风险。

## C14 观测钩子本轮到哪一步

**问题**：PM/QA 已定稿契约（`03-测试-基线测量与场景复现.md` §3.4），问我是本轮一起做还是留给下轮。这决定他们验收标准里写「必须」还是「建议」。

**选项**
- **A. 契约全部六组本轮做**（`data-geo` / `data-veh` / `data-veh-age` / `data-user-fix` / `data-board-match` / `data-match-source` / `data-switch-*`）
- B. 只做车辆数据两条（`data-veh` + `data-veh-age`），其余下轮
- C. 全部下轮

**推荐：A，但按依赖顺序分两笔提交**

**理由与工作量（按代码位置数出来，不是估的）**
- `data-veh` / `data-veh-age`：**前提是先修 D5**（把 `lastUpdateTs` 拆成 `lastVehicleTs`）。拆分本身就是 D5 的修复，钩子只是顺手多写一个属性 ⇒ **净增 ≈ 0**。→ **本轮必须做**，否则「数据陈旧」在自动化里永远隐形（车 5 分钟没更新，页面照样 200、照样不报错）。
- `data-geo`：`useUserFix` 已有 `denied` 与 `fix` 两态，补 `low_acc` / `stale` 判定约 15 行，与 C9（定位分级）同一次改动 ⇒ 边际成本极小。
- `data-user-fix`：一行 effect 写 `ts,acc` ⇒ 可忽略。
- `data-board-match` / `data-match-source` / `data-switch-*`：都挂在 `NavTrackBar` 已有的 `.nav-actions` 上，随 C10 的匹配算法一起写 ⇒ 属算法交付物的一部分，**没有额外成本**。

**共同成本**：这些属性都要「写 DOM」，会引入 `setAttribute` 副作用。硬约束：**必须放进已有 effect，不得新开 effect**，否则在 1371 行 `NavShell` + 1337 行 `useRideTracking` 上再加脏依赖会引入额外重渲染。

**风险**：低。但要守一条纪律：**钩子只读，不得成为业务判断的输入** —— 否则会退化成「为了通过验收而存在」，测试绿了但用户仍然不可用。
