### D2 取证（像素级）

`hole-flash`：`opacity: 1`、外接盒 **16.85 × 16.85 px**、圆心 (247.57, 375.67)（即钉帽孔 (48,16) 的屏幕位置），**t=0 / 100 / 200 / 300 / 420 / 460 / 560 全部如此**。

> 观感后果：M 还没开始画，终点位置就先亮了一个蓝点——"走到终点才点亮"的因果被提前泄底；且它和 §3 段 0「站环+钉首帧就位」的意图相反（钉是隐藏的，孔却亮着）。

### D3 取证

`ripple`：`opacity 0.45`、**12.35px 环**、圆心 (247.57, 469.26)（钉尖 (48,46)），t=0–700ms 恒定；仅 800ms 起才开始扩散。
> 观感后果：钉尖位置有个小亮环挂 800ms，像"脏点"。

### D5 相位取证（解析 + 实测双向确认）

`--ease-travel = cubic-bezier(0.45,0.05,0.55,0.95)` 是 ease-in-out ⇒ **路程进度 ≠ 时间进度**。反解该曲线：

- 光点到达折点（路程 69.28%）的精确时刻 = **370ms**（不是 416ms）
- 416ms 时脉冲触发，光点已经走到 **80.1% 路程**，越过折点 **9.0 用户单位 ≈ 28px**
- 476ms 脉冲峰值，光点已到 **90.6% 路程**（越过折点 ≈ 55px）

实测吻合：420ms 时 `stationScale=1.009`（刚起），460ms 才 1.146（近峰），而光点早已远离折点。
> 观感后果：「到站脉冲」读作"光点跑过去之后，背后的站牌自己闪了一下"，因果倒置。

## 3. `skipped`（点击任意处）

| 项 | 规格 | 实测 | 判定 |
|---|---|---|---|
| 淡出 → 移除 | ≤120ms | **107ms** | ✅ |
| 状态 | `skipped` | `skipped`（可覆盖 done） | ✅ |
| 穿透 | `elementFromPoint` 不落在开屏层 | 屏幕中心命中 `.nav-map__cover`，`closest('[data-splash-root]')` = **false** | ✅ |
| 假移除禁令 | 禁用 opacity/pointer-events/visibility 三种假移除 | 容器真卸载，内联 `animation: brand-splash-skip 100ms` 生效 | ✅ |

### 仲裁结论：**接受 100ms**（不必让 PM 放宽断言）

理由：
1. 视觉上 100ms 与 120ms 同属"一帧到三帧"级别，人眼无法分辨终点的 20ms 差；而"点了没反应"的阈值在 100ms 以上才成立（Doherty Threshold 400ms 是更宽的焦虑线，不是本次约束）。
2. 断言的语义是"跳过后首屏立即可交互"，100ms 动画 + 实测 107ms 正好留出 13ms 余量；改回 120ms 会让断言变成"设计迁就测试口径"，本末倒置。
3. 这条偏差的收益（可机验、有余量）大于代价（20ms 视觉不可辨）。

⇒ **确认 100ms，PM 的「≤120ms 移除」断言口径不用改。**

## 4. `reduced`（emulateMedia reduce）——**D1 现场**

| 采样时刻 | overlay | route dashoffset | route opacity | **pin transform** | state |
|---|---|---|---|---|---|
| 0.1ms | 1 | 1px | 0 | `matrix(0,0,0,0,0,0)` | null |
| 66.6ms | 1 | **0px** | **1** | `matrix(0,0,0,0,0,0)` | null |
| 87ms | 1 | 0px | 1 | `matrix(0,0,0,0,0,0)` | **reduced** |
| 204ms | 1 | 0px | 1 | `matrix(0,0,0,0,0,0)` | reduced |
| 602ms | 1 | 0px | 1 | `matrix(0,0,0,0,0,0)` | reduced |
| 移除 | — | — | — | — | 移除于 **901ms** |

**诊断**：全局杀开关（`globals.css:541`）只把 `animation-duration` 压成 0.01ms、`iteration-count` 压成 1，**没有清 `animation-delay`**。钉的 `animation: brand-anim-pin 260ms ... 600ms both` ⇒ delay 600ms 仍在：
- 0–600ms：`fill-mode: both` 的 **backwards** 分支钉住 `0% { transform: scale(0) }` ⇒ **钉完全不可见**
- 600ms 后：瞬跳到 `scale(1)` ⇒ **钉"凭空蹦出来"**
- 860ms：overlay 仍按原 delay 淡出

所以 reduced-motion 用户看到的不是"静止末帧完整 logo"，而是：**M 瞬间画好、没有钉，停了 600ms 之后钉突然出现，再淡出**。

**这个状态比"空 M"更糟**（终裁采信）：空 M 至少是"没画"，D1 是"画了又没了、然后凭空有了"——三个矛盾状态连续，用户的解释只能是"这 App 坏了"。这也直接踩红 QA 的 S6/P4「静止末帧完整 logo」断言。

> 这与我在 §6 写的 fill-mode 红线是同一个根因的另一半：**我防了 fill-mode，没防 delay**。

### D1 修法（可直接抄，加在 globals.css 品牌区段末尾）

```css
@media (prefers-reduced-motion: reduce) {
  /* 静止末帧：M 路线 + 站环 + 钉一次性呈现为完整 logo，不参与任何补间 */
  .brand-splash__mark,
  .brand-splash__mark * { animation: none !important; }
  .brand-splash__mark .brand-mark__pin { transform: none !important; }
  .brand-anim__dot,
  .brand-anim__hole-flash,
  .brand-anim__ripple { opacity: 0 !important; }

  /* 覆盖层：立刻淡出（100ms），不占用 860ms 的叙事档期。
     ⚠️ 必须沿用同名 keyframes brand-splash-exit —— JS 的 animationend 靠这个名字移除容器。 */
  .brand-splash__overlay { animation: brand-splash-exit 100ms linear 0ms both !important; }
}
```

效果：reduced-motion 下总耗时 ≈ 100ms（而不是 901ms），且画面是完整静态 logo，符合 PM「直接显示静止末帧」。

### D4 诊断

`globals.css` 里 `offset-path` **只在 `.brand-anim--narrative .brand-anim__dot` 上定义**（L8625–8626），循环版 `.brand-anim--loop .brand-anim__dot`（L8694）只给了 `animation`。
⇒ 循环版光点没有路径，`offset-distance` 完全无效，元素停在 `cx/cy` 缺省的 (0,0)，即该 48px 画布的左上角外侧。
⇒ **加载动画的"主角"实际上是隐形的**，用户只看到折点站环每圈脉冲一次 + 钉轻微呼吸——"光点沿 M 走"这个核心语义在加载态丢了。

### D4 修法（1 行）

```css
.brand-anim--loop .brand-anim__dot {
  offset-path: path("M12 48 L12 16 L30 34 L48 16"); /* ← 缺这一行 */
  offset-rotate: 0deg;
  animation: ...
}
```
或把 `offset-path`/`offset-rotate` 提升到公共选择器 `.brand-anim__dot`，两个变体共用（更少重复，也不会再漏）。

### 另需 team-lead 决策：组件未挂载 —— **已解，本期必上**

`grep` 全仓：`BrandRouteLoader` **除自身定义文件外没有任何引用**（首页/导航页均未使用）。页面当前的 `.nav-map__cover` 加载态是**静态骨架 `rc-sk`**。也就是说"加载动画"当时只是**已交付但未接入**的组件。

team-lead 已裁定：**本期必须接入**（替换 `NavMap.tsx:1622` 的静态骨架）——没有这一处接入，负责人的「加载动画」需求只完成了一半。

> 这条同时解释了为什么 §11 的"末帧→加载态"其实是**天然暴露**（见规格 §11.3 v1.5）：加载态本来就在地图容器里跑着，开屏覆盖层盖在它上面，淡出即露出。我原先设计的交叉淡化/收缩方案因此作废——那是在"加载态不存在"的误判下设计的。

## 9. 观感附记（每次进入都播之后的可重复观感）

## 4. 双影实测（P7a）—— 通过，但我的第一版测量方法有错

慢网下（拦截高德域名 4s）loader 真出现，实测几何：

| 元素 | 中心 | 尺寸 |
|---|---|---|
| 大 M（开屏末帧） | (195, 422) = **屏幕中心** | 187.2 × 187.2 |
| 小 M（cover 内） | (152, 390) | 48 × 48 |
| 圆心距 | **53.6px**（垂直 32 + 水平 43） | — |

> 注：垂直差实测 **32px**，不是我此前估的 45px——headless 无 safe-area，`.nav-map--full` 的实际让步是 `tabbar 64px`（844−780）。真机 iPhone 含 safe-area 34 时约 49px。**不影响结论**（都是"不同心"）。
> 水平差 43px 来自 `.brand-loader` 是 **row** 布局（图标在左、文案在右，整体 134px 居中）⇒ svg 偏左。

**判定：双影不可辨。** 三条互相独立的理由：

1. **几何包含**：小 M 包围盒 (128,366)–(176,414) **完全落在大 M 包围盒** (101.4,328.4)–(288.6,515.6) 内部。用户看到的不是"两只 M 并排"，而是"大 M 里面有个小 M"。
2. **同色吞没**：小 M 的竖段（viewBox x=12）恰好落在大 M 竖段的覆盖带内（大 M 屏幕线宽 = 6.5 × 187.2/60 ≈ **20.3px**，半宽 10.2px；两段 x 相差仅 1.4px）。两者同为 `--brand-route`，叠加后**颜色不变** ⇒ 小 M 的左侧轮廓在大 M 的粗线内**根本不可分离**。
3. **不透明底衰减**：overlay 的 `background: var(--bg)` 是**不透明**的，其 `opacity` 同时衰减"自身内容"和"透出的下层"。实测 overlayOpacity：860ms=1.0 / 880ms=0.934 / 900ms=0.777 / 920ms=0.561 / 940ms=0.301 / 960ms=0。
   ⇒ 880ms 时小 M 只有 **6.6%** 透出，920ms 时 44%，**要到 t>925ms 才过半**；而那时大 M 也只剩不到一半不透明度。

**自我修正（记录以免误导）**：我最初用"小 M 坐标 vs 空白背景"的像素差（Δ=289）当作"小 M 完全可见"的证据——**那是错的**，因为我取错了基准：小 M 采样点正处于大 M 的粗线覆盖区，底部本就是品牌蓝，不是背景色。改成"几何包含 + 同色吞没 + 不透明底衰减"三条论证后结论才成立。**单点像素 diff 不能用来判"是否可见"，必须先把图层关系搞清楚。**

## 5. 新缺陷 N1（P2）· cover 前 300ms 是空容器

实测（慢网 + 点击跳过）：

| 时刻 | 覆盖层 | cover | 子元素数 | 文本长度 | 骨架 | 小 M | 文案 |
|---|---|---|---|---|---|---|---|
| 0ms（点前） | 在 | 在 | **0** | **0** | 无 | 无 | 无 |
| 125ms（覆盖层消失） | **移除** | 在 | **0** | **0** | 无 | 无 | 无 |
| 205ms | — | 在 | **0** | **0** | 无 | 无 | 无 |
| 303ms | — | 在 | 1 | 6 | 无 | **有** | **有** |

**成因**：`rc-sk--big` 骨架与外部文案已按设计移除，cover 内只剩 `<BrandRouteLoader>`；而该组件有 `GATE_MS = 300` 门控，前 300ms 返回 `null` ⇒ **cover 是个不透明的空容器**。

**影响分级（v2.1 修正：P1 → P2）**：
- **正常路径**（不跳过）：前 300ms 被开屏覆盖层遮住 ⇒ **不可见，无影响**。
- **跳过路径**：用户约 100ms 跳过 ⇒ **看到约 147ms 的纯色空容器**（QA 逐帧复测：+115ms 开屏撤走，+262ms 才有内容）。点跳过的人是为了快点看到内容，结果先看到一块纯色——可感知，但**损伤有限**。
- **无开屏路径**（客户端路由回首页）：空白 300ms。

**为什么从 P1 降为 P2**（我修正了自己的判断）：cover 有 `--surface-dim` **底色，不是白屏**；147ms 远低于 Doherty 400ms 感知阈值；且只在"主动跳过"这条少数路径可见。我最初把它说成"纯空白地图容器"是**夸大**——纯色底与白屏在感知上不是一回事。

**修法（设计裁定：方案 2）**：`GATE_MS = slot === "map-cover" ? 0 : 300`。

**为什么否掉"文案不受门控"（QA 原推荐的最小改动）** —— 实测证明它更糟：

| 状态 | 文案中心 | loader 整体 |
|---|---|---|
| 只有文案（0–300ms） | cx=**195**（居中） | w=78, cx=195 |
| 图标+文案（300ms 后） | cx=**223** | w=134, cx=195 |

`.brand-loader` 是 `flex-direction: row` + 整体居中 ⇒ 插入 48px 图标后整组重新居中，**文案被推右 28px**。空窗是"没有东西"，跳位是"**东西动了**"——人眼对移动的敏感度远高于对静态缺失，28px 横移是可指认的界面故障，147ms 纯色块大概率无感。
> 注意：若 B 形态是 column 布局（我规格原意），此方案成立；实现选了 row（见 §6 N2），故废。

**为什么否掉"门控起点绑开屏是否仍在"**：会让 loader 依赖开屏组件状态，违反既定「`active` 绑真实 `phase`、不绑 `splashGone`」。

**"闪一下"担忧不成立**：cover 只在地图 loading 时存在；若 50ms 就绪，用户看到的就是"一块底色闪一下"——图标跟它同生同灭，是"整体闪一下"，不比纯色块更糟。A 形态（`request` slot）保持 300ms 门控不变。

## 6. N2 · loader 布局与规格不符（需改规格，非缺陷）

规格 §5.1 写 B 形态是"图标上、文案下（`gap: 8px` 纵向）"，实测是 **`flex-direction: row`**（图标左、文案右，`gap: 8px`，整体 134×48 在 cover 内水平垂直居中）。

**裁定：接受 row，改规格描述。** 理由：
1. "图标 + 文字"横排是加载提示的通用样式（与 A 形态完全一致）⇒ 两形态**布局零差异**，只差位置，"两种加载动画"的可能性进一步降低。
2. 整体宽 134px 在 390px 屏占 34%，视觉稳定，不像 48px 单图标那样"孤零零"。

**a11y 通过**：live region（`role="status"`）就是 `.brand-loader` 本身，`textContent` 长度 6（"地图加载中…"），落在区域内 ⇒ 屏幕阅读器可播报。文案由 `label` 传入（组件外无残留 span）。

## 9. 采样方法的自我修正（供 QA 参考）

`data-splash-state` 的写入发生在 React effect（paint 之后），实测 `t=0` 采样可能是 `null`。⇒ **不要用固定时刻断 state**，用 `waitForFunction` / MutationObserver 等状态出现（架构师已同步 QA）。这不影响"容器移除时机"的测量（那是 DOM 事件驱动的）。
