# ADR-109：剩余时间统一为「首跳位置剩余 + 后续静态跳」

## Status

Proposed（2026-11-04，待 team-lead 裁决）

## Background

导航中刷新后，「站间行驶 ↔ 进站停靠」切换时预计到达时间突变。定位结果：

- `segRemainSec`（客户端上行的位置感知剩余）实际是**首跳剩余**（到下一站），来源是 `md × h[1−p]`，其中 `md` 取自 `route_hop_stats` 的**相邻站对**中位时长（`src/lib/nav/progress.ts:230-243`）。
- 服务端 `recomputeRemaining` 直接把它当**整段剩余**（`src/lib/nav/remaining.ts:234`），未叠加「下一站之后到下车点」的跳。
- 同仓库另一处（`src/lib/recommend/live.ts:183-186`）用的是正确口径：`etaSec = locSeg.remainSecD + restSec`，即「首跳位置剩余 + 后续静态跳」。
- 车辆一停靠，`attachProgress` 因 `status !== "moving"` 跳过该车（`progress.ts:201`），客户端 `segRemainSec` 变 `null`，服务端回退到「从 `nextIdx` 起逐跳」。

**第二处缺陷（与跳变同源）**：停靠时 `progressOf` 给的是 `passedIdx = atIdx − 1`、`nextIdx = atIdx + 1`
（`src/lib/nav/track.ts:76-85`），而 `hopMinutesFrom` 是「从 `fromIdx` 起累加」⇒ 把
「所停站 → 下一站」这一跳**整个跳过** ⇒ 停靠态系统性少算一跳。

数值后果（合成输入，见 `docs/迭代-导航修复-20261104/02-技术-根因与方案.md` §1.2）：
同一 OD 在 24 秒内，剩余时间 0.3 分 → 2.0 分 → 2.67 分（两次都上涨，与「时间应递减」相反），
其中停靠那一刻的 2.0 分比真值 5.0 分少算 3 分钟。

## Decision

**「剩余」只有一个定义，且必须指定「基准站」：**

```
legRemain = 首跳剩余 + Σ（从基准站起到下车点的后续跳）
基准站 pivotIdx = prog.kind === "at" ? prog.atIdx : prog.nextIdx
```

落地三条：

1. `src/lib/nav/remaining.ts` 的当前腿剩余改为 `segRemainSec/60 + hopMinutesFrom(ctx, ride, pivotIdx)`；无 `segRemainSec` 时退化为 `hopMinutesFrom(pivotIdx)` → 再退 `curRide.minutes`（三档回退链保持不变）。
2. 新增纯函数 `remainFromIdxOf(prog)`（`src/lib/nav/track.ts`）= `kind === "at" ? atIdx : nextIdx`，供 `NavShell.tsx:428` 上行。**停靠时必须传 `atIdx` 而不是 `nextIdx`** —— 这是第二处缺陷的修法。
3. 停靠态由客户端显式给 `segRemainSec = 0`（而非 `null`），判据是车辆帧明确显示该车停靠在本段站（`v.atStation != null`）。**不得**用「`progress` 字段缺失」推断停靠 —— 那只说明车丢了。

同步要求：`src/components/nav/NavDetailBody.tsx` 的 `etaBaseMin`（「还有几分钟」）必须同批改为同口径，否则顶部总时长与副标题会立刻分裂成两个真相。

明确不做：不改 `/api/nav/remaining` 的入参**字段集**（`nextIdx` 语义收紧为「基准站」，不新增字段）；不改 `progress.ts` 的 `status !== "moving"` 排除逻辑；不在本批引入基于 `route_station_mileage` 的统一里程轴（见 Consequences 的后续项）。

## Consequences

正面：

- 状态切换单调（同一合成输入：5.34 → 5.00 → 4.67 分，相邻 delta −0.34 / −0.33），符合「时间只会越过越少」的直觉。
- 停靠态不再少算一跳（2.0 → 5.0 分），这是本修法顺带修掉的第二处缺陷。
- 纵条「车上约 N 分」由「只到下一站」修正为「到下车点」，与产品语义一致。
- 停靠时长不再被丢弃：`remainingMin` 恒定而 `arriveAt` 随 `now` 顺延，到达时刻不再系统性偏早。
- 可用三条极简断言锁死（当前实现必红、修好后必绿，同时是根因证据与回归锁）：
  ① 相邻帧 `remaining[i+1] − remaining[i] ≤ +0.1 min`；
  ② 停靠态 `remainingMin === hopMinutesFrom(atIdx)`；
  ③ `|Δ| ≤ |segRemainSec[i]/60| + 0.1`（切换瞬间的精确幅度）。

两个数值上界（推导见技术方案 §1.6.1）：

- 连续刷新 `|ΔarriveAt| ≤ 15 000 ms`（6 000 ms 来自 `round1` 双向量化 + ≤8 300 ms 来自 `h` 曲线 20 桶跨桶阶跃，向上取整留余量）。多段卡另需剔除「`headwayAt` 命中桶变化」的样本对。
- 切换瞬间 delta 用可记录序列直接检验的恒等式（`|Δ| ≤ |segRemainSec[i]/60| + 0.1`），而非用 `fused` 的理论上界 —— 后者依赖 `u` 估计，太松且不可验证。

负面（均已承接）：

- `patchedCard.rides[legIndex].minutes` 的值会变大（变正确），既有快照断言需同步更新。按「活规格」纪律：先改断言，再改实现。具体数值推算见技术方案 §1.5.1（`scripts/test-remaining.ts` ① 组：`rides[0].minutes` 由 2 变 6，`remainingMin` 由 22.7 变 26.7 —— 前提是该用例补传 `nextIdx=1`）。
- 轻轨段无 `segRemainSec`，本 ADR 对轻轨剩余时间精度**无改善**（仍走逐跳静态）。轻轨要改善需要统一里程轴（下一个 ADR）。

后续项（本 ADR 的严格超集，不返工）：

用 `route_station_mileage` 建「沿线里程阶梯」（与 `src/lib/nav/lrt-progress.ts#buildLrtLadder` 同构，该函数实现是通用几何里程函数、非轻轨专用），把车辆投影里程与用户投影里程统一到一条里程轴，再由 `lookupHop` + 段内插值转时间。届时「巴士 / 轻轨 / 停靠 / 行驶」四种状态共用一套进度，本 ADR 的拼接公式成为它的第一阶段特例。
