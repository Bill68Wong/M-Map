# ADR-112：线路运营状态判定（`serviceStateAt`）与「未走标签可乘性过滤」落点

## Status

Proposed（2026-11-04，待 team-lead 裁决；数据前提已由 PM 实测确认）

## Background

需求 8：推荐卡与详情页的**段内并列线路标签**（如 `25/N3`）会把当天不营运的线路也列出来。早上显示 `25/N3`，而 N3 是通宵线（`daily 00:00–06:00`），早上根本不开。

根因（PM 定位，架构复核一致）：`enumerate.ts` 的 `parallelRoutesFor`（`:49-67`）只校验
「共享首跳（`adjOwners`）+ 该线能解出 board→alight 逐跳」，**不读运营时间、也不读实时车**；
`RecommendCard.tsx:133` / `NavDetailBody.tsx:199` / `StationReachFold.tsx:192` 均无条件拼
`[route, ...parallelRoutes]`。

### 判定原语的缺口：`headwayAt` 的 `null` 是多义的

`headwayAt`（`headway.ts:159-200`）只有两种返回：命中 → `HeadwayHit`；否则 `null`。而 `null` 至少覆盖四种情况：

| 情况 | 现状返回 | 真实语义 |
|---|---|---|
| 该线完全不在 `route_frequency` 表里 | `null`（`:164-165`） | **零信息** |
| 有该线，今日无匹配 `dayType` 的行 | `null`（`:177-198` 无命中） | 今天不营运 |
| 有该线，此刻在所有窗口之外 | `null` | 已收班 / 未首班 / 内部断档 |
| 有该线，此刻落在两个时段之间的空档 | `null` | 断档（尖峰专线常见） |

⇒ 若直接把 `null` 当「收班」，任何没抓到班距表的线路会在白天被永久隐藏（**这是架构 v1.0 的担忧**）。

### 数据实测（PM 连库只读查询，2026-11-04）

`route_frequency` 全表 **512 行 / 96 线**；`day_type` 分布：
`mon_sat 230 / sun_holiday 151 / mon_fri 60 / daily 26 / sat 22 / sat_sun_holiday 18 / special 5`。

关键样本（与官方通告逐字一致）：

```
N3  | daily       | 00:00–06:00 | freq 20~25
N1A | daily       | 00:00–06:00 | freq 14~17
N2  | daily       | 00:00–06:00 | freq 15~18
25  | mon_fri/sat/sun_holiday | 06:00…20:00–01:15（4 段，末段 to_min=1515，跨午夜）
```

⇒ **N3 在表里，前置阻断解除**，需求 8 数据上可做。

另有两组「不是零信息」的事实：

- **真实内部断档 10 组**（同 `day_type` 内相邻两行不连续，全是尖峰专线）：
  `17S|mon_sat` 570→930、`25AX|mon_fri` 540→960、`25BS|mon_sat` 570→1020、
  `30X|mon_sat` 600→900、`3AX|mon_sat` 570→900、`51B|mon_sat` 600→900、
  `59|mon_fri` 600→900、`59|sat_sun_holiday` 600→900、`5X|mon_fri` 570→1020、`MT5|mon_fri` 600→900。
- **缺日覆盖 13 条**：`17S 25AX 25BS 2AS 30X 3AX 51B 5X 6B 701XS H2 MT5` 只有 `mon_sat`/`mon_fri`；
  `15T` 只有 `sat_sun_holiday`（与 `live.ts:268` 注释「15T 平日不运营」互证）。

## Decision

### 1. 判定原语：新增纯函数 `serviceStateAt`（client-safe，`nowMs` 可注入）

```ts
export type ServiceState = "open" | "closing" | "closed" | "before_first" | "no_data";
export function serviceStateAt(
  idx: HeadwayIndex,
  route: string,
  nowMs?: number,
  opts?: { gTailMin?: number; gHeadMin?: number },
): ServiceState;

export const SERVICE_G_TAIL_MIN = 20;
export const SERVICE_G_HEAD_MIN = 0;
```

**五态分支表**（`R` = 该线中 `matchesDayType` 为真的行集合；`t0 = nowMin`，`t1 = nowMin + 1440`）：

| 序 | 条件 | 结果 | 理由 |
|---|---|---|---|
| ① | 该线不在 `byRoute`（含「只剩 `special` 行」——载入即被 `headway.ts:79` 排除） | `no_data` | **零信息**，不隐藏 |
| ② | `R` 为空（有该线但今日无匹配 `dayType`） | `closed` | 今天不营运（如 `15T` 平日、12 条线周日） |
| ③ | `t0` 或 `t1` 落在 `R` 任一行区间内 | `open` | 正在窗口内 |
| ④ | 未命中，且 `nowMin` 距「`R` 中最晚的 `maxTo`」≤ `G_tail` | `closing` | 末班刚走，车可能还在路上；未知时保守保留 |
| ⑤ | 未命中，`t0 < minFrom − G_head` | `before_first` | 今天还没首班（文案可给「今天首班 06:00」） |
| ⑥ | 其余（含内部断档、已过 `maxTo + G_tail`） | `closed` | 见下方「为什么断档判 closed」 |

`closing` 的 `maxTo` 必须**自扫 `R` 取最大值**，不能用 `headwayAt` 的 PRIORITY 单命中结果 ——
PRIORITY（`headway.ts:173`）是「取最具体的 `dayType` 那一行」，拿不到当日最晚 `toMin`。
跨午夜行（`toMin > 1440`）用 `t1` 比对，复用 `:171` 的双探针口径。
**不得复制第二套 `dayType` 匹配**：统一调 `matchesDayType`（`headway.ts:48`）+ `macauNowParts`（`lib/lrt/day-type`）。

### 2. 为什么「内部断档 ⇒ `closed`」而不是 `no_data`（采纳 PM 的实证修正，推翻架构 v1.0）

架构 v1.0 主张「断档 ⇒ `no_data`」，理由是「怕白天假隐藏」。PM 用两组实测数据推翻，**架构复核后认同**。

**支点是不对称性**：隐藏判据里 `presence === has` **永远优先显示**，故两种误判的代价不对等：

| 误判方向 | 最坏后果 | 与本次 bug 的关系 |
|---|---|---|
| 误判 `closed`（实际在跑） | 该线在**无车**时不显示 | 「无车」本来就不该显示 ⇒ 无害 |
| 误判 `no_data`（实际不跑） | 该线**全天都显示** | **正是本次要修的 bug** |

逐条对照 `presence` 三态：

- `presence = has`（有车，主线路必有覆盖）：**无论怎么误判都显示**。⇒ 断档里真的在跑的线，只要有车就不会被藏。
- `presence = none`（明确无车）：断档里不该有车 ⇒ 隐藏正确。
- `presence = unknown`（并行线未被 `fetchLive` 覆盖，见 §4）：这才是唯一有风险的一格，且已被 §4 登记为已知取舍。

⇒ `no_data` **只留给零信息**（情况 ①）。有该线就有信息，就该参与判定。

反证检验（PM 给的样例，架构复算成立）：

- `59` `mon_fri` 10:00–15:00 断档：12:00 时 `t0=720` 不在任何窗口、距 `maxTo`（约 1320）远 ⇒ `closed` ⇒ 正确隐藏。
- `17S` `mon_sat` 09:30–15:30 断档：同时段 ⇒ `closed` ⇒ 正确。
- `15T` 平日：`R` 为空 ⇒ `closed` ⇒ 正确（原先会显示）。
- `N3` 05:00：`t0=300 ∈ [0,360]` ⇒ `open` ⇒ 显示（正确，通宵线此刻在跑）。
- `25` 01:00：`t1=60+1440=1500 ∈ [1200,1515]` ⇒ `open`（跨午夜正确）。
- `25` 03:00：`t1=1620 > 1515`，`t0=180 < 360 − 0` ⇒ `before_first`（不是 `closed`，文案更有用）。

### 3. 架构否决了一个曾考虑过的细化（记录以避免反复）

曾考虑把 `G_tail` 从「末班后」推广为「**每个窗口结束后**都留 20 分钟 `closing` 带」（即内部断档开始的头 20 分钟也算 `closing`）。
**否决**，理由与本 ADR §2 的支点冲突：那 20 分钟内断档线会被当作「未知保守保留」而显示，
等于在同一条线上重新引入一小段「不营运却显示」。**规则一致性让位给不对称性** ——
`G_tail` 只挂在当日 `maxTo` 上，语义单一、可测、可解释。

### 4. `presenceOf` 独立成纯模块

`presenceOf(live)` → `"has" | "none" | "unknown"`，与 `serviceStateAt` 分开（前者读实时，后者读时刻表）。
两者组合成隐藏判据：

| `serviceState` | `presence` | 结果 |
|---|---|---|
| `open` | 任意 | **显示**（无车由「未发车估算」承接，不是隐藏理由） |
| `closed` / `before_first` | `has` | 显示 |
| `closed` / `before_first` | `none` / `unknown` | **隐藏** |
| `closing` | `has` | 显示 |
| `closing` | `none` | **隐藏**（仅「明确无车」才隐藏） |
| `closing` | `unknown` | 显示（保守保留） |
| `no_data` | 任意 | **显示**（永不因时间隐藏） |

并行线拿不到实时 ⇒ 恒 `unknown` ⇒ 只在 `closed` / `before_first` 下被隐藏，`closing` 带内会残留 ≤20 分钟假阳性。
**接受，不为并行线补取数**：那会让每次推荐多 N 次 DSAT 调用，撞 `DSAT_QPS = 3` 的全局单桶
（`src/lib/amap/rate-limit.ts:46`）⇒ 成本远大于收益。属**已知取舍**，不是遗漏。

### 5. 过滤落点：`model.ts:609-611`（不是 `enumerate.ts`）

架构 v1.0 曾主张在 `enumerate.ts:49-67` 的 `parallelRoutesFor` 内过滤，**该主张错误，已撤回**。
两条硬证据：

1. `enumerateOptions` / `optionsFor` 在 `fetchLive` **之前**执行（`service.ts:126` vs `:134`）⇒ 那一刻**没有实时、也没有班距上下文**，物理上判不了。
2. 在纯函数里读时钟 ⇒ 边界单测无法注入 `nowMs`。

改为 `src/lib/recommend/model.ts:609-611`（`parallelRoutes: seg.parallelRoutes` 写入 `RideLegView` 的那一处）。四条理由：

1. 是 `/recommend`（`service.ts:147` 的 `modelOption`）与 `/nav`（`nav-service.ts:547` 的 `modelOption`）两条链路的**唯一汇合点**；
2. `ctx.headway`（`model.ts:259`）与 `ctx.live` 都已在上下文里 ⇒ 判定所需的两个输入都齐；
3. 下游 3 个渲染器 + `strips.ts:48`（`boardRouteOf`）+ `favorites/snapshot.ts:81` **全部读 card**
   ⇒ 改这一处它们自动一致，**`snapshot.ts` 无需单独改**（架构 v1.0 的「必须同批改」顾虑因此自动消解）；
4. `siblingSeedsOf` 读的是 `opt.segments[0].parallelRoutes`（**seed，未过滤**，`nav-service.ts:555/598`）
   ⇒ **AC-95 的后续班次建模不受影响**。过滤只作用于「展示」，不作用于「建模」。这是架构 v1.0 担心的回退点。

### 6. 一致性硬要求（PM 补充，架构认可为必须）：同一谓词必须同时作用于 `altBuses`

若只过滤 `rides[].parallelRoutes` 而不过滤 `altBuses`，会出现
「标签里没有这条线、后续班次行里却有它的车」—— 这是比原 bug 更难解释的新矛盾。
⇒ 同一 `isBoardable` 谓词必须同时作用于：

- `/recommend`：`service.ts:161-163`（`m.alts.filter(...)` 处）
- `/nav`：`nav-service.ts:704-724` 的 `backfillAltBuses` 末尾（`m.card.altBuses = dedup` 之前）

## Consequences

正面：

- 需求 8 主场景（早上 `25/N3`）在 `closed` / `before_first` 下**完全生效**，不再依赖实时数据是否覆盖并行线。
- 判定逻辑收敛为两个纯函数（`serviceStateAt` / `presenceOf`）⇒ 可用 3×5 真值表穷举单测，防「沉默逻辑错误」。
- 顺带修掉 13 条缺日覆盖线路（`15T` 平日等）全天显示的问题 —— 这些在本次需求之前就已存在。
- 过滤落点从生成处移到 card 汇合点，`snapshot.ts` / 三个渲染器 / `strips.ts` 全部自动一致，无遗漏风险。

负面（均已承接）：

- `closing` 带内并行线会残留 ≤20 分钟假阳性（§4 已登记为已知取舍）。
- `closed` / `before_first` 下 `unknown` 即隐藏 ⇒ 若某并行线实际在跑但实时未覆盖，会被隐藏。
  缓解：该风险只在 `presence` 覆盖不到的并行线上，且方向与「本次要修的 bug」相反（少显示 vs 多显示），按 §2 的不对称性判为可接受。
- 过滤后**组合卡的后续班次条数会减少**（少了不可乘线）⇒ 必须量测「只减少不可乘线、没误伤可乘线」，
  写成可验收断言（PM 的 AC-12.5）。这是 AC-95 修复的收窄面，不是回退。

验收（采纳 PM 的 PRD §6.4-6.6）：

- 真值表：`serviceState` 五态 × `presence` 三态 = 15 格逐条断言（含 `unknown` 的每一格）；
- 边界样例必须保留：`N3@05:00 = open`、`25@01:00 = open`、`25@03:00 = before_first`、
  `59@12:00 = closed`、`17S@12:00 = closed`、`15T 平日 = closed`、不支持线路 = `no_data`；
- 一致性：任一卡的 `altBuses` 中出现的线路，必须都能在同一卡的 `rides[].parallelRoutes` 或主干线里找到（反向也成立）。
