# ADR-118：终态判定用方向敏感白名单，且只在写入时算一次

## Status

Accepted（2026-11-06 · 迭代批次 `docs/迭代-跨境交通-20261106/`）

> 本 ADR 记录判定架构与它的失效形态。四张白名单的正则条目、fixture 断言与验收用例属于实现，
> 权威定义在 spec §2.10.3 / §2.10.5 / §6，此处不复述，避免正则改动要同步改两份文档。

## ① 我们选了什么

**判定入口只有一个**：`classify(source, dir, raw)`，按 `(source, direction)` 分表匹配
（机场离澳/抵澳、船离港/到港四张表），**锚定开头 + 显式列表**，不用 `includes` 式的字符串包含
（spec §2.10.3 行 1000–1012、§2.10.6 行 1068–1077）。首个命中即返回，未命中走 unknown 兜底。

**结果写入时算好落库**：`is_terminal` 是表列，不是查询时推导。SQL 只读该列
（`AND is_terminal = false`），前端只读 `isTerminal`；**SQL 与前端都不许写第二份判定**
（spec 行 78–82、265、401、1095、1444）。落库后唯一判定入口就是 `classify()` 这个无 IO 的纯函数，
测试只需测它一个。

**未知一律归「非终态」**（`unknown` / `terminal: false`）。理由（spec §2.10.4 行 1028–1031）：
归终态 ⇒ 未知状态被静默剔除 ⇒ **不可恢复的信息丢失**，用户无法知道有这班；归非终态 ⇒ 最坏是
「最近五班」混进一条已走的班次，代价是 5 个位置里丢 1 格，**可恢复**，用户看一眼时刻就知道。
即：漏显示不可恢复，多显示可恢复。

**核心实例（本决策存在的理由）**：离澳 `已啟航 08:20` = 已从澳门飞走、用户赶不上 ⇒ **终态**；
抵澳 `已啟航 預計到達 21:12` = 已从始发地起飞、即将抵达澳门 ⇒ **在途，非终态**。
同一字面在两个方向含义相反（spec §2.10.2 行 938–942、§10 TRAP-01 行 1413；验收用例见 spec
行 1314 的 `status='已啟航 08:20'`，实测原文见
`scripts/fixtures/xborder/airport-arr.json:447` 的 `已啟航 預計到達 21:12`）。
成因是两个接口为同一份 FIDS 数据的两个方向切片，`status` 的参照系随之翻转，上游不会为方向
改字段名或加方向前缀（spec 行 1414）。

## ② 为什么不是另一个（含被否方案的具体代价）

**字符串包含 `includes('已啟航')`，或把四张表合成一张按字面全局判。**
代价不是「可能出错」，是**出错后不会有人来报**。后果链（spec §10 TRAP-01 行 1418–1436）：

```
判错（抵澳「已啟航 預計到達 HH:MM」被当终态）
  ⇒ after=now 把它剔除 ⇒ 抵澳板少了全部「在途即将落地」的航班，整片隐藏
  ⇒ 深夜的抵澳列表本来就少，空板看起来完全正常
  ⇒ 排查者得出「深夜没航班」，与预期一致，不认为有 bug
  ⇒ 只在白天有人真正打开时才暴露，且形态是「少几班」而不是报错 / 白屏
  ⇒ 没人会为「少几班」提缺陷，用户以为「今晚就这几班进港」
  ⇒ 缺陷存活数月，期间所有抵澳数据都不可信
```

spec 行 1436 的对照：「崩了」5 分钟就有人报，「静默少显示」能活几个月——**故障的可见性比
故障的严重性更决定它活多久**。另有两条即时代价：`includes('已啟航')` 即使上游一字不改也会
命中错误分支 `已啟航 預計到達 …`（spec 行 1072）；上游改字（如 `航班延誤至 18:40` →
`延誤 18:40`）时 `includes` 永不命中，表现为「最近五班永远是当日最早的 5 班」，不报错不告警
（spec 行 907）。白名单前缀锚定则放宽方向恒为 `unknown` ⇒ 非终态 ⇒ 多显示（spec 行 1073–1076）。

**SQL 里写方向敏感 `CASE`，或前端按 `statusKind` / `schedTime < now` 自行再推一遍。**
代价是制造第二个判定入口：spec 行 1442 原话「若 SQL 里有一份、TS 里有一份 ⇒ 不是『可能漂移』，
是『必然漂移』，区别只在什么时候被发现」。前端按 `schedTime` 早于当前时刻就隐藏，会同时犯
两个错——把延误未起飞的航班错误隐藏，以及制造第二个判定入口（spec 行 1095）。本项目已有
「同一逻辑两处实现然后漂移」的教训（`proxy.ts:16-20` 记了三次漏登记白名单，spec 行 378）。

**未知归终态。** 代价见 ① 的兜底取舍：静默剔除是不可恢复的信息丢失，且同样落在上述后果链的
「少几班」形态里。

## ③ 什么条件下重新评估

- **上游新增或改写状态字面**（`unknown` 上升）：补白名单条目并重跑 fixture 覆盖率断言。
  方向隔离依赖 dep 表「已啟航 后紧跟数字」这条隐式防线，任何放宽该形态的改动都可能把抵澳
  在途航班判成已飞走，故改动后必须重跑断言（spec 行 1017、1035–1043）。这是**补表**，
  不是改判定架构。
- **船侧出现本轮无实测样本的「取消／延誤／滿」**：先取样本再登记，不得凭空造映射
  （spec 行 934/987）。同样是补表。
- **判定架构本身的重评条件**：当上游把 `status` 从自由文本改为带明确 terminal 标记的结构化枚举时，
  方向敏感白名单可整体退役，届时再评估是否还需要 `classify()` 这一层。
  （此条为本 ADR 设定的前瞻条件，spec 无对应条目，属我方设定而非既有事实。）

除第三条外，方向敏感分表与「写入时算一次」不因上游改字而重评——上游改字正是这两条设计
预设会发生的情况。
