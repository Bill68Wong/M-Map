# ADR-115：下车站收敛（一卡一个下车点）—— 站台码归一、代表站选取、备选降级

## Status

Accepted（2026-11-04，负责人拍板「一卡一个下车点」；本 ADR 记录工程实现决定与两次实测纠正）

## Background

推荐卡此前对「同一线路、同一上车站、多个可下车点」会各出一张卡，造成同线重复。
负责人已拍板采用 **A 方案：一卡一个下车点**（不是卡内并列多下车点）。

工程上这不是「本来就这样」，而是**当前实现并没有真正收敛**，存在两类重复来源，必须分别修：

1. **站台码字符串级去重**：`alightsOf`（`enumerate.ts:203-212`）与 `boardsOf`（`:196-202`）
   末尾都是 `applyStopPriority([...new Set(out.filter(Boolean))])` ——
   `new Set()` 是**字符串全等**，而 `C690/3`、`C690/1`、`C690` 是**同一物理站**。
2. **同线不同下车点**：`enumerateOptions` 对 `alightsOf` 返回的**每一个** alight 各生成一个
   `OptionSeed`（`enumerate.ts:265-275`）⇒ 同一线同一 board 下，N 个 alight 就 N 张卡。

## Decision

### 1. 站台码归一只改去重键，不改展示值

去重键由 `new Set(字符串)` 改为 `dedupeByMain`（按 `mainCodeOf` 归一）。
对应 **PRD R5 / 批次 IMP6**（`dedupeByMain` 替换 `[...new Set(...)]`）。

**硬约束：归一只用于「去重键」与「收敛键」，`board` / `alight` 的展示值必须保留原始站台码**
（如 `C690/3`）。否则用户看到的站名与实际站台不符 —— 这条是 PRD AC-9.17 的硬要求。

### 2. 收敛落点：`service.ts` 建模之后、`sortCards` 之前

**不是 `enumerate.ts`**（团队最初都写错过）。原因：

```
enumerate.ts 只产 OptionSeed（未建模，没有 totalMin）
modelOption 在 service.ts:146-149 的循环里才跑
⇒ 枚举阶段无法回答「哪个下车站更快」⇒ 选不出代表站
```

正确顺序（与 PRD §4.5.1 一致）：
```
枚举 → R1 站内互斥 → R4 设边界 → 建模(modelOption 循环)
→ R2 同线收敛(service.ts) → R3 降级备选 → sortCards → slice(limit)
```

**两条顺序必须遵守，违反即白做**：

| 要求 | 若违反 |
|---|---|
| 收敛在 `slice(limit)` **之前** | 被合并的卡已占名额 ⇒ 首屏从 6 掉到 5，**比不做更差** |
| 备选降级在收敛**之后** | 会把代表自己也塞进 `others` |

### 3. 判定键：`route | mainCodeOf(board) | mainCodeOf(alight)`

- **必须用 `mainCodeOf`**：其语义就是「剥站台号，同站多台是同一物理位置」（`segment-lookup.ts:21-23`）。
- **必须带 `route`**：不同线路即使 mainCode 相同也是不同方案。
- **刻意与 `card.ts:89-92` 的四元组不同**：四元组用于「精确定位到那张卡」，必须用**原始站码**；
  收敛键用于「判断是否同一方案」，必须**归一**。两者用途不同，**不要统一**。

### 4. 代表站 = `card.rides[0].alight` 本身（结构性保证）

> **不得新增独立的「卡面代表站」字段。** 收敛时**直接采用胜出的那张 modeled card 作为代表卡**，
> 把落选卡的 alight 放进 `alightAlternatives.others`，**全程不改写任何卡片字段**。

理由：`buildCardHref` 的 `alight` 在两个调用点都取自 `card.rides[0].alight`
（`RecommendCard.tsx:167` / `card.ts:251`）。只要代表站写进**这个字段**，href 自动同步；
若另设字段而 href 仍读 `rides[0].alight`，就会出现「卡面写 A 站、点进去 B 站」⇒ 详情页 `find` 不到
⇒ `route_changed`（`card.ts:93`），表现为「点了没反应」。

这条把「记得同步 href」从**纪律问题**变成**不可能发生**，与以下两条同源：
ADR-111「`now`/`ahead` 共用同一对象引用」、ADR-113「全站只有一个 pressed 常量」。
**用结构消灭复发路径，而不是靠注释提醒。**

### 5. 代表站的选取按偏好（已定案 A）

| 偏好档 | 选取判据 |
|---|---|
| `balanced` / `fewer_transfers` | `argmin(totalMin)` |
| **`less_walk`** | **`argmin(walkMinutes)`** |

`prefs` 从 `service.ts:111` 直接传入，零额外成本。
**注意**：这改变的是「挑哪一张 card 作为代表卡」，**没有改变「代表站从哪里来」** ——
它仍直接取自胜出 card 的 `rides[0].alight` ⇒ **Decision 4 的结构性保证在选 A 之下仍然成立**。

副作用（可接受）：切偏好档后同一 OD 的代表站会变 ⇒ 卡面文字变，但 href 同源同步，无「卡面/详情不一致」。

### 6. 跨线永不收敛

收敛只在同一 `route` 内发生。**允许两条不同线路各占一张卡**，即使 `board→alight` 的 mainCode 相同 ——
不同线路 = 不同班距/换乘/步行，是真正不同的方案（这正是 `parallelRoutes` 标签要表达的）。
换乘方案只看**首段**（`enumerate.ts:208` 注释「首段才展开」）。

### 7. 备选下车点进详情页，不进卡片列表

```ts
interface AlightAlternatives {
  chosen: string;   // 本卡实际用的（= 四元组的 alight，原始站码）
  others: { code: string; label: string; walkMin?: number; walkM?: number }[];
}
```

`others` 最多 4 条（按步行到目的地距离升序）—— 与 `RouteStack.tsx:28` 的 `MAX_PARALLEL = 3`、
`altBuses ≤3` 同一量级，避免详情溢出。
`card.ts:157` / `:207` 现取 `r.alights[0]!`（**首选项，非本方案实际用的**）⇒ 改为 `input.alight ?? r.alights[0]`。
交互：点选备选 ⇒ 走 `buildCardHref` 重进详情（四元组的 `alight` 变化）⇒ **不需要新状态机**。

## Consequences

正面：

- 同线同站不再出多张卡；代表站与 href 从结构上不可能分叉（Decision 4）。
- 备选下车点能力保留（详情页），不做「静默丢弃」。
- `less_walk` 用户拿到的代表站符合其偏好（Decision 5）。

负面 / 已知边界（均已承接）：

- **board 侧重复对卡片数无影响** —— 见下方「两次实测纠正」。board 归一的收益只在
  「候选全集语义正确」，不在减卡。
- 收敛后**组合卡的后续班次条数会减少**（合并了重复），需量测「只减少不可乘线、没误伤可乘线」。
- `alightAlternatives` 是**新增可选字段** ⇒ 4 个渲染器需支持「读到 undefined 走现状」，
  这是唯一能让本改造做到「一处回滚」的写法。

### 两次实测纠正（记录以防后人重新推算错数字）

**纠正 1：减卡规模是「2 → 1」，不是「最多 5 张」。**
架构初版曾据一组**跨 plan、跨字段**的候选集合推算「`new Set` 得 5 个 ⇒ 最多 5 张卡」，**该推算偏高**。
PM 用**枚举层实测**（`optionsFor` 纯函数、确定性）给出真实规模：

| OD | plan | 线路 | 修复前 alight 候选 | 修复后 | 卡片数 |
|---|---|---|---|---|---|
| `home→gate` | 28 | `25AX` | `M9/3`、`M9/4` | `M9/3` | **2 → 1** |
| `gate→home` | 33 | `25AX` | `C690/2`、`C690/3` | `C690/2` | **2 → 1** |
| `gate→home` | 33 | `51B` | `C690/2`、`C690/3` | `C690/2` | **2 → 1** |

⇒ **单组实测最多 2 个同主码写法**。静态核实的 10 处实例仍有效（证明机制真实），
但结论从「最多 5 张」降级为「单组最多 2 张；alight 侧 3 处真实减卡」。

**纠正 2：board 侧对卡片数零影响。**
因为 `enumerate.ts:263` 是 `boardsOf(first, R)[0]` —— **只取首项**。
而静态命中里重复项从不是首项（首项恒为 `C690/1` 或 `C690/2`），去重后首项不变 ⇒ 卡片数不变。

⇒ **本 ADR 的收益应如实表述为**：alight 侧 3 处真实减卡 + 防御未来数据（万一重复项哪天排到首位）
+ 候选全集语义正确。**不得再写「board 侧会出 5 张卡」。**
