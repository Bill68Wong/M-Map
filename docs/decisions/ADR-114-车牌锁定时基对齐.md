# ADR-114：车牌锁定的时间基对齐（**判定实时化 → 同帧锁牌**）

## Background

负责人现场报告：「当前版本貌似上车后匹配不到车牌了，除了需求中的异常情况，**正常情况也无法正常匹配**。」

### 已被排除的方向

team-lead 已核实 `MATCH_VEHICLE_ENABLED` 在 v3.8.0 / v3.9.0 / 本次三版均为 `false`
⇒ 不是这三笔引入。但「不是这三笔」≠「不是回归」—— 真正的收窄在更早的 v3.6.0，见 §2。

### 根因：同一个函数里藏着两个时间基

`autoBoardOf`（`src/lib/nav/boarding-detect.ts:316-381`）里有两组判据，**看似同一帧、同一份数据**，实际时间基完全不同：

| 判据 | 代码 | 时间基 | 何时成立 |
|---|---|---|---|
| 切换（判定发生） | `r2Of(fixes, colored, {...})` | **回看 45s 的窗口平均速度** | 需等站内静止段被行驶段摊薄到 >8km/h |
| 锁牌 | `lockedPlate = aux.strong ? aux.plate : null` | **当前瞬间的车站挂载状态** | 只在「车刚离本站、尚未到下一站」的 **1 个 hop** 内 |

**第一层：速度被站内停靠稀释。**
`r2Of`（`:183-189`、`:207`）：

```ts
const disp = Math.abs(cum[i1] - cum[i0]);                   // 沿线位移（全程累计）
const dtSec = (win[win.length-1].ts - win[0].ts) / 1000;    // ★ 窗口总时长（含静止段）
const kmh = (disp / dtSec) * 3.6;                           // ★ 被稀释
return kmh > vMin && kmh <= vMax;                           // vMin = 8，严格 >
```

用户上车时站在车里不动（车门未关 / 排队上车 / 塞车）⇒ `disp` 不增、`dtSec` 照增 ⇒ 平均速度被系统性拉低。
推演（$V$ 行驶速度、$D$ 站内静止秒、$M$ 行驶秒）：

```
V=12km/h D=20s ⇒ 需 M>40s（行程>133m）才越线；M=40 时测得恰 8.00 ⇒ 严格 > 判 fail
V=12km/h D=40s ⇒ M=80s 测得 8.00 ⇒ 仍 fail（行程 267m 才触线）
V=15km/h D=20s ⇒ 需 M>30s（行程>125m）
```

**第二层：锁牌有效期只有 1 个 hop，且只在切换那一帧求值。**
`aux.strong` = 存在车 `interval.from` 主码 == 上车站（`:122-124`）；
`interval` 由服务端在 `status === "0"`（已离挂载站、驶向下一站）时给出
（`src/app/api/route-vehicles/route.ts:206-213`）⇒ **下一站一到，`interval.from` 就变**。

**两层拼起来**：`r2Of` 终于通过时（上车后 30~60s），`strong` 往往已过期 ⇒ `plate = null`。
而一旦进入 `riding`，`tryAuto` 立刻返回（`useRideTracking.ts:1070`：`phase !== "boarding"`）
⇒ **本段内不再有任何锁牌机会**。

典型推演（站停 20s、12km/h、首跳 150m）：`strong` 有效期 t=20~65s；`r2Of` 在 t=70s 才通过；
`need=2` 帧后 t=76s 切换 ⇒ **错过 11 秒，`plate` 永久为空**。

这精确解释了「正常上车反而匹配不到」—— 正常上车必然经历站内静止，而**赶车冲刺**全程都在动、无稀释、
且 `strong` 因车刚离站而有效，所以异常路径反而更容易锁上牌。

### 第三层：没有第二条补牌通路

- `MATCH_VEHICLE_ENABLED = false`（`src/lib/nav/match-params.ts:15`）⇒ riding 补牌分支在
  `useRideTracking.ts:898` 直接 `return`。
- `pendingPlate` 的**唯一非 null 赋值**在 `useRideTracking.ts:945` —— 也在那个被挡住的分支内
  ⇒ 当前构建下 `pendingPlate` **恒为 null**，是**死代码**；UI 分支（`NavTrackBar.tsx:164-166`）永不渲染。

### 第四层（数据侧放大）

- `aux` 只从 `rankBoardingVehicles` 结果取，而它过滤掉 `status="unknown"`（`track.ts:239` 只留
  `moving/stopping/terminal`）；`status="unknown"` 正是**报站失败**（`route-vehicles/route.ts:204` 初值）
  ⇒ 报站一失败，该车对 `aux` 完全不可见。
- `interval` 需要 `next?.staCode` 存在（`route-vehicles/route.ts:211-213`）⇒ 车在本方向**末站**出发后
  `interval` 为 null，`strong` 恒 false。

### 是不是行为回退：是，但不在最近三笔

```
git log --oneline -S "lockedPlate" -- src/lib/nav/boarding-detect.ts
git log --oneline -S "aux.strong"  -- src/lib/nav/boarding-detect.ts
  ⇒ 两者都只有一次：69d3cae  feat: v3.6.0 S3 上车判定改定位主导
```

`69d3cae^`（v3.6.0 之前）存在 **`weak` 也锁牌**的分支：

```ts
if (r1.kind === "strong") { return { hit: true, plate: r1.plate, ..., reason: "r1" }; }
if (r1.kind === "weak") {                       // ★ 车「停靠本站」也能锁牌
  const ok = r2Of(...);
  if (ok) return { hit: true, plate: r1.plate, ..., reason: "r1weak+r2" };
}
```

| 对比基准 | 是否回退 | 依据 |
|---|---|---|
| **v3.5.x 及更早** | **是**。`weak`（车停靠本站）可锁牌 ⇒ 在停靠中的车上即可锁牌 | `69d3cae^:boarding-detect.ts` |
| v3.6.0 起（含 v3.8.0 / v3.9.0 / 当前） | **否，行为一致** | `lockedPlate` 自 `69d3cae` 未再变；`MATCH_VEHICLE_ENABLED` 三版同 false |

**准确表述**：这是 **v3.6.0（ADR-108「定位主导」）引入的一次未察觉的能力收窄** ——
当时为消除「同站台来车即判上车」的误判，把 `weak` 从**触发器**降级，
**连带把它的锁牌能力一起删掉了**。而消除误判只需要删「触发」，不需要删「锁牌」。
这个副作用被后续 4 个版本继承。

> 这个表述比「长期存在」更有用：它指出了**可以精准恢复的东西**（把 `weak` 的锁牌权加回来，
> 但保持它不做触发器），而不是笼统地"放宽阈值"。

## Decision

> ⚠️ **本节第 1、2 条已作废**（记忆窗口 / weak 单独分支）。**现行实现见 `ADR-110` §0**：
> 相对距离斜率判据（5 帧 / 6 秒）+ 锁牌条件三条件并集（L-a/b/c）+ 同帧完成。
> 下面保留原文以记录推理路径，**不得据此实现**。
> 第 3 条（`onNotBoard` 可逆化）与第 4 条（`pendingPlate` 定性）仍然有效。


### 1. ~~锁存 `strong` 证据（P0-1，主因修复）~~ **已作废**

新增纯函数与常量：

```ts
/** strong 证据的锁存有效期（ms）。取 90_000 = FIX_KEEP_MS，与定位缓冲同窗口。 */
export const STRONG_SEEN_TTL_MS = 90_000;

export interface StrongSeen { plate: string; ts: number }

/** 每帧更新：aux.strong 成立则覆盖记录；否则保留旧记录。超 TTL 由消费方判过期。 */
export function mergeStrongSeen(prev: StrongSeen | null, auxPlate: string | null, nowMs: number): StrongSeen | null;
```

调用方（`useRideTracking.tryAuto`）持一个 `strongSeenRef`，切换时用
`lockedPlate = aux.plate ?? freshStrongSeen?.plate ?? null`。

**为什么误锁风险为零新增**：能进入 `strongSeenRef` 的车必须**曾经真的**处于
「刚从本站离站且唯一」—— 可锁集合与现状**完全相同**，宽限只改变**使用时机**，不改变**谁能被锁**。

### 2. ~~恢复 `weak` 的锁牌权，但加「单一候选」门（P0-2）~~ **已作废（改为 ADR-110 §0.2 的三条件并集）**

```ts
// 车停靠本站 且 该站只有一辆车 ⇒ 允许锁牌；仍**不做触发器**（trigger 必须靠 r2Of）
```

**关键边界（不得越过）**：`weak` 只恢复**锁牌**权，**不得**恢复**触发**权。
ADR-108 的核心保护是「车辆不得单独触发上车」，这条**保持不变**。

⇒ 单测必须有一条：只有 `weak` 而无 `r2Of` 命中 ⇒ `hit === false`。

### 3. `onNotBoard` 可逆化（前提，同批必做）

`useRideTracking.ts:1898` 的 `autoUsedRef.current = true` 改为「本腿剩余自动次数」递减（初值 2）。
理由：负责人选了自动判定 ⇒「误判一次即永久降级为手动」与该决定直接冲突。

### 4. `pendingPlate` 的如实定性（防止被当成独立修法）

**它不是一条独立可选路径，而是「打开 `MATCH_VEHICLE_ENABLED`」的产物。**
当前它恒为 null（唯一赋值点在被 `:898` 挡住的分支内）。凡写成「让 pendingPlate 升级成 plate」的方案，
都隐含「先解除 `:898` 的 return」= 等于开 match。**必须写进 Spec，否则会有人以为这是低成本路径。**

### 5. 本批不开 `MATCH_VEHICLE_ENABLED`（对架构此前立场的再权衡）

team-lead 要求重新权衡「不开它，正常路径还有没有别的补牌通道」。答案明确：**有，且更可控** ——
Decision 1（锁存 strong）+ Decision 2（weak 唯一候选）。
两者的可锁集合都是**已有证据的子集**（强离站 / 唯一停靠）；
而 match 是**新增一类证据源**（里程-时间曲线相似度），误锁面完全不同且**从未上线验证**。
⇒ 本批用「子集」修，不用「新源」修。P0-4（开 match）的前置是先按 §10 的方式做误锁率量测。

## Consequences

覆盖变化（定性）：

| 场景 | 现状 | 本 ADR 后 |
|---|---|---|
| 车停靠本站，用户上车，车未动 | 否（`weak` 无锁牌权） | **能**（唯一候选门） |
| 同站台另有他线也在停 | 否 | 否（唯一性门挡住，正确） |
| 车已离站，用户还在车上 | 能，但需 `r2Of` 恰好同帧通过 | **能**（锁存，不再受 `r2Of` 时机限制） |
| 车已过下一站才发现 | 否（`strong` 过期） | **能**（90s 内仍可用） |
| 报站失败（`status="unknown"`） | 否 | 否（数据缺失，如实不猜，走手动候选池） |
| 本方向末站出发（`interval=null`） | 否 | 否（同上） |

正面：

- 修掉「正常上车拿不到牌」的主因，且**不引入新的误锁面**（两个修法都是已有证据的子集）。
- 锁牌与判定终于共享同一时间基 —— 这正是本批反复出现的病灶（同一概念两套实现）的第六处。
- `weak` 锁牌权恢复后，「车还没走就判到」与「有车牌」可以同时成立（现状二选一）。

负面（均已承接）：

- `weak` 唯一候选门依赖「该站只有一辆车停靠」这个条件；高峰期同站台多车时该门不生效（正确，但覆盖率下降）。
  这部分由 Decision 1（锁存 strong）兜 —— 车离站后就能锁。
- 报站失败 / 末站出发仍无牌。这两类是**数据缺失**，不应用猜测补；承接方式是 B3 手动候选池 + 可观测钩子。
- `STRONG_SEEN_TTL_MS = 90s` 是**待验证**取值：若某个 hop 的中位时长 > 90s（长距离站间），
  锁存可能在下一次同站来车后仍生效 ⇒ 极端情况下锁到「同线路后一班车」。
  验证方法：用 `route_hop_stats.p50_sec` 求 p99；若 p99 > 90s 则该线需按 hop 时长自适应。

验收判据（详见技术方案 §14.4）：

- 锁牌延迟 `t(plate 首次非 null) − t(phase 首次 riding)` **≤ 12s**（1 个 `POLL_MS` 节拍）；P0-2 生效时可为 0。
- 正常路径锁牌率 ≥ 85%（先测基线）。
- 卡死率（点「我没上车」后再未自动判定）**= 0**。
- 新增三个观测钩子：`data-plate-state ∈ {none,locked,pending}`、`data-strong-seen ∈ {0,1}`、`data-plate-ts`。
  现有 `data-board-match` / `data-match-source` **无法区分**「没机会」/「有机会但没锁上」/「锁上了但 UI 没显示」
  这三种诊断上完全不同的情况 —— 而本次主因恰恰是中间那种。
