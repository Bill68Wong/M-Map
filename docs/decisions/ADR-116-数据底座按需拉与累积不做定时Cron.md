# ADR-116：数据底座用「按需拉 + 累积」，不做定时 Cron、不挂外部调度

## Status

Accepted（2026-11-06 · 迭代批次 `docs/迭代-跨境交通-20261106/`）

> 修订（2026-11-07）：采集强度的计量表述改为定性等价表述，决策内容不变。

> 本 ADR 只记录决策与被否方案的代价。具体表结构、端点、正则与断言的权威定义在被忽略的 spec
> `03-数据底座与API契约.md` §3 / §5 / §7 中；此处不复述，避免同一处实现变更要改两份文档。

## ① 我们选了什么

采集由**用户请求触发**，不设定时器：请求到达时按需拉上游，采集结果 upsert 入库，「累积」是
「有人看就采一轮、采到就留下」的副产物，不是定时任务的输出。

三个配套件，都不引入新依赖（spec §3.3，行 1123–1131）：

- **DB 派生新鲜度**：`SELECT max(last_seen_at) WHERE sail_date/pier/direction`，不另建表。上游失败时
  本轮无 upsert，`max` 停在旧值，TTL 判定自然变 stale，零额外降级逻辑。
- **单飞**：会话级 `pg_try_advisory_lock(hashtext('xborder:PE:dep'))`，拿不到锁就直接读库返回，
  不排队。选 `try` 而非项目里已有的 `pg_advisory_xact_lock`（`src/lib/amap/rate-limit.ts:141`）是因为
  采集跨多个 `await`、不能长时间占事务，且「宁可这一轮不采，也不让用户等」（spec 行 901）。
- **按 (pier, dir) 粒度采集**：只拉用户正在看的那一页，上游压力从全量多页收窄到单页，lock 键
  天然细粒度。

**明确不做**：Vercel 定时 Cron（分钟级高频）、GitHub Actions cron、任何第三方外部调度。
spec §5 裁决表（行 1294/1297）与 §7（行 1334）已把这两项列为「明确不做」，本 ADR 是它的入库版本。

## ② 为什么不是另一个（含被否方案的具体代价）

**A · Vercel Cron 分钟级高频。**
代价不是「没有槽位」——Hobby 上限是 100 个 cron job，现有 `0 18 * * *`（`/api/cron/rebuild`）
并不占唯一槽（spec §0.1 行 29/37、§3.1 行 1110）。**真实代价是频率与精度**：官方文档
`https://vercel.com/docs/cron-jobs/usage-and-pricing`（2026-11-06 取，spec 行 30–35 引原文）写明
每个 job 最低间隔 Once per day，更频繁的表达式 **部署直接失败**
（"Hobby accounts are limited to cron jobs that run once per day. Cron expressions that would run
more frequently will fail during deployment."）；调度精度 Per-hour (±59 min)，「每天 05:05 预热」
实际可能落在 05:05–06:04，不能当时钟用，且一次触发只能拿到触发时刻之后的窗口（机场首班
08:00、内港首班 07:10，spec 行 38）。要做到分钟级高频只能升 Pro，$20/月起（spec 行 1118）。
把「槽位不够」当成理由会导致下一个人用错误前提重评，故在此写死正确的否决理由。

**A′ · GitHub Actions / 第三方外部调度。**
代价是重开一个已经刻意归零的暴露面，且收益为负：

- `docs/复盘-GitHub封号事故-20261028.md` 行 4 记账号被平台停权**持续约 5 周**；行 13 记成因推断为
  「仓库转公开 + 5 天内 30 个 PR」触发反滥用风控，叠加公开内容含政府系统鉴权算法逆向实现与大规模
  自动采集证据（行 23 对请求总量、持续时间与峰值强度三项均有量化记录；行 25：5 天 30 个 PR）；
  行 132 记申诉周期约占项目总周期 8 周的 60%。
- 该复盘 F9（行 50）记「无 `.github/` 目录：无 Actions」；本轮 `ls -d .github` 实测同样不存在。
  引入 workflow 等于重建零护栏面（复盘 C4，行 161）。
- 省下的只有 $20/月（spec 行 1119/1334），spec §7 行 1334 的结论是「收益为负」。

须注意：复盘行 7 自述「成因为证据推断，非平台官方结论」。本 ADR 引用的是**事故先例与暴露面**，
不声称 GitHub 会因 Actions 再次封号——这是对我方证据边界的陈述，不是对平台规则的断言。

**B · 纯按需拉 + 短缓存（本方案是它的超集）。**
三条具体代价（spec 行 1120、1133–1135）：冷启动连库 + fetch + 解析约 1–2s；并发时打上游 N 次；
**无人访问的时段完全不累积**，用户 09:00 首次打开则 09:00 之前的当日班期残缺。① 中三个配套件
逐条对应解决这三条。选择 C 而非停在 B 的代价是比 B 多约 100 行代码，但无新增基础设施、
无 `vercel.json` 改动（spec 行 1121）。

## ③ 什么条件下重新评估

**唯一触发条件：升 Vercel Pro 且确需分钟级高频采集。** 届时的正确路径是升档后启用平台最高频档的官方 cron，
而不是外挂第三方调度（spec §7 行 1334）。

在此之前，任何「加个定时脚本 / 用免费 cron 补一下」的提议按本 ADR 直接驳回，不必重新论证：
被否代价不随提案形式变化（要么 $20/月，要么 5 周封禁级的暴露面），收益恒定，而 B 的三条缺陷
已有对应件解决。若「无人访问时段也必须完整累积」升级为对外硬需求，则属于需求变更而非重评本决策。
